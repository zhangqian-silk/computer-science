# Reasoning、Planning 与计划修订

Reasoning 是模型完成判断和生成时的推理能力；Planning 是把目标组织成步骤、依赖和中间结果；执行器负责真实动作；验证器负责检查结果。四者可以配合，但不能将计划文字、推理解释和外部完成事实混为一谈。

本页讨论任务推进策略。

## 推理与显式计划

一次分类或文本生成可以在单次调用中完成，不需要额外规划器。把每个任务都拆为“分析—计划—执行—复盘”会增加延迟和出错机会。显式计划更适合任务存在多种依赖、覆盖要求、长时间跨度或需要人工审查时。

规划也不必全部交给模型。固定业务顺序可直接编码，模型负责局部未知，例如从错误日志判断需要调查哪个组件。关键选择是哪些不确定性需要语义能力，哪些边界应由程序确定。

## 任务推进策略

| 方式 | 计划/控制放在哪里 | 适用特点 |
| --- | --- | --- |
| 单次直接生成 | 单次请求中 | 输入已足够、无需实际探索 |
| ReAct | 每轮依据新观察提出动作 | 下一步依赖未知环境 |
| Plan-and-Execute | 显式步骤对象＋执行器 | 依赖与验收可分解 |
| Evaluator–Optimizer | 验证反馈驱动修正 | 候选结果可独立检查 |
| 代码化编排 | 程序变量与控制结构 | 大量重复、分支与并行 |

这些不是固定等级。一个显式计划中的“调查未知错误”节点可以运行 ReAct，验证节点可以用确定性测试，多 Agent 又可以执行部分节点。

## 计划步骤与中间结果

“认真分析配置，然后解决问题”没有可检查的边界。更好的计划是“读取配置及启动参数，确认最终端口来源；生成候选修改；在隔离环境运行指定检查”。每步有输入、产物和通过条件，才能用于调度与反馈。

```python
plan = {
    "goal_revision": 3,
    "steps": [
        {"id": "inspect", "depends_on": [], "status": "pending",
         "deliverable": "带来源的端口覆盖关系"},
        {"id": "propose", "depends_on": ["inspect"], "status": "pending",
         "deliverable": "不修改原文件的候选补丁"},
        {"id": "verify", "depends_on": ["propose"], "status": "pending",
         "deliverable": "补丁版本对应的测试结果"},
    ],
}
```

模型可提出这个对象，但程序验证 step ID 唯一、依赖存在、无循环或有显式有限循环、能力可用、预算足够。`status=completed` 不应由模型随意填入而无需证据。

## 计划修订与事实保留

观察到依赖缺失、权限拒绝或假设失败，原计划可能不再有效。重规划应调整未开始或未完成部分，已经确认的外部事实保留；已取消步骤也要标记，而不是直接删除使覆盖检查误以为从未存在。

```python
# 教学代码：只允许替换尚未开始的尾部计划。
def replace_pending_steps(old_steps, replacements):
    preserved = [s for s in old_steps if s["status"] != "pending"]
    existing_ids = {s["id"] for s in preserved}
    if any(s["id"] in existing_ids for s in replacements):
        raise ValueError("新计划覆盖了已发生的步骤")
    return preserved + replacements
```

真实实现还需验证跨新旧步骤依赖、当前执行者是否仍有工作在途、用户是否改变目标。不能在模型重规划时把仍运行工具的任务记录直接删掉，否则晚到结果无法归属。

重规划本身会消耗预算。定义触发条件比每轮无条件重新生成完整计划更重要：关键前提失败、覆盖集合变化、用户修改目标、达到无进展阈值。局部工具暂时超时可能只需受限重试，而非推翻全部路径。

## 反馈质量与修正方向

验证反馈应尽量包含可操作事实：哪条断言失败、期望/实际值、文件版本、缺失证据或权限状态。模糊反馈“再认真一点”无法指导正确修正。把测试 stdout 原样发送数万行也可能让模型忽略真正失败位置。

区分内容错误、资料不足、工具失败、环境问题和权限拒绝。权限不足不应该让模型规划另一种绕过路径；环境依赖缺失不应该促使它随意改业务逻辑来让测试“看起来通过”。

可以引入模型 Critic，但其评价只是一个信号。代码编译、行为测试、资源查询等能提供更直接证据；开放文本需要 rubric 和必要人工检查。避免让生成者与验证者共享未经检查的错误前提。

## 思考、反思与长期记忆

模型解释自己的失败原因不一定正确。反思文本可以作为下一次尝试的候选假设，但应与原始错误、模型/工具版本和环境一起记录。只有经重复验证或用户确认的稳定经验，才适合跨任务复用。

例如“一次请求超时”不能总结成“这个工具不可靠，以后绕开”；“某测试在此环境失败”不能写成“该功能必须删除”。把不确定经验变成永久规则，会让错误持续扩大。

## 产品规划机制对照

Claude Code 公开运行说明采用获取上下文、执行动作和验证的循环视角；这不要求每次都先生成完整计划。编码 Agent 中的计划界面主要让目标和进展可见，不能据界面上的勾选替代实际测试。[[50]](../references.md#source-cc-runtime)

长运行 Harness 的实践则使用任务列表、进展记录和验证产物帮助后续上下文接续。可以借鉴的是让计划与证据可读、可检查；不是把所有项目强制拆成同一种初始化流程。[[29]](../references.md#source-anthropic-long-harness)

当计划变为可执行脚本时，控制状态进一步显式化，但脚本仍可能遗漏目标。必须在执行前校验覆盖集合、预算和能力，运行后检查实际结果。

## 调优推理与规划的实验

固定任务集，比较直接执行、轻量计划、完整计划三种策略。指标包括最终通过率、错误恢复次数、模型步骤、检索调用、总成本和人为介入。长计划耗时更多但明显减少后续错误时可能值得；简单任务同样效果则应去掉额外阶段。

推理预算也要独立作为变量，不与提示、工具和模型版本同时变化。按任务难度分组，记录失败发生在推理还是证据获取。若模型缺少关键资料，增加推理 token 可能只产生更长的错误解释。

测试无解或受权限限制的任务，要求系统明确停止或请求输入。一个“永远想出下一步”的规划器不一定更可靠；能正确识别不能继续，也是任务控制能力的一部分。

## 计划失败的分类

**动作选错**：模型查了无关文件，需要改善输入或工具选择。**前提变了**：代码版本、用户目标或环境变化，需要修订未执行计划。**执行不可行**：无权限或缺资源，需要停止、请求输入或等待，不能靠再生成计划绕过。

例如计划要求“读取线上配置”，但当前身份只有本地权限。合理结果是记录缺少线上证据，返回受限分析；不应尝试寻找另一个能泄露线上资料的工具。计划器的职责是选择可行路径，不是突破授权边界。

## 进展指标与执行证据

可以跟踪已覆盖对象、已验证断言、减少的错误集合和新增有效证据。仅看生成文字长度、token数、工具调用次数都不能说明进展。

```python
def progress_delta(before, after):
    return {
        "newly_verified": after["verified"] - before["verified"],
        "resolved_errors": before["errors"] - after["errors"],
        "new_evidence": after["evidence"] - before["evidence"],
    }
```

集合元素应包含相关资源版本；旧版本的验证不能直接与新版合并。连续几轮没有新事实可以触发停止或人工复核，但探索任务也可能暂时没有成果，因此阈值应按任务类型配置。

## 计划与状态机的职责

计划描述希望发生的步骤，状态机描述实际上哪些转移合法。模型可以提出“先检查、再修改”，但程序仍限制未经批准不能进入写入、未知外部效果不能进入安全重试。计划器不应拥有修改状态机规则的普通工具。

这种分离允许模型灵活处理语义任务，同时让执行边界保持可测试。
