# 提示工程（Prompt Engineering）

Prompt Engineering 研究怎样用指令、示例和输出要求稳定地表达任务。它适用于一次文本生成、信息抽取、工具选择，也适用于 Workflow 和 Agent；不必先有循环。本页集中讨论提示契约及其迭代方法，资料检索和每轮信息选择归 [Context Engineering](context-engineering.md)。

## Prompt 的组成

一份可维护的提示通常能区分目标、依据、约束和交付。目标描述需要完成什么，依据说明允许依赖哪些材料，约束限制方法或结论，交付定义结果结构。角色设定可以提供语境，但“你是一位顶尖专家”不能代替这四项。

```text
目标：从提供的配置中提取服务端口。
依据：仅使用 <config> 中的内容。
约束：没有显式端口时返回 not_found，不猜框架默认值。
交付：返回 status、port、source 三个字段。
```

这条提示同时解决了一个语义歧义：问题是“显式配置值”，不是“实际运行时最终值”。若真实需求是后者，环境变量、命令行覆盖和框架默认值都可能有影响，必须取得更多上下文。提示写得更强硬，不会让缺失事实自动出现。

系统／开发者指令用于应用长期约束，用户消息表达本次任务，附件和检索文本作为资料提供。保持这种区分有助于解释冲突，但不是安全隔离：恶意资料仍可能影响模型，执行边界需要独立控制。[[19]](../references.md#source-openai-prompt)

## 任务表达与判定标准

“准确、全面、简洁”很难作为程序验收。更明确的契约是“每项结论有来源；没有来源的推测单列；输出不超过若干项；缺少必需字段时列出缺失项”。这些要求可检查，也能与评测集中的错误类别对应。

```python
# 数据示例：将提示版本与验收规则并列管理。
prompt_spec = {
    "id": "port-extraction",
    "revision": "3",
    "inputs": ["config_text", "source_name"],
    "required_outputs": ["status", "port", "source"],
    "unknown_policy": "not_found",
    "forbidden_claims": ["已读取其他文件", "已验证线上运行"],
}
```

业务约束不要只存在于文本里。例如“不能返回当前用户无权访问的记录”需要检索与工具层鉴权，不能指望模型读到所有用户的数据后自行遵守。类似地，数字范围、路径白名单和动作上限应由代码执行，Prompt 负责引导选择和解释。

## 示例的作用与副作用

Few-shot 示例能展示分类边界、输出格式或工具选择规则。高价值示例通常是容易混淆的相邻类别，而不是十个相同的正常输入。端口提取至少可以包含缺字段、被注释的旧值、两个环境配置、显式零值不合法、文字中出现端口但不是配置等边界。

示例也会制造偏置。所有示例都回答“已找到”，模型可能倾向忽略缺失；所有工具示例都先搜索，模型可能在直接可回答时也搜索。把示例数量加大并不自动改善任务质量，还会扩大输入和缓存维护成本。

一种可控方法是先写规则，再加入能区分具体错误的最少示例。保持训练/开发样例与最终评测样例分离。若错误只发生在某个产品文档被更新后，先更新资料，不应把新事实永久塞进规则 Prompt 来掩盖知识库过期。

## 工具选择提示与工具定义的分工

Prompt 适合表达策略，例如“先只读确认，再提出修改”；工具描述适合解释局部能力，例如参数单位、作用范围和返回状态。把每个工具的全部字段说明复制进系统提示会增加冲突：工具 schema 更新了，提示中的旧字段还在。

工具选择的提示应定义何时不调用。例如用户只是要求解释已提供的代码，不一定要读取整个仓库；用户要求发邮件但缺收件人，应请求澄清，不能凭上下文猜地址。提示中的例子应同时展示调用与不调用的边界。

调用是否允许，不由这种提示最终决定。工具网关仍校验当前身份与实际参数。若模型经常选择错误工具，先看名称和职责是否重叠，再尝试增加文字限制；“再强调三次不要误用”往往只是把接口设计问题隐藏起来。

## 推理提示的长度与效用

面向普通生成任务，可要求给出关键依据或拆成可检查小步骤。面向推理模型，应先使用该模型公开支持的推理预算和简洁任务约束，不假设强制输出大量逐步思考能提高正确率。解释文本可以用来向用户说明依据，但不能用它作为测试已运行的证据。

在复杂任务中，要求输出计划、风险列表或核验清单，可以使外部状态可见；这与要求暴露内部完整推理不同。计划必须经执行与观察才能获得事实地位。

## 提示优化的对照实验

```python
# 教学伪代码。run_case 调用模型；grade 用独立规则评价。
def compare_prompts(cases, candidates, run_case, grade):
    rows = []
    for case in cases:
        for revision, instructions in candidates.items():
            result = run_case(case, instructions)
            rows.append({
                "case_id": case["id"],
                "prompt_revision": revision,
                "score": grade(case, result),
                "raw_result": result,
            })
    return rows
```

真正运行时要随机化候选顺序，锁定模型/工具/检索版本，重复不稳定样例，并记录成本和延迟。先根据错误分类提出一个假设，如“模型混淆显式值和默认值”；只修改对应规则；比较新旧提示在这类边界和原本正常样例上的变化。

不要让同一个模型按照同一段提示自行宣布改进。结构化任务优先规则验收，开放文本使用明确 rubric、盲审和必要的人工复核。平均分提升也可能掩盖某一高风险子集退化。

## Harness 中的提示设计

Anthropic 的工具工程文章把工具描述与任务评测放在同一反馈闭环；这提醒我们提示效果依赖工具接口和返回内容，不能孤立调一个 system prompt。OpenAI 的 Harness 工程实践则强调仓库中可发现的知识结构和反馈约束。这些是作者工程经验，不构成“某种提示在所有模型上更优”的普遍结论。[[20]](../references.md#source-anthropic-tools) [[21]](../references.md#source-openai-harness)

自建代码 Agent 时，可以将顶层提示保持在稳定职责、操作规则和资料入口层，把项目细节放入版本化仓库文档/Skills。这样修改项目测试命令不必改变整个模型人格，但需要确保入口可发现、链接有效和资料受信任。最重要的测试是 Agent 能否找到并正确使用信息，而不是提示文件写了多少行。

## 提示版本与动态内容

稳定模板应有版本，动态资料应有来源和 hash。只保存最终拼接字符串，出问题时很难区分是规则变化还是检索内容变化。保存渲染 manifest，并为同一输入做可重现的模板渲染测试。

模板插值必须明确转义。把用户内容插入 JSON 字符串需要 JSON 编码；插入 XML 风格边界不意味着具备 XML 安全性；用户输入中的伪造闭合标签仍要作为资料处理。不能把未知输入直接拼进 shell 命令或脚本，这是程序注入问题，不是 Prompt 优化问题。

缓存布局可作为次级优化：稳定模板在前、动态材料按语义合理组织。若为缓存保留已撤销约束，会损害正确性。

## 提示调优记录

每次改动至少留下失败类别、旧行为、改动假设、控制变量、样例集版本、结果及未改善部分。将“答案更像我想要的”改成可复查记录，例如“缺字段样例猜默认值从多少次变为多少次，同时正常提取保持”。本资料未提供真实模型对照数字；具体实验模板在资料包中，运行后再填结果。

## 一次可复查的提示改动示例

假设任务是“提取配置中的端口”。旧提示只写“找到端口，返回JSON”，在缺字段时有时会猜8080。这里先不换模型，而把任务含义显式化：

```text
旧版：找到端口，返回JSON。

新版：
提取本次材料中显式出现的服务监听端口。
不要使用框架默认值补全；注释中的示例值不计入当前配置。
没有直接证据时，status 为 not_found，port 为 null。
source 必须来自输入提供的文件标识。
```

验证集应同时包含显式端口、仅注释端口、没有端口、环境覆盖但未给环境值、多个服务。若新版在“缺字段不猜”上改善，却把有覆盖关系的任务都判缺失，应考虑是否需要另一种任务类型，而不是继续堆例外。

同一用户问题“服务用什么端口”可能指配置静态值，也可能指运行时实际值。Prompt无法单独消除缺失的业务语义。可以让应用要求用户选择，或者输出两类状态并说明需要运行信息。这种任务契约修改往往比调整语气更重要。

## 提示文件的拆分与冲突处理

可将稳定行为规则、输出格式和项目资料入口分开维护，在请求时确定性组合。不要同时在system、Skill、工具描述、用户消息里放四份不同测试命令。约束冲突时由应用优先级规则和当前用户授权处理，不能任意按文件加载顺序覆盖。

用于维护的元数据包括规则拥有者、版本、适用任务、与哪个工具schema匹配、最后评测记录。程序配置或项目事实能从权威来源读取时，不要长期复制进提示文件。

## 提示错误与其他故障的区分

输入被截断、旧schema被缓存、工具实际无权限、检索返回过期版本，都可能表现成模型回答错误。调提示前先保存一次失败请求的上下文manifest，确认模型究竟看到什么。否则修改Prompt只是在对未知输入做猜测性补偿。

这也是Prompt Engineering需要与Context、工具和评测连接，但仍保持自己的职责边界的原因。
