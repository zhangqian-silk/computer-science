# Hooks、Plugins 与扩展管理

扩展系统允许在不改动主循环的情况下加入能力和策略。Hook 是插入点，Plugin 是分发与生命周期单位，Tool 是可调用能力，Skill 是操作知识。它们可以组合，但不能用“支持插件”代替执行顺序、失败语义和资源管理设计。

## 扩展点分类与接口设计

| 扩展点 | 允许改变什么 | 典型失败策略 |
| --- | --- | --- |
| 输入过滤器 | 已授权材料的选择或表示 | 拒绝本轮或保留明确的原输入 |
| 参数变换 | 调用参数 | 变换后重新校验与授权 |
| 准入 Gate | allow/deny/ask | 安全关键失败不得默认放行 |
| 执行包装器 | deadline、计量、受限重试 | 不能脱离调用方取消与幂等契约 |
| 结果投影器 | 用户/模型可见内容 | 不能抹掉已知事实回执 |
| 观察器 | 读取事件并记录 | 隔离非关键观测错误，保留告警 |

把上述角色都放在一个可任意修改全部状态的 callback 中，接口初期灵活，后期很难解释是谁改变了什么。比如结果摘要插件意外抛异常，不应触发写操作重试；统计插件慢，也不该悄悄改变工具执行顺序。

## 顺序、短路与合并规则

一个 pipeline 应说明：先注册还是后注册优先，参数是否逐级传递，多个拒绝怎样合并，是否允许多次 `next()`，某个插件是否可以绕过后续策略。没有这些规则，两个单独正确的插件组合起来仍可能不正确。

参考设计可采用参数变换串行、最终校验、单调拒绝、一次执行、纯结果投影、观察通知。这里的“单调拒绝”表示后面的普通扩展不能把前面硬拒绝改成允许。若需要管理员覆盖，应通过独立、显式的策略通道而非任意插件返回值。

```python
# 教学代码：核心动作展开；组件均由宿主注册，不由模型提供。
def run_pipeline(call, transforms, validate, authorize, execute, render):
    args = dict(call["arguments"])
    for transform in transforms:
        args = transform(args)
    validate(args)                    # 最终参数，而非变换前参数
    if not authorize(call["name"], args):
        return {"status": "denied"}
    receipt = execute(call["name"], args)
    try:
        content = render(receipt)
    except Exception:
        content = {"message": "结果展示失败", "receipt_id": receipt["id"]}
    return {"receipt": receipt, "content": content}
```

这个简化例子未实现跨进程隔离、版本绑定与审批，但明确保证渲染失败不会再次执行动作。实际授权与保存回执需要资源边界支持，不能靠函数名保证原子性。

## Pi 的事件分发与异常传播

Pi 的 `ExtensionRunner` 在指定提交中分别实现通用事件、工具调用和工具结果处理。通用事件路径会捕获并报告扩展错误；工具调用路径遇 `block` 可短路；结果路径允许改变包括 `content`、`details`、`isError`、`usage` 的字段。因而“结果 Hook 只改显示”并不是该接口天然保证。[[43]](../references.md#source-pi-ext-runner)

这个对照的意义是先读每个入口的语义，再决定能放什么扩展。安全 Gate 与 UI 扩展不应该仅因为都叫 Hook 就采用同样的失败策略。对于已有框架，如果无法修改契约，应在外层保存原始回执或在边界收紧可加载插件。

Pi 还通过活动实例检查与惰性上下文避免过期对象继续使用旧状态。自建宿主若把所有上下文属性启动时复制给插件，reload 后旧闭包可能继续操作失效会话；要测试失效对象，而不只测新插件启动成功。[[43]](../references.md#source-pi-ext-runner)

## DSH 的深层可替换性及其代价

DSH 在指定提交里将工具管线和多种能力 provider 暴露为可组合服务，规范输出、渲染和冻结结果通知有明确接口。这样可以替换执行能力而不重写 Loop，但也增加了依赖组合、取消传播和生命周期验证的责任。[[30]](../references.md#source-dsh-tools)

应将“可替换”拆成四个问题：替换哪个接口；消费者如何获取它；在途调用使用新旧哪个版本；旧资源何时结束。只写“everything is a plugin”无法指导实现，也不能证明热替换不会丢任务。

跨安全边界更需要谨慎。同进程插件可以执行任意宿主代码时，一个设计良好的 Hook 返回值约束不等于隔离。DSH 接口也明确协作取消无法硬杀同进程任意代码。高风险第三方扩展应考虑独立进程/沙箱与受限 RPC，而不是依赖约定。

## 工具版本快照与晚到清理

模型请求中公布 v1 工具描述，等待期间更新 v2；响应回来后必须按清楚策略处理。可以绑定 v1 至本轮结束，也可以拒绝旧调用并重新请求。不能模型看旧 schema、执行器却静默调用最新代码。

```python
# 数据示例：注册代次与模型请求的工具快照分别记录。
binding = {
    "name": "read_file",
    "plugin": "workspace",
    "generation": 12,
    "tool_revision": "1",
}
request_snapshot = {"bindings": {"read_file": binding}}
```

Codex 的 `ToolCallRuntime` 保留发布工具列表时的 StepContext，是一个实际版本绑定例子。自建注册表还需要防止旧实例晚到的 `dispose()` 删除同名新实例：清理时比较确切对象或 generation，而不是只按名称 remove。[[14]](../references.md#source-codex-tools)

权限又是另一条时间线。工具版本可以固定，管理员撤销策略应在执行前再次检查。这防止“快照一致”被误用来维持旧权限。

## 生命周期：初始化、发布、排空、释放

合理的 hot reload 流程是先离线构造新实例，验证依赖和注册冲突，再原子发布给新请求；旧实例停止接纳新工作，等待或取消其已拥有工作，最后释放资源。初始化失败不应破坏正在运行的旧版本。

Pi 文档提醒扩展工厂可能在没有会话的场景执行，不应直接在工厂启动长活定时器、Socket 和 watcher。这类资源要在实际使用阶段创建，并通过幂等 shutdown 收尾。[[42]](../references.md#source-pi-ext-doc)

“超时后返回”不等于工作已经静止。若宿主使用 `Promise.race` 或类似方式抛弃插件 promise，插件仍可能写文件。真正的资源释放应等待所有拥有的工作结束；不能合作的插件需要进程级终止边界。

## Hooks 与确定性策略的边界

Claude Code 的公开 Hooks 文档描述不同生命周期事件及相应输入输出。应选择其支持的实际事件和字段，不把新提案、论坛示例当成已发布接口。一个观察型 Hook 不能被描述为能拦截所有写入，执行后 Hook 也不能撤销已经发生的远端动作。[[44]](../references.md#source-cc-hooks) [[45]](../references.md#source-cc-hooks-guide)

宿主能做的确定性校验尽量放在宿主代码。例如路径规则、预算扣减、调用次数上限、审批绑定与资源租约，不必通过模型判断。模型 Reviewer 可辅助风险分类，但要有不能被其覆盖的硬限制。

## 组合测试与调优

测试至少包括两个参数变换的顺序、Gate 抛异常、重复 next、执行成功后结果插件失败、观察器超时、新版本发布时旧调用在途、旧实例释放晚到、关闭时 watcher 未退出。单插件测试通过不能证明组合正确。

测每个扩展的耗时、阻塞阶段、输入输出尺寸和资源数。可优先并行化纯观察器，但不要并行化会按顺序改写参数的插件；可缓存静态 Skill 解析，但不能缓存当前授权结论而忽略撤销。优化对象是明确职责，不能用“全局异步”取代设计。

## 简化实现的建议

只有静态工具和少量提示时，用函数注册表和普通模块即可。需要部署扩展、版本更新或用户自定义行为时，再引入生命周期。扩展系统越开放，越需要接口版本、兼容测试和信任边界；灵活性不是免费属性。

## 插件热更新时序

```text
t0：注册workspace generation12，工具v1
t1：请求R获取v1快照
t2：准备generation13，校验通过
t3：发布v2，新请求开始使用v2
t4：R返回旧schema调用，仍绑定v1
t5：R完成，generation12排空
t6：释放generation12，仅删除其自身资源
```

若t4期间管理员撤销写权限，R虽然仍绑定v1，也必须被当前Gate拒绝。若t2初始化失败，不应影响v1继续服务。若t6晚到，它不能通过`remove("workspace")`删掉generation13。

引用计数、作用域资源和memoized dispose是常见实现手段，具体选哪种要看并发和插件框架。核心不变量是每个资源只有明确拥有者，释放针对确切实例，发布与使用绑定可追踪。

## 插件执行失败的分级恢复

一个可选UI主题加载失败可以降级默认样式；一个必需数据源失败应使相关功能不可用；一个安全Gate失败应拒绝自动执行；一个结果观察器失败可记录告警。将所有异常统一吞掉虽让程序不崩溃，却可能让必需防护悄悄消失。

宿主可声明扩展为required/optional，但声明还需要启动检查和运行时策略。required插件未注册成功时，应阻止依赖任务启动；不是等模型调用后才返回一条含糊错误。

## 扩展范围与可测试性

开放每个内部对象给插件会降低短期开发摩擦，却使宿主无法升级数据结构。优先暴露少量稳定事件、受限状态读取与明确变更命令；内部状态保留封装。真正需要更深替换时，再设计版本化service接口和生命周期契约。

测试插件使用过期上下文、重复注册工具、重复释放、在关闭后发事件，以及试图在结果处理阶段改业务事实。扩展生态越大，这些边界越不能只靠开发者自觉。
