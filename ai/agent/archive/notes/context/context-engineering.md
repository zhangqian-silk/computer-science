# 上下文工程（Context Engineering）

上下文工程研究模型在本次推理时获得哪些信息，以及信息如何随任务推进更新。它连接 Prompt、历史、检索证据、工具描述、Skill 内容和结构化状态。本页负责「选择与组装」，不负责索引实现、业务授权或存储恢复。

## 持久状态与请求上下文

一个会话可能保存几万行终端输出、所有文件补丁、历史计划和多个失败尝试。下一次模型调用通常只需要当前目标、有效约束、相关证据、近期观察和可用动作。把整个数据库内容序列化成消息既浪费窗口，也会让旧信息与新事实竞争。

可把输入构造看作有约束的编译过程：源对象带有身份、版本、权限、相关性和生命周期，编译器选择这些对象，输出供应商能够接受的消息及工具 schema。最终请求有 manifest，能说明每一块材料来自哪里、为什么保留，以及哪些内容被裁剪。

Anthropic 的上下文工程文章强调在有限窗口中选择高价值信息，而不仅是写更长的提示。这里将这一思路具体化为数据与流水线，是参考设计，不声称某个产品内部完整采用以下对象。[[22]](../references.md#source-anthropic-context)

## 上下文材料的元数据

```python
# 数据示例：授权已在材料进入候选集之前完成。
context_item = {
    "id": "doc-42#L18-L35",
    "kind": "evidence",
    "text": "生产环境通过 PORT 环境变量覆盖配置。",
    "source": "deploy-guide.md",
    "revision": "git:abc123",
    "trust": "external-data",        # 不是新增指令权限
    "valid_at": "deployment-2026-09-10",
    "estimated_tokens": 80,
    "priority": 60,
    "required": False,
    "group_id": None,
}
```

`trust` 说明信息用途，不是模型必须遵守的魔法标签。真正的权限由检索和读取接口检查。`revision` 用来识别同一资料的新旧版本；`group_id` 用来绑定不能拆开的内容，例如一次 assistant 工具调用和对应结果。

任务约束应与普通检索内容分开。用户刚确认“只分析，不修改”应被标成当前有效约束，而不是依靠相关性排序碰巧排进前几个片段。反过来，旧计划里“接下来写配置”不能压过新约束。

## 上下文组装流程

参考流水线是：加载当前约束 → 按当前权限获取候选资料 → 消除版本冲突 → 将协议关联内容分组 → 按相关性和预算选择 → 渲染消息与工具 → 使用实际 tokenizer 再校验总长度 → 固定 manifest。

```python
# 教学代码：每个 group 是不可拆分的消息组，tokens 已估算。
def select_groups(groups, available_tokens):
    required = [g for g in groups if g["required"]]
    optional = sorted(
        (g for g in groups if not g["required"]),
        key=lambda g: (-g["priority"], g["id"]),
    )
    chosen = list(required)
    used = sum(g["tokens"] for g in chosen)
    if used > available_tokens:
        raise ValueError("必需信息已超预算，不能静默删除约束")
    for group in optional:
        if used + group["tokens"] <= available_tokens:
            chosen.append(group)
            used += group["tokens"]
    return chosen
```

这不是最优背包算法，也不假设优先级已天然正确。它演示三个工程边界：必需约束先保留；关联组不切碎；选择具有稳定顺序。真实系统还应考虑信息覆盖与多样性：十个几乎相同的片段可能不如三个不同方面的证据。

如果必需信息超限，应切换任务策略、压缩合格历史、分阶段读取或明确拒绝继续，不能在底层偷偷丢掉最前面的系统规则。压缩有独立验证过程。

## 冲突、过期和新观察

同一个文件可能同时存在“检索索引版本”“工具刚读版本”“Agent 自己的修改版本”。这三个来源不能简单拼接。对于正在修改的工作区，工具刚读到的内容通常代表该工作区当前事实；索引结果仍可用于导航，但不能作为覆盖写入依据。

推荐显式记录证据的作用：定位线索、历史事实、当前观察、用户约束或待验证推测。模型可以比较相互冲突的资料，但下游操作必须知道采用哪个版本。比如修改文件前用原始内容 hash 检查是否变化，而不是因为上下文里曾出现这个文件就直接写。

时间信息也要具体。文档发布时间、系统观测时间、业务生效时间可能不同。只给每段资料统一加上“最新”，会掩盖这些差异。对于跨时区日志和配置变更，保留原始时区及事件时间，不要只留摘要。

## 工具与 Skills 的可见性

工具目录过大时，每次公布全部 schema 会扩大成本并增加选择歧义。可以先提供受控发现能力，再按当前任务加载相关工具。这里的“隐藏”只是减少模型选择范围，真实执行网关仍应拒绝未授予的能力，不能把不在 Prompt 里当作安全措施。

Skills 的名称和描述可以常驻，正文按使用需求加载。动态加载仍有成本：正文进入后续请求、附带脚本可能运行、版本可能变化。上下文 manifest 应记录加载了哪个 Skill 版本，而不是只记录“skills enabled”。

实现例子可参考 Pi 的 `transformContext` 与 `convertToLlm` 两步：先改变信息集合，再适配 API 表示。这样单测可以分别检查“选中了正确材料”和“编码后仍保留正确调用关联”。如果两者混在一个巨大的 provider adapter 中，往往难以判定错误来自内容选择还是序列化。[[9]](../references.md#source-pi-loop)

## 上下文快照与外部变化

在一次模型请求发出时固定输入快照，有利于审计和绑定工具版本。但用户取消、权限撤销和外部环境变化仍然可能发生。模型用旧快照提出动作，执行时仍需要现时检查；不能用“当时有权限”跳过现在的拒绝。

```python
context_manifest = {
    "goal_revision": 7,
    "policy_revision_at_build": 12,
    "prompt_revision": "p-3",
    "tool_catalog_revision": "tools-5",
    "sources": [{"id": "doc-42", "revision": "abc123"}],
    "history_boundary": "message-81",
    "omissions": [{"id": "log-17", "reason": "stored_as_artifact"}],
}
```

这份 manifest 只描述请求事实，不是授权票据。允许执行的身份与资源版本应在动作网关重新检查。

## 上下文质量指标

不能只看“输入 token 下降”。应测必要事实覆盖、引用可回查性、关键约束保留、调用参数正确性、无关资料占比、压缩后继续任务成功率，以及最终每个验证成功任务的总成本。

调优时固定模型与任务，只改变一个策略，例如从“全量最近消息”改成“约束＋结构化进展＋相关观察”。记录每次遗漏导致的回查工具次数。输入变短却让模型反复重读同一文件，整体成本可能更高。

用合成反例检查：最后一轮用户撤销写权限；旧摘要与新文件内容不同；同名工具 schema 更新；长日志含伪系统指令；一项工具结果被切掉但调用保留。好的构造器应在这些例子里保留正确边界，而不是只在正常问答里输出顺畅。

## 组装实例：12,000 token 的输入预算

以下是教学分配，不是通用推荐比例。假设某profile允许本轮输入12000 token，构造器拿到：规则1200、工具目录1800、当前目标500、历史调用组4000、检索候选6000、原始日志20000。

先保留规则、必要工具和目标共3500；为合法最近调用组保留4000，剩4500。检索候选按来源覆盖挑选3500；日志只发送500-token失败摘要加原始产物引用，留500余量应对token估算误差。最终tokenizer计数若仍超限，重新选段，不任意截断序列化字符串。

| 信息 | 原始量 | 选择方式 |
| --- | ---: | --- |
| 规则、能力、目标 | 3500 | 保留有效版本 |
| 近期调用历史 | 4000 | 完整关联组 |
| 检索材料 | 6000 | 保留3500，兼顾来源覆盖 |
| 工具日志 | 20000 | 摘要500＋原件引用 |

如果工具目录本身就占10000，问题首先是能力发现和目录裁剪，而不是压缩用户当前要求。若一个不可拆调用组太大，先在工具返回阶段做有契约的转存，不能切掉结果ID。

## 遗漏记录与故障诊断

每项未发送内容记录原因：过期、权限不符、重复、超预算、已转存或与当前目标无关。发生错误时就能检查“正确证据本来存在，但在哪个阶段被删除”，而不只看到最终Prompt。

省略记录不需要暴露被拒绝文档的秘密正文。可记录受控ID和原因，按权限向开发者显示。多租户系统中，连文档标题可能敏感，诊断访问也应授权。

## 相关性评分的局限

一份恶意文档大量重复用户问题关键词，可能被排到前列；一个过期部署说明可能比当前简短配置更像自然语言问题。相关性不能代替信任、新鲜度与证据类型。

因此选择顺序并非一个分数排序到底。先做主体与权限过滤，再解决版本和用途冲突，然后才优化相关性与覆盖。评分器的输入和错误也应纳入评测，否则上下文系统变成不可解释的另一层模型。
