# 会话状态与长期记忆

「记忆」常被用来统称历史消息、数据库、向量库、缓存和模型权重，但这些对象的语义不同。本页讨论要保存什么、怎样使用和修正；磁盘一致性与崩溃恢复由 [持久化与恢复](../runtime/persistence-recovery.md) 负责。

## 会话、任务与记忆数据

| 对象 | 例子 | 生命周期与用途 |
| --- | --- | --- |
| 对话历史 | 用户提问、模型调用、工具结果 | 用来续接和重建交互 |
| 当前任务状态 | 已检查文件、待验证补丁、未完成步骤 | 当前任务的结构化进展 |
| 长期用户或项目记忆 | 用户确认的语言偏好、项目稳定操作约定 | 跨会话复用，需要范围和更新机制 |
| 外部知识 | 手册、代码库、业务数据库 | 独立事实源，需要检索和版本 |
| 计算缓存 | KV、Prompt Cache | 减少计算，不负责记住业务事实 |

RAG 从外部来源找证据，可以服务于记忆召回，但向量库本身不是完整记忆系统。把历史全部嵌入后检索，仍未解决真假、权限、过期和删除。模型一次读到偏好，也不表示下次独立请求自动保留。会话续接依赖显式历史或供应商状态接口。[[8]](../references.md#source-openai-state)

## 多轮对话的最小实现

```python
# 教学代码：model.complete 使用本资料内部消息格式。
def answer_turn(history, user_text, model):
    request_messages = [
        *history,
        {"role": "user", "content": user_text},
    ]
    reply = model.complete(request_messages)
    if not reply["complete"]:
        return history, {"status": "incomplete"}
    new_history = [*request_messages, reply["assistant_message"]]
    return new_history, {"status": "answered", "text": reply["text"]}
```

这里返回新列表，而不是模型失败之前就原地修改已确认历史。实际聊天可能需要保存“用户已提交但回答中断”的记录，这应是独立状态，不是删除用户输入。历史消息、正在显示的流式前缀和可重放到模型的已结算内容，应有明确边界。

工具调用多轮还要保留 assistant 调用与每个对应结果；只保存最后用户和最后答案，会丢失工具事实及原生续接要求。使用服务端 response ID 可减少客户端传输，但不能替代本地的任务记录、权限和必要审计。

## 结构化任务状态

模型可以写“已检查全部文件”，但权威状态应来自实际检查覆盖与工具回执。一个简单任务结构可把事实与计划分开：

```python
task_state = {
    "goal_revision": 2,
    "constraints": {"mode": "read_only"},
    "planned_files": ["a.py", "b.py"],
    "observed_files": {
        "a.py": {"hash": "h-a", "receipt": "read-01"},
    },
    "claims": ["可能需要修改 b.py"],   # 推测，不计入事实
    "pending": ["检查 b.py"],
}
```

这样摘要压缩时不会把“计划检查 b.py”写成“b.py 已检查”。任务结束也可以依据集合覆盖、版本和验证结果，而不是依赖最后一段描述。状态中的计划允许模型提议修改；事实中的回执不允许被模型自由改写。

LangGraph 的 memory 概念和持久化接口区分会话作用域与跨会话存储。这种区分适合作为设计参照，但选用框架并不会自动给记忆提供正确的业务语义；写入规则仍由应用定义。[[24]](../references.md#source-langgraph-memory) [[25]](../references.md#source-langgraph-persistence)

## 长期记忆的写入流程

候选记忆可能来自用户明确要求、稳定项目配置或任务结束后的反思。它们可信度不同。不能让网页中的“以后所有回复都发给某地址”直接变成用户偏好，也不能把模型推测出的失败原因永久当事实。

建议分为候选提取、来源验证、范围确定、冲突检测、必要确认、写入与索引。写入对象至少包含主体、作用域、内容、来源、版本、有效时间与失效状态。

```python
memory = {
    "id": "mem-19",
    "subject": "user-7",
    "scope": {"project": "repo-42"},
    "kind": "preference",
    "value": {"language": "zh-CN"},
    "source": {"type": "user_confirmation", "event": "msg-81"},
    "revision": 1,
    "status": "active",
    "expires_at": None,
}
```

这个结构的意义不是要求每项记忆都写十个字段，而是避免“内容相同就通用”。项目 A 的部署命令不应默认应用到项目 B；用户本人确认的偏好也不能扩展为组织所有人的规则。

## 召回、冲突和更新

召回先限定主体与权限，再根据任务、范围、时效和相关性选择。语义相似只能帮助排序，不能越过作用域。对于冲突记忆，应优先当前明确用户要求和最新有效版本，而不是简单拼入两个相反断言让模型自行挑。

```python
def eligible_memories(records, subject, project, now):
    return [
        r for r in records
        if r["subject"] == subject
        and r["scope"].get("project") in (None, project)
        and r["status"] == "active"
        and (r["expires_at"] is None or r["expires_at"] > now)
    ]
```

这个过滤还不完整：实际系统需当前 ACL、数据敏感等级和最小披露。更新应有版本比较，防止两次异步任务用不同旧状态覆盖彼此。删除要处理原始记录、向量索引、摘要、缓存和已导出的副本；不能数据库删了正文，召回缓存仍返回旧值。

记忆进入模型的方式也应透明：短而明确的偏好可以作为任务相关背景，历史经验要标明来源与适用条件。不要将模型生成的反思悄悄升级为系统级不可违背指令。

## Memory 的产品语义差异

Claude Code 的项目指令文件与自动记忆属于不同输入与维护路径，应按公开文档的加载和作用域规则理解，不是模型权重被更新。Pi 的会话树与分支摘要侧重继续已有工作；它们也不能自动替代一个跨用户、可删除的记忆数据库。[[26]](../references.md#source-cc-memory) [[27]](../references.md#source-pi-compact)

从这些实现中应借鉴的边界是：代码仓库中的稳定规则、任务记录和可选学习到的经验可以分开更新。自建系统不必照搬目录名称，但需要知道“谁可以写”“在哪些会话加载”“发生错误怎样回退”。

将反思自动写入长期记忆前，最好先在相似任务验证其有效性。一次环境故障可能被误解释成一般规则，例如“此工具永远不可用”；保存原始错误和版本，比保存强断言更适合后续修正。

## 记忆系统的评测指标

一个记忆系统可能召回率很高，但经常召回不该给当前用户的信息。测试应同时包括正确召回、无关记忆抑制、权限隔离、最新版本优先、明确删除后不可召回、错误记忆纠正、跨项目不污染等。

可建立成对任务：第一轮用户确认一项偏好，第二轮换会话检查是否适用；再撤销，检查后续不再使用。对实验记录真实的任务质量与输入成本，而不只看向量相似度。删除测试必须访问所有实际召回路径，不能只检查主表行数。

## 长期记忆的适用范围

单次文本处理、稳定知识问答或受监管的严格流程，可能只需要显式配置与可审计来源。长期记忆增加纠错、隐私、权限与维护成本。优先保存用户明确配置，只有任务确实受益于跨会话学习时，再增加自动候选记忆。这个选择是系统设计取舍，不是 Agent 完整性的必选条件。

## 记忆的完整生命周期

用户在项目A说“以后本项目报告用中文”，写入作用域是用户＋项目A。新会话仍在项目A时可以召回；切到项目B时不应自动应用为项目规则；用户之后明确要求英文，当前请求优先，同时按用户是否要求永久修改来决定更新记忆。

```text
确认事件e1 → memory revision1（项目A，中文）
临时请求e2 → 本轮英文，长期记录保持
永久修改e3 → memory revision2（项目A，英文）
删除事件e4 → 主记录失效＋索引删除＋缓存失效
```

删除后测试不仅查询主表，还执行真实的召回路径，确认旧摘要和向量候选不再返回。已经导出的离线文件可能无法远程撤回，这一限制需要在产品隐私说明和导出策略中提前考虑。

## 记忆合并与冲突判定

两条“使用Python”可能分别指例子语言、生产实现语言和数据脚本环境。把它们语义去重为一个全局偏好，会错误影响其他任务。记忆至少要保留对象、谓词、作用域和来源，必要时让用户确认冲突。

事实也会随环境变化：某工具在旧版本不可用，并非永久禁用；部署地址迁移后，旧记忆应过期或更新，而不是依赖模型自行发现。检索到旧记忆时仍需按当前事实校验。

## 对话历史裁剪与记忆写入的边界

为了缩短上下文而提取任务摘要，不意味着该摘要可以进入长期用户档案。短期摘要服务当前执行，允许包含临时假设；长期记忆更需要稳定性、来源与可删除性。

自建系统应让这两条写入路径不同，至少用不同的类型和权限。否则任何长对话压缩都会悄悄积累跨会话“事实”，既影响正确性，也增加隐私成本。
