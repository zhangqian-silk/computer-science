# 工具系统：契约、执行与结果

工具把模型提出的动作变成程序能够执行的操作。模型交互中的工具往返已经说明「声明工具—生成参数—执行—回填结果」；通用工具系统进一步让多个能力共享一致的校验、分派和结果处理过程。

工具名称和参数回答「请求做什么」，执行器回答「由谁、在什么范围内实际执行」。两者需要一致，但不是同一个对象。

---

## 一、工具契约的两个视角

| 契约部分 | 模型需要知道 | 执行器需要知道 |
| --- | --- | --- |
| 名称与描述 | 何时选择、何时不选择 | 唯一注册名及对应实现 |
| 参数 | 字段含义、单位、必填条件 | 类型、范围、资源约束 |
| 返回值 | 有哪些结果、怎样解释 | 结果编码与错误分类 |
| 副作用 | 是否修改对象、是否可撤销 | 权限、审批、幂等与审计 |
| 运行限制 | 必要的等待或规模限制 | 超时、并发、取消和资源释放 |

例如 `read_file` 的描述应说明它读取已有文件，不搜索未知路径，也不修改内容。参数 `path` 应有明确的工作区基准；执行器还要验证实际解析后的目标是否仍在允许范围内。

描述不是越长越好。两个功能几乎相同、名称含糊的工具会增加选择歧义；工具说明应突出对象和操作差异。[[20]](../references.md#source-anthropic-tools)

## 二、通用执行过程

```mermaid
flowchart LR
	C["名称与参数"] --> D["查找注册契约"]
	D --> V["解析与校验"]
	V --> A["资源授权"]
	A --> E["执行操作"]
	E --> R["结果转换与关联"]
```

注册表把模型可见的能力与可执行实现联系起来。未知名称不能被当作任意函数执行；参数是数据，不能直接拼成程序或命令。

一次 `read_file("config.yaml")` 可以按下列顺序推演：

1. 按名称找到当前允许的读取工具。
2. 解析参数，确认路径字段存在且类型正确。
3. 解析工作区内的目标，检查读取权限。
4. 读取内容和必要的版本信息。
5. 构造结果，并关联最初的调用 ID。
6. 将结果交给后续模型输入或界面展示。

格式正确只证明数据满足结构要求，不能证明文件存在、用户有权限或操作能成功。即使模型输出遵守严格 schema，执行器也仍需校验业务条件。

## 三、结果应表达发生了什么

一种结果结构可以是：

```json
{
	"call_id": "call_config",
	"status": "ok",
	"data": {
		"path": "config.yaml",
		"revision": "r2",
		"content": "server:\n  port: 8080\n"
	}
}
```

`call_id` 用于关联；`status` 表达执行结果；`data` 是观察到的信息。结果转换后进入消息协议时，应保留这种语义关系，而不是把所有情况都变成一段「已完成」文本。

| 结果 | 含义 | 典型后续解释 |
| --- | --- | --- |
| `ok` | 操作成功且返回有效结果 | 依据结果继续 |
| `not_found` | 查询完成，但对象不存在 | 说明未找到或澄清目标 |
| `invalid_arguments` | 输入不满足契约，未执行 | 修正参数 |
| `permission_denied` | 不允许执行 | 说明权限限制，不绕过 |
| `timeout` | 等待超过边界 | 判断操作是否可能已经发生 |
| `partial` | 只取得部分结果 | 标明覆盖范围与缺失部分 |

这是结果分类示例，不要求所有工具使用这些英文值。重要的是区分「没有结果」「操作失败」「结果不确定」和「成功但为空」。

长结果可以提供摘要、截断标记和可回查的产物引用。摘要不能丢掉决定后续行动的错误信息、单位和完成状态。

## 四、能力集合怎样组织

工具应围绕稳定的操作对象划分。过细会让模型反复拼接步骤，过粗则可能混入多个副作用、难以校验。比如「读取指定配置」是清楚的能力；「自动修好所有问题」若没有明确输入与验收，就不是可靠契约。

文件、进程、浏览器和远程服务由不同[执行环境](execution-environments.md)支持。MCP 统一部分能力接入，Skill 提供使用方法，Hook 在生命周期事件中运行扩展；它们可以组合，但都不能替代工具本身的输入输出语义。

## 五、并发、副作用与重试

并发首先要求数据依赖允许，同时检查共享资源。两个只读查询可以并行，但如果需要同一时间点快照，还必须有一致性条件；写同一个文件的两个动作不能只因参数不同就视为独立。

模型生成的调用 ID 关联一次交互。若业务操作需要防重复，还需要稳定的操作标识及服务端去重语义；重新生成一个调用 ID 不会自动避免重复写入。

| 情形 | 能否直接重试 |
| --- | --- |
| 参数错误 | 应先纠正，重复同一输入通常无益 |
| 暂时性读取失败 | 在预算和语义允许时有限重试 |
| 已确定未执行的写入失败 | 可按授权及工具约定重试 |
| 写入超时、结果未知 | 先查询或对账，不能盲目重复 |

更换工具版本时，也要考虑正在进行的调用：旧参数应由匹配的契约解释，不能悄悄交给语义已经变化的新实现。

## 六、学习检查

用「查询订单」和「取消订单」比较契约：同样都接收订单号，为什么执行限制和超时处理不同？查询主要取得观察，取消会改变外部状态；超时可能意味着已取消但回执丢失。

再检查一个完整调用是否能回答：输入是什么、是否真正执行、结果依据是什么、能否重复、何时结束。能够说明这些问题，比只记住工具参数 schema 更接近理解工具系统。
