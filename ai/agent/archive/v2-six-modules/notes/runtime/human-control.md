# 人工控制：补充、审批与取消

人工控制使用户能够在任务运行中提供信息、决定动作或停止执行。它不只是一个确认按钮：不同输入改变的对象不同，生效时点和反馈也应明确。

---

## 一、四类运行中输入

| 输入 | 改变什么 | 例子 |
| --- | --- | --- |
| 补充信息 | 可用事实 | 提供缺失配置 |
| 调整目标 | 后续任务要求 | 从修改改为只解释 |
| 审批决定 | 某个待执行动作是否允许 | 确认提交具体变更 |
| 取消 | 是否继续推进任务 | 停止当前工作 |

一句「继续」需要结合上下文判断是在提供审批、恢复等待还是普通对话。不能把它解释为所有未来动作的无限授权。

---

## 二、消息在何时生效

运行中的模型请求已经使用了一个输入快照。用户此时补充消息，并不会改变已经发出的请求；系统可以等待当前步骤结束后使用新输入，或取消当前生成后重新组织。

两种方式各有代价：等待保留当前工作但反馈较慢；中断更快响应，却可能浪费生成并需要处理在途工具。界面应区分「已收到」与「已应用」，避免用户误以为旧动作已被阻止。

若新消息改变目标，应重新检查后续动作，而不是继续执行旧计划。已完成的副作用则要如实说明，不能通过改写任务描述假装没有发生。

---

## 三、审批绑定具体动作

审批信息至少应包含动作、对象、关键参数和预期效果。例如「把配置文件 r2 中超时从 30 改为 60 秒」，比「允许操作文件」更能表达实际决定。

```mermaid
flowchart LR
	A["待执行动作"] --> S["生成确认摘要"]
	S --> U["用户批准或拒绝"]
	U --> V["核对动作仍匹配"]
	V --> E["执行并反馈"]
```

批准后如果目标文件或参数已经改变，应重新核对，必要时重新确认。一次批准不能被其他任务、其他资源或旧请求重复消费。

审批只是允许执行，不是执行成功；拒绝意味着不执行该动作，不应通过改变工具名称绕开拒绝。

---

## 四、取消不是回滚

取消通常先阻止启动新步骤，再向在途动作传播取消，最后收集可确定的状态并释放资源。

| 取消时点 | 可能结果 |
| --- | --- |
| 动作尚未开始 | 可以不执行 |
| 只读动作运行中 | 可停止等待，但仍需回收资源 |
| 写入已提交 | 不能声称未发生，需记录效果 |
| 外部结果未知 | 保留未知状态，可能需要查询 |

取消请求与正常完成可能同时到达。应依据实际记录和状态迁移顺序决定终态，而不是让最后刷新的界面文本覆盖后端事实。

用户可能只要求停止，不要求撤销。撤销也是新的动作，需要检查可逆性与授权范围。

---

## 五、等待与恢复

等待审批的任务应保存待决定事项，使页面刷新后仍能显示同一对象。响应到达时要验证任务尚在等待该决定；已失效的审批不能唤醒另一个动作。

某些运行框架恢复时会重新进入节点，而不是从暂停行继续。因此暂停点前的副作用可能重复，需要按具体执行语义安排。[[47]](../references.md#source-langgraph-interrupts)

学习自检：用户点击取消后为什么可能短时间显示「取消中」？因为系统还在处理在途动作；明确这个中间态比过早声称全部停止更准确。
