# 人工交互与执行控制

人机交互不只是一个聊天输入框。用户可能补充资料、修改目标、批准动作、排队新任务或要求停止；这些输入对运行的影响不同。本页明确它们何时被接受、谁处理、是否改变已在途动作。原生协议细节见 [异构 Agent 接入](scheduling-protocols.md)。

## 人工控制的输入类型

| 输入 | 意图 | 合理的处理边界 |
| --- | --- | --- |
| 补充资料 | 增加信息，不改变任务 | 下一次构造上下文时合入 |
| 澄清回复 | 回答系统正在等待的问题 | 关联到具体请求，不作为新任务猜测 |
| Steer | 改变当前工作方向 | 在可接纳边界更新后续决策 |
| Follow-up | 当前工作完成后继续另一项 | 排队，不抢占正在执行的批次 |
| Approval | 同意某项具体动作 | 绑定候选、参数、身份和期限 |
| Cancel | 停止约定范围的工作 | 停止新派发、传播并确认收尾 |

把所有内容都立即追加到正在发送的模型请求，技术上也无效：请求已在途，模型不会看到宿主后来原地改的列表。必须记录下一步何时消费。

## Steer 与强制取消

Pi 指定Loop在批次/轮次边界消费 Steering，准备阶段后还检查新到消息；Follow-up 在即将停止时才进入下一轮。它不是承诺用户一句“停”就能撤销已经发出的数据库请求。[[9]](../references.md#source-pi-loop)

参考实现可以有独立队列，保留接受与消费状态：

```python
# 教学数据：消息ID由宿主分配；内容不直接决定权限。
control_message = {
    "id": "input-28",
    "kind": "steer",
    "task_id": "task-7",
    "text": "先停止修改，改为只读分析。",
    "accepted_at": "2026-09-10T10:00:00Z",
    "consumed_at_step": None,
}
```

修改目标应增加目标版本，后续计划和审批必须关联新版本。仍在执行的旧动作应按风险决定立即中断、等待结束或对账。不要因为新Prompt写“只读”就认为已经运行的Shell失去写权限。

## 审批绑定实际动作

“是否允许执行工具？”过于宽泛。审批界面应展示工具、目标对象、参数摘要、影响范围、执行身份和必要的差异。修改文件显示补丁；发送消息显示收件人与正文；提交操作显示目标资源和不可逆后果。

```python
approval = {
    "approval_id": "approval-8",
    "subject": "user-7",
    "task_revision": 4,
    "tool_revision": "send-message-v2",
    "action_digest": "sha256:canonical-action",
    "resource_revision": "draft-3",
    "policy_revision": 12,
    "expires_at": "2026-09-10T10:05:00Z",
    "consumed": False,
}
```

摘要 hash 需要基于规范化的实际动作，而不是UI显示截断后的字符串。审批后若参数、目标、代码或策略发生改变，重新评估是否仍匹配；消费也需要一次性和原子性，避免两个工作者同时用同一票据执行。

```python
# 教学逻辑：原子消费与资源一致性必须由 store 实现。
def consume_approval(store, approval_id, action_digest, user_id, now):
    return store.consume_if_matches(
        approval_id=approval_id,
        subject=user_id,
        action_digest=action_digest,
        not_expired_at=now,
        unconsumed=True,
    )
```

这不是 `approved=True` 全局变量。模型历史中的“用户同意了”不能代替授权存储中的批准事实。

## 自动 Reviewer 的角色

风险分类模型可减少常规审批负担，但它的判断也可能被工具文本或上下文误导。应先执行确定性硬限制，再把允许人工判断的灰区交给 Reviewer。超时、格式不合法或不确定结果应回到人工或拒绝，不能默认执行。

OpenWorker 测试里区分硬拒绝、需人工和可由 Reviewer 判断，并检查不合法 verdict 的处理；旧 `auto` 与 `auto-approve` 模式语义也不同。这说明 UI 上一个相似的模式名称，可能隐藏不同权限路径，配置迁移需要明确验证。[[31]](../references.md#source-openworker-tests)

自建系统不能只拷贝“允许/拒绝”模型提示。需要审计 Reviewer 看见的动作是否与实际执行一致，是否包含真实权限范围，输出如何影响硬 Gate。

## 取消的状态机

一个具体取消过程通常经历 `requested → stopping → stopped`，也可能得到 `completed_before_cancel` 或 `unknown_external_effect`。接受取消请求只表示系统收到，不代表工作已经静止。

```python
cancel_result = {
    "request_accepted": True,
    "new_dispatch_blocked": True,
    "model_stream_stopped": True,
    "owned_processes_stopped": False,
    "external_effect": "unknown",
}
```

可以先快速返回“正在停止”，继续推送后续状态。若协议要求 cancel 返回时已 idle，就必须等待实际收尾，不能只发送一个信号。背景工具、子 Agent、远端 job 的范围都要写清，父任务停止是否包含所有后代不能凭名称猜测。

Python 协程取消是协作机制；任务取消异常传播不等于外部进程必然消失，进程清理也不等于远端操作撤销。[[59]](../references.md#source-python-asyncio) 详细执行边界见 [环境](../tools/execution-environments.md)。

## 中断与恢复

人工审批可能等待数小时，不应在数据库事务中持锁等待。保存待审批状态，释放执行资源或保持有限的可恢复句柄；批准后重新检查目标和策略。LangGraph 的 interrupts 会涉及节点重执行，因此审批前发生的副作用要考虑重放，而不是从函数暂停位置天然继续。[[47]](../references.md#source-langgraph-interrupts)

恢复时不要把普通用户回复当成最近一个未完成审批的批准。应该携带审批ID或澄清请求ID，并验证会话主体。用户说“可以”若没有明确对象，尤其有多个待批准动作时，需要消除歧义。

## UI 与后端一致性

前端可以乐观显示输入已发送，但后台必须有接受标识和当前任务状态。重连后应能发现哪些控制输入已接受、已消费、被取消或过期。只保留聊天气泡无法解释“我点了停止，但为什么还在跑”。

审批和取消事件需要脱敏审计，但不要求保存完整内部推理。记录动作版本、决策主体、结果与时间，足以定位谁批准了哪一次真实执行。

## 测试与调优

测试审批过期、参数修改、重复点击、两个工作者同时消费、等待期间策略撤销、取消与完成同时到达、Follow-up 留在队列、Steer 到达压缩期间、用户断线后重新连接。每项应明确预期外部效果数量和最终状态。

交互体验可优化快速回执、进度可见和审批摘要，但不要用“秒回取消成功”掩盖未结束的进程。指标包括接受延迟、实际消费延迟、人工等待、取消到静止时间、误触发与重复操作。它们帮助改善体验，也保留真实责任边界。

## 多项审批的关联与隔离

用户看到“修改配置”与“发送报告”两项请求，只回复“同意”。如果系统自动批准最新一个，可能偏离用户意图。界面应把回复关联到具体审批ID，或向用户明确确认对象，不能仅依对话邻近关系猜测。

审批记录还要绑定目标用户和动作版本。同一个审批链接被另一个账户打开、重复点击、在参数变化后使用，都应被拒绝或重新确认。这个边界属于可信身份系统，不交给模型判断。

## 取消与完成竞争的时间线

```text
t0：工具进入执行
t1：远端提交成功
t2：宿主收到成功回执并保存
t3：用户取消到达
t4：任务停止后续步骤，但已有成功回执保持
```

若t2尚未发生就收到取消，可能需要标记外部状态未知。不能在两条时间线里都返回相同的“已取消，什么都没发生”。用户最需要的是哪些动作已经完成、哪些已停止、哪些仍需查询。

## 排队输入的可见性

显示用户已发送的Follow-up，但后台没有接受它，是一种严重体验错配。返回接受ID，重连时展示accepted/consumed/canceled状态，并允许用户编辑或删除尚未消费项。编辑后的内容保留版本，避免模型看到旧内容却UI显示新内容。

对于Steer，界面应显示将在当前安全边界后生效；对于紧急停止，提供明确Cancel入口。两者可以组合，但不能用同一个按钮隐藏语义。
