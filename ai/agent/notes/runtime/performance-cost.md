# 性能、成本与模型路由

性能优化的目标是以可接受延迟和资源完成经过验证的任务，而不是让某次请求便宜或让某个指标变大。单次输入、输出、工具与调度都有成本；模型能力、上下文策略和执行结构必须一起分析。

## 任务成本分解

对一次任务，可以分别记录模型输入/输出、缓存读写、工具费用、环境资源、验证和重试成本。失败尝试同样计费，应纳入每个成功交付的总体成本。

```text
每个已验证交付的摊销成本 =
评测期全部任务与重试的成本 / 已验证交付数量
```

分母为零时结果未知或无穷，不能报告零成本。不同产品的计费字段并不统一，使用原始usage与版本化映射，避免把缓存token重复相加。价格会变化，笔记提供核算方法，不固定实时报价。

## 墙钟时间与总工作量

串行模型请求的延迟相加，独立工具可以重叠，但共享资源和集成形成关键路径。多个Agent可能降低wall time，却提高总token和机器占用。只汇报最快成功案例会隐藏失败重跑和长尾。

先从Trace定位：队列、环境准备、首token、生成、工具锁等待、执行、验证、人工等待和清理。工具调用排队很长时，提高模型生成速度不会解决瓶颈；输出极长时，Prompt缓存减少prefill也可能影响有限。[[16]](../references.md#source-vllm-apc)

## 测量驱动的优化顺序

先避免无效工作：重复检索、无用工具、无关历史和错误重试。再选择适当上下文与返回长度，然后考虑缓存和并行，最后才是复杂路由与多Agent。这个顺序是参考方法，不是所有工作负载的固定排名。

删减上下文可能增加回查，扩大工具粒度可能降低往返但减少中间验证机会，降低推理预算可能让复杂任务失败。每个优化都有替代成本，必须通过同任务的结果评价。

```python
experiment = {
    "task_set": "config-cases-v3",
    "baseline": {"parallel_tools": 1, "context_policy": "recent"},
    "candidate": {"parallel_tools": 4, "context_policy": "recent"},
    "fixed": ["model", "prompt", "tools", "verifier", "workspace"],
    "metrics": ["verified_rate", "wall_ms", "total_cost", "unsafe_effects"],
}
```

只改变工具并发，不同时换模型、Prompt和任务集，才较容易解释差异。

## 预算预留与结算

并发任务如果都读取“余额足够”再启动，会共同超预算。应在派发前原子预留估计上界，完成后按实际计量结算；无法准确上界的工作需要较保守额度或子预算。

```python
# 教学代码：单进程线程安全预算，整数单位避免浮点费用累积。
import threading

class Budget:
    def __init__(self, limit):
        self.remaining = limit
        self.lock = threading.Lock()

    def reserve(self, amount):
        if amount < 0:
            raise ValueError("预留不能为负")
        with self.lock:
            if amount > self.remaining:
                return False
            self.remaining -= amount
            return True

    def release_unused(self, amount):
        if amount < 0:
            raise ValueError("释放不能为负")
        with self.lock:
            self.remaining += amount
```

真实实现还要以唯一reservation ID防止重复释放、保存状态、限制释放不超过原预留。usage缺失时不能全部退回当零成本；保留未结算状态或按保守策略处理。跨进程则需要数据库原子操作，不能共享一个Python锁。

## 模型路由与质量约束

路由先过滤能力：是否支持所需工具/schema/上下文/续接，再依据任务和资源选择。一个便宜模型不支持当前推理历史，直接切换可能造成错误；一个高能力模型也可能在格式任务上浪费预算。

可在任务起点按类别选择模型，在明确边界升级或降级。边界应重新构造上下文并处理原生状态，不能将旧provider的不透明条目原样塞给新provider。失败回退时还要判断之前是否已经执行工具，避免重新创建整个任务产生重复效果。

```python
# 教学策略：先可行性过滤，再按自有评测表选候选。
def choose_profile(profiles, required, estimated_input):
    feasible = [
        p for p in profiles
        if required.issubset(p["capabilities"])
        and estimated_input <= p["input_budget"]
    ]
    if not feasible:
        raise ValueError("没有满足能力和输入预算的模型")
    return min(feasible, key=lambda p: p["measured_cost_per_verified_task"])
```

最后一项必须来自对应任务分布的评测，不是供应商单价。模型目录更新会改变可用性和默认行为，路由规则需版本化。

## 缓存、压缩和重复计算

缓存命中率高不一定成本低：为了稳定前缀多发十倍无用历史，可能提高命中但更贵。压缩比例高也不一定好：丢了关键事实导致反复查询和修复，会增加总成本。

将两者在同一任务轨迹计量：压缩生成成本、旧前缀失效、后续输入长度、缓存读写、回查和质量。具体规则见 [缓存](../model/kv-cache.md)、[压缩](../context/compaction.md)。不要在每轮无条件重写system prompt以“更新进度”，可把动态状态放入其合适的消息位置。

## 并发的三种上限

模型并发受provider额度与成本限制，工具并发受资源和外部服务限制，任务并发受机器/工作区和租户公平性限制。一个全局 `max_concurrency` 无法解释三者。需要能观察各自队列与等待。

Dsh滚动工具池、Codex共享/排他运行是不同并发契约的实现切片。提高上限前先测工具是否可交换、结果是否按正确身份提交，以及取消是否收尾。吞吐增加而文件冲突更多，不是安全优化。[[49]](../references.md#source-dsh-scheduler) [[14]](../references.md#source-codex-tools)

## Prompt 与推理预算调优

针对简短抽取，控制输出长度和结构可能比大幅修改框架更有效；针对探索任务，高质量工具返回和上下文选择可能减少整个Loop步数。额外规划调用是否节省整体工作，需看后续任务成功率和步骤数。

推理token可能计入输出或有供应商专属统计。应记录原始usage而非只统计用户看见文本长度。隐藏推理较长时，首个可见文本并不是模型何时开始工作，见 [输出信息](../model/outputs.md)。

## 容量与真实基准

基准必须写清模型、输入/输出分布、并发、缓存状态、工具延迟、部署位置与软件版本。自托管还需硬件、精度和调度。冷启动、稳定吞吐、长尾和取消负载分别测，不能拿单用户交互体验预测多租户容量。

记录限流后的放大：一次任务内部重试、HTTP SDK重试、外部调度重试若叠加，会形成突发流量。统一重试责任、指数退避、抖动、上限和剩余deadline，让超载时有可预测降级。

## 优化决策记录

每次改动说明瓶颈证据、目标指标、正确性护栏、实验条件与回滚阈值。保留“不值得采用”的结果同样有价值。代码演示和解析测试不能代替真实性能数据，本资料不提供未经测量的加速或省费百分比。

## 预算预留的并发竞争

余额100单位，两个并发任务各预计70。若都先读余额再扣减，二者都可能启动，实际承诺140。正确的原子reserve应只允许一个成功；另一个排队或选择更小计划。执行完成实际只花50时，释放20，不是释放70。

如果usage缺失，暂保留未结算预留；如果同一完成事件重复到达，不得重复释放。预算因此需要reservation ID与状态，不只是一个可加减数字。

## 路由升级的完整成本

便宜模型尝试失败再升级，成本是首次尝试、失败工具、上下文恢复以及高能力模型的合计。若失败会产生不可逆副作用，升级更需要对账。与“直接用高能力模型”的基线比较，而不是只比较各自单次单价。

对可快速独立校验的任务，先便宜再升级可能有效；对错误难检测的开放任务，低成本答案可能悄悄错误，无法可靠触发升级。路由策略依赖验证器质量。

## 性能结论的适用条件

应写“在任务集X、模型profileY、固定输入分布、并发N、冷暖缓存分别测量的条件下，候选降低了某指标，同时质量区间如何”，而不是“并行快四倍”或“压缩省80%”。

本资料只给实验设计和离线机制测试。任何真实速度、价格或跨产品排名都需要实际数据，不从源码结构直接推断。
