# 可观测性与故障诊断

可观测性把“模型表现不好”“Agent卡住了”拆成可定位的事实：输入缺失、协议错误、模型等待、工具排队、执行失败、审批等待或清理阻塞。本页讨论事件、指标和诊断；任务是否做对由 [评测](evaluation.md) 判断，日志不是业务验收器。

## 请求、步骤与任务的观测层级

至少区分模型请求、工具调用、用户轮次、任务尝试与整个任务。对每个层级记录开始、关键转移和结束原因，而不是只有一个全局运行时长。模型调用ID与业务operation ID不同，关联链要保留。

```python
event = {
    "event_id": "ev-18",
    "task_id": "task-7",
    "attempt_id": "attempt-2",
    "step_id": "step-4",
    "call_id": "call-9",
    "kind": "tool_execution_started",
    "timestamp": "2026-09-10T10:00:00Z",
    "data": {"tool": "run_tests", "queue_wait_ms": 120},
}
```

事件payload不要默认包含全部参数和结果；敏感值可用受控引用、hash或脱敏字段。OpenTelemetry的GenAI语义约定在演进中，应固定采用的schema/版本，并保留内部字段映射，而不是把可能变化的属性名当永久接口。[[65]](../references.md#source-otel-genai-repo)

## 事件、日志与 Trace

Metrics适合聚合趋势，Trace适合关联一次任务内部耗时，日志与事件适合具体状态和故障。把高基数task ID直接作为每个metric label，会增加观测成本；将所有内容只放进日志又不利于发现总体退化。

运行恢复的权威记录与诊断Trace也应区分。Trace可能采样或丢失，不能作为唯一的副作用账本；调试日志中的“success”也不能改变任务状态。相同执行事实可以投影到观测和UI，但存储保证不同。

## 延迟分解

```text
任务总时间 =
队列等待 + 环境准备 + 各模型等待与生成
+ 依赖路径上的工具等待与执行
+ 验证 + 必要人工等待 + 收尾
```

并行时不能直接把所有span相加当wall-clock。先看关键路径，区分模型TTFT、完整响应时间、工具排队、handler执行与结果提交。缓存主要影响某些输入计算，不能解释所有延迟。

Codex的工具运行计时区分进入执行门之前的等待与handler开始，这说明测量点应放在真实边界，而不是函数入口随便计时。多个调用因排他锁等待，不应该被误诊为工具本身变慢。[[14]](../references.md#source-codex-tools)

## 执行终态与文本结束

输出流结束、模型没有后续工具、执行器完成、验证通过和资源清理结束分别是事实。Multica的终态保护接口说明已收到权威结果后，不能因清理还没结束就把任务改成卡死。[[61]](../references.md#source-multica-session)

```python
task_view = {
    "execution": "completed",
    "verification": "failed",
    "cleanup": "running",
    "user_message": "修改已生成，但指定测试未通过。",
}
```

这样的状态比一个`success`布尔值更能解释现实。UI可显示“验证未通过，正在清理”，不必把所有状态压成“失败”而丢失已完成产物，也不能显示“成功”掩盖测试结果。

## 故障诊断上下文

记录模型/adapter版本、Prompt版本、工具目录、上下文manifest、工作区版本、选用策略和实际usage。不要默认保存模型完整内部推理；外部可核验的输入来源、动作参数和回执更适合审计，也更便于最小披露。

对于检索错误，记录查询、索引版本、候选ID和最终选段；对于工具选择错误，记录本轮实际公开的schema，而不是事后查询最新目录。否则复查时看见的输入与当时模型看到的输入不同。

上下文可以含用户秘密。调试采样、访问审计、保留期和导出权限必须一起设计。摘要脱敏也可能漏敏感值，不能把它当唯一防护。

## 故障症状与职责定位

| 症状 | 首先核对 | 常见误判 |
| --- | --- | --- |
| 首字很慢 | 队列、连接、输入长度、cache与prefill | 直接提高模型并发导致更拥塞 |
| 有心跳但无进展 | 当前模型/工具状态、语义活动 | 心跳到达就永远不超时 |
| 工具总是选错 | 本轮描述与可见目录、参数语义 | 不看接口就换更贵模型 |
| 刷新后中间结果消失 | 临时流与持久状态的映射 | 认为模型忘了 |
| 显示完成但没有产物 | 权威回执、资源版本、验收 | 相信最终总结 |
| 取消后资源仍占用 | 子进程、子Agent、远端job所有权 | 只看前端停止动画 |

LangChain Forum的子Agent消息刷新问题适合用作第四行的测试线索：实时流与恢复记录不是自动相同。该帖子是社区现象，不证明所有版本都存在同一故障。[[15]](../references.md#source-forum-subagent)

## 事件重放与差异定位

用纯投影器从已确认事件重建显示状态，可以测试重复事件、乱序、缺口和迟到消息。投影器不能执行工具；重放一次Trace不应该再次发邮件。

```python
# 教学代码：只处理已按可靠存储排序的状态事件。
def apply_view(state, event):
    if event["seq"] <= state["last_seq"]:
        return state
    if event["seq"] != state["last_seq"] + 1:
        raise ValueError("事件缺口，重新加载权威快照")
    updated = dict(state)
    updated["last_seq"] = event["seq"]
    if event["kind"] == "verification_finished":
        updated["verification"] = event["data"]["status"]
    return updated
```

生产版还需重复序号内容一致性、合法前态和执行generation校验。这个小例子重点说明UI状态更新与实际动作分离。

比较两次运行时，先找到第一个关键差异：检索候选、输入上下文、模型动作、工具结果还是验证环境。只比较最后答案往往无法解释根因。

## 指标与告警

除了成功率和费用，应记录未验证比例、未知副作用、重复派发、审批等待、取消收尾、恢复失败和产物缺失。平均值容易掩盖长尾，按任务类型和provider分组看p50/p95及样本量。

告警应对应可操作状态，例如“已知执行完成但清理超限”“未知写操作超过对账窗口”，而不是所有错误都发同样的“Agent failed”。合理的runbook说明查询哪些记录、哪些重试安全、何时人工接管。

## 观测自身的成本

无界工具输出、全量Prompt、每token事件都上传，可能让观测成本接近模型成本，并放大隐私风险。对高频显示做合并，对关键事实保留可靠记录，对敏感内容使用受控引用。采样策略不能删除唯一的安全审计事实。

上线前还要测试观测系统不可用：非关键日志故障不应悄悄阻塞所有任务，关键账本写入失败则不能假装操作已可恢复。明确区分诊断可用性与执行承诺，是可靠运行的一部分。

## 故障案例：运行停滞

若任务有heartbeat，最后语义事件是`tool_admitted`，却没有`tool_started`，应检查资源门、审批或锁等待，不先怀疑模型推理慢。若已有`tool_started`而无settled，检查进程/远端任务。若已有权威final但UI未完成，检查事件投递、消费者积压和清理状态。

同一个表面症状可能对应完全不同责任层。将最后活动拆成网络心跳、模型事件、工具状态和用户等待，就能避免“重启全部Agent”的粗暴处理。

## 事件序号与时间戳

序号用于同一日志内的确定顺序，时间用于跨系统关联和持续时间。不同机器时钟偏差会让timestamp看起来逆序，不能据此判断业务因果。记录父事件/请求关联，必要时使用服务端单调时间计算duration，墙钟用于显示。

重复事件应按ID和内容一致性处理；同序号内容冲突应告警而不是last-write-wins。最终状态不能被更晚的非权威文本覆盖。

## Trace 对照分析

对新旧两个Prompt运行同一任务，比较第一次关键动作差异。若新Prompt多读取了部署文档并避免误判端口，额外工具调用可能是质量收益；若只多生成三段计划而工具路径不变，成本可能无益。

Trace是解释证据，不是仅凭轨迹长度评分。最终仍结合独立验收与任务约束，避免偏好“看起来更像参考答案”的路径。
