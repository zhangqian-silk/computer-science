# 版本管理与发布

Agent行为来自模型、Prompt、工具、Skills、检索、策略和环境的组合。只给代码仓库打一个版本号，无法解释一次运行使用了什么；只升级Prompt，也可能改变真实动作。本页讨论配置、兼容性、发布和运行期变更。

## 运行配置清单（Manifest）

```python
manifest = {
    "application": "config-agent@1.4.0",
    "model_profile": "provider/model-profile-7",
    "adapter": "adapter@3",
    "prompt": "review@12",
    "tools": {"read_file": "2", "run_tests": "4"},
    "skills": {"safe-review": "5"},
    "retrieval_index": "repo-index-20260910",
    "policy": "workspace-policy@8",
    "verifier": "acceptance@6",
    "workspace": "git:abc123",
}
```

这个记录应能连接到具体内容hash或不可变发布对象，而不只是可被覆盖的“latest”。模型服务内部可能仍变化，无法固定时应明确记录别名和观察日期，并用回归集检测漂移。

秘密字段用安全引用，不在manifest中保存真实token。可重现实验还要记录依赖锁、环境变量的非敏感配置、时区和工具路径等相关条件。

## 接口、行为与状态兼容

工具仍叫 `edit_file`，参数也没变，但新实现从“严格匹配失败就拒绝”改为“模糊匹配并修改”，行为风险已经变化。Skill正文改变操作顺序，Prompt改变未知值策略，验证器减少检查，也都属于行为兼容性问题。

为每项发布记录输入兼容、输出兼容、执行效果、权限和恢复兼容。升级前检查旧任务或原生会话是否可继续；不能只依赖npm包版本或HTTP接口能连通。

```python
compatibility = {
    "accepts_old_requests": True,
    "preserves_effect_semantics": False,
    "resumable_old_sessions": "requires_migration",
    "new_permissions": ["network:internal-api"],
}
```

这样的描述会暴露需要人工评审和迁移的改动，而不是用一句“minor update”隐藏真实变化。

## 在途任务与热更新

新任务可以使用新版，在途请求应保留公布过的工具与Prompt快照；下一步是否采用新版需要明确。安全撤销可以即时生效，但功能更新不应偷偷改变旧调用的意义。

插件热更新要先准备和验证，原子发布，再排空旧资源。旧版本释放不能删除新版本注册。正在等待审批的动作若代码或参数改变，旧审批需要失效或重新校验。具体生命周期见 [Plugins](../tools/hooks-plugins.md)。

会话状态schema迁移应保留源数据，使用显式版本和可验证迁移；新代码不能读懂旧记录时应拒绝而不是忽略未知字段继续执行危险动作。回滚还需考虑新版已经产生的外部效果，不能只把二进制换回去。

## 测试金字塔

基础单测检查解析、schema、预算和状态机；机制集成测试在临时工作区运行工具；真实模型回归验证行为；受控故障实验验证重启、取消和外部对账。每层有不同费用与稳定性，不应把所有测试都变成付费模型调用。

固定原生响应fixture能够检测适配变化，但不能证明新模型质量；单元测试通过不能证明沙箱安全；自动评分通过也不代表生产无风险。报告要明确各层覆盖。

对产品升级，选取最容易变化的契约：推理状态回传、缓存字段、工具catalog、原生resume、Hook输出和后台清理。将它们写成兼容测试比维护一张可能过期的功能勾选表更有效。

## Shadow 与 Canary 的副作用边界

只读候选可在授权范围内影子运行并比较输出；写操作不能把生产请求同时发给新旧两套执行器。影子系统应禁写、使用模拟远端或只生成提议；真正执行由一个明确拥有者完成。

Canary按租户、任务风险或流量比例逐步放开，并监控验证通过率、未知副作用、重复执行和费用。若只监控HTTP错误率，行为质量下降可能完全没有告警。

```python
release_gate = {
    "minimum_sample_count": 100,
    "block_on": [
        "unauthorized_effect",
        "duplicate_business_effect",
        "unexplained_resume_loss",
    ],
    "compare": ["verified_rate", "p95_latency", "cost_per_verified_task"],
}
```

样本数示例不是通用统计要求。真实阈值按风险和方差确定；没有足够证据就保留不确定性，不把小样本零事故当成绝对安全。

## 回滚与事故处置

优先能独立关闭高风险工具、某个Plugin、某类模型路由或自动发布，不必每次全系统停机。保留版本相关日志和实际回执，识别哪些任务需要对账、重新验证或通知用户。

回滚可能恢复代码，但不自动撤销已发送邮件、已创建资源或已泄露信息。为可补偿动作设计明确逆操作并再次授权；不可补偿动作需要人工流程。不要把“checkpoint存在”视为全部业务可回滚。

## 资料与源码维护

文档里的源码链接尽量固定提交，并说明读取范围；产品文档按核验日期记录，不把不同版本默认行为拼成统一事实。对于讨论中的提案，只有发布文档或已合并实现才能说明可用；论坛热度不等于产品能力。

OpenAI和Anthropic的Harness工程实践可以作为设计经验，源码与接口说明作为实际实现证据。社区/X内容适合提供新问题与实验线索，正文不可读或未验证时应标明，不凭转述补齐实现。[[21]](../references.md#source-openai-harness) [[29]](../references.md#source-anthropic-long-harness)

本资料的反向实现索引把产品连接回具体专题，不另建重复的产品介绍。更新时优先修改主页面及来源条目，再重新构建HTML，减少多个版本散落而相互冲突。

## 运维检查与文档约束

定期检查失效凭据、孤儿任务、过期审批、未对账操作、产物保留期、源索引新鲜度和第三方依赖。任务长期“running”应能定位到具体等待，而非依赖值班人员重启全部进程。

操作手册应写明哪些重试安全，哪些需要查询远端，哪些只能人工处理。把危险命令直接复制到文档而不写对象和版本检查，同样可能造成事故。

## 发布记录与版本元数据

最小记录包括变更原因、影响主题、适配/策略版本、测试结果、已知限制、灰度观察、回滚方法和数据迁移。学习笔记可以不很形式化，但这些事实不能省。它们让未来开发者理解当时选择，也避免把一次临时实验变成没有条件的长期规则。

## 工具升级的发布检查

候选将`read_file`返回从纯文本改为带来源的对象。先验证adapter和模型历史编码能处理新类型，旧Prompt是否假设纯字符串，缓存键是否需要变更，旧会话恢复时是否仍能读取旧结果。

发布新版本后，新请求使用新目录；旧请求按快照继续或明确重新生成。不要在同一个原生会话里悄悄用旧工具名返回完全不兼容结构，导致模型误解。回滚时保留能读取新记录的兼容代码，否则已有任务可能无法恢复。

## 文档版本与实现兼容

一份Skill或仓库指令将测试命令改了，但工具和CI仍使用旧路径，会造成“模型按文档做对了，实际环境失败”。发布时联合检查文档链接、命令可执行性、工具参数、评测环境和示例。

本知识库使用单一专题正文生成合并Markdown与HTML，避免多份手写内容不同步。来源条目有版本和阅读范围，产品反向索引只链接主页面，不复制结论。

## 运行手册的最小内容

对每类关键故障写明检查入口、可安全动作、禁止动作和升级路径。比如unknown外部效果应先查询，不应值班人员凭直觉点“重试”；清理阻塞应处理资源，不应覆盖已知业务结果。

经验经过验证后进入runbook，未经确认的论坛建议只进入待复现列表。这样后续维护能区分已证实机制、当前配置和候选改进。
