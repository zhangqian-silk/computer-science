# Agent 运行时的工程问题

一个 Agent 跑通 demo 与它能长期承接真实任务，中间隔着的不是模型能力，而是一层通常没人愿意写的东西：上游返回 429 时等多久、流断在一半时那半句话算不算数、命令超时后子进程是不是还活着、进程被杀掉时刚改完的文件有没有被记下来、谁批准了这次删除、以及换一个模型供应方要动多少配置。这层东西没有统一的名字，本文称之为**运行时**——它不产生智能，但它决定智能能不能被可靠地交付。

这些问题有一个共同的形状：**它们都落在「模型提议、程序执行」这条边界上**。模型输出的只是一份动作提议，是否执行、在什么边界内执行、执行结果如何记账，全由模型之外的程序决定。因此运行时工程的核心不是让模型更聪明，而是把这条边界上的每一次交接做成可判定、可恢复、可审计的。

本文先建立**故障分层**——按「谁能判定这次失败」把故障域分开；再自上而下走一遍关键链路：模型网关、工具执行、隔离与沙箱、审批、持久化与恢复；最后是上下文治理、可观测性、成本三块横切关注点，以及四个实现的横向对照。全文只需两点前置约定：**上下文**指一次生成中模型实际可用的信息，磁盘上的文件与历史消息都只是来源；**前缀缓存**依赖前缀逐字节一致，改动越靠前失效范围越大。

本文以四个公开实现为参照：OpenAI 的 Codex、Anthropic 的 Claude Code、开源项目 pi，以及 LangChain 的 LangGraph。

其中「pi」需要先消歧。本文指的是 Mario Zechner 发起、现由 Earendil Works 维护的终端编码 harness，仓库为 `earendil-works/pi`，以 TypeScript 编写并按 MIT 许可发布，文档站为 `pi.dev`。AI 领域另有若干同名产品——Inflection AI 的对话助手 Pi、Pluto7 面向供应链编排的 Pi Agent，以及一些企业内部同名的平台系统——它们与本文所述的 harness 无关。这类同名冲突在检索资料时很容易串台，因而值得在开头点明。

## 一、把故障按「谁能判定」分层

讨论容错时最常见的起手式是列一张故障清单——超时、限流、解析失败、工具报错。清单本身没错，但它是平铺的，而平铺的清单推不出应对策略：同样是「失败了」，有的该重试，有的重试就是在烧钱，有的连「失败了」这件事都不会被报出来。

更有解释力的切法是按**判定依据**分层：这次失败，系统凭什么知道它失败了？

<HarnessFailureMap />

四层的排序不是按严重程度，而是按判定信号的确定性。传输层的信号最硬——状态码就是状态码，因此退避重试足以覆盖。执行层的信号仍然明确，但它带着副作用：失败前可能已经改了文件、已经发出了请求，于是重试之前必须先回答「这个动作能不能再做一次」。状态层的失败在进程活着的时候根本不可见，只有在恢复时才暴露。到了认知层，系统不会产生任何异常——它一切正常，只是做错了事。

**自动恢复的能力沿着这四层单调递减，而把人接回来的必要性单调递增。** 这条规律解释了后文的许多设计选择：为什么审批点总是设在有副作用的动作之前，为什么长任务需要检查点而不只是重试，以及为什么循环检测必须由外部循环来做而不能指望模型自述。

图中标注的 F1–F12 是故障注入点，每一条都配了「期望的系统行为」——这一栏不是装饰，后文会回到它的用法。

## 二、模型网关：重试为什么是两层

把 Agent 接到模型有两种方式：直连供应方，或者经过一层网关。真实系统几乎都选后者，原因不止是「方便切换模型」——网关是唯一一个能同时承担凭据托管、用量归集、多供应方降级与统一观测的位置。而这些职责里最容易做错的是重试。

重试容易做错，是因为它看起来只有一个旋钮，实际上有两层。

<GatewayRetryLadder />

两层的区别在于**失败时已经产出了什么**。传输层的单位是一次 HTTP 请求：连接没建起来、握手失败、服务端返回 5xx——此时什么都没产出，整个请求可以原样重放。流式层的单位是一整条采样流：已经吐出了半段内容才断开——此时重放会产生重复内容，续接又需要服务端支持按位置恢复。把这两层混成一个数字，就会得到「重试次数设的是 5，实际最坏发了 20 次请求」这种意外，而账单和延迟都在这个乘积上。

四个实现的取法：

- **Codex** 把两层做成完全分离的 provider 级配置，`request_max_retries` 默认 4、`stream_max_retries` 默认 5，两者都有 100 次的硬上限；此外还有一条独立的连接重连路径，延迟从 5 秒起翻倍、封顶 60 秒。[[1]](#ref-1)
- **Claude Code** 走环境变量路线，`CLAUDE_CODE_MAX_RETRIES` 默认 10，请求总超时 `API_TIMEOUT_MS` 默认 600000 毫秒。[[2]](#ref-2)
- **pi** 的默认值是三次、基础延迟 2000 毫秒的指数退避，单次延迟封顶 60000 毫秒。[[3]](#ref-3)
- **LangGraph** 本身不持有模型连接，重试落在所选的模型客户端上。

### 空闲看门狗：为什么请求总超时不够用

有一类故障是「连接还活着，但什么都不来」。它逃得过连接超时（连接是好的），也逃得过请求总超时（在总超时触发前，它已经白等了很久）。应对它需要第三个计时器——**空闲看门狗**：距上一个字节到达超过阈值就主动关闭并计入重试。

两个实现的默认值恰好都是 300000 毫秒（5 分钟），但设计取向不同。Codex 的 `stream_idle_timeout_ms` 是一个普通的可调值。[[1]](#ref-1) Claude Code 的 `CLAUDE_STREAM_IDLE_TIMEOUT_MS` 则把 300000 同时作为**下限**——配得更低会被静默抬回，官方给出的理由是要容纳扩展思考的长停顿与代理缓冲。[[2]](#ref-2) 这是一个把「用户会配错」当成常态来设计的选择：宁可牺牲可配置性，也不要让一个善意的调优把正常的长思考误杀成超时。

### 一条不该重试的错误

配额耗尽与瞬时限流经常共用同一个 HTTP 状态码。前者是账户层面的额度用完了，后者是这一刻请求太密。把两者混为一谈，退避重试只会在配额恢复前空耗时间与预算，而且失败信息还会被最后一次重试的报错盖住。

pi 的处理值得细看：它在错误分类里维护了两组模式，一组是**可重试**的瞬时故障（过载、限流、5xx、各类连接与流中断文本），另一组是**不可重试**的额度类错误（配额不足、预算耗尽、计费相关），命中后者时立刻失败而不进入退避。[[4]](#ref-4) 同一项目还有一条相关设计：把 SDK 层的重试次数默认设为 0，文档给出的理由是——如果 SDK 先把配额类错误重试掉，Agent 层就看不到它，可能一直阻塞到配额窗口重置。[[3]](#ref-3)

**这条设计原则值得单独记住：让错误浮到能够正确分类的那一层，而不是在最底层就被吞掉。** 底层分不清「这一刻太挤」和「这个月用完了」，而这两者的正确应对完全相反。

## 三、运行时异常：工具执行的失效与副作用

模型网关那一层的失败是干净的——重试一次，世界还是原来的样子。工具执行不是。这一层的每一次失败都可能已经改变了环境，因而「重试」这个动作本身需要先被论证。

### 超时与进程组

给命令设超时是基本操作，但设超时之后终止谁是个容易做错的细节。终止父进程不等于终止它派生的子进程——一个启动了后台服务的命令被「终止」后，服务往往还在跑，占着端口，让下一次重试以一个完全不同的方式失败。正确的做法是终止整个进程组。

超时值本身也需要分层，两组实现给出了两个不同维度的拆分：

- **默认值与上限。** Claude Code 用 `BASH_DEFAULT_TIMEOUT_MS`（默认 120000 毫秒）管模型没指定超时时的默认值，用 `BASH_MAX_TIMEOUT_MS`（默认 600000 毫秒）管模型能请求的上限。[[2]](#ref-2) 前者管的是「别让常规命令挂太久」，后者管的是「别让模型给自己批一个无限长的额度」。
- **启动与调用。** Codex 对 MCP 服务器分别提供 `startup_timeout_sec`（默认 10 秒）与 `tool_timeout_sec`（默认 60 秒）。[[5]](#ref-5) 两者的失败含义不同：启动超时说明这个服务器不可用，调用超时说明这次调用太慢。合成一个值，要么让启动慢的服务器永远连不上，要么让卡死的调用拖垮整轮。

启动阶段还有一个可用性取舍。Claude Code 默认让 MCP 启动**不阻塞**：服务器在后台连接，工具就绪后再出现；可以通过 `MCP_CONNECTION_NONBLOCKING=0` 回到阻塞等待，而声明为必须加载的服务器无论如何都会阻塞启动。[[2]](#ref-2) Codex 提供的是另一个方向的开关——`required` 置为真时，该服务器初始化失败会让启动直接失败。[[5]](#ref-5) 两者是同一个问题的两面：**一个工具不可用，应该是「少一个工具」还是「这次会话不能开始」**，取决于那个工具是不是任务的必要条件。

### 输出超量

工具返回值是上下文膨胀的最大单一来源，而膨胀的方式往往是一次性的——一条 `find` 打到了 `node_modules`，一次日志查询返回了十万行。

处理它的正确形态是**落盘并回填摘要与路径**，而不是直接截断后塞回去。这里有一个容易被忽略的要求：**截断必须让模型看得见**——一段被悄悄截短的输出，模型会把它当作完整结果来推理，它会确信那个目录里只有它看到的那些文件。

两家的做法：Claude Code 用 `BASH_MAX_OUTPUT_LENGTH` 控制阈值，超出后把完整输出存到文件、只把路径与一小段预览交给模型；MCP 工具的返回值另有 `MAX_MCP_OUTPUT_TOKENS`（默认 25000），子代理输出则由 `TASK_MAX_OUTPUT_LENGTH` 约束（默认 32000 字符、最大 160000）。[[2]](#ref-2) pi 在压缩场景下把工具结果截到 2000 字符并留下一个说明截断了多少字符的标记，理由写得很直接：工具结果通常是上下文里最大的贡献者。[[6]](#ref-6)

### 循环

认知层最典型的故障是重复同一个失败动作：读一个不存在的文件，收到「文件不存在」，再读一遍同一个路径，直到预算耗尽。

这类故障有两个特征决定了它的对策。其一，**它不产生任何异常**——每一次工具调用都正常返回了，只是返回了同一个错误。其二，**它无法靠模型自述来检测**，因为陷在循环里的正是那个要做判断的模型。因此检测必须由外部循环承担，依据是动作与观察的重复模式，处置是打断并升级——要么换策略，要么把人接回来。

预算上限是这条防线的兜底，但它是最后一道而不是第一道：等到预算耗尽才停下来，中间那些步的钱已经花掉了。

## 四、环境隔离与沙箱权限

关于沙箱，最常见的简化是把它当作一个布尔量——「这个工具有没有沙箱」。这个问法答不出有用的结论，因为隔离是一条连续谱，每上一档换来更强的边界，付出的是启动延迟、兼容性与运维复杂度。

<IsolationStrengthLadder />

### 规则匹配与内核拦截不是强弱关系

阶梯上第 1 档与第 2 档最值得分辨，因为它们经常被当成同一件事的两个强度。

**应用层规则在执行之前判定，依据是命令字符串看起来要做什么。** 它的覆盖面很广——可以管所有工具，不只是命令行；它也是审批与审计的天然入口。但它有一个结构性的破绽：一条命令实际做的事可以超出它名字的暗示，规则就落空了。

**内核级沙箱在执行之中拦截，依据是进程实际访问了什么。** 它对「模型选了什么命令」完全无感——无论那条命令叫什么、里面套了几层脚本，越界的文件访问和网络连接都不会成功。代价是它只能覆盖以进程形式执行的东西，且平台能力参差。

Claude Code 的文档把这组关系写得很清楚：权限规则在命令运行前评估、适用于每一个工具；沙箱由操作系统对运行中的进程施加，只适用于命令类工具及其子进程，因而「无论模型选择运行什么，即使一条被允许的命令做的事超出其名字所示，边界依然成立」。[[7]](#ref-7) **两者是互补关系，不是替代关系**——一个能覆盖广度，一个能兜住深度。

### 平台差异：同一个产品，不同的机制

同一档隔离在不同操作系统上是不同的机制，依赖前提与失败方式都不一样：

- **macOS**：Codex 与 Claude Code 都使用系统自带的 Seatbelt 机制；Codex 的做法是在运行时构造策略并通过 `sandbox-exec` 加载。[[8]](#ref-8)[[7]](#ref-7) 这一档在 macOS 上没有额外安装负担。
- **Linux**：两者分道。Codex 用 Landlock 施加文件访问规则、用 seccomp 过滤网络相关的系统调用。[[8]](#ref-8) Claude Code 用 bubblewrap 做命名空间隔离，并需要 socat 把流量中继到沙箱代理，另有一个可选的 seccomp 过滤器用于阻断 Unix 域套接字。[[7]](#ref-7)
- **Linux 上的两个前置条件**：在默认 AppArmor 策略限制非特权用户命名空间的发行版上，需要先为 `bwrap` 单独放开该能力，否则沙箱起不来；在非特权容器里，bubblewrap 无法挂载新的 `/proc`，需要显式允许内层沙箱复用外层容器的 `/proc`，而这会把宿主的进程信息暴露给沙箱内。[[7]](#ref-7)
- **Windows**：WSL2 沿用 Linux 路径，WSL1 因缺少所需内核能力而不被支持。[[7]](#ref-7) Windows 原生则是四者中最不成熟的一块，各实现取向不一。

**「这个工具的沙箱会阻断网络」这句话，在 macOS 与 Linux 上成立的机制不同、失败方式不同、前置依赖也不同。** 把单一平台的实测行为写成产品的通用行为，是这个主题上最常见的错误。

### 默认降级还是硬失败

沙箱依赖缺失或平台不支持时怎么办，是一个安全姿态的选择题。Claude Code 的默认是**降级运行并告警**，同时提供 `sandbox.failIfUnavailable` 把它改成硬失败，文档明确说明这是给「要求沙箱作为安全门禁」的受管部署用的。[[7]](#ref-7)

这个默认值对个人使用是合理的——不要因为少装一个包就让工具不能用。但对于把沙箱当作合规边界的部署，默认降级是一个**静默的缺口**：系统看起来在沙箱里跑，实际上没有。这类「默认值对个人友好、对组织危险」的取舍在运行时配置里反复出现，值得在部署前逐项确认。

### 不内置沙箱也是一种取向

pi 的核心不提供沙箱：默认以启动它的用户权限运行，隔离交给扩展或外层环境。它提供的**项目信任**机制管的是另一件事——是否加载项目本地的设置、扩展与技能，未受信任时这些项目资源不被加载，非交互模式下则依据一个全局的默认信任策略处理。[[9]](#ref-9) 这是一条「加载谁的配置」的边界，不是「能碰什么文件」的边界，两者不应混为一谈。

这个取向本身是自洽的：一个刻意保持最小内核、把一切做成可替换组件的 harness，把隔离留给使用者选择，与它的整体设计一致。但它意味着安全边界必须由部署方另行提供——外层容器、扩展，或者操作系统层面的约束。

### 凭据与沙箱的关系

沙箱挡的是文件与网络，挡不住已经放进环境里的密钥。Claude Code 为此提供了一个专门的凭据块：可以声明哪些文件在沙箱内不可读、哪些环境变量在每次沙箱命令执行前被清除，另有一种掩码模式。[[7]](#ref-7) 值得注意的是这两类保护的**归属层不同**——文件保护属于文件系统层，关掉文件隔离就失效；环境变量的清除独立于文件系统层，即使关掉文件隔离仍然生效。[[7]](#ref-7)

这个细节指向一条更一般的规律：**关掉某一层时，要知道哪些保护随之消失、哪些还在。** 把「沙箱开着」当成一个整体状态，会在关掉其中一层时误判剩余的防护面。

### 内部实践中的额外约束

以上均为公开来源。就企业内部的工程基线而言（经内部渠道核实，与上述公开资料分开表述），面向多用户的云端场景还会额外强调三点。它们在单机 CLI 的语境里不构成问题，但在服务化部署中是硬约束：

- **沙箱实例按用户或会话粒度创建与销毁，禁止跨用户复用**——复用会让上一个会话的残留文件被下一个读到。
- **真实的长期凭据不进入沙箱，也不进入模型上下文**——密钥泄露一旦发生，就会从单会话事故升级为平台级事故。
- **控制链路上每一跳都要重新校验调用者与目标沙箱的归属关系**——只在入口鉴权一次的设计，会让绕过入口的请求直接访问到他人的沙箱。

这三条与公开实现关注的「本机边界」是不同层面的问题：前者防的是租户之间的越界，后者防的是单机上的越权。

## 五、用户交互与审批：链路上那道缝

审批常被当作一个产品问题——弹不弹窗、弹几次。它其实是个状态机问题：**审批把一条本来连续的执行链路切成了两段，而这两段之间可以隔着任意长的时间，甚至隔着一次进程重启。**

<ApprovalExecutionTimeline />

### 无法消除的那道缝

六步里真正棘手的是第 4 步与第 5 步之间：命令已经执行、结果尚未记录。这道缝无法靠更好的检查点机制消除——检查点只能记录「已知发生过的事」，而这道缝的定义恰恰是「发生了但尚未被记录」。

能做的只有三件。把有副作用的动作尽量做成幂等的，让重放不改变最终状态；把副作用推迟到确认之后，让缝隙落在无副作用的一侧；以及在恢复时不假设「没记录就是没发生」，而是回到环境里核对真实状态。第三条最常被略过，也最常导致「恢复之后又执行了一遍」。

### 四种把人接回来的方式

- **Codex** 把沙箱与审批做成两根正交的杠杆——前者定能力边界，后者定越界之后怎么办；审批策略支持按类别分别处理，可以让某些类别的提示浮出、另一些自动拒绝。[[10]](#ref-10)
- **Claude Code** 的组合更细。自动放行模式下，能被沙箱容纳的命令直接执行，容不下的退回常规权限流程；但即使在该模式下，显式的拒绝规则始终生效、针对关键路径的删除命令仍走常规流程、内容相关的询问规则仍会强制提示。[[7]](#ref-7)
- **pi** 的核心不内置审批，这项能力由扩展提供。[[9]](#ref-9)
- **LangGraph** 的取向结构性不同：它把「暂停等人」做成执行图里的一等原语。节点中调用中断会抛出一个特殊异常，运行时捕获后保存状态并等待外部输入；外部用一个携带答复的命令再次调用同一个线程即可继续。[[11]](#ref-11) 好处是「等人」这段时间可以跨进程存活，不依赖某个会话进程一直开着。

Claude Code 还有一个设计得很诚实的逃生口：命令因沙箱拒绝而失败时，拒绝原因（被拒的具体路径或主机）会写进结果让模型看见，模型可以据此提议以「显式关闭沙箱」的方式重试，而这次重试要走常规权限流程。[[7]](#ref-7) **把「沙箱拒绝了什么」具体地告诉模型，比返回一个泛化的失败要好得多**——原因不具体，模型只会盲目重试同一个动作。

### 一条必须提前知道的语义

LangGraph 这个模型有一个后果，文档写得很明确：**恢复时节点从头重跑，而不是从中断那一行继续。** 中断之前的代码会再执行一遍。[[11]](#ref-11)

这不是缺陷，是该模型的语义，但它必须在写代码时就纳入设计。文档给出的实践直接对应这条语义：[[11]](#ref-11)

- 中断之前的副作用要幂等；能推迟的副作用放到中断之后；最好把副作用拆到单独的节点里。
- 不要在单个节点里用循环反复调用中断——每次恢复都会重放此前的全部迭代，导致循环体被指数级地重复执行。正确写法是每次节点调用只中断一次，用条件边回到该节点来实现重试。
- 中断是靠抛异常实现的，用一个裸的 `except` 包住中断调用会把它吞掉，导致暂停根本不会发生。

最后一条值得留意：「异常被用作控制流」的设计在框架里不算罕见，但它对使用者的代码写法提出了不显眼的要求。

## 六、数据持久化与恢复语义

长任务与崩溃恢复把一个平时不必回答的问题摆到台面上：**这次运行的状态，有多少在进程内存里，有多少在进程外面？** 内存里的部分，进程一死就没了。

<StatePersistenceRoutes />

### 三个比「有没有持久化」更有用的问题

**写入粒度决定崩溃后能回到多近的位置。** LangGraph 把这一项做成了显式可配的三档，并把各自的代价摊开说明：[[12]](#ref-12)

- 每步之前同步落盘——持久性最强；
- 下一步执行时异步落盘——性能与持久性兼顾，但进程在执行中崩溃时存在少量检查点未写入的风险；
- 只在运行结束时落盘——性能最好，但中间状态不保存，无法从执行中途的进程崩溃里恢复。

**这是把「持久化的代价」摊开来让使用者选的少见做法**，大多数实现只给一个固定策略。

**记录形态决定半截写入能否被识别。** Codex 与 pi 都用追加式 JSONL：每一行是一条完整记录，写坏的半行可以在读取时识别并丢弃。[[13]](#ref-13)[[14]](#ref-14) 这比就地覆盖一个大状态对象安全——后者被打断时留下的是一个语法上可能仍然合法、语义上却不一致的文件。

**恢复语义决定副作用会不会被重复执行。** 这是四者分歧最大的一项，前一节已经展开过。

### 两种会话模型

Codex 与 Claude Code 的会话是线性的：一条记录，从头读到尾就是当前历史。Codex 的记录文件名里编码了时间戳与线程标识，被回退过的线程会额外附加一个区别于线程标识的记录标识，使同一线程的多条历史能够并存。[[13]](#ref-13)

pi 的会话是一棵**树**：每条记录都带有自己的标识与父标识，当前位置是活动叶子。[[14]](#ref-14) 这让「探索多条路径」成为一等公民——可以跳回任一历史位置继续，而不必新建文件。它还有一个配套设计值得注意：离开一条分支时，可以先把那条分支总结成一条摘要挂到新位置，避免丢掉那条路上得出的结论。[[6]](#ref-6) 代价是恢复语义更复杂：**「当前上下文」取决于从根到活动叶子的那条路径，而不是文件里的全部内容**。

### 并发写

同一份会话被两个进程同时写，是一类只在多窗口或自动化场景下才暴露的问题，而它的表现往往是「恢复时发现记录坏了」——距离事故现场已经很远。

Codex 的处理是加写者锁：另一个进程尝试写同一线程时会被拒绝，而不是交错写入；启动时还会清理上一次留下的陈旧锁。[[15]](#ref-15) **明确失败比交错写入好**，因为前者在事故现场就报出来，后者要到下一次恢复时才被发现。

### 恢复覆盖不到的东西

Claude Code 的检查点机制配有一份坦诚的限制清单，它列的正是这类机制的结构性边界：[[16]](#ref-16)

- **只跟踪文件编辑工具做的改动**——通过命令行完成的删除、移动、复制不在其中；子代理的编辑通常也不在，取决于它以何种方式运行。
- 符号链接与硬链接指向的文件会被跳过，并给出计数提示。
- 会话外部的手工修改与其他并发会话的编辑不被捕获。
- 文件快照只保留最近一批，且有保留期，过期后回退会失败。

这份清单可以概括成一句：**恢复机制覆盖不了它没记录的东西。** 因此它是会话级的快速撤销，不是版本控制的替代品——这也正是该文档自己的结论。

## 七、上下文治理作为一种运行时约束

上下文治理常被归到「提示工程」那一侧，但从运行时的角度看，它是一个硬约束问题：**窗口是有限的，而工具返回值随步数单调增长**，所以长任务必然在某一刻撞到上限。撞上限时的行为是运行时设计的一部分。

四个实现里三个内置了压缩，取向各有侧重。

- **pi** 的触发条件写得最直白：`contextTokens > contextWindow − reserveTokens`，`reserveTokens` 默认 16384，留给模型的回复。检查点设在工具执行完、结果追加之后、下一次助手回复之前。切点从最新往回走，累计到 `keepRecentTokens`（默认 20000）为止，其余摘要。[[6]](#ref-6)
- **Claude Code** 除自动压缩外，还提供对指定区段的定向摘要：可以把某一点之后的对话压成摘要，也可以压之前的那段。关键在于**摘要不改磁盘，原始消息仍留在会话记录里**——它改变的是上下文，不是历史。[[16]](#ref-16)
- **Codex** 的压缩不是单一机制，而是若干条路径并存（本地摘要、远端摘要、以及一种跳过摘要直接换一个新窗口的令牌预算式压缩），并被建模成一次有完整生命周期的操作，前后都可以挂钩子。[[17]](#ref-17) 各条路径各自的触发条件与优先级在公开文档中没有系统说明，本文不对此给出结论。
- **LangGraph** 不内置压缩，由使用者在状态设计里自行决定。

pi 的实现里有两个细节值得单独记：**切点不能落在工具结果上**——工具结果必须与它的调用待在一起，否则历史里会出现一个没有来处的返回值；以及**当单个轮次本身就超过保留预算时**，切点会落在轮次中间，此时生成两份摘要（历史摘要与该轮前半段的摘要）再合并。[[6]](#ref-6)

它还把压缩做成了可被外部接管的事件：扩展可以在压缩前介入，取消它或直接提供一份自己生成的摘要；另有一个失败事件，用于把「尝试压缩」与「压缩的终局」配成对。[[6]](#ref-6) **后者是个容易被忽略的可观测性设计**——只记录尝试而不记录结局，遥测数据里就会留下一堆永远不知道成没成功的开始。

有一条横切的代价必须记住：**压缩改写前缀，因而击穿前缀缓存**，收益要靠之后每一步更小的计价基数慢慢赚回来。这条曲线在第九节量化。

## 八、可观测性与评测：让故障注入点派上用场

前面各节讲的是「应该怎样」，这一节回答「怎么知道它现在是不是这样」。

### 先有轨迹

四个实现在这一维上的共识最强：把每一步的决策、动作、观察持久化成可回放的东西。Codex 为重试与压缩这类关键动作发出结构化事件（记录尝试序号、延迟、所属层次与操作类型），而它的会话记录文件本身就是一条完整轨迹。[[18]](#ref-18)[[13]](#ref-13) Claude Code 支持标准遥测导出，并可按会话开启调试日志用于定位具体问题——比如一次代码回退究竟跳过了哪些路径。[[2]](#ref-2)[[16]](#ref-16) pi 为压缩的开始与失败分别发出事件，供扩展配对成完整记录。[[6]](#ref-6)

**没有轨迹时，一切优化都是猜测。** 这句话在 Agent 系统里比在传统服务里更成立，因为这里的「同一个输入」根本不保证产生同一条执行路径，无法靠重跑一遍来复现。

### 三类指标，不要混着看

- **执行层指标**回答「系统有没有正常工作」：各层重试次数与最终失败率、工具超时率、沙箱拒绝次数与被拒的对象、压缩触发频次与每次的耗时。这类指标**有确定的判定依据**，可以直接告警。
- **成本指标**回答「这件事值不值」：每任务的令牌消耗、缓存命中率、压缩带来的净收益。缓存命中率要按「输入令牌中走缓存价的比例」算，而不是按请求数——一个请求里往往既有命中部分也有未命中部分。
- **任务层指标**回答「事情有没有做对」：完成率、人工介入率、变更引发问题的比例。这类指标没有自动判据，必须靠评测集与人工核对；它们也是唯一能发现第一节里认知层故障的指标——系统一切正常，只是做错了事。

三类混着看会得出错误结论。重试率下降可能只是因为任务变简单了；成本下降可能是因为压缩太激进、模型丢了关键上下文以致提前放弃。**只有三条线并排看，才能分清「改好了」和「换了种失败方式」。**

### 故障注入点怎么用

第一节的 F1–F12 不是清单，是一组可执行的演练。三条纪律：

- **先写期望行为，再开始注入。** 顺序反过来——先注入、再把观察到的行为记成「期望」——等于什么都没验证，只能得到「跑了一下，好像还行」。
- **优先注入平时不会自然发生的故障。** 429 与超时在生产里迟早会遇到，而「在工具已执行、结果未写入时杀掉进程」几乎不会自己发生，却恰恰是恢复逻辑里最脆弱的一环。演练的价值与故障的稀有程度正相关。
- **把修好的故障沉淀成回归用例。** 超时后子进程没被清理、截断没有让模型看见、恢复时重放了有副作用的动作——这几类一旦出现过，在下一个功能里很可能再出现。

## 九、成本与性能：预算旋钮

长任务的成本有一个反直觉的性质：**它随步数近似平方增长，而不是线性增长。** 原因是每一步的输入都包含此前的全部前缀，于是第 $i$ 步的输入约为 $c_0 + d \cdot (i-1)$，$n$ 步累计约为 $n \cdot c_0 + d \cdot n(n-1)/2$——后一项是平方级的。

<BudgetKnobCalculator />

这条曲线给出三个结论。

- **限制步数是比限制单步输出有效得多的闸门。** 把单步输出砍掉一半，省的是那一步的输出费用；把步数砍掉一半，省的是平方项的四分之三。
- **缓存节省达不到单价差的倍数。** 每步新增的那部分必须按原价计，冷启动的首步也是——单价差是收益上限，不是实际收益。这也解释了为什么把一个每次都变的时间戳放在系统提示开头会如此昂贵：它让每一轮的整个前缀都失效，缓存命中率归零。
- **压缩有一次性成本。** 它击穿缓存、需按未命中价重建前缀，收益靠之后的步数摊回；剩余步数不足时压缩是净亏的。上面的计算器可以算出这个拐点——**这也说明压缩阈值应当由评测集确定，而不是拍一个看起来合理的百分比。**

延迟这一侧还有一个与成本不完全同向的量：**用户感知的延迟里，等待重试退避的时间往往比模型生成的时间更长**。两层重试各自退避几轮，用户看到的是一次长时间的「卡住」。这就是为什么重试次数要和整轮的时间预算一起设，而不是各自调到一个「看起来安全」的值。

把前面各节的取向收在一起，可以看出哪些结论已经稳定、哪些仍是开放的设计选择。

<ImplementationContrastMatrix />

矩阵的读法是找**分歧**而不是找赢家。

四家取法一致的地方可以当作通则：会话状态必须落在进程之外；有副作用的动作时机应当由人决定；模型地址与鉴权应当可替换；先有轨迹再谈优化。

取法相左的地方则是必须逐个核对的行为契约，其中两维的后果最重：**沙箱**——两家把内核级隔离做进核心且平台实现各异，一家明确不做、留给扩展，一家不在讨论范围内；**恢复语义**——三家是「重建视图后接着走」，一家是「把那个执行单元再跑一遍」，后者意味着中断前的副作用会重复发生。

## 十一、小结

前面各节的机制细节不必在此重复，真正值得带走的是四条判断方式。

**分层的依据是「谁能判定」，不是严重程度。** 这条判据同时决定了自动恢复的边界：判定信号越弱，能自动做的越少，把人接回来的必要性越强。列一张平铺的故障清单推不出这个结论。

**每个数字背后要问它属于哪一层。** 重试次数是两层相乘才等于最坏请求数，超时要分清默认值与上限、启动与调用，落盘粒度要分清每步、异步与仅退出。把两层合成一个旋钮，得到的不是简化而是意外。

**关掉一层时，要知道哪些保护随之消失。** 沙箱不是一个布尔状态：应用层规则与内核拦截互补而非替代，凭据保护中有的挂在文件系统层、有的独立于它，同一档隔离在不同平台上是不同机制。「有沙箱」从来不是一句可移植的结论。

**有副作用的动作，必须先回答「能不能再做一次」。** 重试、审批后的恢复、崩溃后的重放，问的都是同一个问题。恢复语义是「接着走」还是「从头再跑一遍」，决定了代码该怎么写；而任何恢复机制都覆盖不了它没记录的东西。

最后一点不属于机制而属于态度：**这一层的绝大多数取值都是默认值，而默认值是为最常见的场景挑的，不是为你的场景挑的。** 重试次数、超时阈值、落盘粒度、沙箱降级行为、压缩触发点——每一个都在某种部署下合理、在另一种部署下是缺口。值得花时间的不是记住它们，而是知道去哪里确认它们。
