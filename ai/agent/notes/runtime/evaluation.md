# 评测与故障注入

评测回答系统在一组任务上表现怎样，验证器回答某次具体交付是否满足条件，故障注入回答异常发生时系统会不会做出错误承诺。三者应结合，但不能互相代替。模型自述“任务完成”不是独立验收。

## 评测对象与层次

单次生成检查文本或结构化数据；工具系统检查参数、权限和效果；Loop检查整个任务；多Agent还检查覆盖与集成；运行系统检查恢复、取消和资源。不同层的成功率不能直接混成一项指标。

| 层次 | 典型检查 | 不能由什么替代 |
| --- | --- | --- |
| 响应 | 格式、字段、拒绝/截断处理 | HTTP200 |
| 工具 | 目标正确、授权、实际效果 | tool_call看起来合法 |
| 内容 | 有证据、语义正确、满足要求 | 长篇解释或自信措辞 |
| 任务 | 覆盖、产物、规定验证 | 最后一句Done |
| 运行 | 无重复危险效果、可收尾与恢复 | 进程没有崩溃 |

Anthropic的Agent评测文章强调任务、评分器、轨迹和结果等对象的区分。这有助于设计诊断，但具体业务仍需定义自己的验收条件，不存在通用“Agent分数”。[[66]](../references.md#source-anthropic-evals)

## 验证器与独立证据

代码任务可以结合编译、行为测试、静态分析和人工审查；数据库任务查询最终状态；文本任务依据资料、rubric和人工盲评。不要让验证器只读模型总结，也不要允许Agent随意修改验收测试后宣布通过。

```python
# 教学代码：验证器读取实际执行的记录，不相信候选文本。
def verify_patch(candidate, execution):
    errors = []
    if execution["tested_revision"] != candidate["revision"]:
        errors.append("测试版本与候选不同")
    if execution["test_exit_code"] != 0:
        errors.append("指定测试未通过")
    if execution["missing_required_files"]:
        errors.append("范围覆盖不完整")
    return {"passed": not errors, "errors": errors}
```

这个验证只覆盖明确条件，不证明所有潜在bug不存在。输出中应保留已检查与未检查范围，不能把“本地测试通过”写成“生产绝对正确”。

开放文本可用模型Judge，但应明确rubric、盲化候选来源、控制顺序偏差，并在人工标注集上校准。最好保留具体评分依据而非单个总分，且不要求暴露内部推理；可追溯的引用与检查项更有用。

## 数据集与泄漏

开发集用于迭代，保留集用于评估，真实线上样例要脱敏并标注版本。Prompt或Skill中直接包含评测答案，会让成绩失去意义。Agent还能读取工作区文件，因此隐藏测试、答案和其他候选轨迹需要真正隔离，不能只请求它“不要看”。

任务应覆盖常见、边界、无答案、权限受限、环境失败和长任务，不只挑容易成功的演示。按任务类型、难度、资料长度、工具数量和风险分层，避免整体平均掩盖重要退化。

代码基准要检查未修改版本的baseline：测试本来就失败或依赖网络不稳定，不能把所有失败归于候选，也不能把忽略测试解释成解决。记录环境、依赖锁、任务基线和超时。

## 重复采样与可靠性指标

一次成功说明至少存在一条成功轨迹，不说明每次都可靠。`pass@k`偏向“k次内至少一次成功”；连续或每次成功率关注重复运行稳定性。两者回答不同问题。单纯让候选多试几次，与更可靠的系统不是同一件事。

```python
# 教学统计：这里每次trial是已独立评分的一个任务执行。
def summarize_trials(trials):
    total = len(trials)
    if total == 0:
        return {"count": 0, "success_rate": None}
    success = sum(t["verified"] for t in trials)
    return {
        "count": total,
        "success_rate": success / total,
        "mean_cost": sum(t["cost"] for t in trials) / total,
    }
```

真实报告还应给样本数、置信区间或不确定性、分层结果和失败类型。时间相关的环境或服务变化会破坏简单独立假设，需要随机化运行顺序或使用成对实验。

## 同预算比较策略

比较Prompt、缓存、模型路由、单Agent与多Agent时，固定任务、环境、工具能力和验收。预算可以按总费用、token、时间或允许尝试次数定义，必须明确。给多Agent十倍总预算，却只比较wall time或最终成功数，无法说明架构本身更有效。

还要同时报告未验证与失败。工具返回不足证据可能是“无法确认”，不同于明确断言被反证。用一个分数强行合并会让运行系统偏向隐藏不确定性。

消融实验能定位收益：移除规划步骤、改为固定检索、禁用长期记忆、减少子Agent或恢复串行工具。若去掉一层质量不变且成本下降，就没有理由因架构时髦而保留。

## 故障注入矩阵

```python
fault_case = {
    "id": "remote-success-local-receipt-lost",
    "inject_at": "after_remote_commit_before_local_save",
    "expected": {
        "final_state": "reconcile",
        "blind_retry": False,
        "maximum_external_effects": 1,
    },
}
```

同样模式可覆盖模型流截断、工具参数损坏、目录热更新、审批后策略撤销、取消竞争、并发重复领取、产物缺失、日志丢失和重启。测试应检查实际禁止动作次数，而不只是错误字符串。

故障模拟器需要可控时间、确定的触发点和隔离效果。真实网络断线通常不够可重复；可以先用fake provider精确构造时序，再在真实隔离服务验证协议与幂等。模拟通过不能宣称供应商真实系统已通过。

## 轨迹评分与结果评分

轨迹有助于诊断无效循环、工具误用、违规尝试和额外成本，但不应因“路径不同于参考”就判任务失败。可能存在多条正确路线。结果通过也不能忽略过程中发生的越权或重复副作用。

可把评分分开：任务结果、执行约束、效率、鲁棒性和用户交互。一个任务最终成功但尝试泄露资料，安全维度仍应失败；一个只读分析明确指出缺资料，未必是质量差，而可能是正确边界行为。

## 从失败到回归集

每次真实事故提取最小可重现任务、必要输入版本、错误事件序列和预期不变量，脱敏后进入回归。不要只把“换个Prompt后看着好了”记录成修复。

观测数据可用于选样，但应避免只采样成功或用户点赞任务。社区报告可提供故障假设，必须标记未独立复现；确认后再纳入具体产品版本的回归说明。

## 实验产物

一次完整评测应留下任务集、配置manifest、候选版本、原始结果或受控引用、评分器版本、每项判定、总成本及环境限制。资料包提供离线机制测试和评测模板，没有把它们包装成产品排行榜。真实模型、缓存和多Agent策略比较需要实际运行后填入数据。

## 成对实验报告

同一批任务分别运行基线A和候选B，保留每项配对结果，不只给两列平均分。重点看A失败B成功、A成功B失败、都失败和都成功四类，再按失败机制分类。

```python
def paired_categories(rows):
    counts = {"both_pass": 0, "a_only": 0, "b_only": 0, "both_fail": 0}
    for row in rows:
        a, b = row["a_pass"], row["b_pass"]
        key = ("both_pass" if a and b else
               "a_only" if a else
               "b_only" if b else "both_fail")
        counts[key] += 1
    return counts
```

A成功B失败尤其值得审查，可能是上下文压缩丢约束、路由低估难度或并发引入冲突。小样本不能仅凭净胜几项决定生产推广，结合风险和不确定性。

## 评分器本身的回归

用人工确认的正确和错误产物测试评分器，加入伪造测试日志、错误版本、缺证据、空结果和重复结果。评分器若只匹配“passed”字符串，模型可以无意或有意使其误判。

评分逻辑升级也要版本化，并对旧结果重评分时说明区别。否则看起来模型质量变化，实际是评分口径变了。评分器不应被候选代码或任务Prompt修改。

## 安全与效用的独立评价

一个任务内容完成但发生越权，不应因质量分高而平均成通过。采用硬约束与质量评分分开：安全、重复效果、错误审批等设为阻断项；文本质量和效率在满足约束后比较。

同样，全拒绝系统安全事件少，但效用不合格。分别报告正常任务误拒、危险任务误放和可验证交付，而不是用一个综合分掩盖边界。
