# 任务调度与 Agent 接入

调度把待执行任务分配给具有相应能力和资源的执行者；接入协议让界面、客户端或其他 Agent 能够提交任务、读取进展和取得产物。前者决定执行安排，后者决定通信约定。

---

## 一、从单任务到队列

```mermaid
flowchart LR
	I["任务提交"] --> Q["等待队列"]
	Q --> W["取得执行权"]
	W --> R["推进与反馈"]
	R --> T["记录终态"]
```

队列缓冲突发请求，执行者按资源配额领取任务。任务进入队列只代表已接收，不能在界面上显示为已经开始或已经成功。

可以按到达顺序、公平性、优先级或截止时间选择任务。高优先级不能无限压住低优先级，耗时任务也可能需要限制并发以保护交互请求。

---

## 二、任务、尝试与执行所有权

同一个任务在失败后可能有多次尝试。应分别标识任务 ID 与尝试 ID，防止旧尝试的晚到结果覆盖新结果。

分布式执行中可以用租约表明某个执行者暂时拥有任务。但租约到期只说明所有权失效，不会物理停止旧进程；需要代次或 fencing 等机制在状态写入和外部动作边界拒绝旧执行者。

心跳只反映存活或通信状态，不代表任务有进展。进展应由步骤结果、产物或状态变化体现。

---

## 三、并发与背压

限制可同时执行的任务数，还要考虑单任务内部并发、模型请求数和工具资源。允许十个任务、每个任务再并行十个工具，可能产生一百个在途操作。

背压让上游知道暂时没有容量，可以排队、拒绝或延后，而不是无限接收并在后面集中超时。排队时间应计入用户可见的完成时间。

重试要有上限和退避，并保留原失败原因。无权限和参数错误不应当作暂时性容量故障反复调度。

---

## 四、接入协议应表达什么

一个任务接入面需要说明输入、身份、状态、事件、产物和控制请求。传输成功、任务接受、任务运行和最终完成是不同阶段。

| 信息 | 作用 |
| --- | --- |
| 任务标识 | 查询同一任务 |
| 事件序号 | 增量读取与去重 |
| 状态 | 区分排队、运行、等待和终态 |
| 产物引用 | 取得最终文件或结构化结果 |
| 控制请求 | 取消、补充信息、审批 |

客户端断线后可以依据游标继续读取事件，再核对当前状态。重复收到事件时应去重；缺少事件时不能只凭最后一条自然语言输出判断任务状态。

---

## 五、MCP、客户端协议与 Agent 间协议

MCP 主要连接应用与工具、资源等能力；Agent Client Protocol 面向客户端与 Agent 的交互；A2A 面向 Agent 间的任务与产物通信。这是协议定位的比较，不代表所有实现都支持完整功能。[[38]](../references.md#source-acp) [[39]](../references.md#source-a2a)

接入某种协议不会自动解决任务调度、权限继承和故障恢复。跨执行者传递任务时，应明确身份、允许范围和取消传播，而不是把主任务的全部权限无条件复制过去。

学习自检：为什么任务收到确认后仍可能尚未运行？因为确认可以只表示入队；为什么租约过期后仍有重复写风险？因为旧执行者可能仍活着，需要在副作用边界拒绝过期执行权。
