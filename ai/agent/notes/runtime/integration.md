# Agent 运行时接入

把一个已经能干活的编码 Agent 接进自己的系统，走错方向的原因往往不是选了性能更差的方案，而是**把不在同一个层面上的东西当成了互斥选项**——「用伪终端还是用标准输入输出」「该走标准协议还是该走沙箱」这类问法本身就无法回答，因为前者是字节怎么流动，后者是动作能不能发生，两件事同时成立，也同时需要决定。

这些名词本就是从不同方向长出来的：有的来自模型接口，有的来自终端历史，有的来自编辑器生态，有的来自操作系统安全机制，各自解决一个真实问题，并列摆在一起就成了一份看不出结构的清单。

所以本文的第一件事不是比较，而是**归类**——先把这些名词按「回答哪一层的问题」摆好，再逐层说清在这一层接入实际是在做什么。

---

## 一、五层归属：在哪一层接入，就是在做哪件事

把接入相关的名词摊开，会发现它们分别在回答五个不同的问题：一次生成里输入输出什么、循环怎么转、语义怎么约定、字节怎么流动、动作能不能发生。

<IntegrationLayerStack />

### 每一层的接入形态

「在第 N 层接入」不是一句抽象的话，它对应一件很具体的工程动作。

| 层 | 接入形态是什么 | 你要写的东西 |
| --- | --- | --- |
| 模型层 | 自己发起每一次调用 | 把消息、工具定义、采样参数拼成请求，再解析响应 |
| 运行时层 | 把别人的循环当成整体来用 | 启动、喂任务、收结果；不碰它内部的调度与压缩 |
| 协议层 | 实现约定的方法集 | 一个客户端或一个服务端，按对方能理解的语义收发 |
| 传输层 | 选一条字节通道并按约定分帧 | 读写与分帧代码；不决定任何语义 |
| 隔离层 | 给上面这一切套一个执行边界 | 沙箱策略与审批规则；不改变任何消息 |

这张表解释了为什么只有中间三层存在「接入方式」意义上的选择。**模型层**是无状态的一问一答，在这一层接入等于上面几层全部自建——多轮、循环、压缩、审批都得自己加。**隔离层**则与其余四层完全正交：它不改变任何一条消息的含义，只改变一个动作能不能真的发生，因此既不能替代审批，也不能被审批替代——一个管边界，一个管时机。

### 协议与传输：两个正交的维度

这是全文最该钉死的一处区分，因为混谈它们会直接产出无法回答的问题。

- **传输**决定字节怎么流动、消息在哪里切开。它不知道消息是什么意思。
- **协议**决定一条消息意味着什么、谁能向谁发起、期不期待回应。它不关心字节怎么到达。

两者正交，意味着可以自由组合。同一套协议语义能跑在不同传输上，同一条传输通道也能承载完全不同的协议：

| 实际组合 | 传输承担 | 协议承担 |
| --- | --- | --- |
| JSON-RPC over 标准输入输出 | 子进程管道，按行切分报文 | 请求、响应、通知三种语义与方法集 |
| JSON-RPC over 长连接 | 帧边界由连接本身给出 | 与上一行**完全相同**的方法集 |
| 按行分隔事件流 over 管道 | 同样是管道按行切分 | 只有单向事件，**没有请求—响应配对** |
| 字符流 over 伪终端 | 伪终端设备，无消息边界 | 无协议，语义靠从屏幕网格上推断 |

前两行说明换传输不改语义；第一行与第三行说明同一条管道上可以跑语义完全不同的东西。因此「该用标准输入输出还是该用某协议」是个错问题——它们根本不在同一个维度上，实际接入总是同时选定一个传输和一个协议。

值得注意的是，有的协议会把传输层的纪律写进规范。以一份公开的传输规范为例，它明确要求服务端不得向标准输出写入任何非协议消息，客户端也不得向对方的标准输入写入非协议消息，而标准错误可以自由用于日志。[[5]](#ref-5) 这条约束之所以必要，正是因为传输层不理解语义——它没法替你分辨哪一行是数据、哪一行是日志。

### 相邻层怎么衔接

层与层之间是「下层提供保证、上层据此做假设」的关系，而接入失败往往发生在假设不成立的地方。

- 传输向协议提供**可靠的消息边界**。协议因此假设「收到的是一条完整消息」——所以按固定字节切分而不是按行切分，会让上层拿到半条报文。
- 协议向运行时提供**双向发起的能力**。运行时因此假设「需要问人时能问得到」——所以在单向通道上接一个需要审批的运行时，必然卡死。
- 运行时向界面提供**可解释的状态**。界面因此假设「拿到的是状态本身」——所以从屏幕上推断状态的方案，必须明确告知调用方这一点。

层之外还有一个正交维度：**方向**。界面驱动运行时、运行时获取工具、运行时之间委派，这三个方向解决的问题互不重叠，实践中通常同时存在。把方向弄反是这个主题上最常见的误判——它会让人以为两个互补的协议在竞争。

**先确认一个名词回答的是哪一层的问题，再谈它和谁并列。** 这是本文其余部分的前提。

## 二、协议层：审批能力就是通道方向

协议层的核心不是消息长什么样，而是**谁被允许向谁发起请求**。这一条约束会一路传导到产品能做什么。

### 方法在两端的分布

一个面向「编辑器接 Agent」的公开协议把这件事表达得相当清晰。该协议以 JSON-RPC 2.0 为基础，区分两类消息：期待结果或错误的**方法调用**，以及不期待响应的**通知**。[[1]](#ref-1) 一次典型交互分四个阶段。[[1]](#ref-1)

- **初始化**：客户端调用 `initialize` 协商版本与能力，必要时再走认证。
- **建立会话**：`session/new` 新建会话，或在对方声明了相应能力时用 `session/load` 恢复既有会话。
- **发出请求**：`session/prompt` 送出用户消息，运行时以 `session/update` 通知持续回报进展，期间按需请求文件操作与权限。
- **结束或中断**：客户端可用 `session/cancel` 中断，正常结束时由 `session/prompt` 的响应带回停止原因。

值得单独指出的是方法在两端的分布。运行时侧的基线方法是 `initialize`、`session/new`、`session/prompt`；而客户端侧的基线方法只有一个——`session/request_permission`，用于为工具调用请求用户授权。[[1]](#ref-1)

**审批不是可选扩展，而是客户端必须实现的那一项。** 这个安排是从需求推出来的：模型给出的只是「想调用哪个工具、传什么参数」这一提议，是否执行由程序决定，而这个决定在有人值守时只能由界面前的人给出，所以运行时必须能反向发问。一个只支持单向推送的通道无论字段设计得多好，都表达不出这件事。

客户端侧的可选方法则集中在两类委派上，各自绑定一个能力位。[[1]](#ref-1)[[2]](#ref-2)

- **文件读写**：`fs/read_text_file` 与 `fs/write_text_file`，分别要求 `fs.readTextFile` 与 `fs.writeTextFile` 能力位。
- **终端操作**：`terminal/create`、`terminal/output`、`terminal/release`、`terminal/wait_for_exit`、`terminal/kill`，统一由 `terminal` 一个能力位控制。

这两组的意义不只是「换个人执行」：让编辑器代为读写，运行时才能拿到尚未保存的缓冲区内容，改动也才能以差异视图呈现给使用者；让命令跑在编辑器托管的终端里，使用者才能看见并中断它。委派换来的是**可见性**，不是便利。

### 协议怎么演进

能力协商的规则决定了这类协议怎么演进。`initialize` 请求里的版本号是单个整数，只在出现破坏性变更时递增；客户端必须发出自己支持的最新版本，运行时若支持则回同一个版本，否则回自己支持的最新版本，客户端不支持时应当关闭连接并告知使用者。[[2]](#ref-2)

而新增能力**不算破坏性变更**——因此两端都必须把 `initialize` 里未出现的能力一律视为不支持。[[2]](#ref-2) 这条「缺省即不支持」的规则是向后兼容的实际承载者：它让新特性可以随时加进来，而老实现不需要知道它们存在。

扩展机制是三件套：用 `_meta` 字段挂自定义数据、以下划线前缀定义自定义方法、在初始化时声明自定义能力。[[1]](#ref-1) 三者的共同点是**都不占用未来官方可能使用的名字**，这样自定义部分与协议演进就不会相撞。

还有两条极易被忽略的硬性约定：协议中所有文件路径**必须是绝对路径**，行号采用**从 1 开始**的计数。[[1]](#ref-1) 理由很实际——运行时进程的工作目录、编辑器的工作区根、终端的当前目录三者可能都不相同，相对路径会产生歧义甚至越界；行号的起点若两端各按自己的习惯解释，就会稳定地错开一行。

### 厂商协议给出同一个结论

厂商自研的长连接协议走的是另一条路，但结论方向一致。有一份公开说明把某个编码 Agent 的多个界面——网页端、命令行、编辑器扩展、桌面应用——描述为共用同一套运行时，而它们之间的关键连接是一个双向的 JSON-RPC 接口。[[3]](#ref-3) 双向在这里同样是为审批服务的：当运行时需要在执行命令前获得许可，它向客户端发起请求并**暂停本轮**，直到收到回答。[[4]](#ref-4) 一个只对入站请求回「方法不存在」的客户端在简单场景下能跑通，但遇到需要授权的动作就会卡死。

从这两条路径能提炼出一条可迁移的判断：**先定义协议、再让运行时与各界面都依赖它**，收益是各端可以并行开发、变更影响范围可预测，而且同一套运行时可以同时供多个界面使用。代价则是协议本身成了需要长期维护的契约。

**审批能力不是协议的一项功能，而是通道方向的推论。** 判断一个接入方案能不能承载「有人在旁边看着」的场景，只需要问一件事：运行时能不能反过来向界面提问。

## 三、六种接入面的对比

把接入形态摊开对照，能看出哪些差异是本质的，哪些只是熟练度问题。

<IntegrationSurfaceMatrix />

审批能力与状态精确度两列的排序之所以一致，是因为它们由同一件事决定：通道是不是双向的、拿到的是不是状态本身。剩下的差异则要一条条看。

### 单向事件流：够用，但要处理四件事

单向事件流拿不到审批，是因为它没有让运行时向界面发问的语法。这类通道的典型形态是按行分隔的结构化事件：命令行以非交互方式运行，把事件逐行写到标准输出。它在持续集成场景里几乎是默认选择，也确实够用——没有人在旁边看着，成败用退出码表达就好。但有四件工程细节要处理。

**其一，必须按行缓冲。** 一次读取可能拿到半行，也可能拿到多行；按固定字节切分必错。单行还可能极长，因为其中可能嵌着大段文件内容，所以要有上限保护。末行可能没有换行符，读到结尾时要把残留缓冲刷出来。

**其二，标准输出只放数据，日志一律走标准错误。** 这不只是习惯，有的协议把它写成了硬要求。[[5]](#ref-5)

**其三，这类开关属于弱契约。** 以某个命令行工具为例，逐 token 的增量事件需要显式开启，且要求同时处于打印模式与结构化流式输出；把标准输入也切成结构化格式时，另有一个开关可以把用户消息回放到输出流上，便于自建界面对齐时序。[[6]](#ref-6) 这些标识符的具体拼写随版本变化，其文档甚至明确写着帮助信息不会列出全部选项。[[6]](#ref-6) 生产环境锁版本，是这条通道的必要纪律。

**其四，结构化产出要用约束而不是靠解析文本。** 有的实现提供以 JSON Schema 约束最终响应形状的选项，[[7]](#ref-7) 有的提供在流程结束后返回符合给定 Schema 的校验输出的选项。[[6]](#ref-6) 两者的共同价值是把「下游能不能稳定取到字段」从概率问题变成契约问题。

### 伪终端：能包装一切，代价是状态靠推断

伪终端驱动位于另一个极端。它分配一个伪终端，像人一样喂按键、读画面，因此能包装任何只有终端界面的程序——代价是**状态从此是推断出来的**。这条路上有三个绕不开的点。

**屏幕是网格，不是流。** 现代终端界面会使用备用屏幕、绝对光标定位与局部重绘，同一块区域被反复覆盖，所以只在输出流上做模式匹配是不够的，必须维护一个真实的屏幕缓冲区再从网格上读状态。

**跨平台差异是实打实的。** 类 Unix 系统有伪终端设备；Windows 上对应的机制是伪控制台，微软文档把它称作 pseudoconsole，也常被写作 ConPTY 或 Windows PTY，它需要宿主程序先显式创建再启动子进程。[[8]](#ref-8)

**给了伪终端反而更乱。** 很多程序用「输出是否连着终端」来决定是否启用颜色与进度动画，于是「要不要给伪终端」本身成了一道权衡——要画面就给，要干净文本就别给。

这里有一条方向相反、但同样重要的推论：**如果你写的命令行工具会被 Agent 调用，就不要假设有终端在。** Agent 调用通常没有伪终端，也无法回答交互式提问；一个在缺少输入时挂起等待的工具，会把整条调用链拖到超时。正确的做法是：不是终端就自动进入非交互模式，缺参数直接报错退出；提供结构化输出选项；退出码语义清晰。

### 标准协议还是厂商协议

判据不是能力强弱，而是**对接数量**。标准协议的边际接入成本随对接数量下降——实现一次，对多家生效，能力差异靠协商而非分支代码；厂商协议覆盖自家运行时的完整能力面，包括登录、模型发现、配置管理这些辅助功能，但换运行时要重写绑定。

生态现状可以印证这一点。有编辑器把外部 Agent 的接入做成了注册表安装，并明确划出配置边界：模型与提供方配置、认证与订阅通常归 Agent 自己所有，工具权限则两侧都有一份。[[9]](#ref-9) 自研 Agent 接入时通常只需在设置中声明启动命令与参数，不必改编辑器内核。[[9]](#ref-9) 更关键的是它把责任写清楚了：外部 Agent 通过自己的进程与提供方关系运行，计费、数据留存与数据处理都在使用者与该 Agent 提供方之间。[[9]](#ref-9)

至于原生内建还是外挂适配器，判据是**协议演进速度与能力完整度要求**。协议还在快速变、或不想让内核背上协议负担，适配器更合适——运行时内核不用改，协议层可以独立迭代。但要接受能力缺口：适配器往上游看是一个标准客户端，往下游看是一个具体运行时，两侧能力不对齐的部分只能降级或丢弃。反过来，需要完整的文件系统与终端委派，就得原生做，因为那些委派要求运行时在决定读写与执行**之前**就把动作交出去，这不是外面加一层能补的。

### 拦截点：不改模型也不改 Agent 的接入方式

还有一种接入面容易被忽略：运行时暴露的拦截点。如果接入的目的是管控而不只是调用，它往往是最实用的落点。有官方文档把这套机制的能力面写得很细。[[12]](#ref-12)

- **工具执行前**的拦截点可返回放行、拒绝、询问使用者或推迟；其中拒绝的理由展示给模型，放行与询问的理由只展示给使用者。
- 它还能**改写工具入参**——该字段替换整个输入对象，因此未修改的字段也要一并带上。
- 多个拦截点给出不同决定时，**优先级是拒绝高于推迟、推迟高于询问、询问高于放行**。

**能在动作发生之前改写它的参数，是宿主方最实用的一个接入点**——路径重写、危险参数剔除、注入本地规范，都不需要碰模型，也不需要改运行时。

**需不需要中途问人，是选型的第一问。** 需要，就只能在双向那一侧挑；不需要，最省的那一种通常就够。

## 四、隔离：与上面四层正交的一维

隔离可以整层叠加或整层去掉，而上面四层的代码一行都不用改。它内部真正要回答的问题只有一个：**被关进去的是什么。**

<SandboxScopeLadder />

四档粒度的差别不在用了什么技术，而在每一档**留在外面**的那一列——只关命令通道那一档之所以危险，正是因为绕过它不需要攻破任何东西。所以接入前要问清楚的是「隔离的是命令，还是整个进程连同它的全部工具」。

落地时还有三条边界值得记住，它们各自只需一句话。

- **原语按平台而异**：不同操作系统提供的沙箱机制不同，同一产品在不同平台上的实现也不同，且随版本变动较快，落地前须按当日文档核对。[[10]](#ref-10)
- **网络应当是按目的地的规则，而不是一个开关**：允许预期目标、拦截不希望到达的目标、对不熟悉的域名要求审批，比「联网／断网」这一个布尔值有用得多。[[10]](#ref-10)
- **审批与沙箱分属两层**：沙箱决定技术上能做什么，审批决定什么时候必须停下来问人；两者配合，谁也替代不了谁。[[10]](#ref-10)

最后一条是隔离明确管不到的：它管「能做什么」，不管「被谁指挥」。有一个被广泛引用的模型把致命组合概括为三条边——接触私有数据、暴露于不可信内容、具备对外传输能力——三者同时具备才真正危险，解法是切断其中一条，而最容易在不牺牲可用性的前提下限制的是外泄通道。[[11]](#ref-11)

**提高隔离等级不会降低被外部内容误导的概率，它只降低误导成功之后的破坏半径。** 这两件事必须分开做预算。

## 五、成本：前缀排列是接入设计的一部分

<PrefixCacheEconomics />

前缀缓存与接入的关系只有一条，但它足以改变载荷的组织方式：**缓存匹配的是从头开始的连续前缀，而失效是全有全无的。** 前面任何一处发生变化，它之后的全部内容都不再是同一个前缀——不是打个折，是整段命中归零。[[13]](#ref-13)

于是提示词的排列顺序不是风格问题而是接入设计问题。**工具定义应当排在最前**，因为它体积大且会话内不变，放前面能让可复用的那一段尽可能长；系统提示、静态示例次之；增长中的历史再次之；唯一的动态尾部是本轮的新消息。反过来，往靠前的位置注入每轮变化的内容——当前时间、随机标识、每轮刷新的环境信息——是最典型的失效来源。

有实现把这条认识做成了显式的开关：某个命令行工具提供一个选项，把系统提示里逐机器变化的段落移到第一条用户消息里，其文档说明的动机正是**改善不同使用者与不同机器在跑同一任务时的前缀复用**。[[6]](#ref-6) 同样的信息，只是换了位置，缓存表现就不同。

**缓存省下的不是重复的内容，而是重复的计算。** 这句话决定了接入时该怎么排载荷。

## 六、暂停与恢复：这是状态问题，不是界面问题

需要人介入的接入场景里，有一个判断被普遍低估：**审批暂停不是一个界面等待态。** 运行时必须在精确的中断点把状态持久化，并在拿到决定之后从那个点恢复正确的执行线程。少了持久化这一步，所有审批门都是装饰。

有一个编排框架把这件事做成了一等公民：中断触发时框架用持久化层保存状态，然后**无限期等待**直到恢复执行；恢复需要一个持久化器与一个线程标识，后者实际上就是持久化游标——复用同一个值会恢复同一份检查点，换一个新值则开启一条新线程。[[14]](#ref-14)

这条「恢复即重放」的性质会传导到接入侧：**Agent 调用不是幂等的**，同一个请求重试一次很可能重复产生副作用。对策是走结构化编辑通道并在应用前做冲突检测、为任务级操作设幂等键、重试策略只对明确的瞬时错误生效。

单向通道上的「暂停」值得单独辨析，因为它不是同一件事。有实现在非交互模式下提供了一个推迟语义：工具不执行，进程带着明确的停止原因退出，待处理的那次工具调用被保留在记录中；调用方从结果里读出待处理项、在自己的界面上收集输入，然后再恢复。[[12]](#ref-12) 这条路径能工作，但它的形态是**退出再重入**，而不是「原地挂着等」——差别在于它要求调用方自己保存足以重入的全部信息。

**能停不等于能续，而能续的前提是状态在停下的那一刻已经落到了外面。** 所以评估一种接入方案的人工介入能力时，先问暂停状态存在哪里，再问能否从断点精确恢复——很多实现能「停」却不能「原地续」，只发停止信号而没有恢复路径的，实际含义是只能重新开始。

## 七、按场景收敛：一条可执行的选型路径

把前面几节的判据串起来，可以得到一个逐问收敛的过程。次序不能随意调换，因为它反映的是排除强度。

```
CHOOSE-INTEGRATION(scenario)
	// 第一问：会不会执行不可信代码或读入不可信内容
	// 这一问与其余全部正交，必须单独回答，且先回答
	if UNTRUSTED-INPUT(scenario) then
		isolation ← "进程级隔离 + 默认无网 + 目的地白名单"
	else
		isolation ← "工作区可写 + 按需审批"
	end if

	// 第二问：有没有人在旁边看着并需要中途授权
	if not NEEDS-HUMAN-IN-LOOP(scenario) then
		// 无人值守：成败用退出码表达，产出用 schema 约束
		if NEEDS-STRUCTURED-OUTPUT(scenario) then
			return ("命令行非交互 + 输出 schema", isolation)
		else
			return ("命令行非交互 + 事件流", isolation)
		end if
	end if

	// 有人值守：只能在双向通道一侧挑
	// 第三问：要对接几个界面、几个运行时
	if COUNT-CLIENTS(scenario) > 1 or COUNT-RUNTIMES(scenario) > 1 then
		return ("标准化编辑器协议", isolation)   // 边际成本随对接数量下降
	end if

	// 第四问：单一运行时，是否要用到它的全部特有能力
	if NEEDS-VENDOR-SPECIFIC(scenario) then
		return ("厂商长连接协议", isolation)     // 能力最全，代价是绑定
	end if

	// 第五问：对方有没有任何结构化入口
	if HAS-STRUCTURED-SURFACE(scenario) then
		return ("SDK 或其原生协议", isolation)
	else
		// 兜底：必须明确告知调用方「状态是推断的」
		return ("伪终端 + 无界面终端模拟器", isolation)
	end if
```

前两问的位置由伪代码注释承载。真正要防的是把它们排到后面——那会让人在方案定完之后才发现要处理外部仓库，或者在一条单向事件流上拼出一个假的审批。

两个走向相反的场景可以对照：

| 场景 | 判断路径 | 落点 |
| --- | --- | --- |
| 持续集成里的自动审查 | 无人值守 → 需要稳定字段 | 命令行非交互加输出 schema，成败交给退出码；只读隔离通常就够 |
| 内部统一接入平台 | 有人值守 → 多界面多运行时 | 南向用标准协议接多个运行时，北向暴露给网页与编辑器；执行落在容器化沙箱里，会话状态外置以支持跨执行者恢复 |

**选型时说出被排除的选项与排除理由，比给出结论更有价值**——因为大多数返工发生在「当初没意识到这条也是个选项」而不是「选错了」。而在更长的时间尺度上还有一层：**协议与命令行接口的变动速度远快于这些结论本身。** 方法名、字段名、能力位、命令行选项都会变，而分层归属、协议与传输正交、方向决定归属、审批需要双向、隔离与其余四层正交、前缀稳定性决定缓存、能停不等于能续这几条不会。落地时把前一类当作需要按当日文档核对的参数，把后一类当作可以先想清楚的结构。

有三处已知缺口须如实说明，它们都会实际影响落地判断。

**其一，厂商长连接协议的具体报文形态未能从一手来源核实。** 来源 [3] 的原页在本次核验中无法直接抓取，仅通过检索摘要确认了「双向 JSON-RPC」「一个进程承载多个核心线程」这一架构方向；来源 [4] 作为第三方报道印证了「服务端可主动发起请求并暂停本轮」这一机制。因此本文只写了机制方向，未写任何方法名、字段名或信封细节。多份第三方资料提到该协议在实际传输中省略了 JSON-RPC 的版本信封字段，但这一点未能在官方文档中确认，故未写入正文——接入时应以实测报文为准，不要照抄通用规范做严格校验。

**其二，非交互模式下事件流的完整性边界未能核实。** 多份第三方资料提到某些非交互执行模式下的会话记录运行在受限的持久化档位、部分事件会被丢弃，因此不宜作为唯一审计源。这个说法在工程上很重要——它决定审计系统能不能只依赖一份记录——但本次核验未能在官方文档中找到对应表述，故正文未采纳。若要把会话记录当作审计依据，应当自行实测其事件完整性。

**其三，各实现在「适配器层能力缺口」上的具体表现未逐项核实。** 正文只写了「适配器两侧能力不对齐的部分只能降级或丢弃」这一结构性结论，以及「需要完整的文件系统与终端委派就得原生做」这一推论。具体某个适配器是否转发了文件与终端委派、是否有独立的思考流、外部工具服务参数是否真正接到了下游，都是逐实现且随版本变化的，需要按当日代码与实测确认。
