# 面试题库

本页集中承载 `ai/agent/` 各主题的题目化材料。正文负责讲清知识本身，本页负责检验理解是否到位——因此每题都指向正文的对应位置，答案不重复展开正文中的推导。

按主题分章，顺序与正文一致；新增正文文档时在本页追加对应章节，不在正文内嵌题目或自检区。

题型分三类，各自检验不同的能力：

| 题型 | 检验什么 | 判断是否答对 |
| --- | --- | --- |
| 概念辨析 | 是否把容易混为一谈的对象分清 | 能说出区分依据，而不是复述定义 |
| 过程推演 | 能否在给定条件下推出结论 | 结论与推导路径都成立，且说得出前提 |
| 方案设计 | 能否在有约束的场景中做出取舍 | 给出选择、代价，以及失败时的退路 |

难度标注 **基础** / **进阶** / **深入**：基础对应正文明确写出的结论，进阶需要组合两处以上知识，深入需要在没有标准答案的场景中给出有依据的判断。

## 模型交互 {#llm-api}

对应正文：[模型交互](./model/llm-api.md)。共 3 题。

**1. 单次调用：端口 JSON 与 `read_file` 调用参数，分别应该从哪里取出？** 〔基础〕

先检查请求是否成功、响应是否完整及是否被拒绝。业务结果从 `message.content` 取出 JSON 文本后解析；工具调用则逐项读取 `message.tool_calls`，再解析 `function.arguments`，同时保留调用 ID。前者是回答结果，后者是交给函数的参数。能解释这两条解析路径，也应能指出 `response_format` 与 `tools` 分别约束哪一种内容。

进一步区分输入中的三类信息：few-shot 示例说明期望的规律，当前资料提供本次事实，图片提供可见证据。不应把示例里的 8080 或截图之外的运行状态当成当前答案。

**2. 多轮交互：用户只问了一次，为什么读取配置的例子会调用模型两次？** 〔进阶〕

第一次模型调用提出读取请求，程序执行后，第二次调用才看到文件内容。下一次输入应包含原始用户问题、完整 assistant 调用消息，以及匹配 `tool_call_id` 的 tool 结果；如果原请求还有需要生效的 system prompt，也应继续包含。

换成用户追问「超时呢？」时，新增的是 user 消息，但同样需要前文提供配置依据。用户轮次与模型调用次数应分别计数。

**3. 底层机制：窗口为 8,000 token，输入为 6,000，其中 4,000 命中缓存，还能生成 4,000 吗？** 〔进阶〕

不能。输入仍占 6,000 token，窗口最多只剩 2,000 供生成，且还需满足模型与请求的输出上限。缓存节省的是重复前缀的计算，不会增加窗口容量；是否降低总耗时，还取决于输入处理与后续生成各占多少。

## Context Engineering {#context-engineering}

对应正文：[Context Engineering](./context/context-engineering.md)。共 18 题。

### 概念辨析

**1. Prompt Engineering 与 Context Engineering 是什么关系？** 〔基础〕

前者是后者的一个子集，不是被替代的旧范式。Prompt Engineering 解决「这一句话怎么说，模型才照做」，操作对象是系统提示与用户消息，写好即固定；Context Engineering 解决「这一刻该让模型看见什么」，操作对象扩展到工具定义、示例、检索结果、记忆、历史与工具返回值，且每一轮推理前都要重新决定。判别标准是时间维度：一次性写好的是 prompt 问题，需要每步重新决策的是 context 问题。

**2. 「保存了资料」和「模型看到了资料」差别在哪？** 〔基础〕

对话记录、知识库、长期记忆都只是**来源**；只有经过选择、真正进入本次请求的那部分 token 才构成本次**上下文**。这个区分决定了排障方向：向量库里有正确文档但模型答错，问题在 Select 而不在知识覆盖。

**3. 上下文的七个来源如何按性质归为三类，为什么这个分类比按来源列举更有用？** 〔进阶〕

静态部分（系统提示、工具定义、few-shot 示例）每次调用原封不动，是成本固定项；动态部分（检索知识、记忆）随召回策略变化；累积部分（消息历史、工具返回值）随步数单调增长。分类的价值在于治理手段不同——静态靠一次性写好，动态靠召回策略，累积靠持续治理。而线上问题绝大多数出在累积部分，所以它决定了排障应该先看哪里。

**4. 为什么窗口从 8K 涨到 1M，上下文治理仍然必要？** 〔进阶〕

四层理由，前三层是程度问题，第四层是性质问题：注意力预算有限（$n$ 个 token 要建立约 $n^2$ 对关系，越长越被摊薄）；召回随长度衰减（Context Rot，是梯度而非断崖）；成本与延迟（输入输出约 100:1，开销几乎全在预填，命中缓存也仍要为传输与预填付费）；状态会腐坏（错误、冗余、过期与矛盾信息一并沉积）。前三层扩窗口能缓解，第四层完全不解决——窗口大只意味着「能装」。

**5. 「最小的高信号 token 集合」中的「最小」是不是「最短」？** 〔基础〕

不是。目标是最大化任务达成概率的前提下尽可能小：该给的背景一点不能少，该砍的冗余一点不能留。把它理解成「越短越好」会直接砍掉必要背景，制造另一类失败。

**6. 区分意图、观察与推断，在上下文组织中为什么重要？** 〔进阶〕

三者的可信度和时效完全不同。用户「希望改成 60 秒」是意图，不等于配置「已经是 60 秒」这一观察；今天转述的旧结论是推断，可能已经过期。混淆后果是模型把意图当现状、把过期推断当证据。原则是优先使用与问题匹配的当前证据，而不是按时间新旧或「多数都这么说」下结论。

**7. 上下文中毒与上下文冲突怎么区分？** 〔进阶〕

中毒是**错误内容进入**上下文后被反复当作事实引用，误差在迭代中被放大，源头是单一错误信息；冲突是**两份内容互相矛盾**并同时存在，源头是新旧口径或工具语义不一致。对策方向也不同：中毒要校验工具输出、裁剪被证伪的结论；冲突要显式声明「以下取代此前的 X」，必要时开新会话，而不是在已污染的历史上打补丁。

**8. 保留失败证据与上下文中毒是否矛盾？** 〔深入〕

不矛盾，因为留和清的是不同东西：留的是**真实发生过的失败证据**（失败动作 + 报错原文），它让模型隐式更新先验、降低重犯概率；清的是**被证伪的结论**（错误事实、幻觉推断），留着才会造成中毒。判据是这条信息属于「事情确实这样发生过」还是「这件事就是这样」——前者永远为真，后者已经为假。

### 过程推演

**9. 一条 50 步轨迹，起始上下文 8,000 token，每步追加 1,200 token。累计输入多少 token，末步单次输入多少？** 〔基础〕

第 $i$ 步输入为 $8000 + 1200(i-1)$，末步为 $8000 + 1200 \times 49 = 66{,}800$ token。50 步累计为等差数列求和：$\frac{50 \times (8000 + 66800)}{2} = 1{,}870{,}000$ token。要点是累积部分随步数线性增长，而每一步都要为**此前全部前缀**重新付费，所以总量增长比直觉更快。

**10. 承上题，按未命中 3.00、命中缓存 0.30 美元每百万 token 计价，两种情况的累计成本差多少倍？为什么不是恰好 10 倍？** 〔进阶〕

全未命中为 $1{,}870{,}000 \div 10^6 \times 3.00 \approx 5.61$ 美元。命中缓存时每步只有新增的 1,200 token 按原价、其余前缀走缓存价，且首步冷启动无缓存可用，累计约 0.74 美元，约为 $1/7.6$。差距小于单价的 10 倍，正是因为每步新增部分和首步冷启动都必须按未命中计价——单价差是上限，不是实际收益。

**11. 在第 25 步做一次压缩，把已累积历史压到 40%，为什么当步成本反而上升？** 〔深入〕

压缩改写了前缀，而 KV-cache 依赖前缀完全一致，因此压缩当步缓存被击穿，需要按未命中价重建整个新前缀。收益来自之后每一步的计价基数都更小，靠后续步数把这笔一次性支出赚回来。推论有两条：压缩不是免费的，触发太频繁会得不偿失；剩余步数太少时压缩可能净亏损，所以触发时机本身需要按评测集确定。

**12. 系统提示开头放一个精确到秒的时间戳，会有什么后果？** 〔基础〕

自回归模型下，任何一个 token 不同都会让该位置**之后**的缓存全部失效。时间戳位于最前部且每次调用都变，等于每轮都全量重新预填，缓存命中率归零，延迟与成本同时恶化。需要时间信息就放到上下文末尾，或改为按天等粗粒度。

**13. 中途给 Agent 增删工具，会引发哪两类问题？正确做法是什么？** 〔进阶〕

一是工具定义通常位于上下文最前部，增删会让其后所有动作与观测的缓存失效；二是历史里仍引用着已消失的工具，模型会困惑，在没有约束解码时容易产生 schema 违规或幻觉动作。正确做法是**遮蔽而不是删除**：保留定义不变，用状态机在解码时遮蔽 logits 控制可用性，并给工具名统一前缀（如 `browser_`、`shell_`）以便按组启停。

**14. 一个 Agent 批量处理 20 份同类材料，越往后越机械重复、甚至开始漏判。诊断与对策？** 〔深入〕

这是模式化（few-shot rut），本质是模型作为强模仿者在照抄上下文里已有的「动作—观测」节奏，上下文越同质，行为越脆。对策是引入**受控**多样性：变换序列化模板、替换等价措辞、在顺序与格式上加入少量扰动。分寸在于「受控」——目的是打破惯性并拨动注意力，不能破坏输出的可解析性。它同时给 few-shot 划了边界：示例要典型且多样，堆砌同质样例反而有害。

**15. 一次排障：Agent 在长任务后期反复调错工具。按什么顺序定位？** 〔进阶〕

先看轨迹而不是先改 prompt——没有 trace 时一切优化都是猜。接着按 token 占比排序，找出异常膨胀的那一类（通常是工具返回值）。再用四种失效模式归类症状：工具选错优先怀疑**混淆**，即工具集过大或职责重叠。然后按无损优先施加操作：先 Select（裁最小不重叠工具集、对工具描述做检索）与 Isolate，再考虑 Compress 与 Write。最后单变量实验，并把修好的 case 沉淀进评测集做回归守门。

### 方案设计

**16. 为一个代码库问答 Agent 设计上下文方案：预取还是即时检索？** 〔深入〕

标准答案是混合。变动慢、几乎每次都要用的（项目说明类文件）预先载入以保证延迟稳定；其余交给 `glob` / `grep` 这类原语即时取，上下文里只留轻量标识符（路径、查询、链接），需要时再加载正文。理由是代码库一大，纯嵌入检索就不可靠，需配合关键词、图谱与重排；而元数据本身即信号——`tests/` 下的 `test_utils.py` 与 `src/core_logic/` 下的同名文件含义完全不同，目录、命名与时间戳都在提示该不该读、何时读、有多相关。变动慢的领域（法律、金融）可更偏预取一侧。

**17. 四大操作应按什么顺序考虑？为什么这个顺序不是随意的？** 〔进阶〕

按无损优先：Select（基本无损）→ Isolate（无损，但 token 与协调成本上升）→ Compress（有损）→ Write（额外读写往返）。顺序依据是信息损失风险，而非实现难度。先做无损操作，能在不牺牲信息的前提下解决相当一部分问题；Compress 放在后面，因为你无法预知第 10 步丢掉的观测会不会在第 30 步变成关键，任何不可还原的压缩都是在下注。因此压缩要尽量**可还原**——丢网页正文但留 URL，省文档内容但留沙箱路径，把文件系统当成容量无限、天然持久的外部记忆。

**18. 什么时候该上多 Agent？它在 Context Engineering 里的定位是什么？** 〔深入〕

它是 **Isolate 的一种手段**，不是架构偏好，也不是能力更强的默认选择。适用条件是存在真正隔离的信息或执行边界：多个独立来源可并行调查、子任务需要不同工具或权限、独立结果可用明确协议合并。代价是 token 用量显著上升（有公开报告称相比对话最多约 15 倍）、需要额外的规划与协调。一个明确反例是多个 Agent 使用相同资料、相同模型并互相复述结论——表面上「多人同意」，实际证据高度相关，独立性存疑。判断落点始终是：隔离带来的收益是否值得这份 token 与协调开销。

## 上下文压缩 {#compaction}

对应正文：[上下文压缩](./context/compaction.md)。共 14 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. 「把某条内容从上下文中移除」，在实现上到底改了什么？** 〔基础〕

改的是标记位，不是数组。上下文对应三个不同对象：**事件日志**（磁盘、追加写、不再修改）、**工作集**（内存消息数组，每条带若干标记位）、**请求载荷**（每轮由工作集重新投影，模型只看得到这一层）。所谓「移除」的准确含义是**组装下一次请求时不把它投影进去**。这个区分是后面一切时机与成本判断的前提：不投影零成本、可回退，只有生成摘要才真正产出了新内容。

**2. 为什么清理工具结果不需要调模型，而摘要需要？** 〔基础〕

因为前者只是决定「这一轮不投影」，后者要把一段历史改写成一段更短的等价文本，原文与新文本之间没有可逆映射。由此可得一条通用的提问方式：讨论任何压缩手段时先判断它属于**不投影**还是**改写**——两者在成本、可逆性、缓存破坏程度上都不同量级。

**3. 五级处置阶梯的排序依据是什么？为什么次序不能颠倒？** 〔进阶〕

依据是**信息损失风险**，不是实现难度。源头收窄、轮内清理、轮次边界、决策点闭合都不产生额外模型调用且可回退，只有摘要压缩要付一次采样且不可逆。次序不能颠倒还有第二层理由：**摘要质量与输入长度负相关**。前四级从未生效时，落到第五级要压缩的输入本身就已庞杂，模型挑出「哪些必须保留」的准确率会明显下降——所以前四级做得好，第五级才做得好。

**4. 工具结果该留该弃，判据是什么？为什么不能按新旧判断？** 〔进阶〕

按新旧会同时犯两种错：旧的可能仍被当前推理链引用，新的也可能已经毫无价值。真正的判据是三个维度交叉：**可重取性**（移除后能否凭剩下的信息取回，即是否有路径 / query / 命令行这类恢复句柄）、**幂等性**（重跑会不会改变外部世界）、**不可再生性**（子 Agent 回传、后台任务状态、记忆输出重跑代价极高或无法重跑）。一般化的表述是：**能被移除的前提是已经固化到别处**——磁盘文件、正式回复，或一个能重取它的句柄，三者都没有就不能动。

**5. 写操作结果为什么必须保留？它和只读结果的风险是同一量级吗？** 〔进阶〕

不是。写操作结果承担的不是信息功能而是**记账功能**——它是「这件事已经做过」的唯一凭证。清掉之后，模型在后续评估进度时找不到任何证据表明提交已完成，于是可能再提交一次。所以清理只读结果的收益是省钱，清理写操作结果的代价是**制造重复副作用**（重复提交、重复发消息、重复扣款）。

**6. 「压缩之后旧内容就没了」这个说法哪里不准确？** 〔基础〕

要先问是哪一层没了。请求载荷里看不到了，事件日志通常还在。按三层存储类比：活跃层（当前载荷，容量受限、摘要不可逆）像内存，会话层（摘要与完整日志，可事后回查）像预写日志，持久层（代码、报告、数据集）像磁盘。混淆这两件事会导出完全错误的设计决策——正确的历史保障不是让压缩少丢东西，而是**在压缩之前就把不能丢的写到会话层与持久层**。

### 过程推演

**7. 触发阈值为什么应当是「距上限的绝对缓冲」而不是窗口百分比？** 〔进阶〕

因为要保护的是**生成摘要所需的输出空间**，而这个空间的大小取决于摘要本身有多长，与窗口容量无关：200K 窗口和 1M 窗口写一份结构化摘要需要的输出预算是同一量级。形式是「有效窗口 = 窗口容量 − min(本轮输出上限, 上限常数)」，「触发线 = 有效窗口 − 摘要输出预算」。用百分比的后果是两端都错：小窗口留出的空间不足以生成摘要，越线后连压缩请求都发不出去；大窗口则闲置大量容量、压缩触发过早过频。**同一个百分比不可能同时适配两端，因为它约束比例，而需要约束的是差值。**

**8. 已经设了触发线，为什么还需要反应式兜底？** 〔进阶〕

因为触发线不是硬墙。判定发生在某个检查点，而两次检查之间可能插入一条超大的工具结果——一次线程转储、一份未收窄的日志足以一次顶穿全部缓冲。所以要捕获「超出上下文长度」这类错误、执行一次更激进的压缩再重试。关键是这条路径必须**一次性**：失败就显式报错，否则会陷入「压缩失败 → 重试 → 再次超限」的循环。相应地压缩请求本身要打标记，禁止压缩过程中再次触发压缩。

**9. 一次清理只回收了 154K，为什么可能反而是净亏？** 〔深入〕

因为前缀缓存的复用条件是前缀完全一致，某个位置变了，该位置**之后**的缓存全部失效。所以代价不是「少命中一段」，而是改动点之后的全部内容都要重算——**位置比数量更决定代价**。清掉窗口靠前的一大段，可能让后面几十万 token 全部失效；清掉靠近尾部的同样体积，失效范围可能只有几万。同样的清理动作，位置不同，缓存代价可以差出数倍。对策是三条：设「单次最少回收量」门槛，不达门槛整批放弃；优先清最老的一大段而非每轮修补；挑缓存本就要过期的时刻动手。

**10. 经历多次压缩后，哪些信息最先流失？这对提问方式有什么约束？** 〔进阶〕

规律是**越接近「精确值」的信息流失越快**：工具结果里的具体数值在第一次压缩后就基本没了，改动文件的完整清单流失次之，架构决策与已知边界被逐层概括，用户原话与写进文件的内容基本无损。直接约束是：压缩多次之后**不要向 Agent 询问明细**——「你之前改了哪些文件」的答案已不可信，摘要里可能只剩「重构了鉴权中间件与并发控制」一句。改动清单要现场从版本控制取，测试结论要重新跑。反过来这也给出压缩前的清单：精确数值、确切配置、精确清单、来源链接必须先落盘。

**11. 层叠式与改写式摘要的差别是什么？会导致什么长期后果？** 〔进阶〕

层叠式把上一份摘要作为「此前已压缩的上下文」再次纳入输入，摘要体积单调上升，而它覆盖的每段历史留下的字数越来越少——**体积在涨，分辨率在跌**。改写式把旧摘要喂进去、新摘要出来，是替换而非叠加，体积由预算约束住。第三种是增量更新：首次用一套提示词，之后每次用「把新信息合并进已有摘要」的提示词，明确要求模型维护一份摘要而不是让它自然堆积。

**12. 切点为什么不能落在工具结果上？单个回合就超预算怎么办？** 〔深入〕

工具结果必须与产生它的调用待在一起，切开就破坏配对关系，多数接口会直接拒绝请求。合法切点是用户消息、助手消息这类完整边界。至于单个回合就撑满保留预算——一个回合从用户消息开始、包含其后所有助手响应与工具调用——此时切点只能落在回合中间，做法是分别生成「历史摘要」与「该回合前半段的摘要」再合并。一次吐出数十万 token 的转储就会触发这条路径。

### 方案设计

**13. 让你设计压缩的触发机制，怎么答比报一个数值更好？** 〔深入〕

给组合而不是单点。四种口径各有短板：绝对缓冲精确、与窗口解耦，但对「时机好不好」一无所知；窗口百分比实现简单，但两端都不适配；事件条数最省事，但一条短消息与一份上万 token 的输出同权，口径最粗；模型自主能挑中真正合适的时机（任务边界、结论已提取、即将大量读入、进入长链流程之前、有决定推翻先前上下文），但需要兜底。成熟形态是**模型自主 + 绝对缓冲硬线**：让模型在好时机主动压，同时用硬线防止它一直不压。值得一并提的实测：模型在这件事上偏保守——某终端任务基准上未观察到任何一次自主压缩，但真触发时通常选在明显改善工作流的时刻。

**14. 怎么判断一次压缩改动是改善还是损害？** 〔深入〕

不能看压缩比——它只说明输入变小了，不说明系统变好了。四条：① **先看构成**，每轮记录总 token 与各类别占比，膨胀主因通常一眼可见，缺这份数据时任何优化都无从判断方向；② **按后续任务检验**，从同一执行快照分出未压缩与压缩两支，给相同后续任务，比较约束遵守、证据可回查、未完成事项覆盖、工具重复调用次数与完成率；③ **分层统计保真度**，把高层事实与冷门细节分开统计通过率，合在一起会掩盖真实问题；④ **调提示词先召回后精度**，先确保抓住每条相关信息（哪怕啰嗦），再逐步删减并盯住召回不下滑。此外压缩后的重复读取次数特别有诊断价值：每轮都在重读同一份已稳定的文件，说明保留窗口切得太狠。

## Agent 记忆 {#memory}

对应正文：[Agent 记忆](./context/memory.md)。共 15 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. 「这个 Agent 记得我」，记忆到底存在哪里？** 〔基础〕

不在模型里。模型每一次调用都是无状态的，没有任何跨调用保存信息的地方——上一次算出的东西除了输出文本没有留下痕迹。所谓「记得」是模型**外面**那套机制的性质：有人把该留的内容写到了某处，又在恰当时机取回放进了下一次请求。这句话决定了后面一切设计：不存在「让模型记住」这个动作，只存在「写到某处」加「按需取回」两个动作。

**2. 三层记忆分别是什么？为什么必须分开谈？** 〔基础〕

**工作记忆**是本次请求载荷里的内容，寿命一次调用，容量受窗口硬约束；**会话内记忆**是一个会话的完整状态（检查点或事件日志），寿命一个会话，容量远大于窗口；**跨会话长期记忆**是跨会话仍成立的结论（文件、向量库、图、关系表），寿命直到被改写或删除。必须分开是因为三者寿命差了几个数量级，治理手段完全不同：工作记忆靠挑选与压缩，会话内记忆靠持久化与可恢复性，长期记忆靠有效性判定。混着谈得不出任何可执行的结论。

**3. 三层之间靠什么相连？每一道缺失分别是什么现象？** 〔进阶〕

靠三道**显式的固化路径**，每一道都是真实的写操作，不会自动发生。**落盘**（工作记忆 → 会话内）缺失表现为「重启就没了」，任务无法恢复也无从回放；**抽取与固化**（会话内 → 长期）缺失表现为「每次都要重新交代」——这一道最容易被漏，因为没有任何机制会自动把会话里值得记的挑出来；**召回**（长期 → 工作记忆）缺失表现为「明明存了却不用」，这是最高发的故障，而且排障方向在召回侧不在存储侧，去检查存储有没有那条是白费功夫。

**4. 覆盖写与追加写该怎么选？判据是什么？** 〔进阶〕

判据是这条记忆陈述的是「事情曾经这样发生过」还是「事情就是这样」。**前者永远为真，只能追加**——「上周三试过把重试放在网关层，压测下超时反而上升」这句话不会因为后来的变化而变假，覆盖掉就失去了「当时为什么这么判断」的依据；**后者会过期，必须可覆盖**——用户从深圳搬到成都，「所在城市」这个槽位只应有一个当前有效值，追加写会留下两条互相矛盾的条目，之后召回哪条全凭排序运气。覆盖写与追加写混用是记忆系统最常见的设计错误。

**5. 为什么程序性规程通常不走检索？** 〔进阶〕

因为它的命中率接近 100%，而检索总有漏召的概率。「提交前跑 check」这类约定漏一次就出错，且输出看起来完全合理、只是不符合约定——这是个**安静的错误**，平时都对，只在漏召的那一次出错，而那一次很难被发现。所以高命中率的规程应当常驻注入。代价是它占的是每一次调用的**固定预算**，越写越长之后成本上升而遵守率反而下降，因此需要配套手段：按文件路径作用域按需加载、把细节拆进按需读取的分文件、给索引文件设行数上限。

**6. 相似度检索为什么治不了过期记忆？** 〔深入〕

因为**过期的记忆往往与查询高度相似**。「部署脚本有 bug，需手动执行 step 3」在被问「部署要注意什么」时相似度会非常高，而脚本早已修好。根源是相似度衡量的是「像不像」，而「还成不成立」是另一个维度的问题——向量空间里根本没有编码这个信息。所以无论嵌入模型多好，纯相似度检索都无法解决这类故障，必须另外引入时间、来源、置信度、矛盾检测这些信号。

### 过程推演

**7. 三信号打分是哪三个？把时效权重调到最大会发生什么？** 〔进阶〕

相关度、时效、重要性加权求和，其中时效通常实现为指数衰减，重要性由模型在写入时打分。把时效权重推到最高，过期条目确实被压下去了，但「很旧却一直有效」的稳定偏好也会一起被挤出预算——**衰减对稳定偏好和过期结论一视同仁**。所以调权重不是终点，需要两条补充：按类型分别设定衰减（规程与偏好几乎不衰减，情景经历衰减快），以及在写入时就记录有效期，让「失效」成为可判定的字段而不是靠打分猜出来的结果。

**8. 双时间轴是哪两条时间线？它解决了什么单时间轴答不了的问题？** 〔深入〕

**有效时间**（这件事在世界上何时开始为真、何时不再为真）与**系统时间**（系统何时得知这件事、何时得知它失效）。单时间轴答不了两类问题：一是「用户去年这个时候的工作是什么」这类历史时点查询；二是「我们当时为什么做了那个决定」——这需要知道决策发生时系统所掌握的信息，而不是现在掌握的信息。它还有个工程副产品：矛盾消解变成一次**标注**而非一次删除，保留了完整审计链，可以回答「这条记忆是什么时候、因为什么被判定失效的」。

**9. 写入时的四个操作是什么？哪个最常用，为什么？** 〔进阶〕

新增、更新、删除、什么都不做（由一次模型调用比对新信息与已检索出的候选条目逐条判定）。**最常用的是「什么都不做」**——真实对话里绝大多数说过的话不该成为长期记忆。一个只会新增的记忆系统前两周表现良好，三个月后召回预算被近义重复条目和闲聊占满，反而不如没有记忆。另外「更新」与「删除」的区别是：**有新值来接替的是更新，没有新值、只是「不再为真」的是删除**——把后者错判成前者会留下一条无从解释的空槽。

**10. 「这次简短点」和「我一直喜欢简短」该怎么区分处理？判别信号是什么？** 〔进阶〕

前者是一次性指令，作用域是本次回答，正确处理是什么都不做；后者是稳定偏好，应写入长期记忆。最可靠的判别信号是**用户自己的措辞**：「这次」「临时」「先」「试一下」对应一次性，「一直」「都」「以后」「更喜欢」对应长期。这些词比任何启发式规则都准，因为它们就是用户在直接表达作用域。判错的代价是**过度个性化**：用户此后每次都得到简短回答，而且不知道该去哪里改。

**11. 为什么记忆整理适合放到后台做？** 〔进阶〕

因为它不在用户等待的关键路径上。整理记忆需要读大量历史、做多次判断，放在响应过程中用户要为此等待。更重要的是一个资源置换：**后台过程对延迟不敏感，因此可以用更贵的手段**——读更多历史、做更多轮判断、用更强的模型；而前台召回必须在几百毫秒内返回。把两者分开是在用一个不敏感的资源换一个敏感的资源。常见触发时机是若干轮对话之后，或上下文被压缩时。

**12. 记忆投毒的链条是什么？为什么它比普通提示注入更难排查？** 〔深入〕

三段：**注入**（恶意内容经文档、网页、邮件、代码仓库进入上下文）、**驻留**（被写进长期存储，混入正常行为画像）、**执行**（数周后被召回，此时它带着「这是系统自己的记忆」的可信度）。比普通注入更难排查的原因是**它发作时看不到任何可疑输入**——可疑输入是几周前的事，当初的注入痕迹早已不在任何上下文里。根源在于模型权重是只读的，而记忆运行时可写且跨会话持久。对应的纪律很明确：工具返回内容里的指令性文字不获得写入记忆的权限，无论它多么像一句用户请求。

### 方案设计

**13. 设计一个记忆系统的评测，该怎么做？** 〔深入〕

不能只看召回率——召回了五条对的加三条过期的，召回率很好看而输出可能是错的。四条：① **按后续任务表现检验**而非按召回率；② **分层统计**，把「稳定偏好类」与「精确细节类」的通过率分开算，两者差距通常很大，合在一起会掩盖真实问题；③ **把拒答纳入指标**——「识别出这件事我不知道因此不回答」是记忆系统最关键的安全属性之一，一个会编造记忆的系统比没有记忆的系统更危险，因为它的输出带着「我记得」的可信度外观；④ **把每个修好的故障沉淀成回归用例**，记忆的故障形态是重复出现的。另需注意厂商自评分数的测评口径、检索配置、判分模型都可能不同，不构成中立的产品排名。

**14. 为什么编码类 Agent 的长期记忆大量落在 Markdown 文件而不是向量库？代价是什么？** 〔深入〕

不是因为向量检索不成熟，而是因为**错误代价的形态不同**：一条错误的长期规程会被反复执行到生产代码里。文件路线的收益是可审计（人能直接读到全文）、可 diff 可 review（记忆变更走和代码一样的评审流程，错误能在生效前被人拦住）、用户可直接编辑、天然承载程序性记忆、零漏召（常驻注入）。代价同样清楚：没有语义检索、需要人工维护去重与失效、体积挤占每一次调用的固定预算。所以这一族普遍配了缓解手段——按路径作用域加载、拆分主题文件按需读取、给索引设行数上限。值得注意的是「让模型读规则描述自行决定是否加载正文」这种做法其实是给程序性记忆做了一层检索，说明文件路线与检索路线并不对立，分歧在于索引粒度和谁来判断相关性。

**15. 把记忆建模成「对话缓冲区」为什么不成立？正确的分解是什么？** 〔深入〕

早期框架的缓冲区抽象（保留最近 n 轮 / n 个 token / 滚动摘要）被整体弃用，公开理由是三条：缺少对多用户多会话的内建支持而这是真实应用的基本要求；无法在任意时点保存与恢复，因此做不了错误恢复、人工介入与分支探索；早期实现未面向新式对话接口设计，在工具调用等特性上出问题。三条指向同一根源：**「保留最近几轮对话」既不是会话状态持久化也不是跨会话记忆，它夹在中间两头都不到位**——它假设记忆等于历史的一个子集，于是既承担不了「完整可恢复」（它在丢弃内容），也承担不了「跨会话可召回」（按会话组织，且保留原始对话而非提炼的结论）。正确的分解是拆成两套：会话状态要完整、可恢复、可回放；跨会话记忆要精炼、可召回、可判定有效性。一般化的教训是：**当一个抽象需要不断加参数来适配新场景时，通常是分解方式错了，而不是参数不够多。**

## memory、context 与 knowledge 的边界 {#memory-boundaries}

对应正文：[memory、context 与 knowledge 的边界](./context/memory-boundaries.md)。共 12 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. 三套机制各自回答什么问题？为什么不能互相替代？** 〔基础〕

context 回答「**这一次**让模型看见什么」，memory 回答「跨越**多次调用**的经历如何存续」，knowledge 回答「参数里**没有**的客观事实从哪来」。不能互相替代是因为三个问题彼此独立：扩大窗口只缓解 context 的压力，对另两者毫无帮助；接一个知识库解决了 knowledge，memory 依然缺失。任一个解决了，另两个依然存在。

**2. 区分三者的两条判据是什么？** 〔基础〕

**一是本体在 context 之内还是之外**：memory 与 knowledge 的本体都在外面（记忆存储、文档库），进入 context 只是一次投影，副本不是本体；context 没有「本体在别处」这回事，它就是本次调用的信息集合。**二是移除之后能不能重建**：context 每轮都在重建，knowledge 重新检索即可得到同样片段，而 memory 记录的是一次性发生过的经历，删了没有第二个来源。合起来一句话：**可重建的是派生物，不可重建的才是本体。**

**3. 为什么「能不能被丢弃」不是判据？** 〔进阶〕

因为三者都可以被丢弃：context 每一轮都被丢弃重建，memory 里的过期条目**应当**被丢弃，knowledge 检索到的片段用完即弃。可丢弃性是三者共有的现象，用它区分不了任何东西。同样不构成判据的还有「存放的时间长短」（临时状态可能存在磁盘上，跨会话偏好可能常驻在提示里，介质与寿命不对应）和「是否需要检索」（高命中率的程序性规程常驻注入而不检索，但它确实是长期记忆）。

**4. 工作记忆与上下文窗口的区别？混淆之后会得出什么错误结论？** 〔基础〕

工作记忆是本次调用中模型实际可用的那些信息，是**内容**概念；上下文窗口是模型一次能接收的 token 上限，是**容量**参数。一句话判别：能用 token 计量的是窗口，不能的是工作记忆。混淆之后会得出「窗口够大就不用治理」——窗口大只意味着装得下，不意味着模型能同等地用好其中每一部分。

**5. 检索增强与记忆召回的读路径几乎一样，区别在哪？合成一路会出什么问题？** 〔深入〕

区别在**检索目标**：一个找「关于世界的」，一个找「关于你的」。判别方法是问这条内容有没有一个外部的、可追溯的源。合成一路有两种典型故障：**竞争**——用户偏好与领域文档在同一排序里抢名额，而偏好通常更短、与查询字面重叠更少，于是稳定地排在后面被截断；**误改**——知识库文档被记忆更新逻辑当成可覆盖写的条目改掉了，而记忆维护本该只动自己抽取出来的结论。

**6. 系统提示里的规则与程序性记忆是什么关系？** 〔进阶〕

系统提示是**载体**，程序性记忆是**内容类型**。同一条规程可以放在系统提示里、磁盘文件里，或一个按需加载的规则库里——有实现提供四种加载方式（始终注入、按文件模式自动附着、由模型读描述自行判断、仅在被显式引用时加载），四者承载的都是程序性记忆，只是载体与时机不同。混为一谈的代价是：会得出「程序性记忆就是写系统提示」，于是所有规程都往系统提示堆，而它占的是每次调用的固定预算，膨胀后成本上升而遵守率下降；更可惜的是想不到「按路径作用域按需加载」这类做法。**先问是什么类型的知识，再问放在哪个载体上，是两个独立的问题。**

**7. 长期记忆与知识库怎么分？知识库文档与情景记忆又怎么分？** 〔进阶〕

前一组看**内容因人而异还是对所有人一样**，以及来源是交互还是外部权威文档。判别问法：换一个用户这条还成立吗——成立的是知识，不成立的是记忆。把领域文档抽成每个用户各存一份的记忆，会导致文档更新时记忆不跟着更新。后一组看**有没有绑定到具体时间点与具体事件**：文档说「通常如此」，情景记忆说「那次这样」。判别问法：它需要带时间戳吗。把情景记忆当文档用会过度泛化——「上次这个方案不行」变成「这个方案不行」，而它当时不行可能只是因为当时的特定条件。

### 过程推演

**8. 从「模型无状态」出发，三套机制是怎么被依次逼出来的？** 〔进阶〕

第 1 步把历史一起发过去，同段对话有了连续性——注意这里没有任何「记忆」，只有重复发送。第 2 步历史撞上窗口上限，于是每轮重新决定哪些内容值得占名额（挑选、压缩、隔离），**context 成形**。第 3 步换会话仍从零开始，且压缩掉的细节无处可取，于是需要窗口之外的存储加写入、有效性判定与召回，**memory 成形**。第 4 步还有一类前三步都覆盖不到的信息——模型参数里没有的客观领域事实，它不在历史里也不属于任何人的经历，于是需要外部内容的索引与检索，**knowledge 成形**。三者成形于链条的不同位置，这就是它们不能互替的原因。

**9. 会话状态持久化与跨会话记忆存储的隔离维度与要求各是什么？用同一套设施承担会怎样？** 〔进阶〕

前者按**会话**隔离，要求完整、可恢复、可回放，用于会话连续性、人工介入、时间回溯与故障恢复；后者按**主体**（用户或项目）隔离，要求精炼、可召回、可判定有效性。判别问法：换一个会话还要不要它。只做前者换个会话就一无所知，只做后者进程一崩当前任务无法恢复。用同一套设施承担会出现一类隐蔽故障：**为了可恢复而保存了完整历史，跨会话召回时把整段旧对话都捞了回来。**

**10. 排障第一步为什么是打印本次载荷？它能区分哪几种情况？** 〔进阶〕

因为这一个动作能同时区分三种可能：① 那条内容**根本不在载荷里**→ 问题在召回或组装；② 在载荷里但**排得很后或被截断**→ 问题在排序或预算分配；③ 在载荷里、位置也不差但**模型没照做**→ 这不是记忆或知识问题，是指令与提示的问题。跳过这一步直接改检索策略，很可能改的是本来没坏的部件；直接改提示词，则可能在给一个模型看不到的内容加强调。

### 方案设计

**11. 拿到一条信息，该怎么判断它的归属？** 〔深入〕

四个问题依次问：本次任务结束后还有用吗（无 → 只放本次 context）；因人／因项目而异还是对所有人一样（一样且有外部权威源 → knowledge）；移除后能否从别处重新取得（能 → 只留句柄，别存结果）；几乎每次都相关还是只在特定话题下相关。最后一问带出关键的第四个归属：**跨会话存续之后还有一层分叉——高命中率的走常驻注入，特定话题相关的走检索。** 把硬约束放进检索式记忆是个安静的错误：平时都对，只在漏召的那一次出错。另外两条硬规则：用户自己的措辞是最可靠的作用域信号；凭据不进任何持久化机制，判据不是「有没有用」而是「泄露代价」——记忆和知识库都是设计上可被检索出来的。

**12. 三者的失效形态各是什么？按现象怎么定位？** 〔深入〕

memory 是**过期而不自知**（旧结论一直被召回，失败是静默的，输出看起来合理只是前提已不成立）；context 是**该看见的没看见**（存了、检索命中了，但没进载荷）；knowledge 是**覆盖不全或排序失败**（答案不在库里，或在库里排不进前列——两者表面现象一样都是「答不上来」，但一个要补内容一个要调检索）。按现象定位：「换个会话就什么都不知道」→ 跨会话写入路径缺失；「重启后任务接不上」→ 会话状态持久化缺失；「明明存了却不用」→ 召回侧；「答得头头是道但依据是旧的」→ 有效性判定缺失，需要时间与矛盾信号而非更好的嵌入模型；「同一问题两次答得不一样」→ 存在两条矛盾记忆，写入时没做冲突消解；「说过一次的约束后来失效」→ 该约束只存在于对话历史里。一般化的方法是**观察哪几类信息同时出错、哪几类正常**——三套机制的故障通常不同时发生，好与坏的边界往往直接指出坏在哪一套里。

## 工具调用机制 {#tool-calling-mechanics}

对应正文：[工具调用机制](./tools/tool-calling-mechanics.md)。共 18 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。本章覆盖任意一次调用共有的契约、执行、通知、重试与协议问题。

### 概念辨析

**1. 工具与传统 API 的根本区别是什么？** 〔基础〕

区别在调用方。传统 API 的调用方是确定的程序，参数对不上就编译不过；工具的调用方是一个**会看错、会漏参、会在不该用的时候用**的模型。于是描述、参数形状、返回体量、失败信息全都从「接口美学」变成了影响正确率的变量。一句话概括：**工具是写给非确定性调用者的契约。** 直接推论是——需要确定性的地方不要试图把描述写得更严，而应当把那一步交给代码，因为描述再详尽也仍然是概率性的。

**2. 「工具调用」这四个字里，模型实际做了什么？** 〔基础〕

只做了第一步：**产出一个调用请求**。模型读到工具名、描述与参数 schema，输出一段结构化文本声明「我想调用这个、参数是这些」。这段文本本身不执行任何东西，是否执行由宿主决定。把这一步理解成「模型执行了操作」，是后面所有权限误解的根源——正因为模型只是提议方，权限判定才能够、也必须放在它外面。

**3. 为什么工具描述与参数 schema 必须共用一份定义？** 〔进阶〕

因为它同时是**发给模型的说明书**和**执行前的校验器**。两份定义一旦分开维护就会各自漂移，而模型只能看到其中一份，于是出现「模型以为能传、执行器不认」这类错误，且错误信息往往落在最没有诊断价值的位置。共用一份定义不是为了省事，是为了让「模型看到的契约」与「实际被执行的契约」不可能不一致。

**4. 为什么说安全性必须由工具边界实现，而不能靠提示词？** 〔进阶〕

因为要防的正是模型本身被诱导。一个读到了恶意内容的模型不会拦住自己，它会忠实地执行被注入的指令——此时它并没有「故障」。把安全性寄托在系统提示里的一句「不要做危险操作」，等于**让被攻击的对象充当防线**。所以权限门控必须在宿主侧，且必须发生在实际执行之前。

**5. 参数校验失败，应该抛成协议错误还是当作工具执行结果返回？** 〔基础〕

当作**工具执行结果**返回，带上错误标记。规范对这两类错误的划分很明确：协议错误用于「请求结构本身有问题、模型多半修不好」的情形（工具不存在、请求格式非法），而输入校验错误、业务规则错误、下游接口失败属于另一类——它们包含模型可据以自我纠正的可操作反馈，应当以结果内错误标记的形式返回，客户端也应当把它们提供给模型。「出发日期必须在将来，今天是某月某日」这样的信息模型能直接据以改参数；换成一个错误码，它只能放弃。

**6. 既然参数错误要回灌，为什么权限拒绝不能回灌？** 〔进阶〕

因为**模型会自纠，而自纠在这里是负债**。告诉它「这个路径不允许写」，它下一步很可能换个路径；告诉它「这条命令被拒绝了」，它可能换一条等价命令。同一种能力，在参数错误上是资产，在权限边界上变成了绕过边界的动力。判据可以统一成一句：**看模型改了之后还算不算同一次意图**——参数改对了仍是同一次意图，绕过权限已经是另一回事。

**7. 工具声明里的「只读」「幂等」等标注，能不能用来决定要不要放行？** 〔基础〕

不能。规范原文写明这些属性**全部是提示，不保证忠实描述工具行为**，客户端不应基于来自不受信任服务端的标注做工具使用决策；总览页还专门指出工具行为的描述性信息应被视为不可信。原因很直接：标注是服务端自己写的，一个会删库的工具完全可以标成只读。它们可以用来决定界面怎么展示、要不要建议重试，**安全边界只能建在自己这一侧**。顺带记住默认值的方向——未声明时「破坏性」默认为是、「开放世界」默认为是，即沉默被解释为最危险的那一种。

**8. 客户端超时，能不能认为下游没有执行？** 〔基础〕

不能。超时的语义是「我不等了」，不是「它没做」。规范对取消的描述把这层模糊说得很清楚：取消通知可能在请求处理完成之后、甚至响应已经发出之后才到达，双方必须优雅处理这一竞态，服务端在请求已完成时可以直接忽略取消。所以从调用方视角，「已取消」与「已完成」之间存在一段本质上无法消除的模糊区间。

**9. 进度通知和任务句柄，差别只是「一个轻一个重」吗？** 〔进阶〕

不是，分水岭是**能否跨连接存活**。进度事件和最终结果都走这一次请求的响应流，流断了两者都没了；规范允许实现在收到进度通知时重置超时计时，但同时要求始终保留一个最大超时上限。也就是说进度通知能把连接喂活，喂不出无限寿命，更回答不了「客户端进程重启之后结果去哪儿取」。任务句柄才回答这个问题，它的关键约束是持久性——服务端在任务被持久化创建之前不得返回句柄，因此客户端才被建议把任务标识持久化以便崩溃后继续轮询。

**10. 延迟加载工具定义与代码编排调用工具，省的是同一样东西吗？** 〔进阶〕

不是，两者**正交**。延迟加载省的是**工具定义**——把定义这一项的乘数从「可用工具数」降到「本次命中数」；代码编排省的是**中间结果**——多步结果留在执行环境里，只有最终输出回到上下文。把它们当成同一件事的两种做法，就会在瓶颈判断错时投入了复杂度却没换到收益。正确做法是**先看占用构成**：定义占大头上延迟加载，结果占大头上代码编排，两者都大才叠加。

### 过程推演

**11. 为什么「重试 3 次」这种写法经常不产生效果？** 〔进阶〕

因为**重试次数不是一个可以独立设定的参数**。超时是一条自外向内收窄的链：用户可接受的整体等待 ⊃ 本步调用额度 ⊃ 单次尝试上限。重试排布必须落在本步预算之内，所以次数由「预算 ÷（单次上限 + 退避间隔）」反推而来。写死 3 次而不看预算，常见结果是第 2 次尝试刚发出外层就已超时返回，后面的重试永远不会发生。更严重的一种错法是内层预算大于外层——那时内层配置完全不起作用，因为外层总是先放弃。

**12. 退避里的抖动到底解决什么问题？加了它对预算有什么影响？** 〔进阶〕

指数部分与抖动部分目的不同：指数是给下游恢复留时间，**抖动是打散同步**。没有抖动时，同一批并发调用会在同一时刻集体醒来，对刚要缓过来的下游再补一刀。对预算的影响常被忽略：加抖动之后总耗时变成一个**分布而不是定值**，做预算应当按较高分位数而不是期望值算，否则线上总有一部分请求踩在预算之外。

**13. 一批并行工具调用，最容易出的两类错是什么？** 〔进阶〕

其一是**共享状态的并发写**。并行是默认行为，好处是延迟从串行总和降到最大值，但同一批调用可能同时改同一份状态。框架层面的常见做法不是阻止并发，而是要求为可能被并发写入的字段声明归并函数——**强迫开发者显式声明冲突怎么解决**。其二是纯工程性的：结果必须**按调用标识配对**回灌，不能按完成顺序，先完成的不一定是先发出的。

**14. 一次工具调用穿过七道关卡，哪一道最容易被写错？错了会怎样？** 〔深入〕

最容易写错的是**授权判定与结果回灌这两道的边界**，且两种错法都不报错。把授权失败的细节回灌给模型，会得到一个反复换措辞试探边界的循环——每一次都合法返回，没有任何错误日志。把工具结果写成空字符串（而不是可读的错误信息），模型看不出发生了什么，最省事的选择就是把这个工具再调一遍——现象是莫名其妙的重复调用，排查方向却常被引到模型能力上。**这一层的错误几乎都是静默的**，所以必须在设计时就定清楚每一关失败后结果去哪里。

**15. 恢复一个被人工审批中断的流程，为什么可能重复扣款？** 〔深入〕

因为有一类实现的**恢复是重跑而不是续跑**。异常式中断通过抛出特殊异常暂停并保存状态，恢复时运行时**从头重启整个节点**，而非从中断那一行继续——于是写在中断之前的扣款会再执行一次。官方文档为此明确要求中断之前的副作用应当幂等，并给出反例：中断前创建记录会在每次恢复时产生重复记录。派生的两条约束同样反直觉：不要用宽泛的异常捕获包裹中断（会吞掉用于暂停的异常）；同一节点内多个中断的顺序不能变，因为恢复值是**按下标**匹配的，而在节点内用循环反复中断会导致每次恢复重放此前全部轮次。

### 方案设计

**16. 设计一个工具的参数，哪些该让模型填，哪些不该？** 〔进阶〕

判据是一句话：**凡是程序已经知道的值，不要让模型填**。订单号在上一步已经拿到，就不该设计成 `submit_refund(order_id)` 让模型抄一遍，而应当是无参数的 `submit_refund()`，由代码带上。理由不只是省 token——模型抄写标识符会出错，而这类错误往往指向另一个真实存在的对象，于是不报错，只是退错了单。同一条判据的推论是：**总是连着调用的两个工具应当合并**，每少一次往返就少一次填错机会。另外两条配套原则：用枚举与对象结构让非法状态无法表达；参数名要自解释（`user_id` 而非 `user`）。

**17. 一个 Agent 接了几十个工具之后准确率下降，按什么顺序排查与治理？** 〔深入〕

**先量化再动手**。公开数据给出的量级是：五个服务端 58 个工具约占 55K token，某内部场景优化前工具定义占到 134K——这些都是对话开始前就花掉的。准确率侧最常见的两类失败是选错工具与填错参数，尤其在名称相近时；一条公开建议是单轮开始时可用函数尽量少于 20 个（并注明这只是软性建议）。治理按三层推进：**第一层是设计**——不要把接口一对一包装成工具，把编排逻辑放回工具实现里（用 `schedule_event` 而非三个原子工具，用 `search_logs` 而非 `read_logs`），这层收益最大且最常被跳过；第二层按占用构成选延迟加载或代码编排；第三层才是命名空间前缀与描述调优，且前缀式与后缀式的效果因模型而异，必须按自己的评测选。还有一处易被忽略的收益：**延迟加载不破坏前缀缓存**，因为被延迟的定义根本不进入初始提示——反过来，「每轮动态增删工具列表」的实现恰好会让缓存反复失效。

**18. 要把一批工具从进程内改为跨进程提供，协议选型该看什么？** 〔深入〕

看它**把状态放在哪里**，因为这一条决定了其余所有取舍。一条真实的演进主线是从「有状态富功能」走向「无状态可缓存」：取消握手，每个请求自带协议版本与能力；取消会话标识，需要跨调用状态的改为签发**显式句柄**并作为普通工具参数传回；服务端主动发起改为「返回需要补充输入的中间结果、客户端带着信息重试」；长任务移出核心、阻塞取结果改为轮询；流恢复与消息补发直接移除。拆干净之后，缓存与水平扩展这些常规手段才用得上——列表与读取类结果因此能带上存活时长与缓存范围，也才有了「以确定顺序返回工具列表」这条为缓存命中率服务的建议。**代价必须一并接受**：以前协议兜底的续传与推送成了应用层自己的事，重发就要自己处理幂等。选型时可归纳为：**有状态设计的功能上限更高，无状态设计的运维上限更高。** 另外，改成显式句柄会引入一组新责任——每次调用都要校验调用者对该句柄的权限（句柄是名字不是通行证）、标识符保持不透明、保留策略写进创建工具的描述以便模型看见、对过期句柄返回**工具执行错误**好让模型自己重建。

## Agent 工具族 {#agent-tool-families}

对应正文：[Agent 工具族](./tools/agent-tool-families.md)。共 10 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。本章覆盖各族具体工具各自的约束与接口取舍。

### 概念辨析

**1. 「只读」和「安全」是同一件事吗？** 〔进阶〕

不是，它们是两个独立维度。一条纯粹的读命令照样可以读到工作区之外的敏感文件——读取本身不改变外部世界，但信息已经进入上下文，而上下文可能被外泄。所以**路径约束必须独立于读写判定存在**：即便是只读工具，访问允许范围之外的路径时仍然应当触发确认。把「只读」当成「免检」是一类常见的授权过宽。

**2. 词法检索已经能搜代码了，为什么还要语义检索？** 〔进阶〕

因为两者回答的是不同问题，差别不在「更强」而在**答案的来源**：一个是字符串碰巧匹配，一个是经过编译器认定。词法检索会命中注释、字符串与同名变量，也会漏掉别名导入与再导出；语义检索基于符号与作用域分析，能给出定义位置、引用集合、类型签名与调用层级，并在编辑后即时报出类型错误。正确表述是**按问题分流而非替代**：找字符串用词法、找文件名用模式匹配、「这个符号在哪定义／被谁引用」用语义。语义检索需要一个已启动并索引好的语言服务，冷启动与大仓索引都有成本，某些运行环境下根本不可用。

### 过程推演

**3. 六步生命周期里，哪一步是分水岭？为什么「越早拦下越便宜」不是口号？** 〔进阶〕

分水岭是**实际执行**那一步——六步里只有它真正触到外部世界。前三步（模型决策、参数校验、权限门控）都还在本机内，拦下的代价只是一次往返；跨过执行之后，「撤销」不再是丢弃一个请求，而是要执行一个**补偿动作，而补偿动作未必存在**：已发出的邮件、已提交的事务、已付出的款项都没有对称的反向操作。所以这不是效率建议而是可行性约束：能在前三步判断的事情，不要留到执行之后再判断。

**4. 怎么判定一条命令是只读的？难点在哪？** 〔深入〕

规则只有一条——**整条命令的所有环节都是读，整条才算读**；难点全在组合。判定要逐层过：能否被完整解析（解析不出确定结构时唯一安全的处置是不放行，而不是猜一个）→ 有无写重定向（它能把任何读命令变成写）→ 有无命令替换（里面可以藏任意命令，必须在拆分之前识别，否则整个逃过白名单）→ 按管道与逻辑连接拆成子命令 → 逐条查白名单 → 路径是否越界。两个补充：白名单粒度**可以细到子命令级别**，版本控制工具的查询类与推送类子命令风险完全不同，整体放行或整体拒绝都太粗；路径检查独立于读写判定，理由见第 5 题。

**5. Agent 跑一个开发服务器就卡住了，根因是什么？** 〔进阶〕

根因是**把不会结束的服务当成了会结束的命令**，于是「执行 → 等待 → 超时 → 处置」整条链从第一步就选错了路。正解是先做二分：有终点的命令走前台同步执行、带超时、返回退出码与输出；无终点的服务**显式后台启动**，立即拿到句柄，既不等它也不因为超时杀它，靠轮询输出里的就绪标志、探测端口或调健康检查接口来判断可用（都要带重试上限与退避，不能靠固定等待时间）。手工在命令尾部加一个后台符号不算数——进程确实活着，但没有句柄，之后既读不到输出也无法定点停掉。

**6. 命令超时之后应该杀掉还是转后台？** 〔深入〕

两种处置都真实存在于公开实现中，**差别不在优劣，而在「超时」这个信号被解释成了什么**。转后台把超时理解为「不该继续占着前台」：命令继续跑，返回里带上任务标识与输出路径，对「其实还差几秒」的构建最友好，代价是要为后台任务定义清楚的生命周期。直接终止把超时理解为「这条命令本该更快」：资源边界清晰、不留后台状态，坏处是把「慢」和「卡死」当成同一件事，一个只是慢的构建被杀掉后重跑往往还会超时。两处工程细节值得记住：解析不确定的复合命令不适合自动转后台；被转后台的命令里的目录切换不应延续到后续命令，且这件事要显式声明，以免模型基于一个没发生的变更继续操作。

**7. 长网页读不完怎么办？两种读法怎么选？** 〔进阶〕

用**分页续读契约**：返回体带上当前区间与总长度，未读完就以上次的结束位置作为新起点继续。关键是区分两种读法——需要**完整读全文**（转换、重构、逐段整理）必须用分页；只做**定向查找**则用带查询的片段模式，它不保证覆盖全文。把「读全」和「找到」当成同一种读法，是长文档处理里最常见的失败。另有一处容易被忽略的性质：有实现的抓取工具会先把页面交给一个小模型按调用时给出的要求提取，模型收到的是处理后的答案而非原文——**这意味着一次抓取说「页面里没提到某事」，可能只是提取要求里没问这件事**。

### 方案设计

**8. 设计一个文件工具集，拆还是合？判据是什么？** 〔深入〕

不能用「宁窄勿宽」或「尽量合并」任何一条无条件回答，因为两种切分的依据不同。**拆分的依据是权限与并发语义**：读与写必须分开，因为只读工具可免确认、可并行，写工具需审批、要串行；合成一个工具后授权粒度只剩「整体允许」或「整体禁止」，两档都不是想要的，并且失败也无法归因到具体动作。**合并的依据是任务的自然边界**：一个模型需要连续调用三次、且中间结果对它毫无价值的序列应当合成一次调用，因为那些中间结果本来就要占上下文。所以判据是两问：**这些动作的授权方式是否相同？中间结果对模型是否有独立价值？** 两个都为「是」才合并，任一为「否」就拆开。

**9. 精确修改文件时，为什么用字符串锚点而不是行号？** 〔进阶〕

三层理由，一层比一层重要。表层：**行号会漂移**，模型上一次读到的第 42 行在它自己改过一次之后就不是那一行了，而字符串锚点自带上下文校验。中层：**返回体量小**，回填差异比回填整份文件便宜得多。最深一层：**唯一性要求本身是一个断言**——要求锚点唯一命中，等于强迫模型提供足够上下文；命中多处说明它其实没看清代码，此时失败比改错好；命中零次说明文件已变或记忆有误，同样必须失败。换句话说，这条约束真正的作用是**把「模型以为自己看清了」变成可检测的**。配套的「改前必须先读」防的是另一种失真：模型凭记忆重写整个文件，静默丢掉它没看过的部分。

**10. 什么时候才该升级到浏览器操作？先要定下什么？** 〔深入〕

先定下的是**感知方式**，因为它决定了定位方式，而定位方式一旦确定，token 成本、是否需要视觉模型、以及布局变化会不会让操作失效就跟着被确定——这三者不是可以分别优化的独立维度。结构化的无障碍快照给出带引用的语义节点（确定、便宜、不需要视觉模型），截图给出坐标（随视口与布局漂移，需要视觉模型），原始 DOM 给出选择器（体量最大且噪声多）。默认选快照，自绘界面等快照覆盖不到的场景才切到截图，两者也可以组合——快照负责交互、截图负责判断视觉效果。至于**要不要开浏览器**：不构成理由的是「对象是网页」「页面动态渲染」「某次抓取失败了一次」；构成理由的是需要真实交互（多步表单、流程）、需要登录态下的账号动作、或非图形界面手段确已不足而图形界面有一条可验证的直达路径。浏览器慢、贵、脆，能用普通抓取解决就不要开。登录与验证码不是失败，而是需要人完成的一步，应请求接管后回到原路径继续。

## Agent Skills {#skills}

对应正文：[Agent Skills](./tools/skills.md)。共 14 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. Skill 与「把规程写进系统提示」的根本区别在哪？** 〔基础〕

区别不在内容而在**计费时机**。系统提示占的是每一次调用的固定预算，十条规程还能忍，一百条会吃掉大半窗口，而其中九十九条与当下任务无关。Skill 用渐进披露把这份支出拆成三级：元信息（`name` 与 `description`）常驻、正文命中才载入、附属资源再按需读取。所以一句话概括是：**渐进披露省的不是总量，而是把总量从「乘以安装数」改成了「乘以命中数」。**

**2. 「可打包的资料量在实践中没有上限」这个说法成立的前提是什么？** 〔进阶〕

前提很具体：Agent 拥有**文件系统与代码执行能力**，因此「一份文件存在」与「一份文件进入上下文」是两件可以分开的事。未被读取的附件占用为零，脚本被执行而不被阅读、只有输出计费。没有这个前提，三级模型退化成一级，Skill 与「一段长提示词」就没有区别了。把这句话当成无条件成立的营销话术，或当成纯营销话术一概否定，都错在没看前提。

**3. 三级加载各自乘以什么？由此得到哪两条方向相反的结论？** 〔基础〕

元信息乘**已安装技能数**、正文乘**本次命中数**、附件乘**实际读取的文件数**；此外脚本乘执行次数且只有输出占用。元信息单项约百 token，正文建议低于 5000 token——差两个量级，而只有元信息随安装规模增长。两条结论方向相反：**多装技能的边际成本很低，写长正文的边际成本很高。**

**4. 渐进披露是不是意味着「必要指令可以只读一半」？** 〔基础〕

不是。正文是**整体加载**的，规范明确说明决定激活之后会载入整个文件。所以正文里的约束与检查项应当被完整读到；需要拆分的是**可独立使用且很长**的材料，判据是互斥性而不是长度——某些上下文互斥或很少同时用到时，分开路径才省 token。把一段完整的判据切成两半不是渐进披露，是把判据弄坏了。

**5. Skill 与 subagent 都能「让某类任务做得更好」，怎么分？** 〔进阶〕

两者解决的问题不同：subagent 提供**隔离的执行边界**（独立窗口、更严的工具白名单、可并行），Skill 提供**可被任何执行者加载的做法**。判据很直接——如果多个执行者需要同一套做法，那应当写成 Skill 而不是塞进某一个执行者的系统提示，因为后者不可移植。两者可以叠加：subagent 可以使用 Skill；也有实现让技能声明自己在一个派生的独立上下文里运行，正文成为该上下文的任务描述。

**6. 什么时候不该写成 Skill？** 〔进阶〕

四种情形：需要的是一次性临时指示（写成技能会一直生效）；需要的是外部系统访问权（技能不授予任何执行能力，说明写得再完美也无法访问环境里不存在的通道）；需要的是严格确定的执行（指令是概率性的，确定性只能由代码提供，该写成包内脚本或真正的工具）；需要的是对所有人都一样且有权威外部来源的事实（那是知识库的职责，抽成每人各存一份的技能会导致文档更新时技能不跟着更新）。

### 过程推演

**7. 技能确实装着，模型却从不用它。第一排查方向是什么？** 〔进阶〕

不是模型判断力，而是**描述有没有完整进入清单**。多个实现都给这份清单设了字符预算（按窗口比例折算），溢出时不是硬截断而是分级降级：先缩短描述、再整条丢弃，被丢的往往是最少用到的那些。而描述是从**尾部**被截短的，所以用于匹配的关键词可能正好落在被砍掉的那一段里。由此得到的写法约束是具体的：**关键触发词前置**（因为截断从尾部开始）、**边界写清**（同时给出适用与不适用）、**第三人称陈述**（描述会被注入系统提示，视角混乱会干扰发现）。

**8. 同名技能在两个作用域同时存在，哪一个生效？** 〔深入〕

**这个问题没有跨宿主的统一答案，必须逐产品核对**——这本身就是答案的一半。三种真实存在的取法：一是企业覆盖个人、个人覆盖项目，**方向朝外**；二是从当前工作目录逐级向上扫到仓库根再叠加用户与机器层，且同名**不做合并**，两者都可能出现在选择器里；三是取优先级更高者，且同一层级内跨工具通用的别名目录优先于产品专属目录。共识只有两条：作用域是一条**有序链**而非一组平级目录；越靠近具体工作范围的层级越应当只放该范围专属的内容。凭「项目最具体所以最优先」的直觉迁移，会在第一种实现上得到相反结论。

**9. 一个技能的正文被读入之后，会经历哪些轮转？对写法有什么约束？** 〔深入〕

四件事，各自对应一条写法约束。**其一，正文留在历史里且宿主通常不重读该文件**——所以应当长期生效的内容要写成常设指令而不是一次性步骤。**其二，重复调用不必然重复注入**：内容完全相同时只追加一条「已加载」提示，内容不同（参数变了、动态注入产生新输出）则再次追加完整内容——所以带参数调用同一技能会实打实涨两份。**其三，压缩后重新注入但受上限约束**，有实现的口径是每项保留前若干 token、合计有预算、从最近调用者开始填，因此调用过很多技能时较早的可能被整条丢弃；关键在于**截断保留开头**，所以最重要的约束要写在正文前面而不是压在文末的「注意事项」里。**其四，权限不随内容存续**：预授权在下一条用户消息时清除，而指令内容仍在——于是会出现「技能还在指导行为，当初的免审批额度已经没了」这种状态。

**10. 显式点名与隐式匹配的可靠性来源分别是什么？** 〔进阶〕

显式点名（`$名`、`/名`、`/skill:名` 等形态）换取的是**时机的确定性**：不依赖描述匹配，也不依赖模型此刻是否想起来。隐式匹配换取的是使用上的省心，但受两层因素影响——描述写得准不准，以及模型是否真的会去读那个文件（有实现在文档里明确写了「模型并不总是这么做」）。**推论是：对正确性关键的规程不要只依赖隐式匹配。** 三种加固落在不同层次：提到常驻层、改成显式命令、或用 hooks 之类的确定性机制强制。

**11. 一个插件里 `skills` 字段和 `commands` 字段的路径语义有什么陷阱？** 〔深入〕

同一份清单里两种语义并存：`skills` 声明的自定义目录是在默认目录之外**追加**，而 `commands`、`agents`、`outputStyles` 等字段是**替换**默认目录。凭字段名猜会猜错。同一层面还有两条结构约束：清单文件放在专门的清单目录内，而**其余组件目录必须位于插件根**（这是文档专门列为常见错误的一条）；路径可移植性由环境变量承担而不能硬编码绝对路径——插件根、跨更新存活的可写数据目录、项目根各有对应变量，安装位置本身是不确定的。

### 方案设计

**12. 拿到一个「让 Agent 把某类活干对」的需求，怎么判断该写成什么？** 〔深入〕

按排除强度从硬到软逐问，次序不能调换：① **模型此刻能不能触达所需系统**——不能则是连通性缺口，归 tool 或 MCP，写多少指令都补不上一个不存在的通道；② **时机是否必须由人决定**——有副作用且不希望模型自行决定何时执行的，归命令与审批；③ **命中率是否接近 100%**——是则归常驻层（系统提示或每轮重读的指令文件）；④ **内容是否对所有人一样且有权威外部来源**——是则归检索；⑤ **需要的是隔离执行还是可复用做法**——前者 subagent，后者 Skill。把命中率那一问提前，会把「访问不到数据库」误判成「该写一份数据库规程」；把隔离那一问提前，会把本应可复用的做法绑死在某个执行者的提示里。

**13. 团队要让 Agent 按规范查询数据仓库，这件事应该拆到哪几层？** 〔深入〕

四件事落在四个位置：数据仓库的**连接**归 MCP；「查询前必须按日期范围过滤」这条**规程**归 Skill；**表结构**这类对所有人一样的事实放在技能的分域参考文件里按需读取；「不许对生产库跑写操作」这条**硬约束**归常驻层。任何一处顶替另一处都会各自失败一次——尤其是把硬约束交给带匹配环节的机制，它是个**安静的错误**：平时都对，只在漏召的那一次出错，而输出看起来完全合理，只是不符合约定。

**14. 怎么度量一个技能做得好不好？** 〔深入〕

**分开评价选择与执行**，两者故障形态完全不同。选择侧：正例是否被选中，**邻近但不适用的任务是否被正确排除**（第二项常被漏掉，它才是描述边界的检验）；排查时先确认描述是否完整进入清单，再怀疑模型判断力。执行侧：是否完成必要的读取与检查、输出是否满足任务标准而非机械复述步骤，以及**模型是否跟随了正文里的文件引用**（未跟随往往是链接不够醒目，不是模型不愿读）。三条方法论：**评测先于文档**（先在代表性任务上跑一遍找出缺口，据此建三个场景，再增量写技能，避免解决想象出来的问题）；**跨模型测试**（技能是对模型的补充，强模型上的简洁写法可能对小模型信息量不足，反之属过度解释）；**与不用技能的同一任务对比**质量、输出长度与调用成本。最后一条特别容易漏：**版本更新要同时检查描述与正文**——描述宣传旧能力而正文已改成新流程，会造成「选择正确而执行错误」，现象是技能确实被用了但做的事不对，排查方向在这两份内容的不一致上。

## 知识如何进入一次请求 {#knowledge-supply}

对应正文：[知识如何进入一次请求](./knowledge-supply.md)。共 13 题。该篇正文按可独立发布维护，随文自带来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. 各种知识供给方案该按什么维度归类，为什么这个维度比按技术名称列举更有用？** 〔进阶〕

归类维度是：**把知识综合成可用形态这件事发生在什么时候**——训练时（写进权重）、离线索引时（检索召回）、会话开始时（约定文件）、请求进行中（现场读取、接口直连）。这个维度有用是因为时刻一旦定下，新鲜度、维护成本、可溯源性与可承载规模就跟着定了，四者无法同时占满。按技术名称列举只能得到一份清单，按综合时刻归类才能解释**为什么它们不能互相替代**，以及选型时真正在权衡什么。

**2. 窗口从 8K 涨到 1M，为什么这些机制一个都没被淘汰？** 〔进阶〕

因为窗口只放宽了「一次能装多少」这一件事。而现场读取与接口直连解决的是「怎么知道当前值是什么」，检索召回解决的是「语料比窗口大几个数量级怎么办」，写进权重解决的是「怎么让模型的默认行为就符合要求」。这三个问题与容量无关，任何一个被解决其余的依然存在。窗口变大的实际效果只是让约定文件能写得宽松一点。

**3. 「参数化记忆」与「非参数化记忆」这组区分说明了什么？** 〔基础〕

它划出了所有做副本方案的共同结构：**在模型参数之外再建一份可更新、可溯源的记忆**。检索增强方向的出发点正是——事实存在参数里但难以精确访问与操纵，且知识更新与出处溯源是开放问题。由此可推出一条判断：副本会过期、要维护、可能召不回，这些不是某种实现缺陷，而是选择做副本时一并买下的代价。

**4. 为什么说「关系可以被确定性算出来时，不要用相似度去近似它」？** 〔进阶〕

因为相似度是**没有确定性结构可用时的兜底手段，不是默认选项**。代码里最关键的关系——谁定义了什么、谁引用了谁——可以被精确解析出来，用向量距离去猜只会更差。仓库地图这类做法就建立在这一点上：以文件为节点、依赖为边，用图排序挑出与当前对话最相关的部分，只发签名不发实现，几千 token 就能表达整个仓库的形状。判别问法是：这个关系有没有一种能算准的方式。

### 过程推演

**5. 检索增强链路的九个环节，失败在最终输出上是同一种现象。这对排障意味着什么？** 〔深入〕

意味着**排障必须先归因到某一步，不能从「换个更好的嵌入模型」开始**——在归因完成之前，你不知道要换的是不是它。正确内容可能压根没进索引、可能进了没被召回、可能被召回但排在末尾被截断、也可能全都正常而模型没照着答，而使用者报上来的永远只是「它答错了」。最省力的第一个动作是**打印本次实际发出的内容**：它一次就能把组装载荷之前与之后分开——不在载荷里就去查召回与切分，在载荷里而模型没用对就是指令问题。

**6. 切分与向量化的失误为什么被称为「安静的错误」？各自怎么验证？** 〔进阶〕

共同点是**不报错**。切分切在语义中间，一个结论被拆成两半后两半各自都不足以支撑答案，而召回命中其中一半时看起来一切正常；验证方法是把命中片段原样打印，看它是否是一个自足的意思单元。向量化更隐蔽：片段比模型有效窗口更长时，超出部分被静默截断，等于**后半部分从未入库**而日志无异常；验证方法是取一个长片段，用只出现在末尾的独有词去查，看能否命中。

**7. 为什么稠密向量一路不够，必须同时保留词面匹配？** 〔基础〕

因为稠密向量的盲区很具体：**精确标识符**。错误码、版本号、人名、配置键这类串的语义邻域几乎是空的，而它们在真实流量里占比不低。两路融合时常按名次而非分数进行——各路名次越靠前得分越高，好处是不需要调参、也不要求两路分数可比，因为各路的相关性指标本来就不在同一量纲上，强行加权反而要先解决归一化。

**8. 更新了文档却搜出旧内容、删了文档却还能搜到，通常坏在哪里？** 〔进阶〕

几乎总是**派生层**的问题，而不是更新或删除操作本身失败。四层里只有原文是本体，片段、向量、结构关系都是派生副本；只处理本体不处理副本，副本会继续被召回。四条写入路径延迟不同，因此必然存在一段窗口，各层对「当前有效内容是什么」的回答互相矛盾。

**9. 既然四层的写入延迟无法拉平，正确思路是什么？** 〔深入〕

不是靠时序对齐去消除窗口，而是**在查询侧留一道版本过滤**：每个派生单元携带版本标识，查询时强制按当前有效版本筛选。这样做把最坏情况从「拿旧内容当依据」降级为「暂时召不回」。这个降级是关键所在——**后者是使用者能察觉、能重试的失败，前者察觉不到**。可参照的最小实现是维护「文档标识到内容哈希」的映射，标识重复而哈希变了就重新处理并更新，哈希未变则跳过。

### 方案设计

**10. 给一个编码 Agent 做知识供给：建不建索引？** 〔深入〕

不做二选一。先说清分野的来源：**索引是源码某一时刻的快照，而源码一直在变，且漂移不报错**——它表现为搜出来的内容确实存在过，只是已经不是现在这样。所以变更频率与可投入的维护，往往比语料规模更早把结论定下来。中小规模、改动频繁、关键关系可精确解析时先不建，把列目录、按模式匹配、读取片段交给模型；跨仓跨团队、需要「说不出确切词」的语义定位、或要求毫秒级返回时才建。稳定的组合是**轻量结构做高层导航、现场读取做精确验证、检索召回承担规模**——三者失败模式互不重叠，因此互为兜底。补充一点：索引侧也在解决新鲜度，例如用哈希树做增量、只同步哈希有差异的分支，能把漂移窗口压得很小，但压不到零。

**11. 约定文件该写多少？为什么「把重要的都写进去」是错的？** 〔进阶〕

因为这类文件占的是**每一次调用的固定预算**，而代价是双向的：文件过长会消耗更多上下文**并降低遵守度**——成本上升而遵守率下降，两头都输。正确做法是只放必须默认知道的规则、常用命令和知识入口，详细文档放到可按需读取的位置，并尽量按目录或文件类型收窄加载范围。

**12. 为什么编码 Agent 通常采用「约定文件 + 结构地图 + 现场读取」，而不是直接全量向量检索？** 〔深入〕

三者承担的是不同失败模式：约定文件保存每次都必须生效的规则，结构地图用可精确解析的符号和依赖关系负责导航，现场读取回到当前源码取得证据。向量检索适合大规模语料和只能描述意图的查询，但对定义、引用、调用这类确定性关系没有必要，也会引入快照漂移。稳定组合是结构地图指路、现场读取验证、检索索引承担规模。

**13. 一套 Agent 知识库应如何划分规则、资料、当前状态和任务材料？** 〔进阶〕

高频稳定规则进约定文件或目录级规则；代码结构进符号索引和仓库地图；大规模文档与历史资料进词面和向量索引，并维护版本、权限、删除与重建链路；当前状态和精确事实通过工具或接口回源读取；风格、格式和领域用语可以通过提示词或参数内化，但易变事实不进权重；当前需求、设计和临时探索结果只属于任务上下文，任务结束即失效，不应混入长期知识库。

## Agent 扩展机制 {#extensibility}

对应正文：[Agent 扩展机制](./tools/extensibility.md)。共 14 题，顺序与正文的五个环节一致：分类 → 实现 → 时间与空间 → 接入 → 组合 → 能保证什么。

### 概念辨析

**1. 提示词约束与扩展点约束的根本差别是什么？** 〔基础〕

前者是概率性的，后者是确定性的。「提交前必须跑测试」写在系统提示里多数时候有效，偶尔失效，**而且失效时没有任何信号**；写成一个在收尾位置执行的检查脚本，则同一份输入必定得到同一个判定。这条差别是判断一条需求该落在哪一层的源头：凡是「偶尔不生效也能接受」的放提示词，凡是「必须被保证」的放扩展点。

**2. 四类扩展点各自回答什么问题？误判的代价是什么？** 〔基础〕

时间点开洞回答「到了这一刻要不要停下来做点什么」，能力集开洞回答「模型这一轮能看见哪些可调用项」，打包分发开洞回答「一组扩展如何被整体安装与复用」，管控面开洞回答「允不允许」。误判的代价不是效率损失，而是拿一种扩展去解决它结构上解决不了的问题：模型根本连不上那个数据库时，写多少条查询规范的检查都补不上一个不存在的通道；反过来，模型已经能做的事再加一个工具，只是白占上下文预算。

**3. 观察者、责任链、中间件三种组合范式，差别在什么时候才显现？** 〔进阶〕

**装上第二个扩展的时候。** 单个扩展下三者看起来差不多。有第二个之后：观察者互不影响（返回值不参与控制流，加多少个都安全）；责任链按严格程度汇总，任一拒绝即胜出；中间件层层嵌套，前段按注册顺序、后段逆序，顺序本身是语义的一部分。多数「单独测都好好的，装在一起就不对」的问题根源就在这里，排查第一步是先确认该位置采用的是哪种语义。

**4. 责任链语义下，「放行」是不是覆盖？** 〔进阶〕

不是，只是弃权。想用一个扩展去豁免某个动作做不到——只要另有一处投了拒绝票，它就被压过去了。这与配置文件里「后加载的覆盖先加载的」是相反的语义。同理，加载层级上也有实现明确高优先级配置层**不替换**低优先级的 hook，两边的都会跑，因此「在项目层覆盖掉全局层那个碍事的 hook」这个操作并不存在，只能去关掉它。

**5. 「什么时候跑」与「在哪一层配置」是同一个维度吗？** 〔进阶〕

不是，两者互不决定。**配置层级不决定执行顺序**——多个来源的匹配 hook 全部都会运行，高优先级的配置层不替换低优先级的，所以「在项目层覆盖掉全局层那个碍事的 hook」这个操作根本不存在，只能去关掉它。**触发节奏也不决定作用域**——同一个受管层里可以既有每会话事件也有循环内事件。把两个轴混为一谈会得出两类错误预期：以为高层配置能覆盖低层，或以为先注册的就先执行。顺带一提，顺序本身也分体系：中间件里前置按注册序、后置逆序、包裹式层层嵌套，顺序即语义；而 hook 体系里多个同事件处理器**并发启动**，谁也拦不住谁开始，因此写「先 A 后 B」的依赖不成立，需要顺序就得合进同一个处理器。

**6. 沙箱与审批策略的分工是什么？** 〔基础〕

沙箱规定**技术上能做什么**（能写哪里、能否联网），由操作系统机制落实；审批策略规定**什么时候必须先问**（离开沙箱、使用网络、执行受信集合之外的命令）。两者正交：沙箱是能力上限，审批是触发条件。把两者混为一谈会导致一类常见配置错误——以为设了必问就等于设了边界，而实际上使用者点一次同意，动作照样发生。

### 过程推演

**7. 一个 hook 脚本校验不通过就以退出码 1 退出，工具调用会被拦住吗？** 〔进阶〕

**不会。** 多数实现的约定是只有约定的那一个退出码（通常是 2）表示阻断，其余非零码都被当作非阻断错误：宿主记一笔，然后照常执行。Unix 习惯里非零即失败，但这套协议不这么解释。后果相当隐蔽——脚本跑了、报错了、日志里有记录，但它一次也没拦住过任何东西，通常要等到某次事故才发现。推论是一条纪律：**护栏必须被实测过才算数**，真的去执行那条该被拦的命令，确认结果是拒绝而不是「一条错误日志加一次成功执行」。

**8. 同一个阻断码在工具调用前和在本轮收尾上，后果一样吗？** 〔进阶〕

完全不一样，甚至方向相反。工具调用前是「不执行这个动作」；本轮收尾上是「不许停，继续干」——有实现进一步说明这个位置的拒绝不否决该轮，而是把拒绝理由当作一条新的用户提示词让模型续跑。用户输入事件上则是丢弃这条输入。另有一批事件根本不可阻断，返回阻断码只会退化成一条日志。所以必须逐事件查表，不能凭一处行为外推。顺带一提，收尾事件必须靠「是否已因此续跑过」的标志位防止无限循环。

**9. 工具调用后的 hook 返回「拒绝」，刚才写入的文件会回滚吗？** 〔进阶〕

不会。工具已经执行完了，副作用已经落地。有实现明确说明这里的拒绝**不撤销**已完成命令的副作用，实际行为是记录反馈、用这段反馈替换掉原本的工具结果，然后让模型从这段反馈继续。改变的只是模型接下来读到什么。把它当成事务回滚是一类真实的设计错误——文件已经写了，消息已经发了。

**10. 一个外层中间件实现了重试，内层有副作用，会发生什么？** 〔深入〕

副作用发生三次。包裹式 hook 的语义是外层拿到「继续往下走」的句柄，自己决定调用零次、一次或多次；重试就是多次调用。有框架文档专门说明了状态层的处理——外层多次调用句柄时，此前几次调用产生的**状态更新会被丢弃**。关键在于：被丢弃的是状态更新，**不是副作用**。这条是「重试必须放在幂等边界之外」这一通用原则在中间件模型下的具体形态。

**11. 走 HTTP 的策略服务宕机了，它配的策略还生效吗？** 〔深入〕

不生效，而且动作照常执行。有实现明确说明非 2xx 响应、连接失败、超时**一律是非阻断错误**，要阻断必须返回 2xx 加一个带拒绝字段的响应体。这个设计本身是合理的（网络抖动不该把 Agent 卡死），但它意味着策略服务的可用性直接等于策略的有效性。如果这条策略是安全相关的，就必须显式设计失效方向——把它下沉到本地判定或沙箱层，而不是依赖一个可能宕机的远端。对照来看，有实现在自动审批复核上采取了相反的默认：提示构建、复核会话与解析失败一律**失败关闭**，超时单独上报但动作同样不执行。安全机制的默认失败方向应当是拒绝。

### 方案设计

**12. 要保证「Agent 绝不能对生产库执行写操作」，你会怎么落？** 〔深入〕

分层落，并且清楚每一层能保证什么。提示词与模型侧判定是概率性的，只能减少失误，不能作为依据。拦截式扩展与声明式规则是确定性的，但**覆盖面等于宿主已接线的那几条工具路径**——有实现在文档里自述它是「护栏而非完整的强制边界」，因为往往能通过另一条受支持的工具路径完成等价工作，而且绕过时不会有任何信号。所以真正的答案在管控面：**把能力本身拿走**——生产库的凭据根本不在这个执行环境里，或者用沙箱切断出网。一个很好的参照是把凭据的时间窗切开：准备阶段可联网装依赖并持有密钥，Agent 阶段开始前密钥就被移除。**可以用拦截式扩展减少失误，但不能用它防住对手。**

**13. 团队要强制一套 hook，让所有人都必须跑，怎么做？说出哪些做法是无效的。** 〔深入〕

无效的做法是放进项目作用域就以为完事——项目作用域只是「随仓库分发」，任何人都能在本地关掉它，这是个常见误解。有效的做法是走**受管层**：受管来源的 hook 由策略赋予信任、不能从用户侧界面关闭，还可以配置成只允许受管 hook 运行从而屏蔽用户、项目与插件带来的 hook；对称地，受管来源的配置变更通常不可阻断，hook 仍会触发以便审计但阻断决定被忽略。同时要考虑供应链：有实现采用基于内容哈希的信任模型，非受管 hook 必须先审阅并信任那份确切定义，改动即需重新确认，且**插件自带的 hook 不因安装或启用而被信任**。这个设计的价值在于把两个决定分开了——「我安装了它」与「我看过并认可当前这一版」不是一回事。

**14. 跨宿主搬运一份 hook 配置，加载成功且不报错，但某些条目从未执行过。先查什么？** 〔深入〕

先查**处理器类型的支持范围**，而不是查配置语法。有实现明确说明只有命令型处理器当前真正运行，模型评判型与子 Agent 型**被解析但跳过**，异步标记同样被解析但带该标记的处理器直接跳过。同类问题还有字段级的：一批「解析但尚不支持」的字段一旦被返回，宿主会把该次运行标记为失败、报错，**然后继续执行工具调用**——失败方向是放行。一般化的结论是：**格式在跨宿主收敛，宿主行为没有收敛**。加载顺序、冲突消解、可阻断的事件集合、信任语义、有无热重载，都得逐个核对，把某一家的行为当成通则是这个主题上最常见的错误来源。

## Agent 运行时接入 {#integration}

对应正文：[Agent 运行时接入](./runtime/integration.md)。共 13 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。

### 概念辨析

**1. 「该用伪终端还是该用标准输入输出」这个问题为什么无法回答？** 〔基础〕

因为两者不在同一个层面上。标准输入输出与伪终端都属于**传输层**——只管字节怎么流动、消息怎么分帧；而「会话、事件、审批的语义怎么约定」属于**协议层**。同一套协议语义可以跑在标准输入输出上也可以跑在长连接上，同一个标准输入输出通道上也可以跑完全不同的协议。真正的对立发生在层内：伪终端与结构化事件流的差别不是传输方式，而是拿到的是渲染结果还是状态本身。**先确认一个名词回答的是哪一层的问题，再谈它和谁并列。**

**2. 接入相关的名词可以分成哪五层？哪一层与其余全部正交？** 〔基础〕

模型层（一次生成里输入输出什么）、运行时层（循环怎么转、上下文怎么管、动作要不要放行）、协议层（会话与事件与审批的语义）、传输层（字节与分帧）、隔离层（能写哪里、能不能联网、越界要不要问人）。**隔离层与其余四层完全正交**：它不改变任何一条消息的含义，只改变一个动作能不能真的发生，因此可以整层叠加或整层去掉而上面的代码一行不改。这也是它既不能替代审批也不能被审批替代的原因——一个管边界，一个管时机。

**3. 两个方向相反的协议是竞争关系吗？** 〔进阶〕

不是，而且这是最常见的误判之一。方向决定归属：**界面驱动运行时**解决的是建立会话、发出请求、接收流式进展、回答审批；**运行时获取工具**解决的是发现有哪些工具、参数长什么样、怎么鉴权、结果怎么回填。两者解决的问题不重叠，实践中通常同时存在——一个让界面能驱动 Agent，一个让 Agent 能触达外部系统。还有第三个方向是运行时之间的委派：把一个完整运行时包装成可被调用的能力。同一个运行时既可能是被驱动的一方也可能是发起调用的一方，看的是这一次连接里谁在等谁。

**4. 为什么说「审批能力不是协议的一项功能，而是通道方向的推论」？** 〔深入〕

因为授权判断只能由界面前的人给出，所以运行时必须能**反向发问**。一个只支持单向推送的通道无论字段设计得多好，都表达不出「停下来等一个答复」。这一点在公开协议里被做成了结构性安排：运行时侧的基线方法是初始化、新建会话、发送提示，而客户端侧的基线方法只有一个——为工具调用请求用户授权。**审批不是可选扩展，而是客户端必须实现的那一项。** 相应地，一个只对入站请求回「方法不存在」的客户端在简单场景能跑通，但遇到需要授权的动作就会卡死。

**5. 委派文件读写与终端操作给编辑器，换来的是什么？** 〔进阶〕

换来的是**可见性**，不是便利。让编辑器代为读写，运行时才能拿到尚未保存的缓冲区内容，改动也才能以差异视图呈现；让命令跑在编辑器托管的终端里，使用者才能看见并中断它。这两组委派在协议里各自绑定一个能力位，因此属于要显式声明的可选能力——而这也解释了为什么外挂适配器常在这里出现缺口：这些委派要求运行时在决定读写与执行**之前**就把动作交出去，不是外面加一层能补的。

### 过程推演

**6. 这类协议靠什么做到向后兼容？** 〔进阶〕

靠三件事，其中第一件是真正的承载者。**一是能力协商加「缺省即不支持」**：版本号是单个整数、只在破坏性变更时递增，而新增能力**不算**破坏性变更，因此两端必须把初始化消息里未出现的能力一律视为不支持。这条规则让新特性可以随时加进来而老实现不必知道它们存在。**二是版本协商的收敛规则**：客户端发出自己支持的最新版本，运行时支持则回同一个、否则回自己支持的最新版本，客户端不支持时应关闭连接并告知使用者。**三是扩展三件套**：专用字段挂自定义数据、下划线前缀定义自定义方法、初始化时声明自定义能力——三者的共同点是都不占用未来官方可能使用的名字。

**7. 为什么协议要强制绝对路径、并统一行号起点？** 〔基础〕

因为运行时进程的工作目录、编辑器的工作区根、终端的当前目录**三者可能都不相同**，相对路径会产生歧义甚至越界。行号起点若两端各按自己的习惯解释，就会稳定地错开一行——这类错误的特点是不报错、只是位置不对，因此比崩溃更难查。

**8. 解析按行分隔的事件流有哪些必须处理的细节？** 〔进阶〕

四条。**必须按行缓冲**：一次读取可能拿到半行也可能拿到多行，按固定字节切分必错。**要有单行上限保护**：一行可能极长，因为其中可能嵌着大段文件内容。**标准输出只放数据、日志一律走标准错误**——有的协议把这一条写成了硬要求，服务端不得向标准输出写入任何非协议消息。**结尾要刷缓冲**：末行可能没有换行符。另有一条不属于解析但同属这条通道的纪律：命令行选项与事件字段属**弱契约**，升级会变，生产环境要锁版本。

**9. 「审批能力」与「状态精确度」这两个维度为什么排序几乎一致？** 〔深入〕

因为它们由同一件事决定——**通道是不是双向的、拿到的是不是状态本身**。单向事件流拿不到审批，是因为它没有让运行时向界面发问的语法；读屏幕拿不到精确状态，是因为它读的是渲染结果而不是状态。于是选型的第一问不是「哪个更好」，而是**这次接入需不需要中途问人**：需要，就只能在双向那一侧挑；不需要，最省的那一种通常就够。

**10. 只把命令执行放进沙箱，漏洞在哪里？** 〔进阶〕

文件读写工具、外部工具服务、生命周期钩子都在沙箱之外裸跑，因此**不必攻破，绕过就行**：用写文件的工具改一个会被自动加载的脚本、改持续集成配置、改版本控制目录里的钩子，下一次这些文件被执行时就已经在边界之外。正确的粒度是把整个运行时进程连同它的全部工具关进去。相应的补强是把这些位置从可写范围里挖掉——有实现就在工作区可写策略下把版本控制目录与约定的配置目录按只读递归保护，且当版本控制目录是指针文件时，被指向的实际目录同样受保护。

**11. 前缀缓存的失效为什么是「全有全无」的？由此推出什么排列纪律？** 〔深入〕

因为缓存匹配的是**从头开始的连续前缀**，且写入只发生在标记处、哈希是累积的——标记处及其之前任何一个块发生变化，下一次算出的哈希就不同；而读取是向后回看**已经写下的条目**，不是去寻找稳定内容。于是把标记打在每轮都变的块上会得到最坏结果：每次都付一次全新写入，却永远拿不到一次读取，**比不做缓存更贵**。排列纪律由此确定：体积大且会话内不变的工具定义排最前，系统提示与静态示例次之，增长的历史再次之，唯一的动态尾部放最后。往靠前位置注入当前时间、随机标识或每轮刷新的环境信息，一行就能让它之后的全部前缀作废。

### 方案设计

**12. 拿到一个接入需求，按什么顺序做判断？** 〔深入〕

按排除强度逐问，有两处次序不能动。**第一问必须是「会不会执行不可信代码或读入不可信内容」**，因为隔离与其余选择正交，排到后面就会出现「方案都定完了才发现要处理外部仓库」这种返工。**第二问必须是「有没有人在旁边看着并需要中途授权」**，因为它一票否决掉单向通道；反过来先挑通道，很容易在一条单向事件流上拼出一个假的审批。之后才是：无人值守走非交互模式（需要稳定字段就用 Schema 约束产出，成败交给退出码）；有人值守则看对接数量——多界面或多运行时走标准协议（边际成本随对接数量下降），单一运行时且要用到其全部特有能力走厂商协议，有结构化入口走 SDK 或其原生协议，什么都没有才用伪终端兜底、且必须明确告知调用方「状态是推断的」。

**13. 人工介入怎么实现才算真的可用？评估时先问哪两件事？** 〔深入〕

**先问暂停状态存在哪里，再问能否从断点精确恢复。** 因为审批暂停不是界面等待态：运行时必须在精确的中断点把状态持久化，并在拿到决定后从那个点恢复正确的执行线程——少了持久化这一步，所有审批门都是装饰。很多实现能「停」但不能「原地续」，只发停止信号而没有恢复路径的，实际含义是只能重新开始。还有一类形态是「退出再重入」：工具不执行、进程带明确停止原因退出、待处理调用被保留在记录里，由调用方自己收集输入后再恢复——它能工作，但要求调用方保存足以重入的全部信息。最后一条来自「恢复即重放」这个实现性质：节点会被重新执行，所以**中断之前的副作用必须幂等**；推广到接入侧则是 Agent 调用整体不幂等，对策是结构化编辑通道加应用前冲突检测、任务级幂等键、以及只对明确的瞬时错误自动重试。

## Agent 运行时的工程问题 {#runtime-engineering}

对应正文：[Agent 运行时的工程问题](./runtime/engineering-problems.md)。共 14 题。该篇正文按可独立发布维护，自带完整来源清单，因此本章题目的依据以正文内的编号来源为准，不再回指本页的共享参考资料。正文引用的默认值均标注了核验日期，这些数字随版本变化，答题时重点在判断依据而非记住具体数值。

### 概念辨析

**1. 为什么按「谁能判定这次失败」分层，比按严重程度列一张故障清单更有用？** 〔进阶〕

因为平铺的清单推不出应对策略——同样是「失败了」，有的该退避重试，有的重试就是在烧钱，有的连「失败了」这件事都不会被报出来。按判定依据分层得到四层：传输层的信号最硬（状态码就是状态码），执行层的信号仍明确但**带副作用**（失败前可能已经改了文件），状态层的失败在进程活着时根本不可见（只在恢复时暴露），认知层不产生任何错误信号（系统一切正常，只是做错了事）。由此得到一条贯穿性的规律：**自动恢复的能力沿这四层单调递减，把人接回来的必要性单调递增。** 这条规律解释了为什么审批点设在有副作用的动作之前、为什么长任务需要检查点而不只是重试、以及为什么循环检测必须由外部循环做。

**2. 重试为什么是两层而不是一层？两层的失败语义差在哪？** 〔基础〕

差在**失败时已经产出了什么**。传输层的单位是一次 HTTP 请求：连接没建起来、握手失败、返回 5xx——此时什么都没产出，整个请求可以原样重放。流式层的单位是一整条采样流：已经吐出半段内容才断开——此时重放会产生重复内容，续接又需要服务端支持按位置恢复。把两层混成一个数字的后果是**两者相乘才是真实的最坏请求数**：设成 5 和 4，最坏发 20 次，而账单与延迟都在这个乘积上。因此这两个数要和整轮的时间预算一起设，不能各自调到「看起来安全」。

**3. 应用层规则与内核级沙箱，是同一件事的强弱版本吗？** 〔进阶〕

不是，两者互补而非替代。**应用层规则在执行之前判定，依据是命令字符串看起来要做什么**：覆盖面广（能管所有工具，不只是命令行），也是审批与审计的天然入口，但一条命令实际做的事可以超出它名字的暗示，规则就落空了。**内核级沙箱在执行之中拦截，依据是进程实际访问了什么**：对模型选了什么命令完全无感，无论命令叫什么、套了几层脚本，越界的文件访问与网络连接都不会成功，代价是只能覆盖以进程形式执行的东西且平台能力参差。一个覆盖广度，一个兜住深度——把其中任何一个当成另一个的替代品，都会在对方擅长的那一面留下缺口。

**4. 「这个工具有沙箱」为什么不是一句可移植的结论？** 〔进阶〕

因为同一档隔离在不同平台上是**不同的机制**，连依赖前提都不一样。macOS 上用系统自带的策略机制，无额外安装负担；Linux 上两条路线并存——一类用内核访问控制管文件、用系统调用过滤管网络，另一类用命名空间隔离并需要额外的中继工具把流量导向代理，后者在部分发行版上还要先为沙箱程序放开用户命名空间权限，在非特权容器里还会因无法挂载新的进程文件系统而失败；WSL2 沿用 Linux 路线，而 WSL1 因缺少所需内核能力不被支持；Windows 原生是最不成熟的一块。所以这句话必须落到**具体产品、具体平台、具体版本**才有意义。把某一个平台上的实测行为写成产品的通用行为，是这个主题上最常见的错误。

**5. 项目信任与沙箱管的是同一件事吗？** 〔基础〕

不是。项目信任管的是「**加载谁的配置**」——是否读取项目本地的设置、扩展与技能；沙箱管的是「**能碰什么文件、能连什么网络**」。一个 harness 可以有完善的项目信任机制而完全不内置沙箱：默认以启动它的用户权限运行，隔离交给扩展或外层环境。这是一个自洽的取向（刻意保持最小内核、把一切做成可替换组件），但它意味着安全边界必须由部署方另行提供。把项目信任当成隔离边界，是这两个概念最常见的混淆。

### 过程推演

**6. 配额耗尽与瞬时限流可能返回同一个 HTTP 状态码。混为一谈会怎样？正确做法是什么？** 〔进阶〕

后果是**在配额恢复前空耗时间与预算**，而且真正的失败信息还会被最后一次重试的报错盖住。正确做法是维护两组错误分类：一组是可重试的瞬时故障（过载、限流、5xx、各类连接与流中断），一组是不可重试的额度类错误（配额不足、预算耗尽、计费相关），命中后者立刻失败而不进入退避。更进一步的设计原则是：**让错误浮到能够正确分类的那一层，而不是在最底层就被吞掉**——有实现刻意把 SDK 层重试次数默认设为 0，理由正是 SDK 若先把配额类错误重试掉，Agent 层就看不到它，可能一直阻塞到配额窗口重置。底层分不清「这一刻太挤」和「这个月用完了」，而这两者的正确应对完全相反。

**7. 连接是好的、请求总超时也没到，但什么都不来。这类故障靠什么兜住？** 〔进阶〕

靠**空闲看门狗**——距上一个字节到达超过阈值就主动关闭并计入重试。它是独立于连接超时与请求总超时的第三个计时器：连接超时管不到（连接是好的），请求总超时太迟（触发前已经白等了很久）。有意思的是两个实现的默认值都是 5 分钟，但一个把它做成普通可调值，另一个把这个数同时作为**下限**、配得更低会被静默抬回，理由是要容纳扩展思考的长停顿与代理缓冲。后者是把「用户会配错」当成常态来设计：宁可牺牲可配置性，也不要让一个善意的调优把正常的长思考误杀成超时。

**8. 一条命令超时被终止，为什么下一次重试可能以完全不同的方式失败？** 〔基础〕

因为终止父进程不等于终止它派生的子进程。一个启动了后台服务的命令被「终止」后，服务往往还在跑、还占着端口，于是重试撞上的是「端口已被占用」而不是原来的超时。正确做法是终止整个进程组。超时值本身也该分层：一个是模型没指定超时时的默认值（管的是「别让常规命令挂太久」），另一个是模型能请求的上限（管的是「别让模型给自己批一个无限长的额度」）——两者诉求不同，合成一个值必然牺牲其中之一。

**9. 工具输出超量时，为什么「悄悄截断后塞回去」是错的？** 〔进阶〕

因为**截断必须让模型看得见**。一段被悄悄截短的输出，模型会把它当作完整结果来推理——它会确信那个目录里只有它看到的那些文件，并据此做出后续判断。正确形态是落盘并回填摘要与路径，同时明确标注截断了多少。这条约束在压缩场景里同样成立：有实现在序列化待摘要内容时把工具结果截到固定字符数并留下说明截断量的标记，理由很直接——工具结果通常是上下文里最大的贡献者。

**10. 工具调用 → 审批 → 沙箱执行 → 回写 → 检查点这条链路上，哪道缝无法用检查点机制消除？为什么？** 〔深入〕

第 4 步与第 5 步之间：**命令已执行、结果尚未记录**。它无法消除是因为定义上的矛盾——检查点只能记录「已知发生过的事」，而这道缝的定义恰恰是「发生了但尚未被记录」。能做的只有三件：把有副作用的动作尽量做成幂等的，让重放不改变最终状态；把副作用推迟到确认之后，让缝隙落在无副作用的一侧；以及在恢复时**不假设「没记录就是没发生」**，而是回到环境里核对真实状态。第三条最常被略过，也最常导致「恢复之后又执行了一遍」。

**11. 恢复时「重建视图后接着走」与「把执行单元从头再跑一遍」，差别的后果是什么？** 〔深入〕

后者会让**中断前的副作用重复发生**。有框架把「暂停等人」做成执行图里的一等原语——节点中调用中断会抛出特殊异常，运行时捕获后保存状态并等待外部输入，好处是「等人」这段时间可以跨进程存活。但它的恢复语义是节点从头重启而非从中断那一行继续，中断之前的代码会再执行一遍。这不是缺陷而是语义，必须在写代码时就纳入设计：中断前的副作用要幂等、能推迟的放到中断之后、最好把副作用拆到独立节点。还有两个配套的坑——用裸的异常捕获包住中断调用会把它吞掉导致暂停根本不发生；在单个节点里循环调用中断会让每次恢复重放此前全部迭代，造成循环体被指数级重复执行，正确写法是每次节点调用只中断一次、用条件边回环。

**12. 长任务的成本为什么随步数近似平方增长？这对省钱的着力点意味着什么？** 〔进阶〕

因为每一步的输入都包含此前的全部前缀：第 $i$ 步输入约为 $c_0 + d(i-1)$，$n$ 步累计约 $n c_0 + d \cdot n(n-1)/2$，后一项是平方级的。着力点由此确定：**限制步数比限制单步输出有效得多**——砍掉一半单步输出只省那一步的输出费用，砍掉一半步数省的是平方项的四分之三。另外两条推论：缓存节省达不到单价差的倍数，因为每步新增部分与冷启动首步都必须按原价计（单价差是上限不是实际收益）；压缩有一次性成本，它改写前缀因而击穿缓存、需按未命中价重建，收益靠之后的步数摊回，**剩余步数不足时压缩是净亏的**——这说明压缩阈值应由评测集确定而不是拍一个看起来合理的百分比。

### 方案设计

**13. 要把一个本机跑通的 Agent 做成面向多用户的服务，隔离这一维需要重新回答哪些问题？** 〔深入〕

本机 CLI 防的是单机上的越权，多用户服务防的是**租户之间的越界**，是不同层面的问题。至少三处要重新回答：**实例粒度**——沙箱实例须按用户或会话创建与销毁、禁止跨用户复用，否则上一个会话的残留文件会被下一个读到；**凭据位置**——真实的长期凭据不进入沙箱也不进入模型上下文，否则一次密钥泄露就从单会话事故升级为平台级事故；**控制链路**——每一跳都要重新校验调用者与目标沙箱的归属关系，只在入口鉴权一次的设计会让绕过入口的请求直接访问他人沙箱。此外隔离档位本身也要重估：本机场景下操作系统原语通常够用，而执行完全不可信的代码、面向外部用户时，需要走到用户态内核或独立内核那一档，代价是启动延迟与资源占用。

**14. 为一个长任务 Agent 设计可观测性，应该看哪几类指标？混着看会得出什么错误结论？** 〔深入〕

三类，各自回答不同的问题。**执行层**回答「系统有没有正常工作」：各层重试次数与最终失败率、工具超时率、沙箱拒绝次数与被拒对象、压缩触发频次与耗时——特点是有确定判据，可以直接告警。**成本层**回答「这件事值不值」：每任务令牌消耗、缓存命中率（要按输入令牌中走缓存价的比例算，而不是按请求数，因为一个请求里往往既有命中也有未命中）、压缩净收益。**任务层**回答「事情有没有做对」：完成率、人工介入率、变更引发问题的比例——没有自动判据，必须靠评测集与人工核对，而它是唯一能发现「系统一切正常只是做错了事」那类故障的指标。混着看的典型错误：重试率下降可能只是任务变简单了；成本下降可能是压缩太激进、模型丢了关键上下文以致提前放弃。**只有三条线并排看，才能分清「改好了」和「换了种失败方式」。** 配套的纪律是先有轨迹再谈优化——Agent 系统里同一个输入不保证产生同一条执行路径，无法靠重跑复现。

### 速记卡

| 问题 | 落点 |
| --- | --- |
| 故障分层依据 | 谁能判定这次失败；不是严重程度 |
| 四层的走向 | 自动恢复能力递减，人的必要性递增 |
| 重试两层 | 传输层未产出可原样重放／流式层已产出重放即重复 |
| 真实最坏请求数 | 两层次数相乘，账单与延迟都在这个乘积上 |
| 不该重试的错误 | 配额耗尽与瞬时限流常同码，前者立即失败 |
| 错误分类原则 | 让错误浮到能正确分类的那一层 |
| 空闲看门狗 | 连接超时与请求总超时都兜不住「连着但不来」 |
| 超时终止对象 | 整个进程组，不是父进程 |
| 超时两个值 | 默认值管常规命令，上限管模型自批额度 |
| 截断纪律 | 必须让模型看得见，否则残缺被当成完整 |
| 规则 vs 内核 | 执行前按字符串判定／执行中按实际访问拦截；互补 |
| 沙箱可移植性 | 落到产品＋平台＋版本才有意义 |
| 依赖缺失时 | 默认降级对个人友好，对安全门禁是静默缺口 |
| 项目信任 ≠ 沙箱 | 加载谁的配置 vs 能碰什么 |
| 无法消除的缝 | 已执行未记录；检查点在定义上覆盖不到 |
| 绕开缝的三招 | 幂等／副作用后置／恢复时核对真实状态 |
| 恢复语义 | 重建视图接着走 vs 执行单元从头重跑 |
| 落盘粒度 | 写得越少越快，崩溃后回退得越远 |
| 追加式记录 | 半截写入可识别，优于就地覆盖 |
| 恢复的边界 | 覆盖不了它没记录的东西；不是版本控制替代品 |
| 成本增长 | 随步数近似平方；限步数优于限输出 |
| 压缩的代价 | 击穿缓存需重建前缀，剩余步数不足则净亏 |
| 三类指标 | 执行层／成本层／任务层，并排看才分得清 |
