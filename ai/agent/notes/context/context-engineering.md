## 二、Context：决定每一步让模型看见什么

上下文是一次生成中模型实际可用的信息。对话记录、知识库与长期记忆只是来源，只有经过选择、进入本次请求的部分，才构成本次上下文——保存了资料，不等于模型已经看到资料。

工程目标只有一句：找到能最大化目标达成概率的、尽可能小的高信号 token 集合。「最小」不等于「最短」——该给的背景一点不能少，该砍的冗余一点不能留。下面按「由什么构成 → 为什么必须治理 → 会怎样失效 → 能施加哪些操作 → 长程与工程细节 → 怎么度量」逐层展开。

### 上下文的解剖：七个来源，三种性质

上下文不是「用户输入的那段话」，而是采样时被送进模型的全部 token。把它拆成七个来源、按「静态 / 动态 / 累积」归为三类，才谈得上治理哪一部分：静态部分靠一次性写好，动态部分靠召回策略，累积部分靠持续治理，而线上问题绝大多数出在最后一类。

<ContextAnatomy />

组织时还要显式区分意图、观察与推断：用户「希望改成 60 秒」不等于配置「已经是 60 秒」，今天转述的旧结论也可能已经过期。优先使用与问题匹配的当前证据，而不是按时间新旧或多数投票下结论。

### 上下文是有限资源：四个约束

窗口从 8K 涨到 1M，并不意味着可以随便塞。要治理，有四层理由，且第四层最容易被漏掉：

- **注意力预算有限**：$n$ 个 token 要建立约 $n^2$ 对关系，输入越长，注意力越被摊薄，训练数据里的长序列也更少。
- **召回随长度衰减**：「大海捞针」类评测显示召回随长度递减（Context Rot），是性能梯度，而不是到某个长度才断崖。
- **成本与延迟**：输入输出约 100:1，开销几乎全在预填；长输入即使命中缓存，也仍要为传输与预填付费。
- **状态会腐坏**：循环会把错误、冗余、过期与互相矛盾的信息一并沉积下来——窗口大只是「能装」，这一层扩窗口完全不解决。

### 四大操作：Select / Isolate / Compress / Write

把「上下文该怎么管」落成四个可执行动词，每个都能对应具体实现，也都对应特定失效模式。点选任一操作，查看它的手段、主要治哪类失效与代价。

<ContextOperations />

一个可直接引用的判据：如果人类工程师也说不清某情境该用哪个工具，就别指望模型做得更好。这把「工具太多怎么办」从模型能力问题，转回设计质量问题。

### 动态取用：预取、即时与记忆

静态部分写好之后，主要变量就是「这一步该把哪些外部信息拉进来」。两种检索范式各有取舍：

- **预取式**（推理前嵌入检索）：延迟稳定、实现成熟；但索引会过期，切分边界决定信息完整度，代码库一大纯嵌入检索就不可靠，需要配关键词、图谱与重排。
- **即时式**（运行时按需加载）：只在上下文里留轻量标识符（路径、查询、链接），用工具按需取真正需要的数据；贴近人的认知方式，支持渐进式披露，代价是更慢且依赖好的工具与启发式。

标准答案是混合：把变动慢、几乎总要用的（项目说明类文件）预先载入以保证速度，其余交给 `glob` / `grep` 这类原语即时取；法律、金融这类变动慢的领域更偏预取一侧。元数据本身就是信号——`tests/` 下的 `test_utils.py` 与 `src/core_logic/` 下的同名文件含义完全不同，目录、命名与时间戳都在提示该不该读、何时读、以及有多相关。

记忆则分两层：会话内的**草稿本**（计划、进度、中间结论）与跨会话的**长期记忆**（偏好、案例、需长期遵守的规则）。要主动说出的风险是：记忆**召回**比**写入**难得多，能用固定文件承载的就别急着上向量检索——召回本身就是一个新的错误来源。

### 长程任务的策略

当任务的总 token 量必然超出窗口——大型代码库迁移、跨小时的研究——就需要专门策略绕开窗口限制。按任务的时间跨度与可并行度选择，四者也常组合使用。

<ContextStrategyMatrix />

除策略选择之外，还有两条几乎零成本的注意力技巧：

- **复述目标（Recitation）**：把全局计划反复重写到上下文**末尾**（如持续更新 `todo.md` 并勾掉完成项），把目标推进模型的近期注意力范围，缓解「lost-in-the-middle」与目标漂移，且不需要任何架构改动。
- **保留失败证据**：让模型看到失败的动作与随之而来的报错，它会隐式更新先验、降低重犯概率。与中毒的区别在于——留的是真实失败证据，清的是被证伪的结论。

另外，压缩要尽量**可还原**：与其把网页正文不可逆地丢掉，不如丢内容、留引用（URL、文件路径），把文件系统当成结构化的外部记忆。调优心法是先最大化召回、再提升精度，并从最轻的「清理工具原始返回」做起。

### 缓存与成本：最工程的一段

每轮只在尾部追加、前缀高度重复，因此 KV-cache 命中率是生产阶段最重要的单一指标之一——它同时决定延迟与成本。

### 度量与排障：把上下文当成可观测对象

上下文工程是实验科学，可观测性与固定评测集必须先于优化建设，否则无法判断某次改动是帮助还是伤害。该盯的指标分五层：

| 类别 | 指标 | 为什么看它 |
|------|------|-----------|
| 上下文规模 | 每步 token 数、峰值占用、各类内容占比 | 找膨胀大头：通常某一类（多为工具返回值）异常突出，先治它收益最大 |
| 缓存效率 | KV-cache 命中率、首字延迟 | Agent 特有的关键指标；命中率突然下跌通常意味着前缀被改动了 |
| 压缩质量 | 触发次数、关键信息保留率、压缩后失败率 | 压缩是有损操作，必须验证「压完还能不能干成活」 |
| 召回质量 | 命中率、无用召回占比、错召导致的错误数 | Select 的质量；无用召回既花钱又制造混淆 |
| 任务层 | 完成率、平均步数、错误恢复率 | 最终判据：成功率不变而步数与 token 腰斩，才是真正的优化 |

排障按无损优先的顺序推进：

1. 先看轨迹，不要先改 prompt——没有 trace 可观测性时，一切优化都是猜。
2. 按 token 占比排序，找到异常膨胀的那一类，它通常也是失效根源。
3. 用四种失效模式归类症状：反复引用错误结论 → 中毒，忘掉早期目标 → 干扰，工具选错 → 混淆，前后矛盾 → 冲突。
4. 按无损优先的顺序施加操作：先 Select 与 Isolate，再考虑 Compress 与 Write。
5. 单变量实验 + 固定评测集，并把修好的 case 沉淀进评测集做回归守门。

## 三、一句话记忆法

Prompt 问的是「这句话怎么说」，Context 问的是「这一刻该让模型看见什么」。前者是后者的一个组件——写好 prompt 仍是基本功，但决定 Agent 上限的，是你如何治理那个不断膨胀的信息环境：静态部分写好、动态部分召回、累积部分治理；失效先归类（中毒 / 干扰 / 混淆 / 冲突）再选操作（Select → Isolate → Compress → Write，无损优先）；工程上保住 KV-cache（前缀稳定、只追加、确定性序列化），并把度量与评测集摆在优化之前。
