# Context Engineering

Prompt Engineering 关心「怎么问」，Context Engineering 关心「让模型看见什么」。前者是后者的一部分：当应用从一问一答走向在循环里自主调用工具的 Agent，决定成败的主要变量就从单次表达，转移到对进入模型的那组信息的持续策展。

## 一、Prompt Engineering：单次指令的表达

Prompt Engineering 负责把「已经决定要放进来的信息」表达清楚：让模型一次读懂、稳定执行。以下技法按收益与成本之比排序，前三条几乎在所有任务上都成立。

| 技法 | 做法 | 代价 / 边界 |
|------|------|------|
| 结构化分节 | 把背景、指令、工具说明、输出描述拆成独立区块，用 XML 标签或 Markdown 标题分隔，每节只做一件事 | 边界清晰才稳定可解析、好维护 |
| 少样本示例 | 给典型且多样的范例，覆盖主干形态，一图胜千言 | 质量胜于数量；堆砌边界情况无益 |
| 思维链 | 让模型先写推理再给结论，用标签把「思考」与「答案」隔开，便于程序只取结论 | 数学、逻辑、多步判断收益明显；代价是 token 与延迟 |
| 输出契约 | 明确字段、类型、枚举值与「不知道时怎么填」，优先用结构化输出约束 | 不要靠自然语言描述格式 |
| 校准「高度」 | 足够具体以指导行为，又足够灵活以留出启发式 | 过细退化为写死的 if-else，过粗则给不出信号 |
| 最小起步，按失败迭代 | 先用最小 prompt 在最强模型上跑基线，再针对实测暴露的失败补指令和示例 | 不要一上来就写三千字 |

```xml
<instructions>
判断评论情感。先在 <thinking> 中用一句话说明理由，再在 <answer> 中给出结论。
</instructions>

<output_contract>
<answer> 仅允许两个值：POSITIVE 或 NEGATIVE。
</output_contract>

<examples>
<review>这家店服务很快，菜也好吃。</review>
<thinking>明确夸赞服务与菜品。</thinking>
<answer>POSITIVE</answer>

<review>等了四十分钟，还上错菜。</review>
<thinking>等待久且上错菜，是明确的不满。</thinking>
<answer>NEGATIVE</answer>
</examples>
```

## 二、Context 的构成与约束

Context 是一次生成中模型实际可用的信息——不是用户输入的那段话，而是采样时被送进模型的全部 token。对话记录、知识库与长期记忆只是来源，只有经过选择、进入本次请求的部分，才构成当前 Context：保存了资料，不等于模型已经看到资料。

工程目标可以概括为一句话：找到能最大化目标达成概率的、尽可能小的高信号 token 集合。[[22]](../references.md#source-anthropic-context)「最小」不等于「最短」——必要的背景不可缺省，冗余的内容也不应保留。

### 四个约束：为什么必须治理

窗口容量从 8K 增长到 1M，并不意味着可以不加选择地填充。治理的必要性有四层理由，其中第四层最容易被忽略：

- **注意力预算有限**：$n$ 个 token 要建立约 $n^2$ 对关系，输入越长，注意力越被摊薄，训练数据里的长序列也更少。[[22]](../references.md#source-anthropic-context)
- **召回随长度衰减**：「大海捞针」类评测显示召回随长度递减（Context Rot），表现为性能梯度，而非到某一长度才出现断崖。[[22]](../references.md#source-anthropic-context)
- **成本与延迟**：输入输出约 100:1，开销几乎全在预填；长输入即使命中缓存，也仍要为传输与预填付费。[[79]](../references.md#source-manus-context)
- **状态会腐坏**：循环会把错误、冗余、过期与互相矛盾的信息一并沉积下来——窗口容量只决定「能装多少」，这一层扩大窗口完全无法解决。[[78]](../references.md#source-breunig-longctx)

前两层约束意味着：加入低信号材料会同时消耗长度与注意力，使有效信号在中途见顶。下面的推演可以通过调参观察这一现象。

### 四种失效模式

即便仍在窗口容量以内，选择不当也会使 Agent 逐步偏离目标。按类型定位失效，比笼统归因于模型能力更具可操作性（分类源自 Drew Breunig）。[[78]](../references.md#source-breunig-longctx)

| 模式 | 表现 | 应对 |
|------|------|------|
| 上下文中毒（Poisoning） | 幻觉或错误被反复当作事实引用，误差在迭代中放大 | 校验工具输出，区分「已验证事实」与「模型猜测」；裁剪被证伪的信息，但保留失败记录本身作为纠错证据 |
| 上下文干扰（Distraction） | 历史过长时过度复述既有轨迹，忽略通用判断 | 未满也主动总结与修剪，周期性把目标与约束重述到最近位置 |
| 上下文混淆（Confusion） | 冗余内容被当作依据取用，最常见是工具过多、功能重叠导致选错 | 裁出最小、不重叠的工具集；人也说不清何时该用的两个工具，应合并或删去一个 |
| 上下文冲突（Clash） | 新信息与既有内容直接矛盾，早期错误尝试持续拖累后续推理 | 需求尽量一次给全；口径变更时显式声明「以下取代此前的 X」，必要时另开会话 |

## 三、可施加的操作

### 四大操作：Select / Isolate / Compress / Write

把 Context 治理落成四个可执行动词。它们不是并列备选，而有推荐次序——前两步基本无损，后两步有损或有额外成本。很多团队一上来就做摘要，反而丢了「当时看着不重要、后来才致命」的信息。[[80]](../references.md#source-langchain-context)

| 操作 | 做什么 | 主要手段 | 代价与适用 |
|------|------|------|------|
| **Select** 挑进来 | 每步只把当下需要的信息拉进窗口 | 记忆选择性召回；工具描述检索；RAG（AST 切分 + 关键词 + 图谱 + 重排）；state 按需暴露字段 | 治混淆；基本无损，但召回本身会出错 |
| **Isolate** 隔开来 | 拆开 Context，不让所有东西挤在一个窗口互相干扰 | 子 Agent 独立窗口只回传结论；沙箱里大对象留作变量；state schema 分字段隔离 | 治冲突、混淆；无损，token 与协调复杂度上升 |
| **Compress** 压下去 | 把历史压成更短的等价表示 | 摘要（整轨迹 / 局部 / 交接边界）；裁剪旧消息；工具结果清理（最轻的一档） | 治干扰、成本；有损，可能丢掉后来才显重要的细节 |
| **Write** 写出去 | 存到窗口之外，需要时再读回来 | 会话内草稿本；跨会话长期记忆；文件系统作为外部记忆 | 治干扰、容量；额外读写往返，需设计何时写、何时读 |

由此得到一条判断工具集质量的经验规则：如果人类工程师也无法说清某情境该用哪个工具，模型同样无法做出正确选择。[[22]](../references.md#source-anthropic-context)这把「工具过多」从模型能力问题，转回设计质量问题。

### 动态取用：预取、即时与记忆

静态部分确定之后，主要变量就是「这一步应把哪些外部信息纳入 Context」。两种检索范式各有取舍：

- **预取式**（推理前嵌入检索）：延迟稳定、实现成熟；但索引会过期，切分边界决定信息完整度，代码库规模增大后纯嵌入检索不再可靠，需要配合关键词、图谱与重排。[[80]](../references.md#source-langchain-context)
- **即时式**（运行时按需加载）：只在 Context 里保留轻量标识符（路径、查询、链接），用工具按需获取真正需要的数据；接近人的认知方式，支持渐进式披露，代价是延迟更高且依赖工具设计与启发式规则的质量。[[22]](../references.md#source-anthropic-context)

实践中通常采用混合方案：

- 变动缓慢、几乎每次都要用的内容（如项目说明类文件）预先载入，保证延迟稳定；其余交给 `glob` / `grep` 这类原语即时获取；法律、金融等语料稳定的领域更偏向预取一侧。
- 元数据本身即信号——`tests/` 下的 `test_utils.py` 与 `src/core_logic/` 下的同名文件含义完全不同，目录、命名与时间戳都在提示是否该读、何时读、相关程度。

记忆分两层：会话内的**草稿本**（计划、进度、中间结论）与跨会话的**长期记忆**（偏好、案例、需长期遵守的规则）。[[80]](../references.md#source-langchain-context)值得强调的风险是：记忆的**召回**远比**写入**困难，能用固定文件承载的内容不必急于引入向量检索——召回本身就构成一个新的错误来源。

## 四、长程任务

当任务的总 token 量必然超出窗口容量——大型代码库迁移、跨小时的研究——逐步操作已不足够，需要专门策略绕开窗口限制。按任务的时间跨度与可并行度选择，四者也常组合使用：[[22]](../references.md#source-anthropic-context)

| 策略 | 做法 | 适合 |
|------|------|------|
| 压缩 | 把历史交给模型总结，保留决策、未解 bug 与实现细节，丢弃冗余工具原文 | 需要大量往返的长对话流 |
| 结构化笔记 | 把要点写到窗口之外的持久文件（待办、NOTES.md），需要时读回 | 有清晰里程碑的迭代开发 |
| 子代理 | 主代理持高层计划，子代理以干净窗口深挖后只回传提炼结论 | 可并行拆分的探索与研究 |
| 即时检索 | 只保留轻量标识符（路径、查询、链接），运行时按需加载正文 | 语料庞大、内容多变、依赖元数据线索 |

### 四条注意力与信息保全技巧

策略之外，还有四条几乎不需要架构改动、但在生产环境收益明显的做法。它们都来自同一个观察：模型只按当前 Context 所呈现的样子行动，「呈现什么、以什么形式呈现」本身就构成控制手段。[[79]](../references.md#source-manus-context)

- **复述目标（Recitation）**：把全局计划反复重写到 Context **末尾**（如持续更新 `todo.md` 并勾掉完成项），使目标进入模型的近期注意力范围，缓解「lost-in-the-middle」与目标漂移。在平均约 50 次工具调用的任务中，早期目标距当前位置已经很远，复述相当于用自然语言重新加权。
- **保留失败证据**：让模型看到失败的动作与随之产生的报错，它会隐式更新先验、降低重复犯错的概率。清理轨迹、静默重试看起来更整洁，代价是抹去了唯一能让模型适应的证据。与中毒的区别在于：保留的是真实发生的失败证据，清除的是已被证伪的结论。
- **文件系统即外部记忆**：单次观测（网页正文、PDF、大日志）本身就可能超出窗口容量，而任何不可还原的压缩都有风险——无法预知第 10 步丢弃的观测是否会在第 30 步变得关键。解法是让压缩尽量**可还原**：网页正文可以丢弃，只要保留 URL；文档内容可以省略，只要沙箱中仍有路径。调优次序是先最大化召回、再提升精度，并从代价最低的「清理工具原始返回」做起。
- **破除模式化（不要把自己 few-shot 进套路）**：Context 塞满高度相似的「动作—观测」对时，模型会延续机械节奏，即使该模式已不再最优——批量处理同类材料时最容易出现漂移、过度泛化甚至幻觉。对策是主动引入**受控**的多样性：变换序列化模板、替换等价措辞、在顺序与格式上加少量扰动。它同时给第一章的 few-shot 划定了边界：堆砌同质样例只会让模型更脆弱。

## 五、缓存、成本与度量

### 缓存与成本

每轮只在尾部追加、前缀高度重复，因此 KV-cache 命中率是生产阶段最重要的单一指标之一——它同时决定延迟与成本。[[79]](../references.md#source-manus-context)以 Claude Sonnet 某一时点公开报价为例，命中与未命中缓存的输入单价约为 \$0.30 与 \$3.00 / 百万 token，相差一个数量级；加上输入输出约 100:1、开销几乎全在预填，前缀是否稳定直接决定账单规模。缓存与窗口的基础机制见[模型交互](../model/llm-api.md#cache)，Context 侧的治理动作有三条：

- **前缀必须稳定**：自回归下一个 token 的差异，就会让该位置之后的缓存全部失效。最典型的错误是把精确到秒的时间戳放进系统提示开头。
- **Context 只追加**：不回改此前的动作与观测，并确保 JSON 序列化键序确定——很多库不保证键序稳定，会静默击穿缓存。
- **必要时显式标断点**：不支持自动增量前缀缓存时手动插入缓存断点，至少覆盖到系统提示末尾；自托管还要开启前缀缓存并用会话 ID 稳定路由。

工具集变更要**遮蔽，而不是删除**：工具定义位于 Context 最前部，中途增删会让其后所有动作与观测的缓存失效，还会因历史里引用了已消失的工具而制造冲突。正确做法是保留定义不变，用状态机在解码时遮蔽 logits 控制可用性，并配合统一的工具名前缀（如 `browser_`、`shell_`）按组启停。

单价的量级差异会随步数放大：累积部分单调增长，每一步都要为此前全部前缀付费，因此差距并非恒定的十倍，而是随轨迹延长持续扩大。下面按可复现口径推演一条 50 步轨迹的累计输入成本。

### 度量与排障

Context Engineering 是实验科学，可观测性与固定评测集必须先于优化建设，否则无法判断某次改动是改善还是损害。[[80]](../references.md#source-langchain-context)需要关注的指标分五层：

| 类别 | 指标 | 观测目的 |
|------|------|-----------|
| Context 规模 | 每步 token 数、峰值占用、各类内容占比 | 定位膨胀主因：通常某一类（多为工具返回值）异常突出，优先治理它收益最大 |
| 缓存效率 | KV-cache 命中率、首字延迟 | Agent 特有的关键指标；命中率骤降通常意味着前缀被改动 |
| 压缩质量 | 触发次数、关键信息保留率、压缩后失败率 | 压缩是有损操作，必须验证压缩后任务仍能完成 |
| 召回质量 | 命中率、无用召回占比、错召导致的错误数 | 反映 Select 的质量；无用召回既增加成本又制造混淆 |
| 任务层 | 完成率、平均步数、错误恢复率 | 最终依据：完成率不变而步数与 token 显著下降，才是真正的优化 |

排障的推进顺序：

1. 先检查轨迹，而非直接修改 prompt——缺少 trace 时，一切优化都只是猜测。
2. 按 token 占比排序，找出异常膨胀的类别，它通常也是失效根源。
3. 用四种失效模式归类症状：反复引用错误结论对应中毒，遗忘早期目标对应干扰，工具选错对应混淆，前后矛盾对应冲突。
4. 按无损优先施加操作：先 Select 与 Isolate，再考虑 Compress 与 Write。
5. 采用单变量实验与固定评测集，并把修复的样例沉淀进评测集作为回归守门。

## 六、小结

- **三类来源，三种治法**：静态部分（系统提示、工具定义、示例）靠一次性写好，动态部分（检索、记忆）靠召回策略，累积部分（历史、工具返回值）靠持续治理；线上问题绝大多数出在累积部分。
- **四个约束，扩窗口只能缓解三个**：注意力预算、召回衰减、成本与延迟都随窗口增大而改善，状态腐坏不会——它是循环本身的产物。
- **操作按信息损失排序**：Select → Isolate → Compress → Write，先无损后有损；长程任务在此之上还要复述目标、保留失败证据、外置可还原状态，并以受控变化避免模式化。
- **缓存与度量收口**：前缀稳定、只追加、确定性序列化决定 KV-cache 命中率；改动是否有效，只能由固定评测集判定。
