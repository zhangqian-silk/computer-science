# memory、context 与 knowledge 的边界

这三个词经常被换着用，而它们指的是三套不同的机制：解决的问题不同、本体存放的位置不同、读写路径不同、寿命不同，出问题之后该去哪里查也不同。混着用的代价不在术语层面——**它会让人在错误的层里排障**：明明是召回没进载荷，却去调抽取逻辑；明明是知识库覆盖不全，却去加长期记忆。

本文不从定义出发，因为定义是这三个词最不可靠的部分。起点是一个无争议的事实：**模型每一次调用都是无状态的。** 顺着它往下推，三套机制是被依次逼出来的，而不是被人为划分出来的——这条推导链本身就解释了它们为什么不能互相替代。推导之后是两条可直接使用的判据、六组易混对象的辨析、「拿到一条信息该放进哪一套」的归属判断，以及三者各自的失效形态与排障入口。文中只预设一点背景：上下文窗口是模型一次调用能接收的信息上限。

---

## 一、从无状态出发：三套机制是怎么被逼出来的

把一次模型调用看成一个纯函数：输入一段内容，输出一段内容。它没有任何跨调用保存信息的地方——**上一次调用结束后，除了那段输出文本，什么都没有留下**。

所以「这个 Agent 记得我」不可能是模型的性质。任何形式的连续性都必须由模型之外的机制提供。现在从零开始，每一步只加一件事，看需求是怎么被逐个逼出来的。

<MemoryGenesisSteps />

这条链的每一步都由上一步的「还剩什么没解决」驱动：

**第 1 步：把历史一起发过去。** 想让第二次调用知道第一次说了什么，唯一的办法是重新发送。这就是多轮对话的全部机制——不是模型记住了，而是每次都重发一遍。这一点值得强调，因为它是很多误解的源头：**多轮对话里没有任何「记忆」，只有重复发送。**

**第 2 步：治理这一次要发什么。** 历史随轮次单调增长，迟早撞上**上下文窗口**——模型一次调用能接收的信息上限。于是需要每一轮重新决定哪些内容值得占用本次的名额——挑选、压缩、隔离。**到这一步，context 作为一套独立机制成形了**：它管的是「本次让模型看见什么」。

**第 3 步：把该留的写到窗口之外。** 上一步解决了长会话，但换一个会话仍然从零开始，而且被压缩掉的细节没有别处可取。于是需要一套窗口之外的存储：写入、判定有效性、按需召回。**memory 成形了**：它管的是「跨越多次调用的经历如何存续」。

**第 4 步：把外部权威内容接进来。** 还有一类信息前三步都覆盖不到：模型参数里没有的客观领域事实。它不在历史里，也不属于任何用户的经历——某个框架新版本的接口变更，无论这个用户经历过什么都不会自动知道。于是需要外部内容的索引与检索。这个方向有明确的研究起点：把预训练模型的**参数化记忆**与一个可检索的**非参数化记忆**结合起来，后者是外部文档的稠密向量索引，从而使知识可被更新、生成可被溯源[[1]](#ref-1)。**knowledge 成形了。**

推导到此结束，三套机制都在了。而它们成形于链条上的不同位置，这就是它们不能互相替代的原因：

- context 回答的是「**这一次**让模型看见什么」；
- memory 回答的是「跨越**多次调用**的经历如何存续」；
- knowledge 回答的是「参数里**没有**的客观事实从哪来」。

扩大窗口只能缓解第 2 步的压力，对第 3、4 步毫无帮助；接一个知识库解决了第 4 步，第 3 步依然缺失。**这三个问题彼此独立，任一个解决了，另两个依然存在。**

## 二、三套机制的正面对照

推导给出了各自的职责，下面把它们放在一起逐维度对照。排布上刻意把 context 放在中间——另两者都必须经由「进入 context」这一步才能影响输出。

<MemoryContextBoundary />

对照里有一行值得单独拎出来：**「本体存放在哪」**。memory 与 knowledge 都能回答这个问题——记忆存储、文档索引；只有 context 的答案是「就是它自己」。这个不对称不是措辞巧合，两条判据正由它而来。

另有两行的差异容易被低估：

**一致性要求。** memory 需要 Agent 自己维护一致性——同一事实只应有一个当前有效值，矛盾必须被消解。knowledge 不需要：它的一致性由内容生产方保证，是别人的责任。这个差别直接决定了写入路径的复杂度：memory 的写入必须先检索候选、判断是否冲突，knowledge 的写入就是文档发布流程。

**失效形态。** 三者的典型故障完全不同：memory 是「过期而不自知」，context 是「该看见的没看见」，knowledge 是「召回错片段或覆盖不全」。这一行是全文排障部分的基础。

## 三、两条判据

从上面的对照可以提炼两条判据。它们的好处是**都能在几秒内回答，且不需要先记住任何术语定义**。

### 判据一：本体在 context 之内还是之外

memory 与 knowledge 的本体都在 context 之外——记忆存储、文档库。它们进入 context 只是一次投影，投影出来的那份副本不是本体：删掉它，本体还在；改掉它，本体不变。

context 没有「本体在别处」这回事。它就是本次调用的信息集合，每一轮由组装逻辑现场拼装。

这条判据的实际用途是**判断该在哪里施加变更**。想让某个约束长期生效，就不能只在 context 里做——那份内容下一轮就被重新组装了。想修正一条错误的记忆，改召回结果没有意义，得改存储里的本体。

### 判据二：移除之后能不能重建

- **context 能重建**，而且每一轮都在重建。
- **knowledge 能重建**：文档还在，重新检索一次就得到同样的片段。
- **memory 不能重建**：它记录的是一次性发生过的经历。「上次试过这个方案，压测下反而更慢」——这条删掉之后没有第二个来源，重新做一次压测的代价与当初一样。

所以第二条判据可以更简洁地表述：**可重建的是派生物，不可重建的才是本体。** 这也解释了为什么 memory 的删除需要格外谨慎，而 context 的丢弃可以毫无顾虑：前者可能是唯一副本。

### 「能不能被丢弃」不是判据

这一点需要明确否定，因为它是最常见的错误判据。

三者都可以被丢弃：context 每一轮都被丢弃重建；memory 里的过期条目**应当**被丢弃；knowledge 检索到的片段用完即弃。可丢弃性是三者共有的现象，**用它区分不了任何东西**。

同样不构成判据的还有两个：「**存放的时间长短**」——一条只在本次任务内有效的临时状态可能存在磁盘上，一条跨会话的偏好可能常驻在提示里，存放介质与寿命不对应；以及「**是否需要检索**」——高命中率的程序性规程通常常驻注入而不检索，但它确实是长期记忆。

## 四、六组容易混为一谈的对象

有了判据，可以处理具体的混淆。下面六组是实践中反复出现的，每组的区分依据都不同——这本身就是要点。

<MemoryDisambiguation />

其中三组值得再展开几句，因为它们的代价最隐蔽。

### 检索增强与记忆召回

两者的读路径几乎一样：把查询转成向量、排序、截断、拼进上下文。代码写出来能有八成相似。区别在**检索目标**：一个找「关于世界的」，一个找「关于你的」。

实现上合成一路会出现两种典型故障。**一是竞争**：用户偏好与领域文档在同一个排序里抢名额，而偏好通常比文档片段短、与查询的字面重叠也更少，于是稳定地排在后面被截断。**二是误改**：知识库文档被记忆更新逻辑当成可覆盖写的条目改掉了——记忆维护逻辑本该改的是自己抽取出来的结论，不该动外部文档。

判别方法：问这条内容有没有一个外部的、可追溯的源。有的走检索增强，没有的走记忆召回。

### 系统提示里的规则与程序性记忆

这一组的混淆最微妙，因为它把**载体**和**内容类型**当成了一回事。

系统提示是载体，程序性记忆是内容类型。同一条规程可以放在系统提示里，也可以放在磁盘文件里，也可以放进一个按需加载的规则库里。有实现提供了四种加载方式——始终注入、按文件模式自动附着、由模型读描述自行判断是否拉取、仅在被显式引用时加载[[2]](#ref-2)——四者承载的都是程序性记忆，只是载体与加载时机不同。

把两者混为一谈的代价是：会得出「程序性记忆就是写系统提示」的结论，于是所有规程都往系统提示里堆。而系统提示占的是**每一次调用的固定预算**，膨胀之后成本上升而遵守率反而下降——有实现明确建议控制指令文件的长度，理由正是过长会消耗更多上下文并降低遵守度[[3]](#ref-3)。更可惜的是，混淆之后想不到「规程可以按文件路径作用域按需加载」这类做法：**先问这是什么类型的知识，再问放在哪个载体上，是两个独立的问题。**

### 会话状态持久化与跨会话记忆存储

这一组的区分有明确的框架依据。有实现把两者做成两套并列的设施：**检查点**保存单个线程的状态快照，用于会话连续性、人工介入、时间回溯与故障恢复；**存储**保存图状态之外的应用数据，用于跨线程的长期记忆如用户偏好与共享知识[[4]](#ref-4)。

它们的隔离维度不同（一个按会话，一个按主体），要求也不同：会话状态要**完整、可恢复、可回放**，跨会话记忆要**精炼、可召回、可判定有效性**。只做前者，换个会话就一无所知；只做后者，进程一崩当前任务无法恢复。而更隐蔽的错误是用同一套设施承担两件事——为了可恢复而保存了完整历史，跨会话召回时把整段旧对话都捞了回来。

这段区分有过一次代价不小的历史验证。早期框架把记忆抽象成一组对话缓冲区（保留最近 n 轮、保留 n 个 token、滚动摘要），这批抽象后来被整体弃用，公开理由是：缺少对多用户多会话的内建支持，而这是真实应用的典型要求；无法在任意时点保存与恢复，因此做不了错误恢复、人工介入与分支探索；早期实现未面向新式对话接口设计，在工具调用等特性上出问题[[5]](#ref-5)。三条指向同一个根源：**「保留最近几轮对话」夹在两者中间，哪一头都不到位**——它在丢弃内容，所以承担不了「完整可恢复」；它按会话组织且保留的是原始对话而非提炼的结论，所以也承担不了「跨会话可召回」。

## 五、拿到一条信息，该放进哪一套

前面都是辨析，这一节给可操作的归属判断。

<MemoryRoutingDecision />

样例里出现了四个归属而不是三个，因为「跨会话存续」之后还有一层分叉：**是常驻注入，还是进检索**。

判据是命中率。「提交前跑 check」这类团队约定几乎每次都相关，而检索总有漏召的概率——漏一次就出错，且输出看起来完全合理，只是不符合约定。所以**高命中率的硬约束应当常驻，而不是放进检索式记忆赌它每次都被召回**。这是一个安静的错误：它平时都对，只在漏召的那一次出错，而那一次很难被发现。

反过来，只在特定话题下相关的内容不该常驻——它每一轮都占预算，而绝大多数轮次里毫无用处。

归属判断里还有两条值得单独记住：

**用户自己的措辞是最可靠的作用域信号。** 「这次」「临时」「先」对应一次性，「一直」「都」「以后」「更喜欢」对应长期。这些词比任何启发式规则都准，因为它们就是用户在直接表达作用域。把「这次简短点」记成长期偏好，用户此后一直得到简短回答，而且不知道该去哪里改。

**凭据不进任何持久化机制。** 判据不是「有没有用」而是「泄露代价」——记忆和知识库都是设计上可被检索出来的，凡是写进去的都要假定会被读回。有实现明确提示不要在记忆中存放密钥或未脱敏的个人数据，正因为它们按设计可被检索[[6]](#ref-6)。

## 六、失效形态与排障方向

这一节是全文最实用的部分。三套机制的故障现象不同，排障入口也不同，弄错了会在一个本来没坏的部件上花很长时间。

### 三种失效各是什么样

**memory 的典型失效是「过期而不自知」。** 旧结论一直被召回，没有任何机制告诉系统它已经假了。这类失败是**静默**的：输出看起来完全合理，只是基于一个已经不成立的前提。「部署脚本有 bug，需要手动执行 step 3」——脚本早修好了，而这条记忆与「部署要注意什么」这个查询高度相关，相似度检索会稳定地把它排在前面。根源在于**相似度衡量的是「像不像」，而「还成不成立」是另一个维度，向量空间里没有编码这个信息**：所以无论嵌入模型多好，纯相似度检索都治不了过期记忆，必须另外引入时间、来源、矛盾检测这些信号。

**context 的典型失效是「该看见的没看见」。** 存储里有、检索也命中了，但没进入本次载荷——被预算截断、被排序压后、或者组装逻辑根本没把这一路接进来。

**knowledge 的典型失效有两种形态：** 覆盖不全（答案不在库里）与排序失败（在库里却排不进前列）。这两者的处置完全不同：前者要补内容，后者要调检索——而它们的表面现象一样，都是「答不上来」。

### 排障第一步永远是打印本次载荷

无论现象是什么，第一个动作应当是**打印本次请求实际发出的内容**。理由是这一个动作能同时区分三种可能：

1. **那条内容根本不在载荷里** → 问题在召回或组装，去查检索与预算。
2. **在载荷里但排得很后／被截断** → 问题在排序或预算分配。
3. **在载荷里、位置也不差，模型没照做** → 这不是记忆或知识问题，是指令与提示的问题。

跳过这一步直接改检索策略，很可能改的是一个本来没坏的部件；直接改提示词，则可能在给一个模型看不到的内容加强调。

### 按现象定位

- **「换个会话就什么都不知道了」** → 跨会话记忆的写入路径缺失。注意这一道**必须显式设计**，没有任何机制会自动把会话里值得记的内容挑出来写进长期存储。
- **「重启之后当前任务接不上」** → 会话状态持久化缺失。这是另一套设施，与上一条无关。
- **「明明存了却不用」** → 召回侧。去查存储里有没有那条是白费功夫，它就在那里。
- **「答得头头是道但依据是旧的」** → 有效性判定缺失。需要的是时间与矛盾信号，不是更好的嵌入模型。
- **「同一个问题两次答得不一样」** → 存在两条互相矛盾的记忆，写入时没做冲突消解，于是每次召回哪条取决于排序抖动。
- **「说过一次的约束后来失效了」** → 该约束只存在于对话历史里。长期有效的硬约束应当放在常驻的载体上，只在对话中说过一次的内容会随上下文治理一起消失。
- **「领域事实答错，且用户偏好正常」** → knowledge 侧。两者正常与异常的分离本身就是定位信息。

最后一条一般化之后是个好用的方法：**观察哪几类信息同时出错、哪几类正常。** 三套机制的故障通常不会同时发生，所以「什么是好的」和「什么是坏的」的边界，往往直接指出了坏在哪一套里。

## 七、小结

**起点是模型无状态。** 三套机制不是分类得来的，是沿着「还剩什么没解决」被依次逼出来的：context 管这一次看见什么，memory 管跨调用的经历如何存续，knowledge 管参数里没有的客观事实从哪来。三个问题彼此独立，任一个解决了另两个依然存在。

**两条判据够用了。** 看本体在 context 之内还是之外；看移除之后能不能重建。可重建的是派生物，不可重建的才是本体。而「能不能被丢弃」不是判据——三者都可以被丢弃。

**六组混淆的区分依据各不相同**，没有一条通用规则能同时辨清全部。可迁移的不是结论，而是每组的判别问法：有没有单位（工作记忆与窗口）、换个用户还成立吗（记忆与知识）、有没有外部可追溯的源（记忆召回与检索增强）、这是内容还是载体（程序性记忆与系统提示）、换个会话还要不要它（会话状态与跨会话记忆）、需不需要带时间戳（情景记忆与文档）。

**归属判断在「跨会话存续」之后还有一层分叉**：高命中率的走常驻，特定话题相关的走检索。把硬约束放进检索式记忆是个安静的错误——平时都对，只在漏召的那一次出错。

**排障第一步是打印本次载荷。** 它能一次性区分「没召回」「召回了但被截断」「看到了但没照做」，而这三种的处置方向完全不同。

最后一句：**这三套机制会在同一个瓶颈处汇合——本次载荷的容量。** 无论记忆存得多好、知识库多全，它们都必须挤过这道口子才能影响输出。所以把三者分清并不是为了各自做到极致，而是为了在分配那份有限名额时，知道自己在权衡什么。
