# Prompt Engineering

Prompt Engineering 研究怎样把任务表达成模型可执行、结果可验收的静态契约。Prompt 是进入模型窗口的一部分，但本页只讨论相对稳定的指令、示例与输出约束，不展开知识检索、记忆召回、消息历史和工具结果的动态治理。

---

## 一、任务契约

一份可维护的 Prompt 应区分目标、依据、约束和交付：

| 组成 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 目标 | 要完成什么 | 提取配置中显式声明的服务端口 |
| 依据 | 允许使用哪些材料 | 仅使用 `<config>` 内的内容 |
| 约束 | 哪些结论或行为不允许 | 缺少字段时不猜框架默认值 |
| 交付 | 结果怎样被消费 | 返回 `status`、`port`、`source` |

```text
目标：提取配置中显式声明的服务端口。
依据：仅使用 <config> 中的内容。
约束：没有直接证据时不猜默认值。
交付：返回 status、port、source；缺失时 status 为 not_found。
```

角色设定可以提供语境，但「你是一位顶尖专家」不能代替任务契约。Prompt 也不能补出缺失事实：如果问题问的是运行时实际端口，还必须取得环境变量、命令行覆盖或运行状态等上下文。

## 二、静态内容怎样组织

### 系统提示：校准指令高度

系统提示适合承载稳定的任务范围、行为边界和输出要求。用标题或标签分开背景、指令、工具指导和输出契约，目的是让职责清楚、便于维护，而不是制造复杂格式。

指令要落在两种失败之间：

| 过低：硬编码步骤 | 合适：给判据与边界 | 过高：只有原则 |
| --- | --- | --- |
| 穷举每种情况的固定动作 | 明确目标、可用信号、禁止项和完成条件 | 「专业、准确地完成任务」 |
| 需求变化就继续追加分支 | 允许模型处理未枚举情况 | 缺少可执行信息 |

系统／开发者指令用于应用级稳定规则，用户消息表达本次任务和资料。保持层次有助于解释冲突，但不是安全隔离；权限、数据范围和副作用仍由程序强制执行。[[19]](../references.md#source-openai-prompt)

### 工具定义：不要复制第二份接口

Prompt 表达跨工具策略，例如「先只读确认，再提出修改」；工具描述解释局部能力，例如参数单位、作用范围和返回状态。不要把完整 schema 再复制进系统提示，否则接口更新后容易出现两份互相冲突的定义。

工具选择规则还要说明何时不调用。解释用户已经提供的代码不必读取整个仓库；执行动作缺少关键参数时应请求补充，而不是从历史中猜测。模型频繁选错工具时，应先检查名称和职责是否重叠，再考虑增加文字限制。[[20]](../references.md#source-anthropic-tools)

### 示例：展示边界，而不是堆清单

Few-shot 适合展示难以仅靠规则说清的分类边界、格式或工具选择。示例应少量、典型且有差异：

- 优先选择容易混淆的相邻类别，而不是重复正常样例。
- 同时展示成功、缺失与拒绝等不同结果，避免单向偏置。
- 先写规则，再用最少示例解释真实错误。
- 资料发生变化时更新资料，不把新事实永久塞进 Prompt。

同质的动作—观测示例会诱导 Agent 机械模仿已有节奏。示例越多并不自动越好，它们也会占用窗口并增加缓存维护成本。

### 输出契约：可解析不等于正确

给程序消费时，应明确字段、类型、枚举值、额外字段策略，以及信息不足时的行为。能用 JSON Schema 等结构化输出约束时，不只靠自然语言描述格式。

Schema 只能约束结构，不能证明字段值来自真实材料。事实校验、数字范围、路径白名单、动作上限和权限判断仍需由程序完成。

## 三、怎样迭代 Prompt

Prompt 优化不是凭感觉润色，而是针对真实失败做控制变量实验：

1. 用最小 Prompt 建立基线，固定模型、工具、检索和解码参数。
2. 保存失败请求的完整上下文，确认模型实际看到了什么。
3. 给失败分类，只修改一条相关规则、一个示例或输出约束。
4. 在固定评测集上比较新旧版本，并检查原本正常的样例是否退化。
5. 记录 Prompt 版本、错误类别、改动假设、样例集、成本和延迟。

| 现象 | 优先检查 | 不应先做 |
| --- | --- | --- |
| 同一输入被理解成不同任务 | 目标、术语和判定标准 | 增加无关背景 |
| 输出字段或格式不稳定 | 输出契约与结构化约束 | 反复强调「严格输出」 |
| 正确资料没有进入请求 | Context 的选择与检索 | 把资料事实复制进固定 Prompt |
| 工具无权限或参数被拒绝 | 工具网关与运行时 | 要求模型「务必成功」 |
| 长历史后目标漂移 | 历史治理与目标复述 | 无限扩写系统提示 |

不要让同一个模型根据同一段 Prompt 自行宣布改进。结构化任务优先使用规则验收；开放文本使用明确 rubric、盲审和必要的人工复核。平均分提升也可能掩盖高风险子集退化。

## 四、版本与维护

稳定行为规则、输出格式和动态资料应分开维护，并在请求时确定性组合：

- 稳定模板保留版本；动态资料保留来源、版本或 hash。
- 同一约束不要同时散落在系统提示、Skill、工具描述和用户消息中。
- 模板插值按目标格式转义；标签只能分隔内容，不能提供安全边界。
- 稳定内容放在前部、动态内容后置，有利于复用前缀缓存；正确性仍优先于缓存命中。
- 顶层 Prompt 保留稳定职责与资料入口，项目细节放入可发现、可版本化的文档或 Skills。[[21]](../references.md#source-openai-harness)

Prompt 优化的最终判据不是文字更长或措辞更漂亮，而是在固定任务集上，以更低的歧义和更稳定的输出完成同一契约。
