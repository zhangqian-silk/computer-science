# 上下文压缩

Agent 每一步都在追加历史，而模型每次调用能看到的内容有上限。压缩要在用量撞顶前决定：**哪些内容继续投影给模型、哪些不投影、哪些改写成更短的等价表示**。

- 目标不是「把文字压短」，而是让 Agent 在信息被移除后**仍能把任务做完**
- 压缩改变模型下一次看到什么，不改变磁盘上已发生的事实，也不能让已完成的写操作重新变成待办
- 对话记录、知识库、长期记忆都只是来源；只有经选择真正进入本次请求的内容才算上下文

---

## 一、三层数据模型：「移除」到底移除了什么

「上下文」在实现里对应三个对象：

- **事件日志**：磁盘上的追加写记录，按发生顺序落盘，此后不再修改
- **工作集**：内存里的消息数组，与日志一一对应，每条带标记位（是否已清理、固定保留、正文已转存）
- **请求载荷**：本次调用实际发出的数组，由工作集**投影**而来，每轮重组——模型只能看到这一层

「从上下文中移除」= **下次请求组装时不放进去**，条目并不删除，只改标记位。由此分成两类手段：

- **不投影**：只改标记位，零成本、可回退
- **改写**：额外采样一次生成摘要，原文与摘要之间无可逆映射，不可逆

工程错误多来自把「不投影」的直觉套用到「改写」。短轨迹上摘要载荷并不比纯清理更小（摘要自身也占篇幅），收益要等历史足够长才显现——这是摘要排在最后的原因。

## 二、五级处置阶梯

按信息损失风险从低到高：L0 源头收窄 → L1 轮内清理 → L2 轮次边界 → L3 决策点闭合 → L4 摘要压缩。

- 前四级不产生额外模型调用，只打标记；只有 L4 付一次采样，且唯一不可逆
- 每一级替下一级减负：前四级失效时 L4 输入庞杂，摘要保留准确率明显下降
- 次序不可颠倒、可以跳跃：常见形态是 L0 常驻、L2 默认、L1/L3 按需、L4 兜底
- 压缩触发异常频繁通常不是阈值问题，而是前四级没做——**清理是卫生习惯，压缩是抢救**
- 成熟实现的共识：先卸载超大工具结果，再卸载写操作的陈旧**入参**（完整文件内容已在磁盘，纯冗余），没有可卸载内容时才摘要[[7]](#ref-7)

## 三、工具结果的留弃判据

工具结果是体积最大的累积内容，判据不是新旧（旧的可能仍在引用，新的可能已无价值），而是三个维度：

- **可重取性**：移除后能否凭剩余信息取回？文件路径、检索 query、命令行都是**恢复句柄**
- **幂等性**：重跑会不会改变外部世界？读文件、检索、`ls` 可随意重跑；提交、发布、付款不行
- **不可再生性**：子 Agent 回传、后台任务状态、记忆工具输出无法重跑或代价极高

统一判据：**信息已固化到别处（磁盘文件、正式回复、可重取句柄）才能移除**，三者都没有就不能动。判据落成工具注册字段，新增工具时申报处置等级，清理逻辑自动适配：

| 处置等级 | 语义 | 典型工具 | 移除后留下什么 |
| --- | --- | --- | --- |
| 用完即弃 | 只读、可重取 | 读文件、检索、只读命令 | 占位符 + 路径或 query |
| 可降级 | 只需最近一份 | 测试输出、构建日志 | 退出码 + 首条报错 |
| 可转存 | 超阈值自动落盘 | 大文件、长日志、转储 | 文件路径 + 预览 |
| 不可清理 | 外部世界已被改变 | 写文件、提交、发布 | 原样保留 |
| 固定保留 | 不可再生 | 子 Agent 回传、后台状态 | 原样保留 |

**写操作结果必须保留。** 它很短、看似无用，但承担**记账功能**——「这件事已经做过」的唯一凭证；清掉后模型会重复提交、发消息、扣款。只读结果的清理是省钱，写操作结果的清理是制造重复副作用。

**清理必须留痕。** 工具调用与结果配对，删掉一半多数接口直接拒绝；正确做法是保留调用记录，只把结果正文换成占位符。裸 `[已清理]` 会诱发重跑，占位符必须同时给出结论与恢复路径：

```
{ "type": "tool_use",    "name": "bash", "input": { "cmd": "go test ./..." } }
{ "type": "tool_result", "content": "[已清理：退出码 1，2 个用例失败，完整日志见 ./logs/test-3.txt]" }
```

**Shell 结果最难处理。** 输出体积唯一完全不可预测（跑命令前不知道有多少输出）。优先在源头收窄：管道过滤、限行数、静默、只取所需字段；超阈值输出自动落盘返回路径；长驻进程只能截断保留尾部。

## 四、触发时机

**阈值用绝对量，不用百分比。** 要保护的是生成摘要所需的输出空间，其大小取决于摘要长度、与窗口无关：

$$
\text{有效窗口} = \text{窗口容量} - \min(\text{本轮输出上限},\ C)
$$

$$
\text{触发线} = \text{有效窗口} - \text{摘要输出预算}
$$

- $C$ 为上限常数；摘要输出预算取实测摘要长度的高分位
- 百分比约束的是比例，而需要约束的是差值：小窗口不够生成摘要，大窗口触发过早

**反应式兜底。**

- 触发线不是硬墙：两次检查之间插入一条超大工具结果即可顶穿缓冲
- 捕获「超出上下文长度」错误 → 更激进压缩 → 重试，且只执行一次，失败显式报错，防止压缩重试死循环
- 压缩请求本身打标记，禁止压缩过程中递归触发

**让模型参与决定时机。**

- 固定阈值不知道时机好坏：重构中途是坏时机；任务边界、刚从大量材料提炼结论后是好时机
- 把压缩暴露为工具由模型调用，阈值退为兜底；实测模型偏保守（终端任务基准上零次自主调用），但触发点通常准确[[5]](#ref-5)
- 成熟形态是组合：好时机模型主动压，绝对缓冲硬线防止一直不压
- 避坑：按**可见事件条数**而非 token 触发，几个词的消息与上万 token 的输出被同等对待，水位失真[[6]](#ref-6)

## 五、摘要与压缩后的续跑

**摘要是交接文档，不是叙述。** 读者是接手工作的自己，需要「现在什么状态、下一步做什么」：

- 必备内容：目标与约束、已完成/进行中、关键决策及理由、踩过的坑、下一步动作、必需的数据与路径
- 用户原话逐字保留（任何转述都可能引入目标偏移），值得独立预算
- 先想再写：先分析后产出摘要，质量明显更好
- 摘要请求禁止调用工具、限制轮次、配熔断器，连续失败即停用自动压缩并上报
- 消息序列化成带角色标签的纯文本（`[用户]:` / `[助手推理]:` / `[工具结果]:`），防止模型当成待续写的对话，并在序列化时截断超长结果[[4]](#ref-4)

**续跑靠多路信息各走通道，摘要只承担一路：**

| 通道 | 内容 | 压缩后怎么处理 |
| --- | --- | --- |
| 语义信息 | 意图、方案、判断、进度 | 走摘要 |
| 最近原文 | 最近若干轮完整对话 | 逐字保留，有独立预算 |
| 程序状态 | 待办、子任务状态、配置 | 以附件形式重新注入 |
| 永久指针 | 文件路径、链接、产物清单 | 原样保留，体积极小 |
| 操作规范 | 系统提示、工具定义 | 不属于消息历史，重建一份最新的 |
| 静态约定 | 项目指令文件、长期规则 | 从磁盘重新读取 |

项目指令不进摘要，靠「清空 → 下一轮从磁盘重载」生效[[3]](#ref-3)。直接推论：**长期硬性约束必须写在系统提示或磁盘文件里**，只在对话里说过一次的约束会随摘要消失。

**服务端压缩与客户端压缩。**

- 服务端：越线后生成摘要块返回，后续请求带回该块，服务端自动忽略其之前的全部内容，客户端只管追加[[2]](#ref-2)
- 计费坑：压缩的额外采样不计入顶层 token 统计字段，必须按迭代明细累加[[2]](#ref-2)
- 客户端形态：自实现切点选择、摘要生成与状态重建，使用服务端工具时 token 估算可能失准[[1]](#ref-1)

**切点约束。**

- 不能切在工具结果上（破坏调用配对），合法切点是完整的用户/助手消息边界
- 单个回合就超过保留预算时（如数十万 token 的转储），切点落在回合中间，分别生成历史摘要与回合前半段摘要再合并[[4]](#ref-4)

## 六、重复压缩：摘要会沉，分辨率会降

- **层叠式**：旧摘要作为「此前已压缩的上下文」再次纳入输入，体积单调上升
- **改写式**：旧摘要喂出新摘要，替换而非叠加，体积由预算约束
- 增量更新用两套提示词：首次一套，之后「把新信息合并进已有摘要」，避免摘要自然堆积[[4]](#ref-4)

共同规律：**越接近精确值的信息流失越快**——数字、配置、文件清单、行号两三次压缩后基本不可靠；目标、约束、架构决策保留相对完好。两个推论：精确数值、清单、链接压缩前就该落盘，之后抢救就晚了；多次压缩后不要向 Agent 问明细，改动清单现场查版本控制，测试结论重新跑。

## 七、与前缀缓存的冲突

前缀缓存要求前缀完全一致：某处 token 变化，其后缓存全部失效；压缩本质上就是改动历史。

```
只在尾部追加                     改动中间的历史
────────────────────────        ────────────────────────
系统提示    系统提示   ✓命中      系统提示    系统提示   ✓命中
工具定义    工具定义   ✓命中      工具定义    工具定义   ✓命中
动作1/观测1 动作1/观测1 ✓命中     动作1/观测1 动作1/观测1' ✗改动
动作2/观测2 动作2/观测2 ✓命中     动作2/观测2 动作2/观测2  ✗连带失效
            动作3/观测3 ← 新算                 动作3/观测3  ✗连带失效
只需计算新增的一段               改动点之后全部重算
```

- **位置比数量更决定代价**：清窗口靠前的一大段可能让后面几十万 token 全部失效，清靠近尾部的同样体积只失效几万
- **攒够量再清**：设单次最小回收量门槛，不达标整批放弃；该参数的用途正是判断这次清理是否值得打破缓存[[1]](#ref-1)
- **一次清最老的一大段**，付一次重算；不要每轮修修补补反复付
- **挑缓存本就要失效的时刻动手**：距上次调用已久、缓存大概率过期时，边际成本接近零
- 在系统提示末尾单设缓存断点，避免摘要写入连带重写系统提示[[2]](#ref-2)
- 压缩请求用独立会话标识并禁用缓存写入，一次性提示不值得写缓存[[4]](#ref-4)
- 正面解法：调用方声明哪些工具结果可安全遗忘（业务语义只有调用方清楚），服务端在缓存视图挖空对应位置但不计作前缀变化（机制上只有服务端做得到）——本地记录一条不少，缓存继续命中

## 八、历史如何保障

载荷里看不到 ≠ 事件日志里没了。设计关键不是让压缩少丢，而是**压缩前就把不能丢的写出去**：

- **结构化笔记**：进度、决策、待办定期落盘，需要时读回；数千步的长任务靠文件维持精确计数，靠对话不可能
- **压缩前预警**：接近阈值时提示模型先把重要内容写进文件再清理，已是被实现的机制[[1]](#ref-1)
- **产物即最强的历史**：代码、报告、结构化数据、缺陷清单——摘要会缩，文件不会
- 压缩结果本身也记成日志事件，「哪些已被遗忘」成为既有事实，压缩器即可无状态[[6]](#ref-6)

成熟实现都不物理删除历史，形态不同而已：压缩记成日志事件[[6]](#ref-6)、旧消息打时间戳软删除、完整对话写入虚拟文件系统[[7]](#ref-7)。**压缩应当是历史的一个视图，不是对历史的一次编辑。**

## 九、什么时候不该压缩

四类任务不适合摘要压缩：

- **需要精确回忆早期细节**：摘要丢的恰好是这个，改用外置文件或拆分任务
- **需要跨多个变量维持精确状态**：状态放结构化字段，摘要管语义、字段管事实
- **需要几段原文同时可见的对照类**：摘要迫使反复重读，净亏
- **大量使用服务端工具**：token 统计可能失准，压缩在错误时机触发[[1]](#ref-1)

三个不致命但会静默出错的坑：

- 自定义摘要提示词通常是**整体替换而非追加**，默认提示词的结构化要求全部消失，需自己补回[[2]](#ref-2)
- 只存在于对话历史里的安全约束与权限边界，会随压缩静默消失
- 摘要可能把未完成写成已完成：「下一步检查配置」经两轮转述变成「已检查配置」

对策：自由文本摘要不能作为任务状态的唯一来源；保留独立状态字段与证据引用，发布前机械校验约束、未完成集合与证据 ID 是否一致。

## 十、几种实现的对照

| 维度 | 常见做法 | 分歧所在 |
| --- | --- | --- |
| 触发口径 | 绝对缓冲 / 窗口百分比 | 绝对量与比例之争，见第四节 |
| 保留窗口 | 最近若干 token / 若干条工具结果 / 固定比例 | 度量单位不同，意图一致 |
| 最小回收量 | 不达门槛就不执行 | 门槛取值不同，机制普遍存在 |
| 重复压缩 | 层叠 / 改写 / 增量更新 | 决定摘要体积是否随次数增长 |
| 历史保留 | 事件日志 / 软删除 / 虚拟文件系统 | 形态不同，都不物理删除 |
| 用户原话 | 逐字保留 / 纳入摘要 | 分歧最大的一处 |

分歧点是可调参数，共识点是稳定结论（分层兜底、增量摘要、事件化等共识已并入前述各章）。

## 十一、怎么判断压缩做得好

压缩是有损操作，没有度量的调参只是猜。

- **先看构成再优化**：记录每轮总 token 与分类占比（系统提示 / 工具结果 / 推理 / 消息 / 检索），异常突出的类别优先治理
- **按后续任务检验，不看压缩比**：同一快照分出压缩/未压缩两支，比较约束遵守、证据回查、待办覆盖、工具重复调用、最终完成率[[8]](#ref-8)
- **保真度分层统计**：建一组「压缩后必须仍能答对」的问题，高层事实与冷门细节分开，合在一起会掩盖差距
- **调提示词先召回后精度**：先保证抓住每条相关信息（哪怕啰嗦），再逐步删减并盯住召回不下滑
- 其他指标：触发次数与时机分布、压缩后失败率、缓存命中率、压缩后重复读取次数（诊断价值最高——每轮重读同一文件说明保留窗口切太狠）
- 失真有固定形态（待办写成已完成、丢掉约束、反转测试结果），修好的样例沉淀为回归用例

## 十二、小结

- **先分清「不投影」与「改写」。** 前者只改标记位，零成本、可回退；后者需要一次采样且不可逆。多数工程错误来自把前者的直觉套用到后者。
- **次序由信息损失风险决定，不由实现难度决定。** 前四级都不产生额外模型调用，且每一级都在替下一级减负。
- **能移除的前提是已经固化到别处。** 这比「新旧」「大小」都可靠。写操作凭证、不可再生的状态、用户原话没有别处可固化，所以不能丢。
- **代价不只在信息，还在缓存。** 改动历史会让改动点之后的前缀全部失效，位置比数量更决定成本——这是「宁可让上下文变长也不要修改它」在生产中成立的原因。
- **真正的成果始终活在对话之外。** 代码、文件、报告不会被摘要缩短；成果只存在于对话历史里的任务，压缩做得多精细都是脆的。
