# 上下文压缩

上下文压缩减少下一次模型请求中的历史负担，目标是保留继续任务所需的信息，而不是把文字压到最短。它改变模型的输入投影，不应悄悄修改外部事实、审批结果和原始操作记录。输入预算的基础见 [Context Engineering](context-engineering.md)，计算复用见 [缓存](../model/kv-cache.md)。

## 裁剪、摘要、转存与重建

裁剪直接不发送部分内容；摘要生成较短表达；转存把大产物留在外部、发送引用；重建根据结构化状态与当前事实重新组织输入。四者可以结合，但代价不同：裁剪可能丢信息，摘要可能失真，转存增加回查，重建需要可信状态。

长日志更适合保存原始产物并提取错误位置，而不是让模型把数万行逐字概括。工具参数、用户明确约束、未完成调用和结果关联也不适合任意文本摘要。对正在操作的文件，保留版本和必要范围往往比保留一段“内容大意”更有用。

## 受保护的信息与消息边界

可把候选信息分成三类。不可变事实包括实际工具回执、文件版本、测试结果和授权决定；当前约束包括用户目标、禁止动作和有效范围；可压缩材料包括已完成探索、重复日志和可回查的背景说明。

一个关键陷阱是把未完成事项写成完成事实。例如“下一步检查数据库配置”经过多轮摘要变成“已检查配置”。因此不把自由文本摘要作为任务状态的唯一来源，保留独立的 `pending/observed/verified` 字段与证据引用。

协议也有不可拆分组：assistant 的调用、对应 tool result 和必要的供应商续接内容必须遵守 API 规则。一个看似自然的“保留最后五条消息”，可能刚好切掉调用、只留下结果。

## 上下文压缩流程

```python
# 教学伪代码。store 提供版本化历史；summarize 返回结构化候选摘要。
def compact_session(store, session_id, summarize, validate_summary):
    snapshot = store.read(session_id)
    stable_groups, recent_groups = split_at_safe_boundary(snapshot.groups)
    candidate = summarize(
        history=stable_groups,
        required_constraints=snapshot.constraints,
        pending=snapshot.pending,
    )
    validate_summary(
        candidate,
        constraints=snapshot.constraints,
        pending=snapshot.pending,
        evidence_ids=snapshot.evidence_ids,
    )
    # 只在历史没被新输入推进时发布，避免覆盖并发用户消息。
    return store.compare_and_swap_projection(
        session_id=session_id,
        expected_revision=snapshot.revision,
        summary=candidate,
        retained_groups=recent_groups,
    )
```

这里 `split_at_safe_boundary` 的契约是只在完整消息组之间切分；`validate_summary` 检查约束、未完成事项和引用集合，不承诺能完全自动识别所有语义失真；`compare_and_swap_projection` 避免旧快照覆盖新历史。外部依赖的这些语义必须由实现与测试提供，不能只给函数取名就认为安全。

压缩失败时继续使用原上下文的前提是仍在窗口内；已无剩余空间则应暂停、选择较小的确定性转存方案，或请用户缩小范围。不能把失败摘要照常发布并声称“已压缩”。

## Pi 的历史保留边界

Pi 的压缩文档描述以 `firstKeptEntryId` 标记保留边界，追加压缩记录，而不是直接删除此前事件。重建请求时使用摘要和保留消息；工具结果不能与调用断开。分支摘要则针对从某条分支离开时的工作，服务于分支导航，不等同于整段会话自动压缩。[[27]](../references.md#source-pi-compact)

这个实现切片的启示是：压缩状态可以是历史的一个版本化投影，原始内容仍可回查。自建系统可以采用其他存储格式，但应保留摘要由哪些事件产生、保留范围从哪里开始、后续是否重复压缩同一部分。

它也带来维护成本：原始内容虽然不再进入模型，仍然需要存储权限、脱敏与删除策略。不能声称“摘要了就删除了敏感信息”；长期记忆或索引里可能还有其副本。

## 压缩触发条件

窗口利用率达到某阈值是简单触发器，但下一步工具输出可能远超预估。需要预留输出、下一组观察、系统和工具描述的空间。模型切换到较小窗口时，也要重新计算，而不是继续沿用旧阈值。

还要区分应当频繁的小转存与成本较高的模型摘要。每轮都摘要会增加模型调用，破坏前缀复用并累积语义误差；等到彻底超限才处理又可能无法发送摘要请求。可用渐进策略：先限制单工具返回；再保留引用；然后裁剪重复资料；最后在安全边界生成摘要。

触发频率、摘要预算、近期保留量和回查工具开销应一起评测。没有通用的“保留20%最好”。模型、任务长度、证据密度和工具输出类型都会影响结论。

## 摘要的数据结构与验证

```python
summary = {
    "goal_revision": 4,
    "confirmed": [
        {"claim": "a.py 的目标调用存在", "evidence": "read-17"},
    ],
    "pending": ["验证 b.py"],
    "constraints": ["只生成补丁，不发布"],
    "artifacts": [
        {"ref": "artifact:test-log-2", "kind": "test_log", "status": "failed"},
    ],
    "hypotheses": ["失败可能由环境变量覆盖导致"],
}
```

`hypotheses` 与 `confirmed` 分开，`status=failed` 不因摘要措辞变成通过。验证器可以检查证据 ID 来自原记录、任务版本一致、约束未丢、未完成集合未被无证据删掉。它不能只用另一段同类摘要再次自我评价。

对执行任务，summary 应给出下一步读取入口，而不是保留全部实现细节。例如“原始报错位于产物X第Y部分”比“报错比较复杂，已经详细分析”更有操作价值。引用必须真实可访问且有权限，不能只为节省 token 生成不存在的定位。

## 压缩后的继续执行评测

Factory 的作者实验将压缩后的事实回忆、产物细节、继续任务能力等分开评估。这里借鉴这种评价对象，不把其特定模型和任务的排名推广到今天所有产品。[[28]](../references.md#source-factory-compact)

自建测试可以从同一执行快照分成未压缩与压缩两支，给出相同后续任务；比较约束遵守、证据回查、未完成任务覆盖、工具重复次数、最终通过率以及总 token。压缩比分数只能说明输入变小，不能说明系统变好。

加入对抗性但安全的样例：相似文件名、最新用户撤销要求、某次测试失败后计划重试、未完成的外部写入、旧分支已弃用结论。模型若在压缩后把待对账操作当成“未执行”而自动重试，会造成严重业务错误，必须独立检测。

## 与产品和工程层的连接

长任务 Harness 的公开实践常采用进展记录、产物和分阶段工作，而不是仅靠无限增长对话。可将这些视作压缩的互补手段：把可验证状态留在程序侧，把任务所需入口交给模型。[[29]](../references.md#source-anthropic-long-harness)

压缩会影响缓存前缀，需要在 [性能实验](../runtime/performance-cost.md) 中同时计量首次摘要成本、后续缓存读取、回查次数和交付质量。它也会影响恢复，因此保存摘要版本与原始历史范围；不要只保存最后一段压缩文本而丢掉运行事实。

## 摘要候选的拒绝条件

原状态是：用户要求只读；A文件已读取；B文件待读取；测试失败；一个远端操作状态未知。摘要候选却说“已完成A/B检查，测试正常，下一步重新提交操作”。

这种摘要字数很少、语言流畅，却同时丢约束、伪造覆盖、反转测试结果和诱发重复效果。验证器至少能用结构化状态发现这四类不一致，拒绝发布候选。

```python
required = {
    "mode": "read_only",
    "pending": {"B"},
    "test_status": "failed",
    "unknown_operations": {"op-7"},
}
candidate = {
    "mode": "read_only",
    "pending": set(),
    "test_status": "passed",
    "unknown_operations": set(),
}
violations = [
    key for key in required
    if candidate.get(key) != required[key]
]
assert set(violations) == {"pending", "test_status", "unknown_operations"}
```

实际应用不必要求所有字段字面完全相等，例如待办可以有被验证完成的变化；关键是变化必须由新事实解释，而不是由摘要模型自由决定。

## 压缩与用户新输入竞争

摘要请求开始时读取会话revision10，用户在生成期间追加消息使其变为11。若发布摘要时直接覆盖整个上下文，会丢掉这条新输入。可以使用版本比较失败后重建候选，或只提交对revision10之前前缀的替代并保留新后缀，但后一种方案要严格验证边界与调用关联。

对恢复记录，保存“摘要来源截止位置”和“保留后缀起点”，比保存一个未标版本的summary字符串更有用。并发压缩由一个拥有者执行，避免两个摘要互相覆盖。

## 压缩后的回查成本

压缩后模型需要多读两次原始日志，有时是合理折中；如果每轮都重新读取已经稳定的同一文件，可能压掉了太多可操作信息。记录回查原因、读取范围和结果是否真的改变决策，才能调近期保留量。

优秀压缩不是尽量阻止回查，而是在当前输入成本、必要信息和未来读取之间取得可验证平衡。
