# 上下文压缩

Agent 每一步都在往历史里追加内容，而模型每次调用能看到的内容有上限。压缩就是在这条上升曲线撞上天花板之前，决定**哪些内容还要继续投影给模型、哪些不必、哪些必须改写成更短的等价表示**。

它常被误解为「把文字压短」。真正的目标是让 Agent 在信息被移除之后**仍然能继续把任务做完**——压缩改变的是模型下一次看到什么，不应改变磁盘上已经发生的事实，也不应让一个已完成的写操作重新变成待办。

阅读只需一点背景：**上下文是一次生成中模型实际可用的信息**。对话记录、知识库、长期记忆都只是来源，只有经过选择、真正进入本次请求的那部分才算数。

---

## 一、三层数据模型：「移除」到底移除了什么

「上下文」这个词在实现里对应三个不同的对象，分开它们是理解后文一切时机与成本的前提。

- **事件日志**：磁盘上的追加写记录。每段推理、每条工具结果、每次用户输入按发生顺序落盘，此后不再修改。
- **工作集**：内存里的消息数组，与日志一一对应，但每个条目额外带有标记位——是否已清理、是否固定保留、正文是否已转存。
- **请求载荷**：本次调用实际发出的数组，由工作集**投影**而来，每轮重新组装。模型只能看到这一层。

日志载入工作集，工作集投影出载荷。于是「把某条内容从上下文中移除」的准确含义是：**组装下一次请求时不把它放进去**。条目没有被删除，标记位改了而已。

<CompactionProjection />

这就区分开了两类手段：**不投影**只改标记位，零成本、可回退；**改写**要额外采样一次把历史重写成摘要，原文与新文本之间没有可逆映射。后文讨论任何压缩动作，都先落到这个区分上——工程上的多数错误，来自把前者的直觉套用到后者身上。

对照里还藏着一个容易忽略的现象：在这段只有九条记录的短轨迹上，**摘要投影出的载荷并不比纯清理更小**，因为摘要自身也占篇幅，而清理已经把体积最大的两条正文换成了占位符。摘要的收益要等历史足够长、可清理的内容已清完才显现——这正是它该排在最后的理由。

## 二、五级处置阶梯

按信息损失风险排序，压缩之前还有四级更便宜的手段。

<CompactionLadder />

两点决定了这个次序不能颠倒。

**前四级都不产生额外的模型调用。** 源头收窄在工具返回值构造阶段完成，轮内清理与轮次边界只是打标记，决策点闭合是由任务状态驱动的批量打标记；只有 L4 要付一次采样，也只有它不可逆。

**每一级都在替下一级减负。** 摘要质量与输入长度负相关：前四级从未生效时，落到 L4 的输入已经庞杂，模型挑出「哪些必须保留」的准确率会明显下降。

次序不可颠倒，但可以跳跃。实践中常见的形态是 L0 常驻、L2 作为默认行为、L1 与 L3 按需触发、L4 兜底。一个便于记忆的说法：**清理是持续的卫生习惯，压缩是偶发的抢救。** 如果一条轨迹上压缩触发得异常频繁，通常不是阈值设错了，而是前四级没做。

## 三、工具结果的留弃判据

工具结果通常是累积部分里体积最大的一类，也是压缩的主要对象。判据不是新旧——旧的可能仍在被引用，新的也可能已无价值——而是三个维度的交叉：

- **可重取性**：移除后能否凭上下文里剩下的信息取回？文件有路径、检索有 query 与链接、命令有命令行，这些都是**恢复句柄**。
- **幂等性**：重跑一次会不会改变外部世界？读文件、检索、`ls` 可以随意重跑；提交、发布、付款不行。
- **不可再生性**：能否被重新生产？子 Agent 回传、后台任务状态、记忆工具输出属于「重跑代价极高或无法重跑」。

三条收敛成一句统一判据：**能移除的前提是信息已经固化到别处**——磁盘文件、正式回复，或一个能重取它的句柄。三者都没有就不能动。

按此分类，可以得到一张处置表。它的价值不在穷举，而在**把判据落成工具注册时的一个字段**：新增工具的人顺手申报处置等级，清理逻辑自动适配，不必在清理器里维护工具名白名单。

| 处置等级 | 语义 | 典型工具 | 移除后留下什么 |
| --- | --- | --- | --- |
| 用完即弃 | 只读、可重取 | 读文件、检索、只读命令 | 占位符 + 路径或 query |
| 可降级 | 只需最近一份 | 测试输出、构建日志 | 退出码 + 首条报错 |
| 可转存 | 超阈值自动落盘 | 大文件、长日志、转储 | 文件路径 + 预览 |
| 不可清理 | 外部世界已被改变 | 写文件、提交、发布 | 原样保留 |
| 固定保留 | 不可再生 | 子 Agent 回传、后台状态 | 原样保留 |

### 写操作结果为什么必须保留

它往往很短、看起来「已经没用了」，所以最容易被当作可优化的对象。但它承担的不是信息功能而是**记账功能**——是「这件事已经做过」的唯一凭证。

清掉之后，模型在后续某一步重新评估进度，发现没有任何证据表明提交已完成，于是再提交一次。发消息、扣款、发布同理。**只读结果的清理是省钱，写操作结果的清理是制造重复副作用**，两者不是同一种风险量级。

### 清理时必须留下痕迹

一个常见失误是把整条消息从数组里删掉。工具调用与工具结果是配对的，删掉一半会破坏配对，多数接口直接拒绝请求。**正确做法是保留调用记录，只把结果正文换成占位符**，消息条数与配对关系都不变。

占位符的内容也有讲究。一个裸的 `[已清理]` 会让模型陷入两难：知道调用过，却不知道结果，最省事的选择就是重跑。所以占位符里要同时给出**结论**与**恢复路径**：

```
{ "type": "tool_use",    "name": "bash", "input": { "cmd": "go test ./..." } }
{ "type": "tool_result", "content": "[已清理：退出码 1，2 个用例失败，完整日志见 ./logs/test-3.txt]" }
```

这样模型不必重跑就知道上次的结果，需要细节时也知道去哪里取。

### Shell 结果为什么最难处理

它是唯一「输出体积完全不可预测」的类别：同一条命令可能返回三行，也可能返回三十万行；读文件之前你知道文件多大，跑命令之前你不知道。

处置只能分层，且优先在源头：先用管道与参数收窄（过滤、限制行数、静默模式、只取需要的字段），再对超阈值输出自动落盘并返回路径，最后才在窗口里清理已有正文。长驻进程的输出没有终点，只能截断保留尾部。

## 四、触发时机

清理可以随时做，摘要压缩需要一条明确的触发线。

### 阈值应当是绝对量，不是百分比

要保护的是**生成摘要所需的输出空间**。这个空间取决于摘要本身有多长，与窗口多大无关：无论 200K 还是 1M 窗口，写一份结构化摘要需要的输出预算是同一量级。于是：

$$
\text{有效窗口} = \text{窗口容量} - \min(\text{本轮输出上限},\ C)
$$

$$
\text{触发线} = \text{有效窗口} - \text{摘要输出预算}
$$

其中 $C$ 是上限常数，避免为极大的输出上限预留过多空间；摘要输出预算应取自己实测的摘要长度高分位。

<CompactionTriggerCalculator />

百分比约束的是比例，而需要约束的是差值，所以它不可能同时适配两端：小窗口留出的空间不足以生成摘要，大窗口则闲置大量容量、触发过早。

### 越过触发线之后，窗口仍可能继续膨胀

触发线不是硬墙。判定发生在某个检查点，而两次检查之间可能插入一条超大的工具结果——一次线程转储、一份未收窄的日志，足以一次顶穿全部缓冲。

所以还需要一条**反应式兜底**：捕获「超出上下文长度」错误，执行一次更激进的压缩后重试。这条路径必须**一次性**——失败就显式报错，否则会陷入「压缩失败 → 重试 → 再次超限」的循环。相应地，压缩请求本身要打标记，禁止在压缩过程中再次触发压缩。

### 让模型参与决定时机

固定阈值有个结构性缺陷：它只知道水位到了，不知道**此刻是不是好时机**。在一次复杂重构的中途压缩是糟糕的时机；在用户转向新任务、或刚从大量材料里提炼出结论之后压缩，是好时机。

一种做法是把压缩暴露成工具，让模型自己判断何时调用，阈值退为兜底。[[5]](#ref-5)模型能识别的时机大致是：干净的任务边界；从大量上下文中提取出结果之后；即将读入大量新材料或产出长篇内容之前；进入长链多步流程之前；有新决定推翻了先前上下文；大量岔路与死胡同可归并成一段摘要。

实测结论值得注意：模型相当保守——在一个终端任务基准上没有观察到任何一次自主压缩，但真触发时通常选在明显改善工作流的时刻。[[5]](#ref-5)所以成熟形态是**组合**：模型在好时机主动压，绝对缓冲的硬线防止它一直不压。

还有一种口径需要避开：按**可见事件条数**而非 token 触发。[[6]](#ref-6)一条几个词的消息与一条上万 token 的命令输出被同等对待，触发时机会与真实水位相差很远。

## 五、摘要与压缩后的续跑

### 摘要不是叙述，而是交接文档

摘要的读者是**接手这项工作的自己**，需要的不是「我们讨论了什么」的记叙，而是「现在处于什么状态、下一步做什么」的交接。一份可用的摘要应当覆盖：目标与约束、已完成与进行中、关键决策及其理由、踩过的坑（失败尝试与报错）、下一步的具体动作、继续工作所必需的数据与路径。

两个细节收益远超成本。**用户原话尽量逐字保留**——其余都可以概括，用户的表述不行，任何转述都可能引入偏移，而目标偏移在长任务里代价最高；有的实现为此专门留出独立预算。**让模型先想再写**——给一段草稿空间（先分析、再产出正式摘要），质量明显好于直接要成品。

还有一条容易忽略的加固：**摘要请求必须禁止调用工具**。请求带着完整工具定义，模型有一定概率在这一步尝试调用，而一旦调用被拒绝或返回空，这次压缩就产出了零内容。对应做法是请求里明确要求不调工具、限制这一步的轮次、并给失败路径配熔断器——连续失败若干次就停用自动压缩并上报，而不是无限重试。

### 让任务真正能接着跑的不是摘要本身

压缩之后 Agent 能继续工作，靠的是**几路信息各走各的通道**，摘要只承担其中一路。

| 通道 | 内容 | 压缩后怎么处理 |
| --- | --- | --- |
| 语义信息 | 意图、方案、判断、进度 | 走摘要 |
| 最近原文 | 最近若干轮完整对话 | 逐字保留，有独立预算 |
| 程序状态 | 待办、子任务状态、配置 | 以附件形式重新注入 |
| 永久指针 | 文件路径、链接、产物清单 | 原样保留，体积极小 |
| 操作规范 | 系统提示、工具定义 | 不属于消息历史，重建一份最新的 |
| 静态约定 | 项目指令文件、长期规则 | 从磁盘重新读取 |

最后一行有个容易误解的地方：项目指令类文件通常**不会**被写进压缩后的消息，而是靠「清空 → 下一轮从磁盘重新加载」生效。[[3]](#ref-3)这个设计是对的，全局规则每轮自动重载，没必要挤进摘要。它的直接推论是：**必须长期生效的硬性约束应当写在系统提示或磁盘文件里**，只在对话里说过一次的约束会随摘要被概括甚至消失。

### 服务端压缩与客户端压缩

服务端形态下，压缩表现为响应里的一个专门内容块：服务端检测到输入越线，生成摘要并作为一个块返回；后续请求把这个块带回去，服务端自动忽略它之前的全部内容。[[2]](#ref-2)客户端只需追加，不必自己实现摘要逻辑与「哪些消息该丢」的状态。

代价分别在两处：

- **服务端形态**有个容易踩的计费坑——压缩需要一次额外采样，而顶层 token 统计字段**不包含**这次用量，必须按迭代明细逐项累加，只看顶层字段会系统性少算。[[2]](#ref-2)
- **客户端形态**要自己实现切点选择、摘要生成与状态重建，且在使用服务端工具时对 token 用量的估算可能失准，导致压缩在错误的时机触发。[[1]](#ref-1)

### 切点不能落在任意位置

一条硬约束：**不能切在工具结果上**。工具结果必须与产生它的调用待在一起，切开就破坏配对。合法切点是用户消息、助手消息这类完整边界。

还有一种边界情况值得预先设计：**单个回合本身就超过了保留预算**。一个回合从用户消息开始，包含其后所有助手响应与工具调用；当这一个回合就撑满预算时，切点只能落在回合中间，做法是分别生成「历史摘要」与「该回合前半段的摘要」再合并。[[4]](#ref-4)一次吐出数十万 token 的转储就会触发这条路径。

## 六、重复压缩：摘要会沉，分辨率会降

长任务里压缩不止发生一次。第二次面对的历史已经包含第一次的摘要，于是有两种处理方式：**层叠式**把旧摘要作为「此前已压缩的上下文」再次纳入输入，体积单调上升；**改写式**把旧摘要喂进去、新摘要出来，是替换而非叠加，体积由预算约束。

<CompactionFidelityDecay />

无论哪种形态，都有一条共同规律：**越接近「精确值」的信息流失得越快。** 具体数字、确切配置、文件清单、行号在两三次压缩后基本不可靠；目标、约束、架构决策这类高层信息保留得相对完好。

这条规律有两个直接推论。其一，凡是精确数值、确切配置、精确清单、来源链接，**压缩之前就该落盘**，之后再抢救就晚了。其二，压缩多次之后**不要向 Agent 询问明细**——「你之前改了哪些文件」的答案已经不可信，摘要里可能只剩「重构了鉴权中间件与并发控制」一句。改动清单要现场从版本控制取，测试结论要重新跑。

## 七、与前缀缓存的冲突

前缀缓存的复用条件是**前缀完全一致**：自回归模型下，某个位置的 token 变了，该位置**之后**的缓存全部失效。而压缩与清理本质上就是在改动历史——这是压缩独有、也最容易被忽略的一笔成本。

```
只在尾部追加                     改动中间的历史
────────────────────────        ────────────────────────
系统提示    系统提示   ✓命中      系统提示    系统提示   ✓命中
工具定义    工具定义   ✓命中      工具定义    工具定义   ✓命中
动作1/观测1 动作1/观测1 ✓命中     动作1/观测1 动作1/观测1' ✗改动
动作2/观测2 动作2/观测2 ✓命中     动作2/观测2 动作2/观测2  ✗连带失效
            动作3/观测3 ← 新算                 动作3/观测3  ✗连带失效
只需计算新增的一段               改动点之后全部重算
```

于是有个反直觉的结论：**位置比数量更决定代价。** 清掉窗口靠前的一大段日志，可能让后面几十万 token 全部失效；清掉靠近尾部的同样体积，失效范围可能只有几万。

三条可操作的纪律：

**攒够量再清。** 设「单次最少回收量」门槛，不达标就整批放弃——为省几千 token 打破几十万 token 的前缀是净亏。这不只是经验法则，它已被做成接口参数，其文档明确说明该参数的用途正是判断「这次清理是否值得打破缓存」。[[1]](#ref-1)

**优先清最老的一大段，而不是每轮修修补补。** 前者一次性付一笔重算，后者反复付。

**挑缓存本就要失效的时刻动手。** 距上次调用已久、缓存大概率过期时，破坏性操作的边际成本接近于零。

摘要还有一处额外开销：它是新内容，必须写入缓存，没有额外断点时会连带让系统提示也重新写入。**在系统提示末尾单设一个缓存断点**，可让系统提示的缓存跨多次压缩持续有效，只有摘要那一小段需要新写。[[2]](#ref-2)

这个冲突有正面解法：把清理的职责下推到接口层——调用方声明「哪些工具结果可以安全遗忘」，服务端在缓存视图里挖空对应位置而**不计作前缀变化**。本地消息记录一条不少（便于调试与回放），缓存又继续命中。它成立的前提是职责分离：判断「哪条可以忘」是业务语义，只有调用方清楚；「挖空但保持前缀可复用」只有服务端做得到。

## 八、历史如何保障

「压缩之后旧内容是不是就没了」——按第一节的三层模型，答案很清楚：**请求载荷里看不到了，事件日志通常还在。** 把这两件事混为一谈会导出完全错误的设计。

于是正确的设计不是让压缩少丢东西，而是**在压缩之前就把不能丢的写出去**。三条具体做法：

**结构化笔记。** Agent 定期把进度、决策、待办写到窗口之外的文件，需要时读回。价值随任务长度增长——在长达数千步的任务里，靠对话历史维持精确计数不可能，靠文件则可以。

**压缩前的预警。** 接近清理阈值时给模型一个提示，让它先把重要内容写进文件再执行清理。这已是被实现的机制：清理策略与记忆工具同时启用时，接近阈值会自动触发这样一段提示。[[1]](#ref-1)

**产物即最强的历史。** 最可靠的保障不是任何记忆机制，而是把中间结论沉淀成产物：代码、报告、结构化数据、缺陷清单。摘要会缩，文件不会。

值得注意的是，「完整历史留在别处」几乎是所有成熟实现的共同选择，只是形态不同——有的把压缩本身也记成事件日志里的一条事件[[6]](#ref-6)，有的给旧消息打时间戳做软删除，有的把完整对话写进虚拟文件系统[[7]](#ref-7)。没有一家真的物理删除历史。

这个一致性本身就是信号：**压缩应当被设计成对历史的一个视图，而不是对历史的一次编辑。**

## 九、什么时候不该压缩

四类任务不适合摘要压缩：

- **需要精确回忆早期细节的**——摘要丢的恰好是这个，应改用外置文件承载，或拆分任务；
- **需要跨多个变量维持精确状态的**——状态应放进结构化字段与摘要分离，摘要负责语义，字段负责事实；
- **需要几段原文同时可见的对照类**——摘要会迫使模型反复重读，净亏；
- **大量使用服务端工具时**——token 统计可能失准，压缩在错误的时机触发。[[1]](#ref-1)

还有三个「不致命但会静默出错」的坑：

- **自定义摘要提示词通常是整体替换，不是追加。** 写了自定义提示词，默认提示词里那些结构化要求会全部消失，需要自己补回来。[[2]](#ref-2)
- **约束会随压缩静默消失。** 只存在于对话历史里的安全约束与权限边界，压缩之后可能就不见了。
- **摘要可能把未完成写成已完成。** 「下一步检查数据库配置」经两轮转述变成「已检查配置」，是真实且危险的失真。

最后一条值得写进校验逻辑：不要把自由文本摘要当作任务状态的唯一来源，保留独立的状态字段与证据引用，发布摘要前校验约束、未完成集合与证据 ID 是否一致。一个摘要可以字数少、语言流畅，同时丢掉约束、伪造覆盖范围、反转测试结果——这几类不一致都能用结构化状态机械检出，不必依赖人工阅读。

## 十、几种实现的对照

分歧点标出了哪些参数是可调的，共识点标出了哪些结论是稳定的。

| 维度 | 常见做法 | 分歧所在 |
| --- | --- | --- |
| 触发口径 | 绝对缓冲 / 窗口百分比 | 绝对量与比例之争，见第四节 |
| 保留窗口 | 最近若干 token / 若干条工具结果 / 固定比例 | 度量单位不同，意图一致 |
| 最小回收量 | 不达门槛就不执行 | 门槛取值不同，机制普遍存在 |
| 重复压缩 | 层叠 / 改写 / 增量更新 | 决定摘要体积是否随次数增长 |
| 历史保留 | 事件日志 / 软删除 / 虚拟文件系统 | 形态不同，都不物理删除 |
| 用户原话 | 逐字保留 / 纳入摘要 | 分歧最大的一处 |

几个各自代表一类思路的细节：

**分层兜底是共识。** 没有一个成熟实现一上来就调模型摘要：先卸载超大工具结果，再卸载陈旧的工具入参，只有「已经没有可卸载的内容」时才摘要。[[7]](#ref-7)「卸载工具入参」这一层最容易被漏掉——写文件的调用参数里带着完整文件内容，而它已经在磁盘上了，属于纯冗余。

**摘要可以是增量更新。** 首次压缩用一套提示词，之后每次用另一套「把新信息合并进已有摘要」的提示词。[[4]](#ref-4)它与层叠式的差别在于明确要求模型维护一份摘要，而不是让摘要自然堆积。

**序列化方式会影响摘要质量。** 把消息序列化成带标签的纯文本（`[用户]:` / `[助手推理]:` / `[工具结果]:`）而非原始对话结构，是为了防止模型把它当成一段待续写的对话；同时在序列化时截断超长工具结果。[[4]](#ref-4)

**压缩请求不必写缓存。** 这类一次性提示几乎不会被复用，用独立会话标识并禁用缓存写入更合理。[[4]](#ref-4)

**把压缩记成事件，压缩器就能无状态。** 压缩结果本身也作为一条事件写进日志后，「哪些内容已被遗忘」就是日志里的既有事实，压缩器不必自己维护这份状态。[[6]](#ref-6)

## 十一、怎么判断压缩做得好

压缩是有损操作，没有度量的调参只是猜。

**先看构成，再谈优化。** 每轮记录总 token 与各类别占比（系统提示 / 工具结果 / 推理 / 消息 / 检索）。绝大多数膨胀问题都能从占比里直接看出来：某一类异常突出，优先治理它收益最大。

**按后续任务检验，而不是按压缩比。** 压缩比只说明输入变小了，不说明系统变好了。可用的做法是从同一执行快照分出未压缩与压缩两支，给相同的后续任务，比较约束遵守、证据可回查、未完成事项覆盖、工具重复调用次数与最终完成率。[[8]](#ref-8)

**分层统计保真度。** 建一组「压缩后必须仍能答对」的问题，把**高层事实**与**冷门细节**分开统计。两者通过率差距通常很大，合在一起会掩盖问题。

**调提示词先召回、后精度。** 先确保抓住轨迹里每条相关信息（哪怕啰嗦），再逐步删减并盯住召回不下滑。反过来做很难收敛。

除完成率之外值得单列的指标：压缩触发次数与时机分布、压缩后的失败率、缓存命中率（压缩会拉低它）、以及压缩后的重复读取次数。最后一项诊断价值最高——每轮都在重读同一份已稳定的文件，说明保留窗口切得太狠。

压缩的失真往往是特定形态的（把待办写成已完成、丢掉某类约束、反转测试结果），一旦出现过就很可能再出现，所以每次修好的样例都该沉淀成回归用例。

## 十二、小结

四句话。

**先分清「不投影」与「改写」。** 前者只改标记位，零成本、可回退；后者需要一次采样且不可逆。多数工程错误来自把前者的直觉套用到后者。

**次序由信息损失风险决定，不由实现难度决定。** 前四级都不产生额外模型调用，且每一级都在替下一级减负。

**能移除的前提是已经固化到别处。** 这比「新旧」「大小」都更可靠。写操作凭证、不可再生的状态、用户原话没有别处可固化，所以不能丢。

**代价不只在信息，还在缓存。** 改动历史会让改动点之后的前缀全部失效，位置比数量更决定成本——这也是「宁可让上下文变长也不要修改它」在生产中成立的原因。

最后一点不属于技术结论但同样重要：**真正的成果始终活在对话之外。** 代码、文件、报告、数据集不会被摘要缩短。这既是压缩敢于有损的前提，也是判断一次压缩设计是否可靠的最终标准——如果任务的成果只存在于对话历史里，那么无论压缩做得多精细，它都是脆的。
