# Knowledge 与 RAG：共享知识的索引与检索链路

Context、memory 与 knowledge 的边界已经由专门的边界导引页区分：context 是当轮输入，memory 是绑定主体的可变状态，knowledge 是按权限共享、随来源版本更新的资料。本页只展开 knowledge 一侧：共享资料如何从来源同步为可检索的索引投影，又如何在生成时被取回、过滤、引用并注入 context。tool observation 读取的是业务系统当前状态，不属于本页范围。

---

## 定义与职责

Knowledge 是独立于单个会话和主体存在的共享资料集合：产品文档、制度文件、Wiki、代码库及其结构化投影。它不在线随交互改写，由离线流水线从权威来源同步；正确性判据是「是否忠实于来源的当前版本」，而不是模型是否相信。

RAG（Retrieval-Augmented Generation）是使用这类资料的生成链路：在生成前从外部索引检索证据，连同引用一起放入本次 context，再要求模型只依据证据作答。RAG 不是知识库本身。知识库是包含来源、片段、元数据与索引的数据层，RAG 是该数据层参与生成的一种装配方式；同一个知识库也可以供搜索、代码导航或审计使用。

Knowledge 层承担四项职责：

- **可检索**：把不同格式的来源转成统一的文本片段与索引，使查询能在可接受延迟内命中证据；
- **可授权**：检索全程服从来源的租户与文档权限，未授权内容不进入候选、日志与最终上下文；
- **可追溯**：每个片段都能回到来源、版本与具体位置，答案中的主张可被引用核验；
- **可演进**：来源更新、删除或更换编码模型后，索引能够增量更新或整体重建，并保持版本对应。

它不承担另外两类职责。绑定用户或项目、随交互失效的信息属于 memory，需要写入门控、冲突消解和按主体删除；订单状态、库存、余额等强一致实时数据属于业务系统，应由工具现场读取，作为 observation 注入。把实时状态复制进知识库，等于用一份持续过期的副本回答关于「现在」的问题。

## 来源类型

知识来源决定解析方式、更新频率和证据定位的最小单位。接入一个来源前，先要确认它能否提供稳定标识、版本依据和权限信息；三者缺一，后续的去重、更新与鉴权都无法可靠完成。

| 来源 | 典型内容 | 证据定位单位 | 更新触发 |
| --- | --- | --- | --- |
| 文档库 / 网盘 | 产品手册、设计文档、PDF | 标题路径、页码、段落 | 文档发布或内容变更 |
| Wiki / 知识库 | 词条、FAQ、操作指引 | 页面、章节、锚点 | 页面编辑 |
| 制度与规范 | 政策、流程、合同模板 | 条款编号、版本号 | 制度发版 |
| API 文档 | 接口定义、字段说明、错误码 | 接口名、字段名 | 文档版本更新 |
| 代码仓库 | 源码、注释、配置、符号 | 文件、行号、FQN | 代码提交 |

API 文档是 knowledge，API 调用返回的实时结果不是 knowledge；前者是对系统的静态描述，后者是业务系统在当前时刻的状态。代码仓库除文本内容外还携带可由静态分析确定的调用、继承和引用关系，其结构化利用属于代码检索专题，本页只讨论与通用 RAG 相同的数据链路。

来源在系统中对应一条 source 记录，最小字段包括：

| 字段 | 作用 |
| --- | --- |
| `source_id` | 来源的全局稳定标识，贯穿所有派生数据 |
| `source_uri` | 回到权威来源的定位地址 |
| `source_version` | 来源版本标识；没有显式版本时用内容哈希替代 |
| `tenant` 与 ACL | 租户标识与授权主体集合 |
| `updated_at` | 来源侧的最后修改时间，用于排序、新鲜度过滤和增量判定 |
| `content_hash` | 规范化内容的哈希，用于判断「更新事件」是否真的改变了内容 |

以修改时间作为唯一变更依据并不可靠：时间戳可能变化而内容不变，也可能被错误回填。内容哈希决定是否需要重建派生数据，修改时间只用于展示与新鲜度判断。

### 采集与同步

全量同步拉取来源的完整快照，增量同步只处理自上次位点以来的变更。增量同步依赖来源提供可靠的变更信号：版本号、修改时间、内容哈希或变更事件。信号不可靠时，只能周期性全量校验兜底。

- 全量同步解决初始化、批量重建和兜底对账问题，代价是带宽与构建成本随语料规模线性增长；
- 增量同步解决持续更新的新鲜度问题，代价是必须维护同步位点、处理乱序与重复事件；
- 只做增量、不做全量对账，无法发现漏同步和链路中途产生的脏数据。

### 解析与规范化

解析把二进制与半结构化格式转成保留版面结构的文本。规范化统一编码、空白、标题层级和语言标记，并输出规范化内容用于哈希计算。这一阶段要保留的不只是文字：表格的行列归属、标题的嵌套关系、代码块的语言、图片的图注，都是后续切分与定位的依据。

解析失败必须显式可见。版面复杂的 PDF 被抽成无结构字符串时，表格错位和标题丢失不会在后续任何阶段报错，却会让相关问题系统性答错。每个来源应记录解析成功率和字段完整率，失败版本不发布。

### 清洗与去重

清洗移除导航栏、页眉页脚、版权声明等与问题无关的模板噪声；去重合并同一内容在不同导出物中的重复副本。去重应作用在来源或段落层，并保留来源映射，不能因为文本相似就删除不同版本中表述相近但效力不同的条款。

清洗过激会删除有效证据，去重过激会把「看似重复、实则版本不同」的内容合并掉。保守做法是保留内容、标记模板噪声，由检索阶段降权，而不是在不可恢复的前提下直接删除。

## 切分：Chunking

切分把规范化文本转成检索单元。一个 chunk 应能独立支持下游的一次判断或回答，同时保留回到原文的定位信息。切分首先是语义决策，其次才是长度控制：固定长度滑窗只适合没有结构的原型文本，正式链路应沿来源自身的边界切。

### 按来源结构选择边界

| 内容类型 | 切分边界 | 必须保留的定位信息 |
| --- | --- | --- |
| 层级文档 | 章节、小节、段落 | 完整标题路径、层级序号 |
| 表格 | 整表或按语义行组 | 表题、列头、行归属 |
| 代码 | 文件、类、函数、方法 | 仓库、文件路径、起止行、语言 |
| 长条款 | 条款号、款项 | 制度名称、条款编号、版本 |

标题路径是切分的一部分而不是冗余字段。孤立的「第三条」无法回答问题；带上「报销制度 v3 → 第三章 → 第三节 → 第三条」后，片段才自带适用范围。

表格不能按字符数硬切。列头与数据行分离后，每一行都失去语义；行数多的表格应整表保留或以行组为单位并重复列头。代码同理，函数签名与其 docstring、返回值被切开后，任何一半都不足以支撑回答。

### Parent / Child 结构

小块的嵌入向量主题集中、召回精确，但缺少上下文；大块上下文完整，却会稀释局部事实并增加编码成本。Parent/Child 用两层结构折中：小块（child）参与召回，命中后取回所属大块（parent）补足语境。

它依赖三个条件：child 与 parent 的归属关系稳定；parent 与 child 共用同一 source 版本；返回 parent 时仍保留 child 命中的精确位置。版本更新若只重切了其中一层，召回内容与上下文就会来自不同版本。代价是索引存储膨胀，以及父子边界需要随切分策略整体维护。

块长短没有脱离模型和数据的通用最优值，应由检索指标、引用定位准确率和生成忠实度共同验证：块过短的典型症状是答案只剩半句条件，块过长的典型症状是精确事实排名下降、注入噪声增加。

切分同时产出片段的标识与定位元数据（字段全集见下一节）。其中起止位置——页码、行号或字符偏移——是切分阶段的直接产物，它不是展示字段，而是引用核验与权限回收的依据。

## 片段元数据与权限模型

片段的元数据分两类：一类解决「回到哪里、属于哪个版本」，一类解决「谁可以看见」。

| 字段 | 解决的问题 |
| --- | --- |
| `source_id` / `source_version` | 片段归属与版本对应，更新时整组替换 |
| `source_uri` + 位置 | 引用跳转与原文核验 |
| `chunk_id` / `parent_id` | 双层结构与父子取回 |
| `content_hash` | 内容变更检测与缓存失效 |
| `tenant` | 租户隔离，是最外层的硬边界 |
| ACL / 授权主体集合 | 文档级、目录级或字段级的可见范围 |
| `index_version` / `embedding_model` | 向量由哪个索引版本、哪个模型生成 |
| `updated_at` / 时效标签 | 新鲜度排序与时间过滤 |

权限可以在同步时快照进索引，也可以在查询时回源鉴权。快照方式过滤快，但来源侧权限变更要等待同步才能收敛；实时鉴权准确，但每次召回都要承担鉴权延迟。常见组合是：租户等粗粒度权限随索引固化，文档级 ACL 尽量随索引同步并在返回前回源复核。两种方式都必须保证权限收紧操作尽快生效，并明确可接受的收敛窗口。

先取全局 Top-K 再做权限过滤是错误顺序：过滤后候选可能所剩无几，更严重的是未授权内容已经进入检索日志、重排服务和缓存。权限条件应在召回前或召回中下推，使搜索只在授权空间内进行；下推不彻底导致的召回不足，要用扩大授权空间内的搜索宽度补偿，不能靠「先看到再过滤」调试。

## 索引：稀疏、稠密与混合

### Embedding 与向量索引

稠密通道把每个 chunk 编码为向量，用近邻搜索召回语义相关片段。编码器决定向量空间中「什么算相近」，ANN 索引只决定在给定空间里以多少精度逼近精确 Top-K；两者的误差要分开测量。模型训练目标、池化方式、相似度度量、索引结构与过滤更新属于文本嵌入和向量检索专题，本页不重复展开。

知识层在这条通道上的职责是保证对应关系正确：

- 向量必须与生成它的文本、切分版本和编码模型版本绑定记录；
- 每个向量带有所属 `index_version`，使检索结果可追溯到具体索引发布；
- chunk 长度不能超过编码模型的有效窗口，截断会让块尾部永远无法被召回；
- 查询分布与文档分布跨领域、跨语言时，应验证通用模型是否适用，而不是默认任何文本共享同一空间。

更换 embedding 模型等于更换打分空间，旧向量不可复用，必须在新索引版本中整体重算；双写、灰度与回滚流程见「版本、更新与删除」。

### 稀疏、稠密与混合

稀疏与稠密通道的打分机制、互补的失败模式以及 ANN 近似误差的测量属于向量检索专题。知识层在此之上要处理的是多通道融合的两个特有问题。

其一是分数口径不可比：BM25 分数与余弦相似度不能直接相加，可用只依赖排名的 RRF，或在已校准的可比口径上加权；无论固定还是学习权重，都必须在冻结查询集上验证，不能凭单批查询调节。

其二是通道覆盖会被融合掩盖：某一路的召回池过小，该路证据根本进不了融合序列，而融合后的单一列表看起来仍然正常。应分别记录稀疏与稠密通道各自的候选数和覆盖率，把「一路失效」与「融合排序错误」区分开。当查询只含错误码、版本号、API 名等精确 token 时，单稠密通道会系统性漏召，这类查询必须由稀疏通道兜底。

`source_version` 与 `index_version` 的完整区分见「版本、更新与删除」。

## 在线检索：过滤、融合、重排与截断

在线链路把一次查询转成证据集。除召回外的每一步都在改变候选集合，因此必须逐层记录候选数量和来源，最终答案出错时才能定位丢失发生在哪一层。

1. **查询规范化**：补全省略、统一格式是可选项，不是必选项。本来已经精确的短查询被改写后，可能丢失唯一的精确词项。
2. **多路召回**：稀疏、稠密及可选的结构化通道各自返回候选，先保证相关证据进入候选池。
3. **权限与元数据过滤**：按租户、ACL、时间、语言、文档类型下推过滤，并记录过滤选择率。
4. **融合与去冗**：合并通道结果；同一文档的多个重叠 chunk 折叠为一个文档组，保留最优点位，避免一份文档占满预算。
5. **重排**：在小候选集上做联合编码精排。重排只能在给定候选内排序，漏召必须在上一层解决；双编码器、late interaction 与 cross-encoder 的接口差异属于文本嵌入专题。
6. **截断**：在 token 预算内选取最终证据，同时考虑分数与文档覆盖：机械取 Top-K 可能让同一文档重复出现、互补证据被丢弃。

三个环节的目标不同，应分别观察指标：候选数与覆盖率属于召回，顺序属于重排，预算内的证据覆盖与重复率属于截断。用一个参数同时调节三层，会让失败无法归因。

## Context 注入与引用溯源

证据进入 context 前要打包成带引用的结构。最小证据单元包含：引用编号、`source_uri` 与 `source_version`、标题路径、具体位置（页码 / 行号 / 锚点）和片段文本。来源元数据与片段文本必须绑定在一起传递，不能只在系统层维护一个模型看不到的映射。

生成侧的指令约束包括三层：

- 只依据给定证据回答，证据不足时拒答或说明无法确认；
- 关键论断附引用编号，一个论断由多处支撑时引用多个来源；
- 来源之间冲突时，不私自选择——按来源权威性与时效性说明分歧。

引用格式解决「挂没挂引用」的问题，不解决「引用对不对」的问题。片段出现在上下文中、模型却把它挂给无关结论，是典型的 citation 错误；faithfulness 与引用准确性的定义、claim 级蕴含校验属于生成评估专题。知识层对校验的特有职责是保证每个引用都带有可核验的版本和位置，否则生成侧无从校验。

注入上下文的不相关证据会稀释有效信息并诱导模型作答。context relevance 衡量打包截断后进入 context 的片段对问题的实际覆盖与噪声比例：检索把相关片段排到了前面，不代表截断后的最终集合仍然相关。它作用在注入层，与召回排序是两个指标。

## 版本、更新与删除

### Source version 与 index version

两类版本必须分开。`source_version` 标识来源内容的某一版，由来源系统或内容哈希决定；`index_version` 标识一次索引发布，由切分策略、编码模型和索引参数共同决定。一个索引版本对应多个 source 版本，一次 embedding 模型升级则会让所有 source 在新索引中重新投影。

查询结果应同时可追溯到两者：答案引用的是哪一版文档，这一版文档由哪一版索引召回。

### 增量索引与全量重建

增量索引处理单个 source 的版本替换：新内容走完 ingestion 链后，以新 revision 生成该文档的新片段与向量，校验通过后原子切换该文档的有效版本，旧片段置 tombstone 并保留回滚窗口。它依赖变更能被准确定位到文档级，且新旧版本的片段可整组对应。

全量重建适用于三类变化：切分策略改变（片段边界全部重画）、编码模型或索引参数改变（打分空间改变）、以及索引损坏或长期增量后无法对账。全量重建期间新旧索引并存，通过双写、双读对比和灰度流量验证新索引，确认指标正常后再切读；旧索引保留一个回滚窗口，不能先删旧索引。

### 删除与可见性

删除是沿派生链逐层生效的操作：源删除后，chunk、向量、倒排项、文档组缓存、答案缓存都要失效。只删除展示层而留下可检索向量，会让被删文档仍能被召回；向量库中的删除常以 tombstone 实现，物理 compact 前的窗口需要在产品语义中明确。

### 缓存隔离

检索结果缓存和语义答案缓存都必须把隔离条件放进缓存键：`tenant`、调用方权限指纹、`source_version` 或 `index_version`。只按 query 文本复用缓存，会让权限较低的用户命中高权限用户的答案；文档更新后缓存不失效，则会让旧答案无限期存活。语义相似度复用还需要相似性阈值与会话范围的约束，缓存层不生产知识，只在隔离条件完全一致时复用结果。

## 评估

RAG 链路的评估必须分层。最终答案正确不能证明召回正确——可能是模型用参数内知识作答；最终答案错误也不能直接归咎于生成——证据可能从未进入上下文。Recall、Precision、MRR、nDCG 的定义、公式与多阶段归因方法属于检索评估专题，本页只说明各指标在知识库系统中回答的问题。

### 检索质量

| 指标 | 回答的问题 | 适用任务 |
| --- | --- | --- |
| Recall@K | 标注相关的证据有多少进入前 K | 多证据问题、召回通道验收 |
| Precision@K | 前 K 中有多少是相关证据 | 噪声敏感、上下文预算紧的场景 |
| Hit@K | 是否至少有一个可回答证据进入前 K | 单一事实问答 |
| MRR | 第一个相关证据排在多靠前 | 单答案、导航式查询 |
| nDCG@K | 分级相关证据的整体排序是否合理 | 证据重要性不同的复杂查询 |

标注前必须先约定评价单元：同一文档被切成多个重叠 chunk 时，按 chunk 计数会夸大召回；需要文档覆盖就按文档聚合，需要证据定位就按片段标注。无标注文档应视为未知而非负例，否则新发现的相关内容会被算作错误。

### 生成侧指标与拒答

Faithfulness 与 citation accuracy 的定义和校验方法属于生成评估专题。在 RAG 链路上需要补充测量的是 context relevance——打包截断后注入片段的覆盖与噪声，它对应截断层而不是召回层；以及拒答的两个方向：证据不存在时正确回答「无法确认」的比例，和证据存在时误拒答的比例。只统计有答案问题，会把覆盖边界上的编造内容计为成功。

### 链路归因

多阶段归因的分层表和 oracle 对照方法属于检索评估专题。落到 RAG 链路上，trace 必须额外覆盖两段：过滤前后的候选集合（用于定位权限与元数据过滤造成的丢失），以及最终注入片段和模型输出（用于区分截断问题与生成问题）。

离线切片在该页列出的通用集合之外，还应补三类知识库特有的查询：权限隔离（同一查询在不同授权身份下的结果）、版本新鲜度（刚更新与刚删除的文档）以及表格与条款定位。质量指标与延迟、索引构建成本、内存占用、更新可见时间一起报告；ANN 参数按 Recall–Latency 曲线选取，口径同样见检索评估页。

## 常见失败模式

| 失败模式 | 发生层级 | 典型成因 | 后果与检查方式 |
| --- | --- | --- | --- |
| 切分断义 | 切分 | 固定长度硬切；表格、条款被拆开 | 答案只含半句条件；检查命中 chunk 是否是自足证据 |
| 解析丢结构 | 解析 | PDF 抽文本丢失表格行列与标题 | 表格、编号类问题系统性答错；检查解析产物而非最终答案 |
| 孤儿片段 | 删除 / 更新 | 源已删但向量或倒排项仍在 | 已删、已改文档仍被召回；核对 chunk、向量、缓存的失效链路 |
| 过期索引 | 版本管理 | 增量漏同步；模型升级后未全量重算 | 回答旧版本事实；核对 source 与 index 版本对应 |
| 通道淹没 | 融合 | 一路候选数过小或融合权重失衡 | 精确匹配或语义匹配单边失效；分通道统计覆盖率 |
| 权限穿透 | 过滤 | 先召回后过滤；缓存键不含权限 | 未授权内容进入候选、日志或缓存；检查过滤下推与返回前复核 |
| 候选不足 | 过滤 | 过滤选择率高但搜索宽度未补偿 | 有权限的正确内容也查不到；测量过滤前后候选数 |
| 引用错配 | 注入 / 生成 | 片段无位置；模型为论断挂无关引用 | 引用存在但不支持结论；做 claim 级蕴含校验 |
| 无拒答 | 生成 | 证据缺失仍强行作答 | 编造内容且看似有据；评估无答案切片与拒答正确率 |
| 来源冲突 | 内容治理 | 多版本制度、互相矛盾的文档并存 | 模型私自选择其中一方；标注权威性与时效，要求显式说明冲突 |

## 取舍边界

**RAG 与直接读源。** RAG 用离线索引换取大规模语料上的低延迟检索，代价是一条需要持续维护的派生链。语料小、目录可枚举、对实时性要求高时，由 Agent 用文件搜索和读取工具直接访问源，反而避免索引滞后；大规模跨团队语料才需要完整索引。两者常组合为「索引定位、读源确认」。

**RAG 与实时 API。** 文档化的静态描述进入知识库；订单、库存、余额等权威实时状态由工具现场查询。判据是问题问的是「资料怎么说」还是「系统现在是什么状态」。后者复制进知识库会持续过期。

**全量与增量。** 变更是局部的、可定位的，用增量索引；打分空间或片段定义变了，用全量重建。把策略变更伪装成增量更新，会让新旧片段混在同一索引版本中，问题无法归因。

**召回深度与成本。** 增大 K、启用改写和重排都能提高召回，但同时增加延迟、噪声和生成侧的上下文压力。调整顺序应从证据丢失的实际层级出发：候选中没有相关内容时加宽召回；候选中有但排不到前面时改重排；证据齐全但答错时改生成侧约束。覆盖不足是召回问题，不能靠更强的生成模型弥补。

知识库不能回答它不包含的内容。来源缺失、权限未授予或解析失败造成的覆盖空洞，在任何排序指标上都不会显现，只能靠来源清单对账、无答案率分析和人工反馈发现。RAG 工程的主要复杂度不在「能不能召回」，而在让派生副本在持续更新中保持授权正确、版本一致且每个结论可追溯。
