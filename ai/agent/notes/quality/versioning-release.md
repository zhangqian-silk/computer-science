# 版本、回归与发布

Agent 行为由提示、工具、上下文策略、控制逻辑和模型设置共同决定。版本管理记录这些组成的变化，回归检查判断变化是否破坏已有能力，发布则把经过检查的组合投入实际使用。

---

## 一、版本不只有程序代码

| 对象 | 可能改变什么 |
| --- | --- |
| 指令与 few-shot | 任务解释和输出风格 |
| 工具描述与实现 | 动作选择和执行语义 |
| 检索索引与资料 | 模型依据的事实 |
| 压缩与记忆策略 | 后续可见的信息 |
| 控制与运行时 | 路径、终止、恢复 |
| 评分规则 | 对「成功」的判断 |

一次实验或发布应能定位实际组合。只保存「新版」标签不能解释之后的行为差异。

```json
{
	"release": "agent-r4",
	"instructions": "prompt-r3",
	"tools": "tools-r2",
	"context_policy": "context-r5",
	"workflow": "flow-r2",
	"evaluation_set": "cases-r6",
	"grader": "grader-r2"
}
```

这份记录用于定位版本，不包含凭据，也不要求把所有原始输入公开保存。

---

## 二、从变更到回归

```mermaid
flowchart LR
	C["变更与假设"] --> T["针对性检查"]
	T --> R["关键回归集"]
	R --> E["质量与成本比较"]
	E --> D["发布或继续修订"]
```

针对性检查证明想修的问题改善；回归集检查此前正常任务是否退化。工具 schema 变化要覆盖旧参数和错误情况，压缩变化要覆盖长历史的约束，提示变化要覆盖容易混淆的边界。

修复一个失败样例后，可将其抽象成同类变体，避免只记住原题。保留集不应成为反复手工调提示的训练材料。

---

## 三、有限范围发布

可以先在受控任务或小范围流量中比较，再逐步扩大。观察任务结果、错误类型、越权风险、尾延迟和成本，不只关注服务是否在线。

阈值应来自产品目标，而不是套用统一数字。高风险写入任务与只读摘要任务，对错误和回退的容忍范围不同。

---

## 四、回退的边界

回退程序或提示不能自动撤销已经发送的消息、写入的数据和对外发布的内容。需分别处理行为版本、持久状态和外部副作用。

运行中的任务可能保存旧契约或检查点。切换版本时，应决定让其按旧版本结束、迁移状态，还是明确停止并重新开始；不能把旧状态交给不兼容的新逻辑继续解释。

评分规则变化后，历史分数也需要重新解释。若旧版和新版使用不同评分器，只比较总分可能把标准变化误认成系统进步。
