# 工具调用机制

工具位于模型与外部系统之间。模型依据概率分布选择操作，参数可能不完整，也可能不符合业务约束；外部系统则要求操作具有确定的身份、权限、顺序和结果。工具机制要解决的问题，是在模型输出、网络传输、人工确认和下游执行均可能失败的情况下，仍然能够判断一次外部操作是否合法、是否已经执行，以及执行后系统处于何种状态。

---

## 一、概念边界

这里需要区分三个层次：模型的调用能力、应用定义的工具、跨进程协议。

| 概念 | 层次 | 含义 |
| --- | --- | --- |
| Function Calling / Tool Calling | 模型 API 能力 | 同一能力的两种叫法：模型把一次调用意图编码为结构化的名称与参数，而不是自然语言 |
| Tool | 应用层能力定义 | 由名称、描述、参数模式和执行器构成的、模型可选择的可执行操作 |
| MCP | 互操作协议 | 规定工具与上下文如何跨进程被发现、描述、调用和返回 |

Function Calling 与 Tool Calling 是同义词，OpenAI 官方文档将二者并列写作「function calling (also known as tool calling)」。名称差异来自接口版本：早期 Chat Completions API 用 `functions` / `function_call` 字段，后续统一接口改用 `tools` / `tool_calls`，能力本身没有变化。本文统一称为工具调用（Function Calling）。

Function Calling 只覆盖模型「输出结构化调用」这一步，不包含运行时的校验、授权、执行和结果处理；后者由应用的工具运行时完成，是本文后续各节的内容。它与 ReAct 也不是替代关系：ReAct 是「推理—行动—观察」的循环策略，Function Calling 是循环中一次行动的结构化表达方式，现代 Agent 通常用 Function Calling 承载 ReAct 循环里的动作。

Tool 与普通函数或 API 的区别在于使用对象和调用方式。普通函数由程序员在代码中静态调用，参数由程序保证；工具由模型依据描述在运行时动态选择，参数可能错误，因此描述本身就是接口约定，且必须在运行时补充校验、鉴权、幂等和结果整形。

一次调用包含五个相互独立的判断：

```text
模型提出调用请求 ≠ 参数合法 ≠ 授权通过 ≠ 外部操作完成 ≠ 任务目标达成
```

MCP 是工具的跨进程分发协议，不是工具本身，也不是安全边界。没有 MCP 仍可在应用内直接注册工具。

## 二、调用链路

一次工具调用不是「模型返回 JSON，然后程序调接口」这么短，而是一条跨越模型、运行时和外部系统的控制链。

<ToolMechanicsSpec figure="pipeline" />

每一轮都从编排层重建模型输入开始。输入由用户当前请求、历史消息、工具定义和上一轮工具结果共同组成；第一次调用没有工具结果，后续调用则把工具结果作为新的观察加入。模型在本轮输出上分两类：产生工具调用，或在信息充分时不调用工具而直接给出最终答复。后者是模型输出分支，而不是工具执行结果。执行层只负责完成工具调用并返回结果；是否继续调用、是否结束循环，由下一次模型调用决定。

图中的编号表示一次工具调用经过的九段。编排层先准备注册信息、工具定义和本轮输入；模型层决定继续请求工具还是给出最终答复；执行层完成校验、授权、调用、通知、结果整理与回填。09 的工具结果沿 ReAct 回环回到编排层，由编排层重新组装下一轮输入；该回环持续到模型不再请求工具为止。各段的主要失效形式列在下表。

| 环节 | 责任方 | 典型问题 | 处理方式 |
| --- | --- | --- | --- |
| 注册与发现 | 编排层、注册表 | 工具数量过多、名称冲突、定义过期 | 权限过滤、候选召回、版本和定义指纹校验 |
| 筛选与注入 | 编排层 | Schema 占用过多上下文，近义工具相互干扰 | 仅注入当前任务所需工具，并保持列表稳定 |
| 构建本轮输入 | 编排层 | 历史、工具定义和工具结果缺失或顺序错误 | 按本轮请求重新组装上下文，工具结果按调用标识归位 |
| 模型输出分支 | 模型 | 工具名称不存在、JSON 截断、参数越界，或在信息不足时直接结束 | 工具调用进入校验；最终答复结束循环 |
| 解析与校验 | 运行时 | 类型、枚举、必填项或业务范围不合法 | 按白名单、Schema 和业务规则校验 |
| 授权与确认 | 策略层 | 权限不足、缺少 scope、高危操作未确认 | 拒绝或暂停执行，不引导模型尝试绕过 |
| 幂等控制与执行 | 运行时、工具 | 超时、重试、重复提交、下游故障 | 幂等键、状态查询、熔断、降级和对账 |
| 通知与结果整理 | 工具、运行时 | 长任务断线、结果过大、截断后信息不完整 | 进度通知、任务句柄、分页、落盘和结构化结果 |
| 结果反馈与验收 | 编排层 | 调用标识错位、错误信息为空、模型反复尝试 | 按调用标识配对结果，并依据环境最终状态验收 |

<div class="atms-callout atms-callout--key">
<span class="atms-callout__k">关键原则 · 错误信息用于下一轮推理</span>
参数错误、业务规则错误和可恢复的下游故障，应作为工具执行结果返回模型，并说明错误原因、合法取值及修正方式。协议级错误只用于工具不存在、消息格式非法或能力不受支持等模型无法通过修改参数解决的情况。权限拒绝不应写成可能诱导模型改换路径的提示：参数错误适合由模型修正，权限边界不应交由模型试探。
</div>

工具结果必须与调用标识一一对应。并行调用的结果可以按任意顺序返回，但每个 `tool_calls` 条目都必须有对应的结果消息。压缩历史时也不能单独删除其中某条工具结果，否则后续请求可能因调用记录不完整而失败。

### 循环护栏

即使单次调用合法，ReAct 循环仍可能因反复调用或目标漂移造成损失，常见病态包括反复调用同一工具、两个工具来回乒乓、始终不收敛。运行时需要四类护栏：

- **硬上限**：限制最大步数、token、耗时、费用和下游调用次数，触顶后基于已有信息收敛并说明未完成项；
- **重复检测**：对工具名与归一化参数做哈希，窗口内重复计数，命中后回灌历史结果并提示不要重复调用；
- **无进展检测**：连续若干步没有新信息或状态变化时切换策略或上报阻塞；
- **预算感知**：把剩余预算写入上下文，使模型主动选择成本更低的路径。

任务是否完成以外部环境的最终状态为准，而不是模型的自述。

## 三、工具的结构与实现

一个可被模型可靠使用的工具，包含定义面、执行面和控制面三部分。

| 组成面 | 内容 | 作用 |
| --- | --- | --- |
| 定义面 | `name`、`description`、输入输出 Schema、行为注解 | 供模型选择、运行时分派和策略层判断 |
| 执行面 | 参数绑定器、执行器、错误归一化、结果整理器 | 把合法参数变为一次确定的外部操作并整理返回值 |
| 控制面 | 所需 scope、幂等键来源、超时与限流、人在环要求 | 声明并落实该操作的安全与可靠性约束 |

### 定义面

模型通常不能直接读取工具源码和内部文档，工具定义就是它判断用途的全部依据。

| 字段 | 主要使用者 | 设计要求 |
| --- | --- | --- |
| `name` | 模型、路由器 | 名称稳定、语义具体，能够与相近工具区分 |
| `description` | 模型 | 说明能力范围、适用条件、限制、副作用和替代工具 |
| 输入 Schema | 模型、运行时 | 通过类型、枚举、取值范围和必填项限制不合法参数 |
| 输出 Schema | 模型、调用方 | 稳定表达执行状态、关键标识、分页信息和错误 |
| 行为注解 | 界面、运行时 | 提示只读、破坏性、幂等性和开放世界属性，但不构成授权 |

工具选择错误往往不是因为模型缺乏推理能力，而是描述没有给出排他条件。较完整的描述通常包括四类信息：能力本身（操作、对象和关键限定）、适用边界（不处理哪些对象、应改用哪个工具）、输入输出约束（格式、单位、时区、枚举、分页和返回上限）、代价与副作用（是否写入、计费、外发、删除，是否需要人工确认）。

### 执行面与控制面

运行时已经掌握的信息不应再要求模型填写。例如上一步已经取得订单号，退款工具应由运行时自动绑定该标识，而不是要求模型再次转录。经常连续调用且中间无需模型判断的两个工具，也可以合并为一个工具，以减少标识符复制错误和多余往返。

实现一个工具运行时，至少需要以下部件：

- **注册表**：保存工具定义、来源、版本和行为注解；
- **候选筛选**：按权限和任务相关性决定本轮注入哪些工具；
- **参数校验器**：做结构校验、类型归一和业务范围检查；
- **策略判定点**：在执行前完成 scope 校验、限流和人在环确认；
- **执行器**：发起调用并处理超时、重试和幂等；
- **结果整理器**：裁剪、分页、落盘并生成结构化结果；
- **循环与预算控制**：限制步数、时长、费用和调用次数；
- **审计记录**：记录调用参数、授权快照和执行结果。

工具返回值既是程序中的 API 响应，也是下一轮模型输入。错误应可修正、字段应稳定、关键实体应可识别；结果契约的具体控制方法见第五节。

### 模型出参的校验

即使模型开启了结构化输出，工程侧仍要保留兜底校验。常见故障与处理方式如下：

| 故障形态 | 成因 | 处理方式 |
| --- | --- | --- |
| JSON 截断或不闭合 | `max_tokens` 截断、流式未收完 | 先判断 `finish_reason`，截断则提高上限重新生成，不做括号补全 |
| 字段类型不符 | 参数被字符串化，如 `"limit": "20"` | 宽松解析层做类型转换与范围裁剪，合法后再执行 |
| 幻觉字段或幻觉工具名 | Schema 未封闭、工具集含相似项 | 封闭额外字段；工具名走白名单匹配，未命中直接返回错误 |
| 枚举越界 | 描述未穷举合法值 | 在 Schema 中显式声明枚举，错误消息列出合法取值 |
| 必填项缺失 | 用户输入本身信息不足 | 不猜测默认值，返回可读错误，让模型向用户追问 |

## 四、工具分类与执行策略

工具能否重试、并行或自动执行，应由其属性决定，而不是由名称或提示词决定。

<ToolMechanicsSpec figure="dimensions" />

四个属性维度相互独立。一个只读的网页抓取工具仍可能引入提示注入；一个具备幂等性的退款操作仍然需要金额阈值和人工确认；开放世界工具返回的文本即使出现在工具结果中，也不因此成为可信指令。

除属性维度外，工具还可按实现形态分类，实现形态决定延迟、确定性与主要风险。

| 实现形态 | 典型形式 | 确定性 | 主要风险 |
| --- | --- | --- | --- |
| 内置函数 | 本地计算、格式处理 | 高 | 逻辑错误、边界条件 |
| 远程 API | 业务系统的读写接口 | 中 | 超时、权限、重复提交 |
| 脚本与 CLI | 沙箱内命令 | 高 | 命令注入、资源越界 |
| 数据库与检索 | 查询、搜索、向量召回 | 中 | 越权读取、结果规模 |
| 子 Agent | 委派给独立上下文执行 | 低 | 上下文隔离、结果可信度 |

### 行为注解与授权边界

`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 等字段由工具提供方声明。存在缺陷或不可信的 Server 可能为删除操作标注只读属性。Host 必须依据 Server 身份、工具名称和版本、实际参数、用户 scope、目标资源及操作风险独立作出授权判断。

缺少标注时可以采用保守的默认解释，但默认值只能约束未填写标注的实现，不能防止提供方故意伪造属性。真正的安全边界应由白名单、参数级规则、沙箱、审批和审计构成，而不是工具描述或行为注解。

## 五、执行语义与故障处理

### 结果规模控制

结果设计的目标不是尽可能完整地返回原始数据，而是提供与后续判断直接相关的信息，同时控制上下文规模。

| 方法 | 解决的问题 | 设计要求 |
| --- | --- | --- |
| 字段选择 | 排除内部字段和无关数据 | 优先返回名称、类型、状态和游标，避免无约束的 `SELECT *` |
| 语义化标识 | 降低长标识导致的遗忘和虚构 | 保留内部 ID 的同时，为选择和展示提供可读名称 |
| 结构化结果 | 减少自然语言解析 | 用稳定字段表示状态、错误、分页和关键实体 |
| 分页与范围限制 | 控制单次返回大小 | 设置默认 `limit`，返回 `next_cursor`、总数或完成状态 |
| 落盘与引用 | 处理大文件和批量结果 | 上下文中只保留路径、摘要和 Schema，详细内容按需读取 |

治理顺序应从工具接口开始：先提供过滤、字段选择和分页能力，再由运行时整理结果，最后才考虑压缩历史记录。先读取全量数据再在运行时截断字符串，会丢失总数、分页游标、错误码和结果边界。

### 通知三态

短任务可以绑定一次请求，长任务、人工审批和外部作业不能假设客户端始终在线。

<ToolMechanicsSpec figure="notify" />

进度通知只能表明请求仍在执行，可用于刷新活性判断，但不能取消最大执行时限。任务句柄必须在服务端完成持久化创建后返回，使客户端在断线或重启后仍能依据任务标识查询状态。

### 持久任务的状态机

长任务对外暴露统一的状态集合，客户端按状态决定轮询、补充输入、等待结果或放弃：

<ToolMechanicsSpec figure="task-state" />

`working` 表示任务执行中；`input_required` 表示任务暂停等待客户端补充信息，补充后继续；`completed`、`failed`、`cancelled` 是三个终态。任务实现还应定义 TTL、轮询间隔建议、最终结果保存时长和补充输入的回填方式。协议把长任务收编为统一状态机，价值在于客户端能用同一套轮询入口、进度界面和取消语义处理不同来源的工具，而不必适配每个 Server 自定义的 `start_job` 与 `get_job_status`。

### 取消的三个层次

取消按作用范围分三层，语义强度不同：

| 层次 | 机制 | 语义 |
| --- | --- | --- |
| 请求级 | 取消通知 | 通知式，接收方应停止处理，但已产生的副作用无法回滚 |
| 传输级 | 关闭请求对应的响应流 | 连接断开即视为取消；流不可恢复时需要以新请求重发 |
| 任务级 | 任务取消 | 协作式，服务端确认意图但不保证真正停下 |

因此取消不能作为「副作用未发生」的保证；写操作取消后必须对账或补偿。

### 超时与重试

超时不是单个固定阈值，而是一条由外向内逐层收窄的预算链：任务总时限、当前步骤预算、单次工具执行时限、下游请求时间，以及结果整理和后续模型调用所需时间。子调用的超时应取自身配置与父任务剩余预算中的较小值，而不是写死常量，否则任务尾段会出现子调用尚有额度、父任务却已到期的错配。

<div class="atms-callout atms-callout--trap">
<span class="atms-callout__k">注意 · 客户端超时不等于操作未执行</span>
超时只表示调用方停止等待响应，并不表示服务端事务已经回滚。写操作超时后应先查询业务状态，或使用同一幂等键重新提交，不能直接发起新的写入请求。
</div>

能否重试先按错误性质分类，再看操作是否幂等、预算是否允许：

| 类别 | 典型错误 | 处理 |
| --- | --- | --- |
| 可重试的瞬时错误 | 连接超时或重置、DNS 抖动、HTTP 408 与 429、500、502、503、504 | 指数退避并加随机抖动，429 优先服从 `Retry-After` |
| 不可重试的确定性错误 | 参数或 Schema 不合法、401 与 403、404、业务规则拒绝 | 不重试，直接返回模型修改参数或终止 |

抖动用于打散多个调用者同时重试形成的脉冲；熔断解决持续故障，避免在已不可用的下游上反复消耗任务预算，熔断后应给出可执行的降级路径。退避、熔断和限流的通用实现见系统设计专题。

### 幂等

模型会因网络重试、多轮遗忘、用户重放而重复发起同一操作，因此写类工具默认必须幂等。幂等按作用域分三层：

| 幂等范围 | 防止的重复来源 | 标识示例 |
| --- | --- | --- |
| 单次执行 | 同一次请求的网络重试 | 编排层调用标识、请求标识 |
| 单次会话 | 模型在同一会话中重复提出相同操作 | `session_id + tool + normalized_args` |
| 业务周期 | 用户或系统重复发起同一笔业务 | 订单号、退款单号、业务事件标识 |

幂等键有三种来源，优先级从高到低：业务唯一键，语义最清晰；由工具名与归一化参数确定性派生，参数需先排序键、去空值、统一数值精度，否则同义参数会得到不同键；由编排层在调用前生成 `Idempotency-Key` 并在重试中沿用。每次重试重新生成随机 UUID 只能区分两次网络请求，不能防止同一笔业务被执行多次。

防止重复执行需要三层配合：传输层让重试沿用同一键并缓存首次结果；编排层对「工具名加归一化参数」做窗口内重复检测，命中则回灌历史结果；业务层以唯一约束和单向状态机作为最终防线。

### 并发层级

Agent 语境下的并发分三层，控制手段不同：

| 层级 | 含义 | 控制手段 |
| --- | --- | --- |
| 单轮多调用 | 模型一次返回多个工具调用 | 信号量或协程池限流；只对彼此独立的只读操作并行，写入或有参数依赖的调用串行化 |
| 多 Agent 并行 | 多个子 Agent 各自调用工具 | 全局配额池加每个 Agent 的子预算，防止共享资源写冲突 |
| 多会话并发 | 平台层大量会话同时运行 | 租户隔离、优先级队列与背压，避免单个大任务饿死其他会话 |

需要注意，部分模型在同轮并行调用多个函数时会关闭严格结构模式，此时 Schema 校验必须由运行时自行完成。

## 六、安全与人在环

安全控制不能依赖工具描述或模型自觉，必须落在运行时的独立判定点上。

### 授权与开放世界

授权判定应先于工具执行：按 Server 身份、工具名和版本、实际参数、用户 scope 和目标资源判断，拒绝规则优先于允许规则，且不应被「放宽模式」绕过。最小 scope 授权、参数级策略和高危操作增量授权，比一次性授予宽泛权限更可控。

网页、邮件、工单等开放世界工具返回的内容属于不可信数据。其中可能藏有诱导模型读取私有数据或外发信息的指令，因此应与私有数据读取和外发能力隔离，并对出站目标加以限制。工具结果即使出现在上下文中，也只按数据处理，不按指令执行。

### 人工确认的恢复语义

人工确认解决的是副作用是否允许发生，而三种暂停机制的差别在于恢复后从何处继续执行。

<ToolMechanicsSpec figure="approval" />

异常式中断在恢复时会重新执行整个节点，因此中断前的写操作必须幂等，或者把扣款、发布、外发等操作放在用户确认之后。可序列化状态适合持续较长时间的审批流程，但要求状态完整持久化。回调式放行在运行时中等待授权结果，外部调用尚未发出，重复风险最低。选型的关键不是能否暂停，而是副作用应安排在确认点之前还是之后。

除「在何处恢复」外，确认还需确定授权范围。授权可按本次调用、本会话同类操作、长期放行分级，并对每一次确认记录工具版本、参数与授权时间快照；高危操作不应提供长期放行选项。

## 七、工具规模与注册表管理

工具数量增加后，会产生两类性质不同的上下文开销：

| 开销类型 | 产生原因 | 治理方法 |
| --- | --- | --- |
| 工具定义开销 | 大量 Schema 在每轮请求中重复出现，且通常位于提示词前部 | 权限过滤、分组、语义召回、延迟加载、少量核心工具常驻 |
| 中间结果开销 | 多步工具结果全部进入历史上下文 | 字段裁剪、分页、落盘、代码编排，仅返回最终摘要 |

按需检索主要减少工具定义开销：初始只保留少量核心工具和一个工具检索入口，命中候选后再展开完整定义。代码编排主要减少中间结果开销：循环、筛选和聚合在执行环境中完成，只有最终结果进入上下文。两者针对不同问题，可以组合使用。

工具数量增长带来的退化是非线性的：Schema 开销随数量线性增长，但候选间语义边界模糊后，选择准确率会在某个区间明显下降。因此需要按规模选择候选方案：

| 方案 | 机制 | 代价 |
| --- | --- | --- |
| 静态分组 | 按业务域预先分组，只挂载相关组 | 确定性强但不灵活，跨域任务需手动切换 |
| 语义检索 | 工具描述入库，按任务召回 Top-K | 可扩展到上千工具，但召回不准则工具不可达 |
| 分层路由 | 先判命名空间再加载该系统工具 | 搜索空间逐层收窄、可解释，但需要维护层级 |
| 模型自主检索 | 提供 `search_tools` 元工具，由模型按需检索 | 与推理融合，但多一次往返，依赖模型主动使用 |

生产上通常组合使用：权限过滤先排除不可见工具，语义召回粗筛，再由规则或小模型精排到少量候选，同时让少量高频核心工具常驻，避免召回失败导致基础能力缺失。

动态工具集合还要求注册表承担以下职责：

- **命名空间隔离**：内部标识包含团队、Server 和工具名称，避免不同来源的 `read_file` 相互覆盖；
- **先授权后召回**：用户无权使用的工具不应进入语义候选；
- **定义指纹**：识别描述、Schema、scope 或副作用是否发生实质变化；
- **变更确认**：敏感工具的定义变化后重新确认授权，因为用户授权的只是某一时刻的工具快照；
- **版本兼容**：新增可选参数可以兼容，删除字段、收窄枚举、改变单位或副作用时应使用新工具名；
- **质量度量**：按工具版本统计选择失败率、参数错误率、执行失败率、人工拒绝率、结果大小、重试次数和幂等键命中率。

动态注册还要解决三个运行时问题：变更如何被感知（Server 声明列表可变更，变化时通知客户端重新拉取）、缓存如何失效（工具定义是提示词的一部分，变更会击穿前缀缓存，因此列表应保持确定性顺序并标注新鲜度）、热变更的安全边界（实际执行的工具可能已不同于授权时的版本，需要指纹比对与重新授权）。

工具治理的目的不是隐藏工具，而是在合适的任务阶段向模型提供少量合法、相关且定义清晰的候选。工具数量较少时，全量注入更简单；当工具来自多个团队且持续变化时，注册表、候选召回和审计机制才成为必要设施。

## 八、MCP：跨进程标准化

若没有统一协议，$M$ 个 Host 接入 $N$ 个工具来源需要编写 $M \times N$ 套适配代码。MCP 将工具发现、能力描述、调用和结果返回标准化，使集成数量降为 $M+N$。

<ToolMechanicsSpec figure="trust" />

Host、Client 和 Server 的职责应当明确区分：

| 角色 | 职责 |
| --- | --- |
| Host | AI 应用，持有模型访问权、用户身份、工具策略、预算、人工确认和最终执行决策权 |
| Client | Host 为每个 Server 建立的独立连接，隔离不同 Server 的上下文与能力 |
| Server | 提供 Tools、Resources、Prompts 的本地或远程服务，应按外部依赖处理 |

三类服务端原语按照「由谁决定使用」区分：

| 原语 | 决定者 | 内容 | 典型形式 |
| --- | --- | --- | --- |
| Tools | 模型选择，Host 授权 | 可能产生副作用的操作 | 函数调用 |
| Resources | 应用或用户选择 | 通过 URI 定位的只读上下文 | 文件、Schema、配置 |
| Prompts | 用户显式触发 | 可参数化的提示模板 | 斜杠命令 |

| 传输方式 | 适用场景 | 要点 |
| --- | --- | --- |
| STDIO | 本地工具、CLI 集成、开发调试 | Server 作为子进程经标准输入输出通信，日志必须走 stderr，避免污染协议流 |
| Streamable HTTP | 远程、多客户端、生产部署 | 单端点 POST，可在响应上以流式返回，支持无状态部署与标准 HTTP 授权 |
| HTTP + SSE | 已弃用 | 双端点设计，已被 Streamable HTTP 取代，新实现不应采用 |

### 无状态化演进

协议演进的主线，是逐步减少对连接状态的依赖：

<ToolMechanicsSpec figure="evolution" />

这一方向解释了为什么工具列表应保持确定性顺序，为什么列表结果可以携带缓存范围和有效期，也解释了为什么长任务需要独立扩展。协议简化并不意味着复杂度消失，而是将其转移到任务句柄、授权管理、应用状态和扩展协商中。

### MCP 不解决的问题

标准化的是消息格式与发现流程，不是信任关系：

- Server 提供的描述、注解和返回结果不能直接作为授权依据；
- 不应将签发给其他受众的 token 原样转发给下游，以避免 Token Passthrough 和 Confused Deputy；
- 工具定义动态变化时仍需校验指纹、发出告警，并对敏感能力重新授权；
- 本地 STDIO Server 通常与用户进程具有相同权限，协议确认不能替代操作系统沙箱；
- 长任务、幂等、人工确认和结果治理仍由 Host 与应用承担，详见前文对应章节。

## 九、Tool、Skill、CLI 与子 Agent 的分工

不是所有能力都应以常驻工具形式提供。四类载体处理的对象不同：

| 载体 | 处理对象 | 使用方式 | 适用场景 |
| --- | --- | --- | --- |
| Tool | 原子操作及其副作用 | 模型逐轮选择，运行时授权执行 | 查询、写入、发送消息、修改文件 |
| Skill | 过程性知识与验收标准 | 元信息常驻，正文匹配后加载 | 领域规范、操作流程、检查清单 |
| Code / CLI | 确定性数据处理与编排 | 模型生成或选择命令，在沙箱执行 | 日志统计、批量转换、循环过滤 |
| 子 Agent | 独立上下文中的子任务 | 委派执行，只回传结论 | 探索性调查、需权限隔离的并行任务 |

选型时先判断缺的是什么：缺外部系统的连通能力，接入 MCP Server 或注册 Tool；缺可复用的操作流程，编写 Skill；需要处理大量中间数据，交给脚本或 CLI；需要隔离噪音输出或工具权限，委派给子 Agent。工具提供「能做什么」，Skill 提供「何时、按何种顺序做」，二者正交互补。

Skill 不授予执行权限。它可以说明何时调用工具以及完成后如何检查，但授权、scope、审批和副作用边界仍由工具运行时负责。Skill 的三级渐进式加载、与 Prompt、Knowledge、Subagent、MCP 的完整对照，以及指令与脚本的分工，属于 Skill 机制本身。

面向 Agent 的 CLI 应具备稳定契约：

- `--help` 与子命令说明可在运行时查询，无需将完整参数表常驻上下文；
- stdout 返回机器可读结果，stderr 输出日志和诊断信息；
- 退出码区分成功、参数错误、业务失败和环境缺失；
- 支持幂等重入、断点恢复和 `--dry-run`；
- 大日志写入文件，stdout 仅返回摘要、路径和状态；
- 错误信息包含错误码、原因和修复建议，使模型能够判断应修改参数、补齐依赖还是请求授权。

工具结果作为本轮上下文的组成部分，与历史、记忆和知识的分工在于：历史和记忆保存跨轮信息，知识提供可检索的背景材料，工具结果反映外部系统在调用时刻的状态。
