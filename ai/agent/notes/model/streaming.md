# 流式响应与模型适配

流式接口把一次响应分成多个事件交付，减少用户等待，并允许应用显示进展。它改变的是传输和消费方式，不自动改变模型能力，也不保证更低的总完成时间。这里处理字节、事件、内容项和终态之间的转换。

## 字节流、协议事件与业务消息

一段 TCP 数据可能只包含半个 UTF-8 字符，一次读取也可能包含多个 SSE 事件。SSE 数据里的 JSON 又可能是某个内容块的增量，而不是完整 assistant 消息。直接对每次网络 `read()` 调用 `json.loads()`，只在碰巧对齐时正常。

解析链应当是：增量字节解码 → 按传输规范组帧 → 解析事件 JSON → 按响应/内容项 ID 累积 → 接收权威完成状态。HTTP 断开不是正常完成事件，最后一段文本看起来完整也不能证明后面的工具调用不存在。OpenAI 流式文档定义了区分文本增量与响应事件的处理接口。[[13]](../references.md#source-openai-stream)

客户端显示可以提前；执行承诺不能提前。UI 显示“参数正在生成”与工具实际进入执行状态，应有不同事件。不要把流式回调当成可靠消息队列；其重复投递、丢失和重连行为需要应用另行定义。

## 工具参数的独立组装

```python
# 教学代码：输入已由 SSE/JSONL 层解码，事件格式为内部示例。
import json

class CallAssembler:
    def __init__(self, byte_limit=64_000):
        self.calls = {}
        self.byte_limit = byte_limit

    def add_delta(self, call_id, name, fragment):
        current = self.calls.setdefault(
            call_id, {"name": name, "parts": [], "size": 0, "done": False}
        )
        if current["done"] or current["name"] != name:
            raise ValueError("调用身份变化或完成后继续增量")
        current["size"] += len(fragment.encode("utf-8"))
        if current["size"] > self.byte_limit:
            raise ValueError("参数超过上限")
        current["parts"].append(fragment)

    def finish(self, call_id):
        current = self.calls[call_id]
        if current["done"]:
            raise ValueError("重复完成事件需要由上层去重处理")
        arguments = json.loads("".join(current["parts"]))
        if not isinstance(arguments, dict):
            raise ValueError("本工具协议要求对象参数")
        current["done"] = True
        return {"id": call_id, "name": current["name"], "arguments": arguments}
```

两项调用的片段可以交错到达。按“最近工具名”累加会造成参数串线。上例只负责组装，不意味着 `finish()` 之后立即运行：保守策略是等待整个响应成功结算；支持 item-level 早派发的实现，则必须依据供应商对该 item 的权威完成语义，并预先定义稍后响应失败时如何收尾。

重复完成事件也不能每次执行。上层可用响应 ID 与 item ID 记录同一传输事件是否已经消费；若重复 ID 携带不同参数，应报协议冲突，而不是静默覆盖。

## 原生流到内部事件的适配

内部事件不应只有 `text_delta`。至少需要表示响应开始、内容项开始/增量/结算、调用结果、响应结束和错误。对于 UI，不一定需要公开全部内部事件；对于执行器，最终状态必须能追溯到供应商事件。

| 内部层 | 可暂时丢弃或合并 | 不能随意丢弃 |
| --- | --- | --- |
| 用户显示 | 高频文本 repaint、重复进度条 | 最终答案、需用户操作的请求 |
| 模型输入历史 | 仅用于 UI 的日志 | 已接受调用、对应结果、必要原生续接条目 |
| 恢复记录 | 可从最终文本重建的显示片段 | 已承诺动作、回执、完成与失败边界 |
| 观测 | 高频重复采样 | 请求标识、实际用量、关键错误和终态 |

这不是要求四套全量日志，而是说明同一数据可以有不同投影。把所有进度都塞回模型既浪费上下文，也可能让模型把日志误当成用户新要求。

Pi 的模型消息转换边界，以及 Codex 持有当前步骤工具上下文的实现，都说明传输与业务执行可以分开。尤其当流式期间工具集发生更新，本轮调用不能随意绑定新 schema；下一轮才采用新快照，策略撤销则仍应即时生效。[[9]](../references.md#source-pi-loop) [[14]](../references.md#source-codex-tools)

## JSONL／RPC 与 HTTP 请求

编码 Agent 的原生 RPC 通常还存在会话、请求接受、流式进展和最终结果四层。一个 `prompt accepted` 只证明输入被接纳，不能将其映射成任务完成。请求 ID、原生 session ID 和任务 ID 也有不同生命周期。

对于逐行 JSON 协议，要按真实协议规定的 LF 分隔，而不是任意“看起来像换行”的 Unicode 字符。每条记录有大小上限；stdout 用于协议，日志放 stderr 或独立事件。若 CLI 混入 ANSI 终端控制字符，优先使用其机器接口，不靠宽松正则猜测正常输出。

远程断开后，可以重新获取权威任务状态、重新订阅事件，或者显式判定无法续接。不能仅靠重发同一 prompt 恢复：这可能创建新原生会话，并重复外部动作。

## 阶段超时与取消范围

至少区分连接建立超时、首个有效事件超时、语义无进展超时、总 deadline 和工具自身 deadline。每隔几秒收到心跳只能说明连接活着，不说明任务有进展；一次合法的长工具调用也可能没有文本输出，不能仅凭“没有字符”杀掉。

取消要传播给 HTTP 请求、当前模型流、已开始工具及其子进程。但释放 UI 的等待不等于这些工作已停止。取消协作代码可能要排空，非协作同进程代码无法可靠硬杀，外部已提交动作需要对账。

一个实际需要防止的竞争是：工具已经达到终态，取消恰好到达。Codex 指定提交在处理取消时先检查终态或任务是否已结束，再决定是否 abort；该设计避免用晚到取消覆盖已知结果。它不等于保证远端操作可回滚。[[14]](../references.md#source-codex-tools)

## 背压与存储

缓慢浏览器不应阻塞模型流读取，直到供应商超时。可在网络读取与 UI 推送之间使用有界队列，对文本增量做合并，保留最终快照；执行事件要么可靠写入，要么让消费者知道需要重同步，不能无声丢弃。

若队列满后把所有增量积累到内存，所谓“流式省内存”就不成立。限制单响应大小、单工具输出和每订阅者积压，并记录丢弃的是显示增量还是关键事件。敏感内容应在写日志前按目标通道处理，不能指望 UI 隐藏就保护后端存储。

LangChain Forum 中有人报告子 Agent 的中间消息在页面刷新后消失。这是一份用户现象记录，不是本资料独立复现的框架缺陷；它适合转成测试：实时显示数据是否也进入可恢复状态，最终汇总是否足够重建进展，刷新后有哪些明确损失。[[15]](../references.md#source-forum-subagent)

## 验证与调优方法

构造离线事件序列，比依赖真实网络随机失败更有效。把同一 UTF-8 文本在每个字节位置切开；让两项工具调用交错；重复一项结算；省去最终事件；完成后追加增量；让队列消费者故意慢十倍。预期不只是“解析不崩溃”，还包括无提前执行、无重复调用、错误状态不被最后一段文字掩盖。

调优分别报告 TTFT、首个可用内容时间、最终完成时间、解析与转发时间、缓冲峰值和取消到资源静止时间。首字符更快但完整任务更慢，不一定是改进；一个字符的“正在处理”也不应被算成用户已得到有效答案。

## 时序实例：两项调用交错与中途断开

考虑下列已解码事件：

```text
1 response_started
2 call_started c1 read_file
3 args_delta c1 '{"path":"a'
4 call_started c2 read_file
5 args_delta c2 '{"path":"b.py"}'
6 call_finished c2
7 args_delta c1 '.py"}'
8 call_finished c1
9 connection_closed（没有response_completed）
```

展示层可以显示两项参数已经形成；保守执行层仍返回整体未完成并保持执行数为零。若采用item完成即派发，c2可能已经执行，此时必须保存它的真实回执，把整体响应异常与已完成动作分开，不能重连后盲重放两项工具。

这正是早派发的权衡：减少等待，但增加部分失败状态与恢复复杂度。对于只读工具可以较早尝试；具有不可逆效果的工具则需要更严格的完整性和审批边界。不要把低延迟策略无条件应用到所有工具。

## 断线重连的三种策略

**重新订阅**从已持久事件序号续收，适合运行独立于客户端的服务。**重新取快照**获取当前权威状态，允许丢失某些显示增量但不丢关键结果。**重新发请求**只在确定原请求未产生需要保持的动作，或原生协议明确支持幂等续接时使用。

实现时可在客户端保存`last_seen_seq`，服务端回答增量或要求重拉。若历史保留已过期，返回明确的重同步指令，不伪造连续事件序号。重复增量和重复终态的去重应基于身份，不能仅用文本相同判断；模型可能合法输出两个相同句子。

## 协议分帧与性能测试

先用字节切片验证协议正确性，再用大流验证内存与速度。小fixture可以穷举每个切分位置，真实大文则使用受控随机分段。衡量组装器保留了多少未完成内容，超长工具参数是否及时拒绝，日志是否泄露原始秘密。

网络读取任务与UI输出任务之间有界队列要有明确满队列策略。不能为了不卡UI无限缓存，也不能丢掉唯一的工具完成回执。将高频文本合并成最新快照、关键结果可靠提交，是一种可测的折中。
