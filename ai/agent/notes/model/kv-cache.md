# KV Cache 与请求缓存

缓存复用的是计算或结果，不是模型对用户的长期记忆。这里区分模型内部 KV、跨请求前缀复用、供应商计费缓存和应用结果缓存；输入内容怎样选择见 [Context Engineering](../context/context-engineering.md)，持久业务状态见 [Memory](../context/conversation-memory.md)。

## KV Cache 的复用原理

在常见的因果 Transformer 解码中，已经生成位置的 Key 和 Value 可供后续 token 注意力计算使用。继续生成时保存这些张量，避免每一步重新计算全部历史位置的 K/V。它仍需要让新 Query 读取相关历史，因而不是“历史长度从此不影响计算”。

一次新请求若与旧请求共享完全一致、兼容的前缀，推理服务还可能复用那段前缀的 KV。这里的关键是模型计算所见的 token 和配置，不是人眼觉得语义相同。空格、工具 schema 顺序、系统指令前插内容和模型/适配版本，都可能改变复用条件。[[4]](../references.md#source-hf-cache)

vLLM 的 Automatic Prefix Caching 文档把收益明确定位在 prefill：复用已存在前缀的计算，不减少生成新 token 的 decode 工作。因此长输入短输出与短输入长输出，应分别测量，不能只报一个“缓存加速倍率”。[[16]](../references.md#source-vllm-apc)

## KV Cache 的显存估算

对使用全长度 K/V、层间结构一致的普通 MHA/GQA 解码器，可近似估算：

$$
M_{\mathrm{KV}} = 2 L B T H_{\mathrm{kv}} D s
$$

其中 `L` 是层数，`B` 是活跃序列数，`T` 是每序列已缓存 token 数，`H_kv` 是 KV 头数，`D` 是每头维度，`s` 是每元素字节数。前面的 2 来自 K 和 V。下例是教学算例，不是任何实际产品型号。

```python
layers, batch, tokens = 32, 1, 8192
kv_heads, head_dim, bytes_per_value = 8, 128, 2
bytes_used = (
    2 * layers * batch * tokens
    * kv_heads * head_dim * bytes_per_value
)
print(bytes_used / (1024 ** 3))   # 1.0 GiB，未计分配器等额外成本
```

将并发序列增加四倍，未共享条件下缓存量也约增四倍。这说明长上下文和高并发为什么会竞争显存，而不是只看权重大小。分页分配、前缀共享、KV 量化、滑动窗口、MLA 或其他结构会改变该估算；不应把公式无条件用于所有模型。

对使用远端 API 的开发者，不能直接控制这些张量。最相关的手段是请求布局、长度控制、并发和可观测使用量，而不是假装应用缓存目录里存在服务端 KV。

## 缓存类型与职责

| 缓存 | 保存什么 | 正确性与失效重点 |
| --- | --- | --- |
| 单次生成 KV | 中间注意力状态 | 同一次模型计算的合法续接 |
| 跨请求前缀 KV | 已计算的相同前缀 | 模型、token、配置、租户与服务端策略 |
| 供应商 Prompt Cache | 对缓存读取/写入的产品接口和计量 | 具体模型与 API 版本、断点、保留策略 |
| 应用结果缓存 | 问题或工具请求对应的业务结果 | 数据新鲜度、身份、授权、幂等和失效 |

把一次答案按问题字符串缓存，不是 KV Cache。订单状态变化后同样问题应得到新答案；把两位用户的“查询我的订单”共用一个缓存键，会产生权限泄露。语义缓存若把相似问题视为等价，更需要界定哪些任务允许近似，不能用于任意工具执行结果。

## 请求布局：稳定性与语义优先

常见布局是稳定指令、稳定能力描述、可复用资料、当前历史与动态查询。这个顺序是候选优化，不是比指令优先级更高的规定。供应商消息协议、工具调用配对、当前事实和权限必须先正确。

```python
# 教学数据：记录布局版本，工具目录按固定键排序。
request_manifest = {
    "prompt_revision": "p-12",
    "tool_catalog_revision": "tools-8",
    "retrieval_snapshot": "docs-2026-09-10",
    "prefix_digest": "sha256:...",
    "dynamic_suffix_digest": "sha256:...",
    "provider_cache_policy": "verified-profile-A",
}
```

不要把当前时间戳、随机 ID 或整条实时日志无条件放进系统指令开头。需要日期时可将它放在其语义所属的动态部分，并在输入 manifest 记录。也不要为了命中继续发送已撤销规则或过期事实；缓存效率不能替代正确性。

压缩会改变前缀，工具热升级会改变 schema，模型切换也可能改变续接格式。应把这些作为显式的缓存失效事件，而不是把命中率下降都归因于服务端波动。

## 供应商语义必须分别适配

Anthropic 的缓存使用量把普通输入、缓存读取和创建作为分项；其输入合计不能直接套用别家的 `input_tokens` 定义。OpenAI 的计量及显式/隐式断点也有模型代际差异。所引文档中的模型族与缓存断点规则表明：有共同的稳定前缀，不代表一定存在对应的有效缓存断点或自动回退到最长可复用片段。[[17]](../references.md#source-claude-cache) [[18]](../references.md#source-openai-cache)

因此本笔记不提供“给所有 API 前面加静态 Prompt 就必命中”的通用代码。实现一个按 provider/model/profile 版本化的使用量映射和缓存配置。不能支持的显式配置应拒绝，不能静默接受但实际不生效。

```python
def anthropic_input_total(usage):
    # 若原始数据缺失，这里返回未知而不是伪造 0。
    names = (
        "input_tokens", "cache_read_input_tokens",
        "cache_creation_input_tokens",
    )
    if any(name not in usage for name in names):
        return None
    return sum(usage[name] for name in names)
```

这段仅演示该组字段的合计，不计算费用，也不适用于所有供应商。多级缓存或不同保留时间的写入类别应继续保留，避免先合并再无法还原价格条件。

## 冷缓存与暖缓存实验

固定模型、输出上限、工具目录、资料版本、并发和网络位置，建立四组请求：完全重复；只变动态问题；修改前缀一个字符；工具目录同内容不同序列化。记录原始 usage、TTFT、总完成时间、最终质量与失败率。

随机化组别顺序，分别做冷启动和稳定阶段，避免把服务端热身当成缓存效果。若 API 的模型存在显式缓存断点，实验还要分别验证有断点与无断点。结果应按文档规定解释，没有命中不必然说明 KV 机制失效，可能只是服务没有可读取的产品缓存项。

收益可用自己的成本模型衡量：

```text
预期节省 = 可复用输入成本差
           − 缓存写入额外成本
           − 为保持前缀而多发送的输入成本
           − 为维护缓存新增的系统成本
```

这是分析框架，不是供应商报价公式。使用实际账单规则代入；更不能通过重复发送无用历史“提高命中率”却让每个成功任务更贵。

## 与 Agent 开发的关系

Agent 多轮历史通常自然增长，适合分析前缀复用；但检索资料替换、计划重排、Tool Search 和 Skills 加载也会改变输入。观察一个 Agent 的缓存应同时记录“本轮为什么构造这些信息”，否则只能看到命中跌了，看不到原因。

自建服务还要避免租户间缓存侧信道和数据混用，分配保留与驱逐策略，测热租户是否挤占其他用户资源。直接使用 API 时这些底层策略往往不可控制，更应把缺失数据标成未知，不能把缓存当成应用持久保证。

## 请求增长与重复输入量

假设系统指令和工具描述共2,000 token，初始资料8,000 token，每轮新增用户/观察1,000 token，连续运行5轮。忽略输出回填细节的教学输入序列是10,000、11,000、12,000、13,000、14,000，总输入60,000 token；并不是只计最终14,000。

```python
inputs = [10_000 + 1_000 * i for i in range(5)]
assert sum(inputs) == 60_000
```

缓存可能让部分重复输入以不同计算和价格处理，但不会让历史在语义或计量上天然免费。压缩成较短输入又可能破坏部分缓存，所以应比较整个轨迹，而不是单轮的`cached_tokens`。

这个算例刻意没有套用真实价格。不同模型的读取、写入、长上下文和输出规则需要分别计算，保存原始分项才能以后重算。

## 缓存实验的结果分析

| 观察 | 可能原因 | 下一步验证 |
| --- | --- | --- |
| 前缀文本相同但无命中 | 断点、保留期、路由、token/工具序列化不同 | 对比实际请求和当前模型缓存规则 |
| 命中率上升但总费用上升 | 输入量、写入费或额外调用增加 | 看每任务合计，而非比例 |
| TTFT改善，总时间不变 | decode或工具执行占主要路径 | 拆分延迟 |
| 冷请求偶尔很快 | 排队变化或服务热身 | 随机化并重复对照 |
| 压缩后短期变慢 | 新前缀需要重建，另有摘要调用 | 评估后续多轮摊销 |

不要根据单个请求得出“缓存无效”或“此布局最佳”。请求延迟有噪声，provider实际缓存状态部分不可观测。保留无法解释的情况比编造内部GPU行为更可信。

## 结果缓存的失效例子

缓存`get_order("A102")`时，键中至少要反映资源身份和合适的授权范围，记录查询时刻与状态版本；内容是否可以短期复用由业务决定。用户第二次请求创建相同订单不是读取缓存问题，而是新业务意图，不能因参数相同直接返回旧写入结果。

把结果缓存、去重账本和KV缓存放在不同对象中，即便它们底层都使用Redis。它们的失效、权限和正确性条件不同，物理存储相同不能消除语义差异。
