# 知识如何进入一次请求

Agent 回答「这个接口超时后会重试几次」时，依赖的通常不是模型参数，而是某个仓库、文档或系统在当前版本中的知识。问题因此不是「模型知不知道」，而是：**哪一份权威内容，经过什么读取或索引路径，进入了这一次请求。**

Agent 的知识库不是单一向量库。它围绕权威源、派生副本、召回与读取、请求载荷和证据溯源组成：代码与文档是事实源，约定文件承载高频规则，结构地图负责导航，检索索引承担规模，接口与现场读取负责当前值，最终只有进入本次载荷的内容才能影响回答。

## 一、五条供给路径

<KnowledgeSupplyRoutes />

这五条路径按「知识被提前处理的时刻」排列，差异不在技术名词，而在新鲜度、维护成本、可溯源性和可承载规模之间的取舍：

- 现场读取与接口直连不提前保存知识，适合当前状态和精确验证；
- 约定文件由人维护、随项目版本化，适合每次都必须生效的规则；
- 检索召回离线建立副本，适合远超上下文窗口的语料；
- 参数内化适合固化风格、格式和领域用语，不适合承载易变事实。

窗口扩大只会提高一次可容纳的内容量，不会消除副本新鲜度、权威系统访问和默认行为塑造这些独立问题。选型时先问四件事：权威源在哪里、内容多久变化、关系能否精确解析、检索失败时应拒答还是允许旧答案。

## 二、检索知识库：从语料到请求载荷

检索增强把模型参数视为参数化记忆，把外部语料索引视为可更新、可溯源的非参数化记忆[[1]](#ref-1)。它的主要价值是承载大规模语料，主要代价则来自副本：需要持续构建、删除、重建和对账，也可能漏召回。

<RetrievalPipelineStages />

链路分两段：离线段把原文解析、切分、向量化并写入索引；在线段改写查询、多路召回、重排、组装载荷，最后要求模型按证据回答。工程上要抓住四条规则。

1. **先归因，再调参。** 解析失败、切坏、漏召回、排序靠后、载荷截断和生成不遵守证据，最终都表现为「答错了」。第一步应打印实际发出的载荷，先判断证据是否进入本次请求。
2. **词面与语义都要保留。** 稠密向量适合意图相近的查询，但对错误码、版本号、配置键、人名等精确标识符不敏感；词面检索负责精确命中。多路结果常按名次融合，避免直接比较不同量纲的分数[[2]](#ref-2)。
3. **切分和向量化要显式校验。** 片段必须保留语义边界、原文位置、权限和版本；片段超过嵌入模型窗口时，超出部分可能被静默截断。更换嵌入模型意味着相似度空间变化，通常需要重建并灰度切换索引。
4. **引用与拒答是主链路的一部分。** 每个片段都要能回到原文位置；没有命中证据时应明确拒答，不能让模型用参数中的模糊印象补空。

## 三、不建副本：规则、地图与现场读取

在编码 Agent 和中小规模项目知识中，默认方案不应总是向量索引。更常见的组合是：约定文件给规则，结构地图给导航，工具读取给证据。

### 3.1 现场读取

现场读取把列目录、按模式匹配、读取文件、查询符号等原语交给 Agent，由它在任务中逐层展开。它读到的是当前状态，不存在索引快照漂移；代价是多轮工具调用、更高延迟，以及对规划能力的依赖。

这种路线强调渐进式披露：先读目录和索引，再读必要文件；大规模探索可放入子 Agent，只把结论交回主上下文，避免检索过程污染主对话[[3]](#ref-3)。

### 3.2 约定文件

约定文件适合放置每次任务都必须遵守的规则、常用命令和知识入口，例如编码规范、测试方式、目录边界。它应随源码版本化，并按目录或文件类型作用域加载。

约定文件占的是每次调用的固定预算。文件过长会同时增加成本并降低遵守度，因此不应把完整知识库复制进去；稳定规则和索引进文件，详细文档按需读取[[4]](#ref-4)。

### 3.3 结构地图

代码中的类、函数、调用关系和依赖边可以被语法工具精确解析。仓库地图只发送关键符号、签名和依赖关系，用较小的预算让 Agent 看清仓库结构，再决定读取哪些实现。

这条路径的原则是：**关系能确定性计算时，就不要用相似度近似。** 向量检索适合表达模糊的语义关联；定义、引用、调用、类型这类可精确计算的关系应优先交给解析器和图结构[[5]](#ref-5)。

## 四、什么时候需要预建索引

<RetrievalRouteComparison />

现场读取和预建索引的分野来自一个事实：**索引是权威源在某一时刻的快照，而权威源会持续变化。** 快照漂移通常不会报错，只会返回曾经正确、现在过期的内容。

可以先按以下条件判断：

- 单仓或中小目录、改动频繁、查询包含确切符号时，优先现场读取；
- 跨仓、跨团队、文档量大、查询只能描述意图，或要求低延迟时，需要预建索引；
- 大多数编码场景采用组合：结构地图负责导航，现场读取负责当前实现，检索索引负责大规模语料和语义定位。

索引新鲜度可以通过增量同步改善。例如为文件和目录维护哈希树，变更后只同步哈希不同的分支，并按内容缓存未变化片段的向量[[6]](#ref-6)。这能缩小漂移窗口，但不能把副本变成权威源。

## 五、副本模型与一致性

<FourLayerConsistency />

知识库通常包含四层数据：原文、片段与元数据、向量、结构关系。原文是唯一事实源，其余都是派生数据。规模不大时，关系数据库、搜索引擎和向量扩展可以合并部署；规模扩大后，再按对象存储、元数据过滤、近邻检索和图遍历的访问模式拆分。

副本一致性的关键不是让所有写入瞬时完成，而是控制不一致窗口的输出：

- 每个片段携带文档标识、内容版本、权限、时间和原文位置；
- 查询时按当前有效版本过滤派生结果，宁可暂时召回为空，也不返回旧证据；
- 以文档标识到内容哈希的映射驱动增量处理，哈希变化才重建片段、向量和关系[[7]](#ref-7)；
- 删除文档时同时处理所有派生层，避免「原件已删、索引仍可命中」；
- 权限过滤必须发生在召回链路中，不能先取回无权内容再靠提示词要求模型忽略。

## 六、Agent 知识库的落地分工

| 内容类型 | 推荐形态 | 关键约束 |
| --- | --- | --- |
| 每次必须遵守的规则 | 约定文件、目录级规则 | 短、稳定、可版本化，避免写入低频说明 |
| 代码结构与模块关系 | 符号索引、仓库地图 | 只放签名和依赖，实现仍回源读取 |
| 大规模文档与历史资料 | 词面索引、向量索引、重排 | 维护版本、权限、删除和重建链路 |
| 当前状态与精确事实 | 工具调用、接口直连、现场读取 | 服务端负责权限、参数校验和审计 |
| 风格、格式、领域用语 | 提示词、约定文件或参数内化 | 行为可固化；易变事实不进权重 |
| 当前任务材料 | 对话上下文、任务文件、子 Agent 结果 | 任务结束即失效，不混入长期知识库 |

最终所有路径都要经过同一道约束：本次请求的上下文容量。不能重新获取的任务状态优先保留；文件、目录和检索结果这类可重新获取的内容按需加载。知识库设计的目标不是让 Agent「记住所有内容」，而是让它在需要时拿到**当前、有权限、可溯源、足以支撑答案**的最小证据集。
