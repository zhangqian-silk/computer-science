# Subagent 与多 Agent 协作

多 Agent 把工作分配给多个模型驱动执行者。真正需要设计的是任务边界、上下文、能力、所有权、通信与集成，不是只给同一个模型设置多个角色名字。本页按这些职责分析，动态生成的编排代码见 [Dynamic Workflows](dynamic-workflows.md)。

## 执行者组织与控制方式

固定 Workflow 可以并行调用多个 Agent；主 Agent 可以按需委派；一个生成脚本也可以控制多个子 Agent。人数并不决定控制方式。先判断任务是否可隔离、结果是否可验证，再决定是否引入多个执行者。

| 组织 | 控制与信息路径 | 常见适用条件 |
| --- | --- | --- |
| Agent-as-tool | 父调用子任务，等待结构化结果 | 边界清楚、子任务短期隔离 |
| 后台子任务 | 父继续工作，稍后接收结果 | 独立耗时任务、有清楚所有权 |
| Handoff | 当前处理责任转交另一执行者 | 专长或权限阶段发生变化 |
| Lead＋Peers | 协调者与同伴交流，可能共享任务板 | 需要双向协作和冲突处理 |
| 外部调度 | 队列向独立 Agent 会话分配任务 | 多任务服务、跨机器运行 |

Handoff 不是“多调用一次函数”：要定义当前责任是否已转移，未完成工具谁管理，用户的后续输入送给谁，失败后谁通知。缺少这几个规则，会出现两个 Agent 都认为对方已经处理。

## 子任务输入契约

子 Agent 通常看不到父会话的全部隐含背景。传入目标、具体证据、限制、产物格式、完成条件和预算，避免只说“你负责测试”。同样不能把全部历史无差别复制，否则失去隔离收益并增加泄露范围。

```python
delegation = {
    "task_id": "review-auth",
    "goal": "检查列出的路由是否缺少身份校验",
    "scope": ["routes/a.py", "routes/b.py"],
    "base_revision": "git:abc123",
    "evidence_refs": ["repo-snapshot-7"],
    "allowed_capabilities": ["read_file", "search_code"],
    "deliverable": {"findings": "带路径、范围、依据和未验证假设"},
    "limits": {"max_model_steps": 8, "deadline_seconds": 120},
}
```

子任务获得的是能力交集，不应自动继承父的全部组织凭据。父要求 read-only，子任务不能通过委派更高权限工具绕过。权限边界必须落在执行接口，不能只在子任务 Prompt 写“请只读”。

## 结果覆盖与完成验证

```python
# 教学代码：严格检查每个任务恰好对应一个结果。
def collect_results(expected_ids, results):
    by_id = {}
    for result in results:
        task_id = result["task_id"]
        if task_id not in expected_ids or task_id in by_id:
            raise ValueError("未知或重复子任务结果")
        by_id[task_id] = result
    missing = set(expected_ids) - set(by_id)
    if missing:
        return {"status": "incomplete", "missing": sorted(missing)}
    failed = [key for key, value in by_id.items()
              if value["status"] != "verified"]
    return {
        "status": "ready_to_integrate" if not failed else "incomplete",
        "failed": failed,
        "results": by_id,
    }
```

子 Agent 的“完成”仍需要父侧核验：引用是否有效，产物是否属于约定版本，要求检查的对象是否全部覆盖。空列表可能表示“没有发现问题”，也可能表示没有完成调查；必须结合状态和证据区分。

汇总器应处理冲突而不是直接拼接。例如两个执行者对同一函数作相反判断，要对照具体源码版本和假设，不采用多数票替代验证。使用相同模型、相同输入得出的多个答案往往高度相关，不能当作独立证据。

## 所有权、取消和消息队列

创建请求、已接受输入、运行中会话和持久子任务是不同阶段。创建超时可能尚未接受；接受后父请求断开，子任务是否继续取决于契约。没有明确所有权转移，就容易形成父已退出、子仍持有资源的孤儿工作。

DSH 的指定子代理设计把持久 Session 与当前活跃 Activation 分开，并区分一次性委派和可延续子会话。可延续路径在输入接受之后转由管理器拥有生命周期；调用者信号不再自动等同于关闭子会话。该源码/文档切片很适合用于理解“取消一次请求”与“销毁执行者”不同。[[51]](../references.md#source-dsh-subagent)

自建实现应记录 parent、child、accepted message ID、当前状态和资源 owner。取消可以自上向下传播，但释放通常要等待子孙静止；发送到已结束子任务的消息应明确拒绝或按约定冷恢复，不能创建一个同名新任务悄悄吞掉原意。

## Teams 的协作与限制

Claude Code 的公开 Agent Teams 文档描述 Lead、独立同伴上下文、共享任务与直接通信；与只能向父返回结果的简单委派不同。页面也标注实验性以及会话恢复、任务状态、关闭和嵌套等限制，并包含多个版本行为变更。应按部署版本核验，不沿用旧工具名或“恢复一定带回所有同伴”的假设。[[52]](../references.md#source-cc-teams)

从这个案例借鉴的是独立上下文与协调接口的分工。共享任务板需要唯一任务身份、原子领取、依赖关系与状态来源。任务板勾选不是业务事实；模型可能忘记更新，也可能过早更新，因此需要从工具回执和产物核验集成。

通信不应把每个同伴所有 token 广播给所有人。可选择发送摘要、明确问题、证据引用和需要处理的冲突。广播过多会让上下文污染与费用按人数放大，还会让所有同伴继承同一错误结论。

## 工作区隔离与合并

并行修改代码时，用各自工作区或 worktree 保留基线，记录补丁对应版本。简单地按不同目录分配并不总能避免冲突：公共接口、lockfile、生成代码和测试配置仍可能共享。

集成者应先检查产物完整和版本，再按依赖顺序合并，在组合结果上运行测试。每个子分支的测试通过只证明局部环境下结果；跨模块契约和共享资源可能在合并后失败。安全审批若绑定的是原子补丁，合并改变产物后要重新判断是否需要审批。

## 不同实践的条件性结论

Cursor 的多 Agent 工程实践强调任务分工与协调，而 Cognition 的文章警惕上下文碎片化带来的损失。两者提醒我们，是否受益取决于边界、上下文复制和合并方式，不应选择一句“多 Agent 更好/不要多 Agent”作为普遍规则。[[53]](../references.md#source-cursor-scaling) [[54]](../references.md#source-cognition-context)

这里建议先比较三种同预算基线：单 Agent、单 Agent 加受限子任务、多个协作 Agent。记录总耗时、总调用量、重复检索、冲突、集成失败和人工修复。并行 wall time 降低但总成本大幅增加，可能仍适合时效任务，但应明确 tradeoff。

## 协作机制的故障测试

测试父在创建中取消、子接受后父断线、子返回空结果、未知任务 ID、两个结果冲突、一个子超时、依赖子任务失败、用户修改总体目标、同伴泄露无权信息。检查资源是否清理、缺失是否明确、没有把“多数完成”写成“全部完成”。

先把只读调查任务拆分，确认输出与集成契约，再扩展到实际写入。多 Agent 的复杂度来自并发和独立状态，不会因为模型能力变强就自动消失。

## 并行审查与结果集成

给A审查API权限，B审查输入校验，C运行测试。A返回高风险问题但没有代码位置，B返回带证据的正常结果，C测试环境缺依赖。合并器应该得到“B已验证，A需补证据，C未完成”，而不是三个Agent各说一段就输出完整报告。

让A补证据时只重做必要范围；修复C环境后重新测试对应代码版本。若期间代码已改变，B的旧结论也可能需要失效。这体现多Agent并不是简单并行map后拼接字符串，而是多个版本化证据的集成。

## 消息传递中的身份与权限

一条同伴消息应带发送者、目标、任务、来源和内容类型，由宿主填写身份，不能相信模型自填“我是管理员”。跨Agent文本仍是不可信工作数据；它可以提供观察和建议，不能自动授予工具或修改审批。

通信拓扑可以限制父子、同伴或特定角色。更多连接不必然更好：全广播可能放大误导与token。先定义哪些信息需要共享，再设置通道，而不是让所有Agent互相聊天后期待自发收敛。

## 子任务粒度与执行成本

任务拆得细，失败可局部重做，但重复指令和上下文复制增加；拆得粗，协调成本小，却可能因一次失败损失更多工作。可对相同范围分别使用1、4、16个分片，记录输入总量、重读文件数、wall time、缺失与合并错误。

并发上限是资源约束，分片数是任务设计；两者分开调。创建100个待运行子任务、并发只4，与创建4个巨大任务有不同恢复和调度行为。
