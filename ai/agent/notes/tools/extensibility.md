# Agent 扩展机制

所有成熟的 Agent 宿主都做了同一件事：**在循环的若干位置预留接口，让外部代码参与进来。** 这些接口就是扩展点。

它们存在的理由是一条判据：**提示词是概率性约束，扩展点是确定性约束。**

写在系统提示里的「提交前必须跑测试」多数时候有效，偶尔失效，而且失效时没有任何信号；写成一个在收尾位置执行的检查脚本，则要么通过要么不通过。

这个差别决定了一条需求应该落在哪一层，也是后文所有判据的源头。

---

## 一、怎么分类：四类扩展点

把市面上的扩展机制摊开会看到一堆名词——hooks、callbacks、middleware、tools、MCP、skills、plugins、marketplace、sandbox、approvals。

它们看似平行，其实回答的是四个不同的问题。有效的分类维度只有一个：**它在循环的哪个位置介入，以及它改变了什么。**

<ExtensionPointMap />

四类的区分不是分类学趣味：**误判类别的代价，是拿一种扩展去解决它根本解决不了的问题。**

- **时间点开洞**改变的是「到了这一刻，要不要停下来做点什么」。它不新增任何能力，只在既有流程上插话。
- **能力集开洞**改变的是「模型这一轮能看见哪些可调用项」。它扩大动作空间。
- **打包分发开洞**不改变任何运行时行为，只解决「一组扩展如何被整体安装、版本化、跨团队复用」。
- **管控面开洞**决定「允不允许」。它是唯一一类不依赖模型配合的扩展。

最常见的误判是拿第一类去补第二类：模型根本连不上那个数据库，于是有人写 hook 去检查查询语句——但通道不存在的时候，写多少检查都没有意义。

## 二、怎么实现：契约的三个要件

一个扩展点要能被依赖，必须说清三件事：**什么时候触发、收到什么、返回什么会被怎么解释。**

前两件通常在文档里写得很清楚，第三件则是绝大多数误用的来源。

### 入参：结构化上下文，而非自由文本

扩展点的入参通常是一个 JSON 对象，通过标准输入、HTTP 请求体或函数参数送达。公共字段一般包括会话标识、工作目录、事件名、当前权限模式。

事件特有字段则视情况而定——工具类事件带工具名与入参，收尾类事件带最后一条助手消息。[[1]](#ref-1)[[2]](#ref-2)

有一个细节值得记住：**轨迹文件路径通常会给，但不保证格式稳定。**

有实现明确声明，提供这个路径只是为了方便，其格式并不是面向扩展的稳定接口，随时可能变。[[2]](#ref-2)依赖它解析历史的扩展，会在某次升级后安静地失效。

### 返回值：同一个脚本，六种被解释的方式

这是契约里最容易出错的部分，值得单独拆开看。

<HookReturnContract />

其中最该记住的是那条「习惯上的失败码」。多数实现的约定是：**只有约定的那一个退出码表示阻断，其余非零退出码都被当作非阻断错误——宿主记一笔然后照常执行。**

有文档专门为此加了提醒，说明它把惯常的失败码视为非阻断错误并继续执行，若要强制策略必须用那个特定的码。[[1]](#ref-1)

于是一个「校验不通过就以失败码退出」的脚本看起来完全在工作——它跑了，它报错了，日志里有记录——但它一次也没拦住过任何东西。

第二条是退出码与结构化输出**不能混用**。常见约定是：打印结构化决策就必须以成功码退出，否则决策会被整个丢弃。[[1]](#ref-1)

第三条是阻断的含义**随事件变化**。同一个阻断码在不同事件上的后果是：[[1]](#ref-1)

- 工具调用前：不执行；
- 本轮收尾：不许停、继续干；
- 用户输入：这条输入被丢弃；
- 另有一批事件：根本无效，只是记进日志。

必须逐事件查表，不能凭一处行为外推。

### 处理器形态：声明了不等于会执行

同一套配置结构下，处理器可以有四种形态：执行一条命令、发一个 HTTP 请求、交给模型做一次评判、派生一个子 Agent 去核查。

但**支持程度差异极大**。有实现明确说明，只有命令型处理器当前真正运行，模型评判型与子 Agent 型会被解析但跳过；异步标记同样会被解析，但带该标记的处理器直接跳过。[[2]](#ref-2)

一份配置可以完全合法地加载、不报任何错，而其中某些条目从未执行过。跨宿主搬运配置时，这是排查的第一站。

字段级也有同样的问题：同一处文档列出了一批「解析但尚不支持」的字段——在工具调用前事件上，询问用户决策、终止流程、停止理由等都属此类。[[2]](#ref-2)

一旦返回这些字段，宿主会把该次 hook 运行标记为失败、报错，然后继续执行工具调用——**失败的方向是放行**。

### 失败与超时：默认值比你想的宽松

扩展是外部进程，必然要处理挂起。两个实现的公开默认值都相当宽松：

- 一处对命令型处理器默认 600 秒，对由模型评判的处理器默认 30 秒、对派生子 Agent 的处理器默认 60 秒；[[1]](#ref-1)
- 另一处对命令型处理器同样默认 600 秒。[[2]](#ref-2)

十分钟对一个「每次工具调用前都跑一遍」的检查来说显然过长。**给每个处理器显式设一个贴合它实际耗时的超时**——否则一个偶尔卡住的脚本会把整条循环挂在那里。

还有一类容易被忽略的失败：走 HTTP 的处理器无法用状态码表达阻断。有实现明确说明，非 2xx 响应、连接失败、超时**一律是非阻断错误**，要阻断必须返回 2xx 外加一个带拒绝字段的响应体。[[1]](#ref-1)

这个设计本身合理（网络抖动不应该把 Agent 卡死），但它意味着策略服务宕机时策略就不生效了——如果这条策略是安全相关的，失效方向必须显式设计，而不能听任默认。

## 三、时间与空间：两个独立的维度

扩展点有两个坐标：什么时候跑，以及在哪一层配置。

这一节要点明的判断是：**这两件事互不决定。**

配置层级不决定执行顺序，触发节奏也不决定作用域。很多难查的误用，根源就是把这两个轴混为一谈——比如以为「在项目层配置的 hook 会覆盖全局层的」，或者以为「先注册的就先执行」。

### 时间轴之一：三种触发节奏

把事件按触发频率排开，会看到一个清晰的分层。有实现直接在文档里点明了这个结构：事件分为每会话一次、每轮一次、以及循环内每次工具调用三种节奏。[[1]](#ref-1)

| 节奏 | 每次会话触发几次 | 典型事件 | 设计含义 |
| --- | --- | --- | --- |
| 每会话 | 1–2 次 | 会话开始、会话结束 | 可以做重活：拉取环境信息、初始化依赖 |
| 每轮 | 与用户交互次数同阶 | 用户输入提交、本轮收尾、本轮异常结束 | 适合做输入校验与交付验收 |
| 循环内 | 数十到数百次 | 工具调用前、工具调用后、权限请求、权限被拒 | 必须快。这里每多 100 毫秒，一次长任务就多等几十秒 |

除这三种节奏外，成熟实现还会暴露一批状态变更事件：[[1]](#ref-1)

- 子 Agent 启动与结束；
- 压缩前后；
- 配置文件变更、工作目录变更、被监视的文件发生改动；
- 指令文件被载入；
- 任务被创建或被标记完成。

这些事件多数不可阻断，存在的意义是可观测性。

节奏直接决定了**该在哪一层做什么**。想在每次工具调用前做一次网络请求去查询策略服务，听起来合理，实际上会把每一步都拖慢；正确的做法是在会话开始时把策略拉下来缓存住，循环内只做本地判定。

### 时间轴之二：顺序与并发

同一时间点上有多个扩展时，它们之间的先后不是随意的。

在中间件形态下，顺序是语义的一部分而非风格问题。文档给出的规则是：**前置 hook 按注册顺序执行，后置 hook 逆序执行，包裹式 hook 层层嵌套、第一个中间件包住其余所有。**[[4]](#ref-4)

在 hook 形态下则相反——顺序几乎不可依赖。有实现说明，多个同事件的命令型处理器**并发启动**，因此一个 hook 无法阻止另一个 hook 开始执行。[[2]](#ref-2)

这条差异有直接后果：**在 hook 体系里写「先跑 A 再跑 B」的依赖是不成立的**，需要顺序就得把两步合进同一个处理器。而在中间件体系里，调整注册顺序就是在调整语义。

### 空间轴之一：作用域分层

包与配置的安装作用域通常分三到四层：个人（跨所有项目）、项目（随仓库共享）、本地（项目内但不进版本控制）、以及企业受管。[[7]](#ref-7)

关键规则是：**各层的 hook 全部都会运行，高优先级的配置层不替换低优先级的 hook。**[[2]](#ref-2)

这与配置文件里「后加载的覆盖先加载的」是完全不同的语义。它意味着「在项目层覆盖掉全局层那个碍事的 hook」这个操作根本不存在——只能去关掉它。

受管层是其中唯一有强制力的一层。它的语义在两处文档里都写得很明确：

- 管理员可以配置只允许受管 hook 运行，从而屏蔽用户、项目与插件带来的 hook；[[1]](#ref-1)[[2]](#ref-2)
- 受管来源的 hook 标记为受策略信任，**不能从用户侧的界面里关掉**；[[2]](#ref-2)
- 某些配置变更事件对受管来源的改动不可阻断——hook 仍会触发以便审计，但阻断决定会被忽略，以确保企业设定始终生效。[[1]](#ref-1)

**把项目作用域当成团队强制是一个常见误解。** 项目作用域只是「随仓库分发」，任何人都能在本地关掉它。需要强制的东西必须走受管层。

### 空间轴之二：进程边界与路径寻址

扩展代码跑在哪里，决定了它能做什么、以及怎么找到它。

- **进程内**：扩展是宿主进程里的一个函数或对象，共享内存与生命周期。中间件属于这一类。
- **跨进程**：扩展是一个被拉起的子进程或一个远端服务。命令型 hook 与跨进程协议属于这一类，代价是每次调用都要付进程启动或网络往返。

跨进程还带来路径问题。安装位置是不确定的，因此必须靠变量寻址，并且要区分两类目录：**指向安装目录的变量每次更新都会变化，不能在那里存状态。**

另有一个跨更新存活的数据目录，用于依赖、生成物与缓存。[[7]](#ref-7)

最后是加载时机：有实现明确说明自己**没有热重载**，hook 定义变更后需要重启会话或用专门的命令重载。[[7]](#ref-7)这决定了「改一行配置就能验证」是否成立。

## 四、如何接入：能力、打包与信任

前两节讲的是「在既有流程上插话」。这一节讲另一件事：**把新能力接进来。**

它有一个前者没有的成本结构：**工具定义是每一轮都要随请求发出的**，它占据上下文，也参与模型的每一次选择。

### 三条能力供给路径

- **进程内注册**：把一个函数连同名称、描述与参数模式登记进注册表。适用于本来就在同一个代码库里的能力。
- **跨进程协议**：把能力放在另一个进程甚至另一台机器上，用一套协议发现与调用。[[5]](#ref-5)适用于跨语言、跨团队、需要独立部署的能力。
- **按需加载的规程**：补的不是通道而是判断——这件事在这里该按什么步骤做。它不授予任何执行能力，所需工具必须由环境另行提供。

协议这一侧真正值得单独拿出来的是一处设计：服务端能提供的三种原语，**是按「谁来控制」区分的**，而不是按数据类型。[[5]](#ref-5)

| 原语 | 是什么 | 由谁决定何时用 |
| --- | --- | --- |
| 工具 | 可被调用的函数 | 模型 |
| 资源 | 提供上下文的数据源 | 应用 |
| 提示 | 可复用的交互模板 | 用户显式选用 |

三者在技术上都可以是「返回一段文本」，区别只在控制方。这个划分把「谁负责决定用不用它」变成了协议层的事，而不是留给每个实现各自约定。

### 接多少：能力集本身是一个扩展点

工具定义是常驻开销，因此能力集不是越大越好。接上十个服务端、暴露几百个工具，每一轮请求都要带着这几百份定义，而其中绝大多数与当下的任务无关。

于是「这一轮暴露哪些工具」本身成了一个扩展点。中间件形态下这件事做得很自然：在包裹模型调用的 hook 里按当前状态筛选一个子集再往下传。

收益是提示更短、模型在更少选项里选得更准、可以按用户权限动态过滤。[[4]](#ref-4)

注意这里有一个前提：可选的工具**仍然要预先全部注册**，筛选只发生在每轮组装请求时。[[4]](#ref-4)

动态变更还有一个代价——工具定义排在请求最前面，改动它会让前缀缓存整体失效。

### 打包：创作原语与分发原语

单个扩展写好之后，跨仓库复用需要另一层。有一个把两者关系说得很清楚的口径：**技能是可复用工作流的创作格式，插件是可安装的分发单元**。

先用技能把工作流本身设计好，想让别人安装时再打包成插件。[[8]](#ref-8)

过早打包，每改一行都要走一遍分发流程；始终不打包，则无法版本化也无法跨仓库复用。

包的形态有两处设计值得记下：

- **清单可以省略。** 一处明确说明清单是可选的：省略时按默认位置自动发现组件，并从目录名推导包名。[[7]](#ref-7)
- **同一份清单里，不同字段的路径语义可以不同。** 技能字段声明的目录是在默认目录之外追加，而命令、子 Agent、输出风格等字段是替换默认目录。[[7]](#ref-7)两种语义并存在一个文件里，凭字段名猜会猜错。

### 信任：安装不等于信任

扩展是会执行的代码，因此「这段代码是谁写的、有没有变过」本身需要被管理。

一处实现给出的机制是基于内容哈希的信任记录：非受管的命令型 hook 在运行之前，**必须先由使用者审阅并信任那份确切的定义**。

信任按当前哈希记录，于是新增或改动过的 hook 会被标记为待审阅并在此期间跳过。[[2]](#ref-2)

受管来源的 hook 则由策略赋予信任。同一处还明确了两条边界：[[2]](#ref-2)

- **插件自带的 hook 不因安装或启用而被信任**，在审阅之前一律跳过；
- 项目本地的 hook 只在该项目被信任后才加载，未信任的项目里仍会加载用户级与系统级的 hook。

关键不在哈希本身，而在它把两个决定分开了：**「我安装了它」与「我看过它并认可当前这一版」是两件事。** 没有这个区分，供应链上的一次静默更新就等于一次未经审查的代码执行。

同一条原则也约束外部能力的接入：**接入一个外部能力提供方，等于把它的信任等级并入自己的系统。**

它返回的内容是不可信数据——其中出现的「忽略之前的指令」保持数据身份，不获得指令优先级。规范也要求支持一键配置的客户端必须在执行前完整展示将要执行的命令并取得明确同意。[[6]](#ref-6)

## 五、如何组合：第二个扩展才让范式显形

单个扩展工作正常，不代表两个扩展一起工作也正常。

多数关于扩展的困惑都出在这里，而三种经典结构给出的答案完全不同。

<ExtensionCompositionSemantics />

**观察者**的代表是只负责记录的生命周期回调。一套框架把这条分工做得相当彻底：它提供两个作用域的回调——一套绑定整个运行过程（含从一个 Agent 交接到另一个 Agent 的时刻），一套绑定单个 Agent。

而这些回调方法的返回类型全是空。[[3]](#ref-3)也就是说，它们在类型层面就无法参与控制流。阻断、审批、执行改写交给另外的机制。

这不是能力缺失，而是有意的分工：把「知道发生了什么」与「决定要不要发生」分成两套接口，各自的失败形态就不会互相污染。

**责任链**的代表是权限判定。多个扩展各自投票，宿主按严格程度汇总。两个实现给出的规则方向一致：

- 一处在工具调用前事件上定义了明确的优先级序列——拒绝优先于延后、延后优先于询问用户、询问用户优先于放行；[[1]](#ref-1)
- 另一处在权限请求事件上的表述更简洁：**任何一个拒绝都胜出**，若无人拒绝则放行使请求不再弹窗，若无人表态则走正常审批流程。[[2]](#ref-2)

这条规则有一个反直觉的推论：**「放行」不是覆盖，只是弃权。**

想用一个扩展来豁免某个动作是做不到的——只要另有一处投了拒绝票，它就被压过去了。

**中间件**的代表是近年框架侧的主流形态。一套框架把这条路径走得很完整：它区分节点式与包裹式两类 hook。

- **节点式**在固定位置顺序执行：Agent 启动前、每次模型调用前、每次模型响应后、Agent 结束后；
- **包裹式**围绕每次模型调用与每次工具调用，由中间件自己决定把控制权往下传零次、一次或多次——传零次是短路，传多次就是重试。[[4]](#ref-4)

当多层同时修改状态时，有一条细则值得注意：**最外层在冲突键上胜出，而若外层实现了重试逻辑、多次调用了下游句柄，此前几次调用产生的状态更新会被丢弃。**[[4]](#ref-4)

这是「外层重试 + 内层副作用」这个经典陷阱的精确版本：状态更新被丢弃了，副作用没有。文件写了三遍就是三遍。

### 一条可执行的归属判断

把前面的判据串成顺序，可以得到一个逐问收敛的过程。次序不能调换，因为它反映的是约束的强度：**不可达是硬事实，必须保证是硬要求，其余都是组织选择。**

```
PLACE-EXTENSION(need)
	// 第一问：需要的能力是否存在通道。不可达是硬事实，写指令补不上
	if not REACHABLE(need.target) then
		return "能力集：本地工具或 MCP 服务端"
	end if

	// 第二问：是否必须被保证，而不只是「多数时候成立」
	// 这一问不能后移，否则会把安全约束交给概率性机制
	if MUST-GUARANTEE(need) then
		if CAN-REMOVE-CAPABILITY(need) then
			return "管控面：沙箱或凭据边界"      // 最可靠：不给出口
		else
			return "管控面：规则 + 拦截式扩展"    // 次选：确定性检查，但覆盖不完全
		end if
	end if

	// 第三问：介入之后要不要改变控制流
	// 这一问不能前移，否则「记录一下就好」的需求会被做成沙箱
	if not AFFECTS-CONTROL-FLOW(need) then
		return "观察者：生命周期回调"            // 只记录，不决定
	end if

	// 第四问：是否需要包裹整个调用（重试、缓存、改写请求）
	if NEEDS-WRAP(need) then
		return "中间件：包裹式 hook"
	else
		return "责任链：位置式 hook"
	end if
```

## 六、扩展到底能保证什么

前面几节讲的是怎么让扩展工作。这一节讲一个更容易判断错的问题：**它能保证什么。**

<GuardrailEnforcementBoundary />

最能说明问题的证据来自实现方自己。一处在工具调用前事件的文档里写道：它可以拦截命令执行、通过补丁工具进行的文件编辑以及 MCP 工具调用，**但它仍然是护栏而不是完整的强制边界**。

理由是宿主往往能通过另一条受支持的工具路径完成等价的工作。[[2]](#ref-2)同一份文档还列出了两处具体缺口：[[2]](#ref-2)

- 它并不拦截所有的命令调用，只拦截简单的那些——更新的那套支持流式输入输出的执行机制，拦截并不完整；
- 也不拦截网络搜索等非命令、非 MCP 的工具调用。

也就是说，拦截式扩展的覆盖面等于「宿主已经接线的那几条路径」，而不是「所有能达成该效果的方式」。一条被拦住的命令，换个工具、换条路径就过去了，而且不会有任何信号提示你护栏被绕过了。

同样的诚实出现在事后拦截上：工具调用后事件的拒绝**不撤销已经完成的副作用**，实际行为是把反馈记下来、用它替换掉工具结果，然后让模型从这段反馈继续。[[2]](#ref-2)

把它当成事务回滚是一类真实的设计错误——文件已经写了，消息已经发了。

还有一处语义的方向与直觉相反：收尾事件上的拒绝**不是否决这一轮**，而是告诉宿主继续跑，并把拒绝理由当作一条新的用户提示词。[[2]](#ref-2)这个位置的「阻断」实际是「续跑」。

### 需要保证时，把能力拿走

既然拦截不完整，真正的保证只能来自不依赖模型配合的那一层。一处文档把两层分工讲得很清楚：[[9]](#ref-9)

- **沙箱模式**规定技术上能做什么——能写哪里、能否联网；
- **审批策略**规定什么时候必须先问——离开沙箱、使用网络、执行受信集合之外的命令。

沙箱的强度来自它由操作系统落实而非应用层自觉。[[9]](#ref-9)两处设计与扩展治理直接相关：

- **可写根目录里仍有受保护路径。** 版本控制目录、Agent 配置目录被递归地设为只读，即使它们位于可写范围内。[[9]](#ref-9)这防止 Agent 改写约束自己的那份配置。
- **凭据的时间窗可以被切开。** 云端环境采用两阶段模型：准备阶段可以联网安装依赖，Agent 阶段默认离线；为环境配置的密钥只在准备阶段可用，Agent 阶段开始前就被移除。[[9]](#ref-9)这是「把能力拿走」而非「在半路检查」的一个漂亮例子。

失败语义同样值得照搬：**构建提示、审查会话与解析失败一律按失败关闭处理，超时单独上报但动作同样不执行。**[[9]](#ref-9)

注意这与第二节那条「超时与网络失败默认放行」正好相反。两种默认方向都存在，必须各自明确选定，不能听任框架决定。

### 怎么确认它真的在起作用

扩展点加多了会变成一层看不见的基础设施。三件事值得盯：

- **护栏必须被实测过才算数。** 既然覆盖面是「已接线的路径」，唯一可靠的确认方式就是真的去试——让它执行那条该被拦的命令，确认结果是拒绝，而不是一条错误日志加一次成功执行。
- **决策来源必须可区分。** 「被拒绝了」信息量有限，「被哪一层拒绝的」才能指导行动：规则命中、hook 判定、还是使用者手动拒绝，三者的改进方向完全不同。有实现的遥测事件里就把决策来源单列为一个字段。[[9]](#ref-9)
- **循环内扩展的耗时要乘以调用次数看。** 一个中位数 80 毫秒的检查，在一次数百步的任务里就是几十秒。另外，超时与失败按契约默认不阻断流程，于是不会有人来报障，只能靠指标主动发现。

## 七、几种实现的横向对照

分歧点标出了哪些参数是可调的，共识点标出了哪些结论是稳定的。

| 维度 | 常见做法 | 分歧所在 |
| --- | --- | --- |
| 配置结构 | 事件 → 匹配组 → 处理器三级嵌套 | 高度一致，连字段名都基本相同 |
| 处理器类型 | 命令、HTTP、模型评判、派生子 Agent | **支持程度差异极大**：有实现四类齐备，有实现只有命令型真正执行，其余被解析但跳过 |
| 阻断表达 | 特定退出码，或结构化决策字段 | 码值一致性高，可阻断的事件集合差别大 |
| 多 hook 汇总 | 取最严：拒绝优先 | 一致 |
| 跨层覆盖 | 各层 hook 全部运行 | 有实现明确高优先层不替换低优先层 |
| 加载与信任 | 配置即加载 / 须按哈希审阅后才运行 | **分歧最大的一处** |
| 热重载 | 有 / 无 | 无热重载者需重启会话或显式重载 |
| 观察与管控 | 合一 / 分离 | 有框架刻意让生命周期回调只观察，阻断另走一套 |
| 组合范式 | 责任链 / 洋葱模型 | 决定「顺序是不是语义的一部分」 |
| 分发单元 | 清单 + 组件目录 | 可打包的组件类型数量差异很大 |

两个细节值得单独记住。

**分层的默认值可以互相抵消。** 网络控制那一层有一张很清楚的真值表：[[9]](#ref-9)

- 网络关闭 + 代理策略打开：策略不起任何作用；
- 网络打开 + 代理策略关闭：无限制的直接外联；
- 两者都开：流量才真正受策略约束。

两个看起来都「打开了」的开关，组合起来可能等于什么都没做。

**观察与管控分离是一种可选的架构立场。** 把生命周期回调的返回类型定成空，[[3]](#ref-3)与把决策字段塞进同一套 hook，是两种不同的取舍。

前者接口更窄、语义更干净，不会出现「日志脚本意外拦住了一次调用」；后者更灵活，代价是每个扩展都要想清楚自己的返回值意味着什么。

---

最后一点不属于机制而属于判断：**扩展点是确定性的，但确定性有边界。**

一个扩展能保证「同样的输入得到同样的判定」，不能保证「所有该被判定的输入都会经过它」。把前者当成后者，是这个主题上最昂贵的一类错误——它不会在测试里暴露，只会在某次事故里。
