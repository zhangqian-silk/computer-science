# 工具调用机制

工具层连接的两端性质相反：一端是概率性的，模型可能调错工具、填错参数、在不该动手的时候动手；另一端是确定性的，数据库要么扣了款要么没扣。**这道接缝上的设计错误几乎都不报错，只是静默地多做一次或少做一次**——多扣的一笔钱、重发的一封邮件、被跳过的一次权限检查，日志里都没有红色的行。

本文只讨论任意一次调用共有的机制，不涉及具体某一族工具的接口形态。

---

## 一、一次调用的完整链路

一次工具调用经过七个环节，每个环节由不同角色负责，失败之后的去向也不同。

| # | 环节 | 负责方 | 典型失败 | 失败去向 |
| --- | --- | --- | --- | --- |
| 1 | 意图产生 | 模型 | 工具名不存在；参数是无法解析的 JSON 片段，流式场景常因截断产生 | 回灌模型 |
| 2 | 参数校验 | 运行时 | 日期格式不对、数值越界、必填项缺失、把 ID 填成人名 | 回灌模型 |
| 3 | 授权判定 | 策略层 | 命中拒绝规则；需要审批而当前是无人值守模式 | 中止本轮 |
| 4 | 幂等与去重 | 运行时 | 并行批次里出现两条语义相同的写操作；恢复时重放已完成的调用 | 就地处理 |
| 5 | 执行 | 工具实现 | 下游 5xx、连接被重置、超时、进程被杀 | 回灌模型 |
| 6 | 结果整形 | 工具实现 | 一次返回三十万行顶穿窗口；或只返回一串 UUID，模型无从判断下一步 | 回灌模型 |
| 7 | 回灌 | 运行时 | 配对错位、结果丢失、错误信息写成空字符串 | 中止本轮 |

**决定实现复杂度的不是环节数量，而是每一关失败之后结果去哪里。** 七关里有四关应当把失败回灌给模型让它自纠，其余三关不应当。

各关还有各自的护栏，其中几条反直觉的值得先记住：第 4 关的幂等键应当由调用内容派生而非随机生成，否则重试时算出的是新键、去重形同虚设；第 5 关的客户端超时不等于下游没执行；第 7 关回灌空结果比回灌错误信息更糟，模型看不出发生了什么，最省事的选择就是把工具再调一遍。

### 四段报文

落到接口上就是四段报文。下面用「查天气」走一遍，字段名取自某主流接口[[7]](#ref-7)，其他实现键名不同但结构共通。

**第一段，请求带上工具声明。** 工具不是注册在服务端的持久对象，而是每次请求都要重新带上的参数。

```
{

&#x9;"model": "\<model-id>",

&#x9;"messages": [

&#x9;	{ "role": "user", "content": "北京今天要带伞吗" }

&#x9;],

&#x9;"tools": [

&#x9;	{

&#x9;		"type": "function",

&#x9;		"function": {

&#x9;			"name": "get\_weather",

&#x9;			"description": "查询指定城市的当前天气。城市名需为中文全称，不含「市」字后缀。",

&#x9;			"parameters": {

&#x9;				"type": "object",

&#x9;				"properties": {

&#x9;					"city": { "type": "string", "description": "城市中文名，如：北京" },

&#x9;					"unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }

&#x9;				},

&#x9;				"required": ["city"],

&#x9;				"additionalProperties": false

&#x9;			},

&#x9;			"strict": true

&#x9;		}

&#x9;	}

&#x9;]

}
```

**第二段，模型返回调用意图而非答案。** `content` 为空；`arguments` 是 **JSON 编码后的字符串**而非嵌套对象，必须先解析、也可能解析失败；`id` 是配对凭据。

```
{

&#x9;"role": "assistant",

&#x9;"content": null,

&#x9;"tool\_calls": [

&#x9;	{

&#x9;		"id": "call\_a1b2c3",

&#x9;		"type": "function",

&#x9;		"function": {

&#x9;			"name": "get\_weather",

&#x9;			"arguments": "{\\"city\\":\\"北京\\",\\"unit\\":\\"celsius\\"}"

&#x9;		}

&#x9;	}

&#x9;]

}
```

**第三段，执行结果作为一条新消息追加回去**，角色为 `tool`，必须带上刚才那个 `id`。工具抛异常时也走这条通道——把错误写进 `content`，模型才有机会自纠。

```
{

&#x9;"role": "tool",

&#x9;"tool\_call\_id": "call\_a1b2c3",

&#x9;"content": "{\\"error\\":\\"city 未识别：『北京市』。请去掉『市』字后缀重试。\\"}"

}
```

**第四段，带完整历史再请求一次**，模型这次才给出自然语言答复。`messages` 必须包含前三段全部内容且顺序不变，`tools` 需原样再带一遍。

```
{

&#x9;"messages": [

&#x9;	{ "role": "user", "content": "北京今天要带伞吗" },

&#x9;	{ "role": "assistant", "content": null, "tool\_calls": [ { "id": "call\_a1b2c3", "…": "…" } ] },

&#x9;	{ "role": "tool", "tool\_call\_id": "call\_a1b2c3", "content": "{…}" }

&#x9;],

&#x9;"tools": [ "…同第一段…" ]

}
```

由此得到两条硬约束。

**配对是强制的。** 每个 `tool_calls` 条目都必须有 `tool_call_id` 对应的结果消息，少一条多数接口整体拒绝请求，而不是忽略那一条——这也是压缩上下文时不能单删某条工具结果的原因。并行调用时结果按 ID 配对，不按完成顺序。

**工具声明每轮重复付费。** 一个 30 个工具的工具集，在十步任务里要被完整传输十次。

### 第二关与第三关的差别

参数校验失败应当作为工具执行结果回灌。这被写进了公开规范：协议层错误用于「请求结构本身有问题、模型多半修不好」的情形（工具不存在、格式非法），而输入校验错误、业务规则错误、下游失败应以结果内的错误标记返回，因为它们含有模型可据以自我纠正的反馈[[1]](#ref-1)。

日期格式写错了，模型看到「出发日期必须在将来，今天是某月某日」就能改。授权失败相反，不回灌细节——告诉它「这个路径不允许写」，它下一步很可能换个路径试。**自纠能力在参数错误上是资产，在权限边界上是负债。**

判据是：**看模型改了之后还算不算同一次意图。** 参数改对了仍是同一次意图，绕过权限已是另一回事。

## 二、契约：模型凭什么知道该调什么

模型看到的工具只有一份声明：名字、描述、参数模式，以及可选的输出模式与行为标注。没有源码，没有文档站。**这份声明就是全部。**

- **名字**决定第一轮筛选。名字相近的工具会互相干扰，`notification-send-user` 与 `notification-send-channel` 这种成对出现的是选错高发区[[5]](#ref-5)。常见做法是按服务与资源分层加前缀，但前缀式与后缀式的效果因模型而异，应按自己的评测选[[6]](#ref-6)。

- **描述**决定什么时候调。写成给新同事看的说明：显式写出隐含前提、专有名词、资源关系，而不是摘抄接口文档[[6]](#ref-6)。

- **参数模式**决定能不能填对。核心原则是**让非法状态无法表达**——用枚举而非自由字符串，用一个 `mode` 字段而非两个可能互斥的布尔量[[7]](#ref-7)。参数名要自解释，`user` 不如 `user_id`。

- **输出模式**可选，声明后服务端必须按它返回、客户端应据它校验[[1]](#ref-1)。价值在集成侧：结果可被程序可靠解析。

描述不是越详细越好——**工具定义注入系统消息、按输入 token 计费、每次调用重付一遍**[[7]](#ref-7)，它的成本乘以的是调用次数。

### 参数该由模型填还是代码填

判据很明确：**凡是程序已经知道的值，不要让模型填。**

订单号在上一步已拿到，就不该设计 `submit_refund(order_id)` 让模型抄一遍，而应设计成无参数的 `submit_refund()`，由代码带上[[7]](#ref-7)。这不只是省 token——模型抄写标识符会出错，而这类错误往往指向另一个真实存在的对象，于是不报错，只是退错了单。

推论：**总是连着调用的两个工具应当合并。** 每次 `query_location()` 之后必然跟一次 `mark_location()`，就把标记并进查询里[[7]](#ref-7)。

### 标注是提示，不是安全边界

声明里可带行为标注：是否只读、是否具破坏性、是否幂等、是否与外部世界交互。界面可据此决定要不要弹确认框，运行时可据此决定要不要自动重试。

但规范的定性很明确：**这些属性全部是「提示」，不保证忠实描述工具的真实行为**，客户端不得基于来自不受信任服务端的标注做工具使用决策[[2]](#ref-2)；工具行为的描述性信息应被视为不可信，除非来自可信服务端[[3]](#ref-3)。

标注的语义诱人得很像权限模型，但声明是服务端自己写的——一个恶意或粗心的服务端完全可以给会删库的工具标上只读。**真正的安全边界只能建在自己这一侧**：白名单、参数级规则、沙箱、审批。

几个默认值的方向本身就是设计意图：未声明时只读默认为否，具破坏性默认为**是**，幂等默认为否，开放世界默认为**是**[[2]](#ref-2)。**沉默被解释为最危险的那一种**——但这保护的是漏写标注的诚实服务端，防不住故意写错的那个。

## 三、结果整形：返回什么比返回多少更重要

工具结果是上下文里增长最快的一类内容，这一层直接决定 Agent 能跑多久。

### 只返回高信号信息

优先返回与上下文相关的内容而非追求全面，避开内部 UUID、缩略图地址、MIME 类型这类底层标识符，优先给名称、类型这些能指导下一步的字段[[6]](#ref-6)。

其中最反直觉的一条：**把字母数字 UUID 换成语义化名称、哪怕只是从 0 开始的序号，就能显著提高检索类任务准确率**，因为它减少幻觉[[6]](#ref-6)——模型记不住 `a3f9-…`，于是会编。

两种都需要时（先按名字搜人、再按 ID 发消息），可加一个 `response_format` 参数让模型自选简洁或详细，实测简洁模式约用三分之一 token[[6]](#ref-6)。

### 体积在源头收窄

分页、范围选择、过滤、截断都应带默认值，而不是等调用方指定；一个可参照的量级是某编码 Agent 默认限制工具响应在 25,000 token 以内[[6]](#ref-6)。

截断不是问题，**裸截断才是**——砍掉之后要告诉模型怎么取下一段，否则它只会把同一个调用再跑一遍。同理，错误信息要写成「做什么能修好」，而不是错误码加调用栈[[6]](#ref-6)。

两者是同一条原则：**工具的返回值也是提示词**，它在教模型下一步怎么做。

### 格式没有标准答案

XML、JSON、Markdown 会实打实影响效果，且不存在通用最优，只能实测[[6]](#ref-6)——「我们统一用 JSON」这类工程洁癖在此处要让位于评测结果。

## 四、结果怎么回来：三种通知形态

| 形态   | 结果走哪条通道           | 连接断掉之后 | 适用             |
| ---- | ----------------- | ------ | -------------- |
| 同步返回 | 本次请求的响应           | 结果丢失   | 耗时稳定在秒级以内      |
| 进度通知 | 本次请求的响应流，中途附带进度事件 | 结果丢失   | 耗时较长但客户端会一直等   |
| 任务句柄 | 服务端持久化，客户端凭标识轮询   | 结果仍可取回 | 耗时不可控，或客户端可能重启 |

分水岭不是快慢，而是**能否跨连接存活**：前两者绑在一次请求的响应流上，流没了就什么都没了，客户端重启后无处可取。

进度通知的机制是客户端在请求里带一个进度标识，服务端据此推送进度事件，进度值必须单调递增[[4]](#ref-4)。实现**可以**在收到进度通知时重置超时计时，但**应当**始终保留一个最大超时上限，以限制行为异常的一方[[8]](#ref-8)。它能把连接喂活，却喂不出无限寿命。

任务句柄的关键约束是持久性：服务端在任务被**持久化创建之前不得返回句柄**，最终一致的部署里必须等到一致之后再响应[[9]](#ref-9)——句柄一旦返回，用它去查一定能查到。客户端则应把任务 ID 持久化，以便崩溃重启后继续轮询[[9]](#ref-9)。

配套字段各自对应一个运维问题：建议轮询间隔防止客户端把服务端轮垮，存活时长决定任务何时被标记失败乃至删除。**两者在生命周期内都可能变化**[[9]](#ref-9)，不能只读一次就缓存住。

### 客户端超时不等于下游没执行

超时的语义是「我不等了」，不是「它没做」。由于网络延迟，取消通知可能在请求处理完成之后、甚至响应已发出之后才到达，双方**必须**优雅处理这种竞态[[8]](#ref-8)。从调用方视角，「已取消」与「已完成」之间存在一段无法消除的模糊区间。

两条推论都很硬：**对非幂等操作，超时之后不能直接重试，必须先查状态**；**要能查状态，就得在发起之前留下凭据**——幂等键、业务单号、任务 ID 至少有一个。

## 五、并发、超时与重试

这三件事共用一个预算，必须一起算。下图可以拖动各层时限，观察实际能跑几次重试。

<ToolRetryBudget />

**超时是一条链，不是一个数。** 从外到内至少三层：用户可接受的整体等待、本步调用的额度、单次尝试的上限，三者必须是真包含关系。内层大于外层时内层配置不产生任何效果——外层先放弃，内层还在等。

**重试次数因此不是独立参数**，它由「本步预算 ÷（单次上限 + 退避间隔）」反推而来。写死「重试 3 次」不看预算，往往是第 2 次刚发出外层就已超时返回。

**退避的作用是错开，不是减少。** 指数部分给下游恢复留时间，**抖动部分打散同步**——没有抖动时同一批并发调用会在同一时刻集体醒来，对刚要缓过来的下游再补一刀。抖动还有个副作用：总耗时变成分布而非定值，做预算应按较高分位数而非期望值算。

**只有确认幂等的调用才允许自动重试。** 读操作、检索、只读命令可以随便重试，提交、发布、付款、发消息不行。判断依据不是工具标注（上一节已说明为何不能信），而是自己这一侧对工具的了解。

非幂等但需要重试的，引入由**调用内容派生**的幂等键，下游据此去重。常见失误是用随机 UUID 作幂等键且重试时重新生成，这样只能防重放，防不了重试。

**并行带来的是共享状态问题。** 并行调用默认开启、可显式关闭[[7]](#ref-7)，收益是延迟从串行总和降到最大值，代价是同一批调用可能同时修改同一份状态。框架层的常见做法是要求为可能被并发写入的状态字段声明归并函数[[10]](#ref-10)：不阻止并发，而是强迫开发者**显式声明冲突怎么解决**。

## 六、工具规模：装不下的时候怎么办

工具数量上到几十上百时，出现的是另一类问题。

token 成本是显性的那一半：五个服务端合计 58 个工具约占 55K token，再接入一个稍大的服务端就接近 100K，某内部场景优化前工具定义占到 134K[[5]](#ref-5)——这些都是**在对话开始之前就已花掉的**。

准确率是隐性的那一半，且更致命：工具一多，最常见的失败就是选错工具与填错参数，尤其名字相近时[[5]](#ref-5)。一条公开建议是**单轮开始时可用函数控制在 20 个以下**，并注明这只是软性建议[[7]](#ref-7)。

出路有三条：全量注入之外，可以按需检索、代码编排，或两者叠加。下图对照四种方案的占用构成。

<ToolSurfaceScaling />

两条出路省的**不是同一样东西**，这是选型时最容易混淆的地方。

**按需检索省的是工具定义。** 把不常用的工具标记为延迟加载，初始只注入一个检索工具，命中的才展开成完整定义。对照数据：约 77K token 起步降至约 8.7K，节省约 85%；大工具库场景下准确率也有提升，同一组内部评测中两个模型分别从 49% 到 74%、从 79.5% 到 88.1%[[5]](#ref-5)。

附带好处是**延迟加载不破坏前缀缓存**，因为被延迟的工具压根不在初始提示里[[5]](#ref-5)——反之若实现成「每轮动态增删工具列表」，缓存会反复失效。

**代码编排省的是中间结果。** 模型写一段代码在沙箱里调用工具，循环、筛选、聚合都在代码里完成，只有最终输出回到上下文。复杂研究类任务平均用量从 43,588 降到 27,297 token，约减少 37%；20 多次调用写在一个代码块里，省去 19 次以上完整推理[[5]](#ref-5)。

两者正交、可叠加，**先看占用构成**：定义占大头就上延迟加载，结果占大头就上代码编排。

### 第三条路：减少工具本身

一条设计手段常常比前两条更有效：**工具不该是接口的一对一包装。**

与其提供 `list_users`、`list_events`、`create_event` 让模型自己编排，不如直接提供 `schedule_event`；与其 `read_logs`，不如 `search_logs` 只返回匹配行与上下文[[6]](#ref-6)。

道理在于 Agent 与传统程序的**可供性不同**：传统程序遍历一万条记录毫无压力，模型逐条读过去却是在烧自己最稀缺的资源[[6]](#ref-6)。

## 七、跨进程：协议解决什么，不解决什么

工具跑在别的进程甚至别的机器上时就需要标准化协议，否则每接一个新工具源都要写一遍适配。要标准化的只有几件事：怎么发现工具、怎么描述参数与输出、怎么发起调用、怎么区分两类错误、长任务怎么办、连接怎么建立。

演进主线只有一句话：**把状态从连接上摘下来**，它能解释大量具体字段的取舍。下图可逐项查看被拆掉的机制及其替代方案。

<McpProtocolEvolution />

早期是有状态富功能设计——先握手协商能力，连接带会话标识，服务端可反向发起请求，响应流断了还能凭事件 ID 续传。功能全，代价是每一条都要求「这条连接活着且状态还在」。

后来这些前提被逐条拆掉[[11]](#ref-11)：

- 取消握手，每个请求自带协议版本与能力

- 取消会话标识，跨调用状态改为签发显式句柄、作为普通工具参数传回

- 服务端主动发起改为返回一个需要补充输入的中间结果，客户端带着信息重试

- 长任务移出核心成为可选扩展，阻塞取结果改为轮询

- 流恢复与消息补发直接移除，断了就重发

拆干净之后常规的基础设施手段才能用上：列表与读取类结果统一带上存活时长与缓存范围两个字段，并建议**以确定的顺序返回工具列表**以提高缓存命中率[[11]](#ref-11)。两条是配套的——正因为列表结果不再随连接变化，缓存才成立。

**有状态设计的功能上限更高，无状态设计的运维上限更高。** 当一个协议开始追求水平扩展与缓存，它一定会往回收缩依赖长连接的能力。代价是以前由协议兜底的续传与推送成了应用层自己的事——**复杂度没有消失，只是换了个地方。**

### 状态句柄的四条要求

无状态之后，服务端维持跨调用状态只能签发显式句柄。规范给出的每条要求都对应一类真实故障[[1]](#ref-1)：

- **授权**：句柄是名字不是通行证，每次调用都要校验调用者对它的权限，否则拿到别人的句柄就等于拿到别人的状态。

- **不透明**：编码了内部结构的句柄会诱使别人解析或猜测。

- **生存期**：句柄比任何一条连接都活得久，保留策略应写在创建工具的描述里（如「购物车 24 小时无活动后过期」），让模型在决定要不要创建状态时就能看到。

- **过期错误**：对已过期或未知的句柄返回**工具执行错误**，让模型自己重建——又一次落在第一节那条判据上。

## 八、权限、审批与人在环

工具是 Agent 唯一能改变外部世界的通道，所以权限控制必须落在这一层，落在提示词里是不作数的。

### 为什么提示词层面的约束不够

「致命三件套」指的是：**能访问私有数据、会接触不可信内容、具备对外通信能力**。三者同时具备时，攻击者可以通过在内容里植入指令，诱导 Agent 读取私有数据并发送出去[[12]](#ref-12)。

防不住的原因是模型无法可靠地按来源区分指令的重要性——系统提示、用户消息、网页正文、工具返回值最终都被拼成同一串 token[[12]](#ref-12)。你可以叮嘱它不要听信网页里的指令，但恶意指令的措辞有无穷多种写法。

这解释了三件事：工具标注为什么不能当权限用；「护栏」类产品声称的 95% 拦截率为什么不够（Web 安全里 95% 是不及格分）[[12]](#ref-12)；以及真正的对策为什么是**架构性的**——要么切断三件套中的一条边，要么让不可信输入进入之后无法触发有后果的动作。

### 判定按「工具名 + 参数」，不按工具名

某公开实现的评估顺序是[[13]](#ref-13)：钩子（可直接拒绝）→ 拒绝规则（命中即阻断，**旁路模式下也生效**）→ 询问规则（走确认流程，旁路模式下同样生效）→ 权限模式整体判定 → 允许规则 → 运行时回调。

**拒绝规则优先于一切模式。** 安全底线不由运行模式决定，否则一个为效率临时开的旁路开关会把所有精心配置的边界一起关掉。

**规则粒度是「工具名加参数模式」。** `Bash` 这样的裸名拒绝规则会把整个工具从模型视野移除，而 `Bash(rm *)` 保留工具、只拒绝匹配的调用[[13]](#ref-13)，用错了要么过松要么过紧。

这条链上有个陷阱：**被前面某一步自动批准的调用不会再走到后面的回调**。把安全检查写在回调里，而该工具恰好被一条允许规则覆盖，这项检查就被静默跳过了——不报错，只是没执行。对策是写成钩子，它跑在所有步骤之前[[13]](#ref-13)。

同类思路在另一套框架里表现为执行时机：输入侧校验默认与主流程**并行**以降低延迟，但判定出来时主流程可能已消耗 token、甚至已执行工具；改成阻塞式则保证主流程根本不会启动[[14]](#ref-14)。**并行省的是延迟，阻塞省的是副作用**，这个取舍必须显式做出。

### 人在环：真正的问题是恢复语义

「执行前停下来等人点头」的几种实现，差别不在如何暂停，在**如何恢复**。

| 机制 | 恢复方式 | 副作用风险 |
| --- | --- | --- |
| 异常式中断 | 从头重跑整个节点 | 暂停点之前的写操作会重复执行 |
| 可序列化状态 | 从状态快照继续 | 取决于快照粒度 |
| 回调式放行 | 就地等待回调返回 | 调用未发出，无重复风险 |

下图以「读取订单 → 扣款 → 请求批准 → 发货」这条轨迹对照三者恢复后的实际执行次数。

<ToolApprovalResume />

异常式中断的机制是抛出特殊异常，运行时捕获后保存状态并暂停；恢复时**从头重新执行整个节点**，中断之前的代码会再跑一遍[[15]](#ref-15)。官方文档给出的规则很明确——中断之前的副作用**应当幂等**，并举了反例：在中断前创建一条记录，每次恢复都会创建重复记录[[15]](#ref-15)。

由此派生出两个不直观的约束[[15]](#ref-15)：**不要把中断包在宽泛的异常捕获里**，那会把用于暂停的异常一起吞掉；**同一节点内多个中断的顺序不能变**，恢复值按下标与中断点匹配，条件性跳过会造成错位。同理，在节点内用循环反复中断会导致每次恢复重放此前所有轮次，正确写法是每次调用只中断一次、靠条件边路由回来。

根源只有一个：**恢复是重跑，不是续跑。** 换成可序列化状态或回调式放行，约束完全不同。所以选型该问的不是「能不能停下来」，而是「**恢复之后从哪里继续**」——这决定了副作用该写在暂停点的哪一侧。

## 九、几种实现的横向对照

前面各节的结论落到具体产品上，分歧集中在四处。**参数错误作为工具执行错误回灌**是唯一几乎无分歧的一条。

| 维度     | 分歧所在                                |
| ------ | ----------------------------------- |
| 工具定义规模 | 全量注入与延迟加载的取舍，取决于工具数与命中率，不是越省越好      |
| 结果体积   | 源头截断、转存文件、代码编排三者治理层次不同，可叠加          |
| 权限判定   | 规则链、模式、回调的先后顺序差异很大，必须逐产品核对          |
| 人在环    | 恢复语义完全不同，也是唯一一处**选错了不报错、只多花一笔钱**的维度 |

## 十、怎么判断工具做得好

**评测任务要够复杂。** 避免简单的沙箱式任务，强任务可能需要数十次工具调用[[6]](#ref-6)。「搜索日志里的某个 ID」是弱任务，「某客户报告被重复扣款三次，找出所有相关日志并判断是否影响了其他客户」是强任务[[6]](#ref-6)——后者才会暴露分页默认值、字段裁剪、错误信息的真实问题。

**除准确率外收集过程指标**：单次与整任务耗时、调用总次数、token 消耗、工具错误数[[6]](#ref-6)。它们有直接的诊断价值：大量冗余调用通常意味着分页或 token 上限设小了，大量参数非法错误通常意味着描述不清或缺少示例[[6]](#ref-6)。

**读原始轨迹，而不只看汇总。** 模型在反馈里**没说**的往往比说了的更重要，因为它并不总是言行一致[[6]](#ref-6)。一个实例：某工具上线后模型总在查询参数里多加一个年份，导致搜索结果有偏，修正方式只是改了工具描述[[6]](#ref-6)——这类问题读代码发现不了，只能靠读轨迹。
