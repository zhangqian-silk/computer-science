# Agent 工具族

给 Agent 配工具时，真正要做的决定其实不是「提供哪些功能」，而是**每一族工具的接口该长成什么样**：文件操作是做一个万能工具还是拆成五个？命令执行怎么判断一条命令能不能免审批直接跑？开发服务器这种永不退出的进程，为什么套用普通命令的执行链路一定会卡住？

这些问题都有确定的答案，而且答案不来自偏好——**每一族的接口形态，几乎都能从它面对的那个具体约束反推出来**。所以本文逐族要找的是那个约束，而不是罗列工具清单：工具名逐产品不同、随版本变化，约束是共通的。知道约束，就能判断一个没见过的工具设计得对不对，也能看出某个看起来更省事的做法代价在哪。

覆盖范围是通用 Agent 几乎都要具备的那几族：**文件、命令、进程、网络、浏览器**把 Agent 接到外部世界，**代码语义、编辑格式、任务状态与时间、子 Agent、对人的动作**则解决「多步任务怎么才不跑偏」。

阅读只需三点背景，都不必深究：

- **模型通过输出结构化的调用块来使用工具**，程序执行后把结果作为新消息追加回去。
- **工具结果占上下文预算**，所以分页、截断与字段裁剪不是优化而是必需品。
- **只读工具通常可以免确认执行，写操作需要审批**——各族会就地说明自己的权限约束落在哪里，但不展开权限系统本身的设计。

文中的具体默认值（超时秒数、字符上限等）多来自某一产品在核验日的公开文档，属一方经验；可迁移的是结构，不是数值。

## 一、文件操作：为什么拆成五个工具

最直觉的设计是做一个万能文件工具，用一个动作参数区分读写改。主流实现一律不这么做，而是拆成读、写、改、按名找、按内容找五件事。四条收益各自对应一类真实故障。

**权限模型变简单。** 只读工具可以免确认自动执行，写工具单独走审批。合成一个之后授权粒度就只剩「整体允许」或「整体禁止」两档，而这两档都不是想要的。这条收益在权限规则的写法上直接可见：有实现让读类工具共用一种路径规则格式、写类工具共用另一种，于是「允许改这个目录」和「允许读那个目录」可以分别表达。[[1]](#ref-1)

**并发语义变清晰。** 只读工具可以放心并行调用，写工具必须串行。工具一旦合一，调度器就无法从工具名判断这次调用能不能与别的同时进行。

**token 预算可以分别调。** 读取需要分页与上限，搜索需要截断与输出模式，两者的参数策略毫无共同之处。

**错误可以归因。** 失败落在具体动作上，模型才知道该改什么。万能工具的失败信息里必然混着五种动作的失败原因。

### 修改为什么用字符串锚点而不是行号

精确修改的输入是一段**必须唯一命中**的原文，而不是行号区间。理由有三层。

**行号会漂移**：模型上一次读到的第 42 行，在它自己改过一次之后就不是那一行了；字符串锚点则自带上下文校验，内容对不上就匹配不到。

**返回体量更小**：改动前后的差异比整份文件小得多。

最关键的一层是：**唯一性要求本身是一个断言。** 要求锚点唯一命中，等于强迫模型提供足够的上下文；命中多处说明它其实没看清代码，这时失败比改错好；命中零次则说明文件已经变了或记忆有误，同样必须失败。这条约束不是为了让编辑更方便，而是**把「模型以为自己看清了」变成可检测的**。有实现明确把三项检查并列为编辑生效的前提：改前要读过、锚点要精确匹配、且必须唯一——多处命中时要么补足上下文缩小到一处，要么显式声明全部替换。[[1]](#ref-1)

「改之前必须先读」这条配套约束防的是另一种失真：模型凭记忆重写整个文件，静默丢掉它没看过的部分。值得注意的是这条约束正在被有条件地放宽——有实现允许较新的模型在「读这个文件本来也不需要审批」的前提下直接编辑未读过的文件，因为锚点匹配当前内容这件事本身已经提供了安全性。[[1]](#ref-1) 这是个有意思的演化方向：**当一项检查的目的可以由另一项更本质的检查达成时，前者就可以退化为条件性的。**

### 一条反模式：用命令行绕过文件工具

用 `cat`、`sed`、`echo >` 走命令通道读写文件，是把上面所有收益一次性放弃：绕过了改前必读的校验、绕过了分页与上限、绕过了读写分离的权限判定，还拿不到带行号的输出。它看起来更灵活，代价是这次操作退回到了无法被治理的状态。

有意思的是这条边界也不绝对。有实现承认「用某些只读命令看过文件」同样满足改前必读的要求，但精确限定了范围——单文件、无管道、无重定向的若干查看类命令才算数，并且只影响编辑资格，不改变权限判定。[[1]](#ref-1) 这个处理很能说明工具边界的设计取向：**不是禁止另一条路径，而是精确说明它在哪一段等价、在哪一段不等价。**

## 二、命令执行：能力最强，约束也最需要设计

命令执行把「任意可执行的东西」都变成了可调用工具。代价是攻击面同样是任意的。三处约束值得展开。

### 会话状态：哪些留得下，哪些留不下

常见的误解是「命令跑在一个持久的 shell 会话里，所以上一条命令的一切都还在」。真实情况要碎得多，且**逐产品不同**。以一个公开了完整行为契约的实现为例：[[1]](#ref-1)

| 状态 | 是否延续 | 细节 |
| --- | --- | --- |
| 工作目录 | 有条件延续 | 只在项目目录或显式添加的工作目录内延续；越界会被重置回项目目录并在结果里说明 |
| 环境变量 | **不延续** | 一条命令里的导出，在下一条里读不到 |
| 别名与函数 | 可用 | 来自 shell 启动文件，在会话开始时被一次性捕获并应用到每条命令 |

同一份文档还说明，每条命令跑在各自的进程里——这与「一个长期存活的交互式 shell」是完全不同的模型。

这些差异共同指向一条可迁移的写法：**用绝对路径，不要依赖上一轮的目录切换或变量导出。** 需要环境变量长期生效时，应当通过宿主提供的机制注入，而不是指望一条命令的副作用留到下一条。

### 超时与输出：两个都必须分档的量

固定超时必然两头不讨好：对一次目录列举太松，对一次依赖安装太紧。可行的形态是「默认值 + 可由调用方按命令提高 + 有硬上限」。一个公开的取值是默认两分钟、上限十分钟，两者都可用环境变量调整。[[1]](#ref-1) 这是某一产品在核验日的默认值，不是行业标准——但「分档且有上限」这个结构是共性的。

输出侧同样需要分层，而且这里有一个容易被忽略的细节：**成功与失败的输出预算可以不一样。** 同一份文档给出的做法是，输出先流式写入工作文件（超过极大阈值的命令会被终止），命令结束后再从文件读回：[[1]](#ref-1)

| 结果 | 内联上限 | 超出部分 |
| --- | --- | --- |
| 有效 | 约 30,000 字符 | 返回文件路径加一小段预览，模型自己去读或搜 |
| 失败 | 约 10,000 字符 | 以首尾节选给出，**不给路径** |

这个不对称是有道理的：成功结果里模型可能需要任意一段细节，所以给路径让它自取；失败结果里真正有用的信息高度集中在开头的报错与结尾的汇总，中间部分几乎总是噪声。

同一份文档还记录了一处更精细的判断：退出码为 1 是否算失败取决于具体命令——对若干检索与比较类命令，退出码 1 表示「没有匹配」或「存在差异」，属于正常的否定答案而非错误。[[1]](#ref-1) 这类特判看起来琐碎，但它防的是一类真实的浪费：**把「没搜到」当成「搜索失败」，模型会反复重试一个本来已经给出答案的命令。**

### 读写判定：难点全在组合

只读命令可以免确认执行，写命令要走审批，所以必须先判定读写属性。单条命令不难，难的是管道、逻辑连接、命令替换与重定向。

<ReadOnlyGate />

两点值得从判定规则中单独提出来。

**其一，白名单的粒度可以细到子命令。** 版本控制工具的查询类子命令与推送类子命令属于完全不同的风险等级，把整个命令名一并放行或一并拒绝都太粗。权限规则支持命令模式匹配正是为此。[[1]](#ref-1)

**其二，「只读」与「安全」是两个维度。** 一条纯粹的读命令照样可以读到工作区之外的敏感文件。所以路径约束必须独立于读写判定存在——这也解释了为什么即便是只读工具，在访问工作目录之外的路径时仍然应当触发确认。[[1]](#ref-1)

白名单挡不住未知，所以还需要隔离层兜底。有实现把沙箱策略分成三档——只读、工作区可写、完全不设限，并默认关闭网络访问、把写权限限制在当前工作区内；即便在可写的根目录里，版本控制目录与若干配置目录仍然递归保持只读。[[2]](#ref-2) **沙箱与白名单不是替代关系**：白名单判断「这条命令该不该放行」，沙箱兜住「万一放行错了，它最多能碰到什么」。

## 三、进程：把不会结束的东西当成会结束的

这是工具层里错误形态最固定的一处。开发服务器、文件监视、日志跟随这类进程永不返回；如果沿用「执行 → 等待 → 超时 → 处置」的同步链路，整条链从第一步就选错了。

权限上这一族继承命令执行的判定——**后台化不降低风险等级**：一条需要审批的命令转到后台仍然需要审批，而它在后台持续运行这件事本身还引入了额外的回收责任。

<ProcessRouteDecision />

超时之后怎么处置，存在真实的实现分歧，而分歧点本身很能说明问题。

- **超时即转入后台**：命令没被杀掉，而是移到后台继续执行，结果里说明发生了什么并带上任务标识与输出文件路径。同一实现列出了三类刻意不自动转后台的命令，其中一类是「无法被完整解析成简单命令的复合命令」——解析不确定时不做自动处置。[[1]](#ref-1)
- **超时即终止**：资源边界清晰、不留后台状态，坏处是把「慢」和「卡死」当成了同一件事。

前一种做法还记录了一个容易出错的细节：被转入后台的命令里的目录切换不会延续到后续命令，并会在结果里显式声明，以免模型基于一个没有发生的目录变更继续操作。[[1]](#ref-1)

两者无优劣之分，差别在于「超时」这个信号被解释成了什么。但真正稳定的结论在更前面一层：**这一步判断错了，后面的超时策略怎么调都救不回来。**

后台任务另有两条「不做就会出事」的要求。**一是必须有句柄**：手工在命令尾部加一个后台符号不算——进程确实活着，但拿不到标识，之后既读不到输出也无法定点停掉。**二是必须有生命周期**：一个公开实现的规则是，前台子 Agent 启动的命令在该子 Agent 给出最终响应时结束，主对话或后台子 Agent 启动的则在最终响应之后继续运行。[[1]](#ref-1) 这类规则决定了「任务跑完之后端口还占不占着」。

判断服务是否就绪则是另一条独立纪律：**不能靠固定等待时间。** 可靠手段是轮询输出里的就绪标志、探测端口或调健康检查接口，都要带重试上限与退避。固定等待在快机器上浪费时间，在慢机器上直接失败。

## 四、网络：检索与抓取是两件事

检索负责找到入口，抓取负责读懂一页。两者的返回体量、失败模式、安全约束都不同，合成一个工具会同时损失召回质量与安全边界。

### 两者的形态差异

检索侧的要点是召回与并行：

- 一个复合问题拆成几个正交的查询并行发出，比串行追问收敛快得多。
- 返回摘要而非全文，让模型自己决定深读哪一条。
- 结果带上发布时间，模型才能判断新旧冲突。

有实现在这一层还做了两件事：单次调用内部可以发起多轮后端检索再返回；给整个会话设一个检索次数上限，达到上限后返回的是「请用已有信息继续」的提示而不是错误——**因为错误会诱导重试**。[[1]](#ref-1) 这个细节值得记住：给模型的失败信息会塑造它的下一步行为，失败信息的措辞是设计的一部分。

抓取侧有一个常被忽略的性质：**它可能是有损的。** 有实现的抓取工具并不把原始页面交给模型，而是先转成 Markdown，再用一个小模型按调用时给出的提取要求处理一遍，模型收到的是处理后的答案。[[1]](#ref-1) 这个设计省了大量 token，但代价必须说清楚：**一次抓取说「页面里没提到某件事」，可能只意味着提取要求里没问这件事。**

这就引出抓取的另一半设计——分页续读契约。需要完整读全文时（转换、重构、逐段整理），返回体应当带上当前区间与总长度，未读完就以上次的结束位置继续；只做定向查找时，则用带查询的片段模式，它不保证覆盖全文。**把「读全」和「找到」当成同一种读法，是长文档处理里最常见的失败。**

### 安全：这一层不做就等于没做

抓取工具直接把外部内容引入系统，防护要按请求生命周期分层。

| 阶段 | 要做的事 | 不做会怎样 |
| --- | --- | --- |
| 发起前 | 限定协议；拒绝 URL 内嵌凭证；走域名允许／拒绝规则 | 任意协议与凭证走私 |
| 解析后 | 拒绝解析到私有网段、环回、链路本地与云元数据地址的主机名 | 内网与元数据服务被读取 |
| 重定向 | 限制跳数，且**每一跳都重新过同一套校验** | 攻击者用自有域名跳转到内网地址 |
| 响应中 | 超时、体积上限、内容类型校验 | 单次抓取拖垮或撑爆整个会话 |
| 返回后 | 把正文当数据，不当指令 | 间接提示注入 |

重定向那一行是最容易漏、也最值得强调的：**只校验首个 URL 是一个经典漏洞。** 攻击者只需要一个自己控制的、看起来正常的域名，跳转到内网地址即可。

不同实现在这里的取舍不同，三种做法各自代表一个方向：

- **把隐式跳转变成显式决策**。有实现在 URL 重定向到不同主机时不自动跟随，而是返回一个说明原始地址与目标地址的结果，由模型决定要不要再发一次请求。[[1]](#ref-1) 代价是多一轮往返。
- **缩小注入面**。另一处实现让检索默认走一个维护好的结果索引而非实时抓取，以减少来自任意实时内容的注入，同时明确提示即便如此也应把检索结果视为不可信。[[2]](#ref-2)
- **让规则的优先级不可被绕过**。同一份文档记录了一条值得借鉴的细节：**主机名解析到非公开地址时，即便匹配了允许规则也仍然被拒绝**。[[2]](#ref-2)

最后这处还坦承，这道检查「减少但不能消除」解析重绑定风险——若把恶意解析纳入威胁模型，就还需要在更低层做出口管控。[[2]](#ref-2) **能把自己防护局限写清楚的文档，比只列功能的文档可信得多。**

还有一条独立于安全的工程要求：**错误要可归因。** 回给模型的失败信息要说清是协议、主机、解析、重定向还是策略拦截导致的，模型才能决定换一个地址、问用户还是放弃。一个模糊的「抓取失败」只会让它原地重试。

## 五、浏览器：先定下怎么看见，再谈怎么操作

动作集（点击、输入、滚动）是浏览器工具里最不需要讨论的部分。真正决定成本与稳定性的是前一层：**Agent 靠什么看见页面，靠什么指认元素。**

<BrowserPerceptionModes />

主流选择是无障碍树快照而非截图，理由在官方文档里被列成了一张对照表：token 成本低、精确（引用直接指向具体元素，而不是靠坐标估算）、快、确定（同样的结构给出同样的交互，而布局变化会让坐标失效）、且不需要视觉模型。[[3]](#ref-3)

快照的形态本身也值得看一眼：它是一棵带角色、名称与状态的节点树，每个节点带一个引用标识，动作直接指名这个标识。[[3]](#ref-3) **这意味着「模型看到的」和「模型能操作的」是同一个东西**——而在截图模式下，这两者之间隔着一次坐标估算。

几处工程细节都来自同一份官方文档：[[3]](#ref-3)

- **引用会失效。** 它只在当前快照内唯一，页面一变就过期，此时工具会明确报错要求重新取快照。所以「导航之后重新观察」不是良好习惯而是硬要求。
- **大页面不要整取。** 有专门的检索能力只返回匹配节点及其上下文，比取整页快照便宜得多。这与文件工具里「先定位再读区间」是同一条思路。
- **两者可以组合。** 需要判断视觉效果时，结构化快照负责交互、截图负责观察，不必二选一。

这就回到那个真正的判断题：**什么时候才该开浏览器。** 不构成理由的有三条：对象是网页、页面是动态渲染的、某次抓取失败了一次。构成理由的是：需要真实交互（多步表单、流程），需要登录态下的账号动作，或者非图形界面手段确已不足而图形界面有一条可验证的直达路径。浏览器慢、贵、脆，能用普通抓取解决的就不要开浏览器。

## 六、代码语义：从按字面找到按含义找

前面的文件工具解决的是「按字面找、按字面改」。工程代码里真正的问题往往是语义的：这个符号在哪定义、改了它会影响谁、这次编辑有没有把语法写坏。

这一族的权限形态很清楚：**查询类动作全是只读的，可以免确认并行调用**；真正需要审批的只有落盘那一步，也就是它与文件写工具共用的那条边界。

### 词法检索与语义检索的分工

语言服务器协议原本是给编辑器用的，现在成了 Agent 的常见配件。它与文本检索的差别不在「更强」，而在**答案的来源不同**：一个是字符串碰巧匹配，一个是经过编译器认定。

| 问题 | 该用什么 | 为什么 |
| --- | --- | --- |
| 找一段字符串 | 词法检索 | 零配置、即时、通用 |
| 按文件名找文件 | 模式匹配 | 同上 |
| 这个符号在哪定义 | 语义检索 | 词法检索会命中注释、字符串与同名变量 |
| 谁引用了它 | 语义检索 | 词法检索会漏掉别名导入与再导出 |
| 它的类型签名是什么 | 语义检索 | 不必打开文件就能拿到 |
| 改完有没有类型错误 | 语义检索 | 编辑后即时诊断，不必单跑一次构建 |

有实现把这层能力做成了一个工具，并明确列出它提供的动作：跳转定义、查找引用、取位置处的类型信息、列出文件符号、跨工作区按名检索符号、查接口实现、追调用层级；同时在每次文件编辑后自动报告类型错误与告警，使模型不必另起一次构建就能发现问题。[[1]](#ref-1)

但它有明确的代价，同一份文档也写清楚了：这类工具需要为对应语言安装并启动语言服务器，没装就处于未激活状态，某些运行环境下根本不启动。[[1]](#ref-1) 加上大仓库的索引成本，结论是**它是补充而不是替代**——按问题类型分流，而不是用一个替掉另一个。

### 两种编辑形态

除了唯一命中的字符串替换，另一条主流路线是让模型直接产出**补丁**。有实现把它做成了签名工具，并为此定义了一套专门的格式：一个 `*** Begin Patch` 与 `*** End Patch` 构成的信封，中间是若干文件操作——新增、删除、更新，更新块里以 `@@` 标出定位上下文，以行首的加号、减号、空格区分新增、删除与上下文行，还支持在更新的同时移动文件。[[4]](#ref-4)

两种形态的适用面不同：

- **字符串替换**更简单稳健，失败信息明确（没命中就是没命中），适合小范围精确修改。
- **补丁**能一次跨多个文件、改动意图显式、天然可审计（它本身就是一份可读的差异），适合成批的结构性改动。
- 补丁的代价是它自带语法：格式写错或上下文行对不上会整片失败。有意思的是，实现层面为此做了让步——公开的解析器源码明确说明它比正式文法更宽松，允许标记前后有多余空白，并为某个已知需要宽松解析的模型保留了额外容错。[[4]](#ref-4) **一种格式需要为模型放宽解析，这件事本身就说明了工具与传统接口的区别。**

### 编辑工具自带校验

有一个来自研究工作的设计值得单独讲：在编辑函数里内置代码检查，语法不通过就**丢弃这次编辑**，并把错误连同改动前后的片段一起回给模型，要求重改。[[5]](#ref-5)

它的价值不在于「能查语法」，而在于**把错误拦在落盘之前**，而不是等几步之后跑测试才发现。纠错回路从「编辑 → 若干步 → 测试失败 → 回溯定位」缩短成了「编辑 → 立刻失败 → 重改」。

这项工作提出的更一般的主张是：语言模型是一类新的使用者，应当为它们专门设计接口，而不是把给人用的界面原样搬过去。同一篇工作里的另一个例子是文件查看器——按窗口展示带行号的代码，而不是一次输出整个文件。[[5]](#ref-5) 这个主张后来在很多地方被独立地重新发现：带行号的读取、唯一命中的编辑、结构化的失败信息，本质上都是同一个思路。

## 七、编辑格式：token 成本与应用可靠性的取舍

上一节的两种编辑形态是从**接口**角度分的，这一节换一个角度：同样是把改动交出来，用什么**格式**承载？这是「输出格式影响模型能力」最清楚的实例。

一组公开基准给出的结论颇为反直觉：**要求模型在标准 Markdown 代码块里返回整个文件，在当时测试的全部模型上都是最可靠有效的格式；而改用函数调用接口来传递编辑，表现反而更差**[[7]](#ref-7)。作者给出的解释是：更复杂的输出格式会引发两个问题——它让模型写出更差的代码（格式化本身占用了注意力），同时降低了模型对格式本身的遵守度[[7]](#ref-7)。

但整文件重写有它自己的代价，也被明确写了出来：同等效果下它**显著增加成本与延迟**，而把整个文件逐字重新打出来这件事，在较慢的模型上是不可接受的[[7]](#ref-7)。所以该基准的最终选择是分模型而定，而不是统一取一种。

另一组数据说明了第三种格式存在的理由：某个模型在搜索替换块格式下只得 20%，且在 12 道题上输出了「其余部分不变」这类偷懒注释；换成统一 diff 格式后提升到 61%，偷懒次数降到 4 次[[8]](#ref-8)。

把这三段放在一起，得到的不是「哪种格式最好」，而是一条判断：**整文件最可靠但最贵，diff 类最省但对格式遵守度要求高——一旦模型输出跑偏，编辑根本应用不上去。** 取舍点随模型变化，所以这是个必须拿自己实际使用的模型重测的参数，不能靠直觉选定后一劳永逸。

## 八、任务状态与时间：让长任务不跑偏

模型没有稳定的工作记忆，多步任务里很容易漏步骤、重复劳动或悄悄换目标。常见的解法是把计划**外部化成一个可读可改的状态**。

### 待办清单的两条约束

这类工具在几家实现里形态相近，有的是一个整体提交的清单，有的是一组增删改查接口。[[1]](#ref-1)[[6]](#ref-6) 两条约束都是为了对抗同一个问题——状态漂移。

**全量替换。** 每次提交完整列表，未出现的条目视为删除。增量更新看似省事，但模型对「我上次提交了什么」的记忆并不可靠，增量语义会让本地状态与模型认知逐渐分叉。

**单一进行中。** 同一时刻只允许一条处于进行中。这条约束的作用不是管理效率，而是防止模型同时声称在做三件事、实际一件都没做完。

配套的还有两条纪律：做完一条立刻标记，不批量补记；受阻时保持原条目为进行中，另开一条描述要先解决的问题，而不是把受阻的条目标记为完成。

有一个反向的观察值得记下来：有实现在较新的模型上**默认不提供**这组工具，理由是这些模型不靠外部清单也能跟踪多步工作，而工具定义与配套提醒本身要占上下文。[[1]](#ref-1) 这是个很好的提醒——**外部状态是对模型能力缺口的补偿，缺口变小时，补偿本身就成了成本。**

### 计划模式：一种受限执行态

计划模式的本质是一个**只读的执行态**：只读工具可用，写操作被禁，先出方案、经人批准再动手。[[1]](#ref-1)[[6]](#ref-6)

它的关键机制在于退出：**退出计划模式本身是一次需要审批的动作。** 这让「方案已获认可」成为一个显式的、有记录的事件，而不是双方各自假设的默契。价值可以用一句话概括：**改动越大，返工成本越高，而对齐方案是整条链上最便宜的纠错点。**

### 时间维度：让 Agent 跨越一次对话

这一类能力容易被忽略，但它把 Agent 从「一问一答」变成了「能跨时间自主推进」。有实现提供了三种形态：[[1]](#ref-1)

- **定时触发**：在未来某个时刻或周期性地触发一段提示。要点是作用域与生命周期——属于哪个会话、会话恢复时是否重建、过期如何清理。
- **自定步调的唤醒**：Agent 在每轮结束时自己决定下一轮什么时候跑，并可以显式停止。这比死循环轮询省得多。
- **事件监听**：把后台命令的每行输出、或一个长连接的每条消息作为事件实时送回模型，使它能在对话中途对日志、文件变化或状态轮询做出反应。

第三种形态与第三节的「后台运行再回读」有本质区别：回读是模型主动去看，监听是事件主动找来。**前者的观察时机由模型决定，后者由外部世界决定。**

## 九、子 Agent：把上下文压力换成组织结构

当任务的探索过程会产生大量中间信息、而最终只需要一个结论时（读十个文件定位一处问题），最有效的办法不是压缩，而是**换一个窗口去做**。

子 Agent 的核心语义只有一条：**它在自己的上下文里工作，父对话看不到它的中间过程，只收到最终那一段结果。**[[1]](#ref-1) 其余性质都由这一条派生。

三个边界必须讲清楚，因为它们都是「设计使然」而非缺陷。

**信息损耗是它省上下文的原因，不是它的毛病。** 正因为只回传结论，中间那几十次工具调用才没有占据父对话的窗口。直接推论是：**子任务描述必须自包含**——背景、约束、验收标准要一次讲全，因为执行者看不到父对话里的上下文。

**权限与环境都不自动继承。** 工具集应当按任务收窄（例如探索类子 Agent 不给命令执行能力），这是最小授权在这一族最自然的落点。环境同理：有实现明确规定子 Agent 的会话**从不延续工作目录的改变**。[[1]](#ref-1) 所以跨 Agent 协作要靠绝对路径或显式传参，不能靠共享的隐式状态。

**并行的代价在写操作上。** 多个子 Agent 同时改同一批文件会互相覆盖。只读探索适合并行，写操作要串行或分区——有实现为此提供了工作区隔离能力，让并行改动落在各自独立的目录里。[[1]](#ref-1)

还有两处细节值得记住：给子 Agent 设**轮次上限**防止跑飞，到达上限时把结果标记为部分输出并允许恢复继续；以及后台子 Agent 的**权限请求要能回到主会话**让人拍板——否则它只能在遇到需要审批的动作时自行放弃。[[1]](#ref-1)

三个边界合起来给出委派的适用条件：**只有当子任务能被清晰界定、且产出可验证时，这笔交换才划得来。**

## 十、对人的动作也是工具

工具容易被默认为「对机器的动作」，但对人的动作同样需要被实现成工具。它们回应四个不同的问题。

**需求不清时怎么问。** 以选择题形式澄清歧义，比自由文本更容易回答、也更容易被程序消费。有实现的默认行为是问题一直等待回答，同时提供可选的超时——超时后关闭对话框、提交已选项并告知模型可能无人在场。[[1]](#ref-1)

同一份文档在这里划出了一条准确的界线：这个超时**只作用于选择题，审批提示永不因闲置自动放行**。[[1]](#ref-1) 道理是两者的默认方向相反——**问一个问题没人答，可以先按判断继续；一次授权没人批，绝不能默认通过。**

提问的纪律只有一条：**只在会改变结论时才问。** 会改变结论的关键歧义要一次问清，并给出选项与倾向性建议，把判断成本留在自己这边；不会改变结论的，自行选择并注明假设。

**高风险时谁拍板。** 不可逆动作前必须停下征得同意，审批线应当按**可逆性与影响半径**预先划定并写下来。有实现把这条做到了工具注解层面：即便一次调用同时声明了只读特征，只要它声明了破坏性，就仍然需要审批。[[2]](#ref-2) 这个「取更严的那一项」的合成规则是对的——**风险标记之间不应当相互抵消。**

**被卡住时怎么继续。** 登录、单点登录、扫码、验证码不是失败，而是需要人完成的一步。正确处置是请求接管，完成后回到原路径继续。

**做完了怎么交付。** 长任务完成要能主动触达；产物要以可打开的形态送到人面前，而不是只在过程记录里提一句路径。[[1]](#ref-1) 最后这条尤其容易做错：**交付一份操作过程记录，而不是对方真正要的那个东西。**

## 十一、小结

前面每一节都在回答「这一族的接口为什么长这样」，逐族的结论不再重复。这里只留三条跨族才看得出来的东西。

**同一个错误换了层次就认不出来了。** 用命令行绕过文件工具、给长跑服务加个后台符号、只校验重定向的第一跳、靠固定等待判断服务就绪——这四件事分属四族，形状却完全一样：都是用一个更省事的做法换掉了某种可检测性，而放弃的东西（治理、句柄、整链防护、真实状态）在出事之前都不会显形。**判断一个捷径值不值得走，看它把什么变成了静默的。**

**三组区分横跨各族，且都是出事的高发处。** 「只读」不等于「安全」——读操作照样要过路径约束；「有句柄」不等于「有生命周期」——后台任务还得定义什么时候回收；「快照便宜」不等于「快照万能」——自绘界面在无障碍树里根本没有节点。三组都是把某一维度的结论当成了另一维度的结论。

**失败信息是接口的一部分，不是接口的附属品。** 编辑前的唯一性断言让「模型以为自己看清了」变得可检测，编辑时的内置检查把错误拦在落盘之前，检索到上限时返回提示而非错误以免诱导重试——这三处分属三族，但设计动机同一个：**模型读到什么样的失败，就会做出什么样的下一步。**
