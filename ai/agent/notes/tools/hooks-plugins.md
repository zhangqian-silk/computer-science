# Hooks 与 Plugins：事件扩展与能力封装

Hook 是围绕某个运行事件执行的扩展逻辑；Plugin 是把工具、知识、配置或 Hook 等内容组织为可安装单元的方式。前者描述「何时运行」，后者描述「如何分发和组合」。不同宿主的事件与封装格式并不统一。

---

## 一、事件扩展的基本位置

| 扩展位置 | 可处理的信息 | 可能用途 |
| --- | --- | --- |
| 输入到达后 | 用户输入及任务状态 | 记录、规范化 |
| 模型调用前 | 已组装的请求 | 附加必要项目资料 |
| 工具执行前 | 名称、参数、身份 | 校验或请求确认 |
| 工具执行后 | 实际结果 | 转换结果、记录指标 |
| 任务结束时 | 终态与产物 | 清理资源、保存摘要 |

这是概念性分类，不能据此假设所有产品都有相同事件。真实宿主的返回值可能是观察、修改、拒绝或暂停，应按对应契约解释。[[44]](../references.md#source-cc-hooks)

---

## 二、Hook 怎样参与一次动作

```mermaid
flowchart LR
	I["待执行动作"] --> H["执行前扩展"]
	H --> P["最终策略校验"]
	P --> T["实际工具"]
	T --> O["执行后扩展"]
	O --> R["结果"]
```

图中扩展如果改变了参数，最终校验必须针对改变后的实际动作。对原始路径的批准不能自动覆盖 Hook 改写后的另一个路径。

多个 Hook 需要确定顺序、是否允许短路以及如何合并修改。例如一个扩展补全参数，另一个执行审计，应明确审计记录的是补全前还是执行时的值。

观察性扩展一般不应影响核心动作；阻断性扩展则要明确失败时是否禁止执行。安全检查失效不能默认放行，普通统计写入失败也不必一定使已完成业务操作失败。

## 三、Plugin 的组成与生命周期

Plugin 可以包装一个工具集合、一份 Skill、一个连接器，或几类资源的组合。安装只说明内容进入宿主，激活才表示注册的扩展开始参与运行。

典型生命周期包括载入、配置校验、注册、使用、停止接收新工作、等待在途动作结束及释放资源。对于简单静态知识包，生命周期可能很轻；对于持有进程和远程连接的扩展，需要明确清理责任。

卸载不能自动撤销此前发出的邮件、写入的数据或已运行的外部任务。应把「移除后续能力」与「撤销历史副作用」分开。

---

## 四、版本与组合

若工具说明和实现被不同步更新，模型可能按旧参数作出决定，而执行器按新含义执行。一次在途请求应能对应其使用的能力版本，或者在不兼容时明确拒绝。

热更新还涉及旧连接何时释放、排队调用由哪个版本处理、卸载后的回调如何收尾。只有确实需要不中断更新时才引入这些机制；普通重启加载的生命周期更容易解释和验证。

多个插件共享名称、事件或全局状态时，也可能互相影响。命名空间、明确的状态所有权和组合测试比「每个插件单独测试通过」提供更多保证。

## 五、学习检查与参考资料

再比较 Skill 和 Hook：Skill 通过上下文影响模型如何行动；Hook 由宿主在事件点调用。Plugin 可以包含二者，但不会消除这种区别。
