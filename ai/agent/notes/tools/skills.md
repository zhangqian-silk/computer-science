# Skills：操作知识与渐进加载

Skill 是围绕一类任务组织的操作知识包。它把适用条件、步骤、检查要求和参考资料放在可发现的位置，供 Agent 在需要时加载。Skill 不会因为被读入上下文就新增工具权限，也不等于模型权重发生变化。

Agent Skills 格式以 `SKILL.md` 为入口，包含元数据与正文，并可携带脚本、参考资料和模板。以下说明通用知识组织，不依赖某个宿主的触发快捷方式。[[40]](../references.md#source-skills-spec)

---

## 一、Prompt、Tool 与 Skill

| 对象 | 主要回答 | 例子 |
| --- | --- | --- |
| Prompt | 当前需要怎样回答或行动 | 「只解释，不修改」 |
| Tool | 可以实际执行什么 | 读取文件、搜索文档 |
| Skill | 一类任务通常怎样完成和检查 | 文档审阅步骤与检查清单 |

Skill 正文会成为提示信息的一部分，但它作为独立知识包，还包含发现、选择和资源组织问题。一个文档审阅 Skill 可以指导读取正文和核对引用；若没有网络工具，它不能凭说明文字真正访问外部来源。

---

## 二、渐进加载

```mermaid
flowchart LR
	I["名称与适用描述"] --> S["匹配任务"]
	S --> B["读取正文"]
	B --> R["按需读取参考资料"]
	R --> A["执行并核对"]
```

第一层让系统知道有哪些知识包；第二层在选择后提供完整步骤；第三层只加载当前需要的细节或模板。这减少无关输入，但要求描述能正确区分任务。

「适用于所有工作」几乎没有选择价值。较好的描述能同时表达正例和边界，例如「审阅技术文档的结构、术语与引用；不处理程序运行故障」。

渐进加载不是把已经选中的必要指令只读一半。入口正文中的约束和检查应先完整理解，再决定读取哪份附属资料。

---

## 三、一个知识包应该写什么

以「配置说明审阅」为例，可以组织为：

| 内容 | 示例含义 |
| --- | --- |
| 适用任务 | 解释或审阅配置说明 |
| 输入 | 配置正文、问题、可用来源 |
| 核心步骤 | 识别字段，核对单位，区分声明值与运行值 |
| 结果要求 | 给出结论、依据与未知项 |
| 检查 | 不把修改建议写成已经执行 |
| 附属资料 | 字段词表、审阅模板 |

正文应把必要动作和可选扩展分开。过多彼此无关的流程会扩大输入，也会让触发边界变模糊；可独立使用且很长的材料可以放入参考资料。

---

## 四、加载、执行与信任

Skill 是可读的操作知识，不天然可信。宿主应确定包来源、版本和允许使用的资源；包内引用不能成为越出任务范围读取秘密资料的理由。

包内脚本若被使用，它属于实际工具执行，需要参数、权限和结果检查。文档说「运行验证」不等于验证已经运行；脚本报告成功也仍要对应本次输入和产物。

多个 Skill 同时适用时，要检查步骤是否重复、输出要求是否冲突、工具使用范围是否一致。冲突不能靠最后加载的文件自动覆盖。

---

## 五、如何评价 Skill

分别评价选择和执行：

- 正例任务是否选中，邻近但不适用的任务是否被排除。
- 选中后是否完成必要读取和检查。
- 输出是否满足任务标准，而不是机械复述步骤。
- 与没有 Skill 的相同任务相比，质量、长度和调用成本如何变化。

版本更新应同时检查描述和正文。描述仍宣传旧能力、正文却改成新流程，会造成选择正确而执行错误。

学习自检：一个包含完美说明但没有必要工具的 Skill 能完成外部操作吗？不能。它提供方法，实际能力和授权来自执行环境。
