# Skills 与操作知识加载

Skill 是按用途组织的操作知识及相关资源，不是一个新的模型角色，也不必包含独立 Agent。它可以指导一次调用、提供一个固定操作流程，或被 Agent 按需使用。输入怎样编排见 [Context](../context/context-engineering.md)，承载 Skill 的插件生命周期见 [扩展宿主](hooks-plugins.md)。

## Skill 与 Prompt、Tool 的关系

Prompt 表达当前指令，Tool 提供可执行能力，Skill 描述何时以及怎样完成一类工作。一个“代码审查”Skill 可以包含检查方法、结果模板和辅助脚本；模型仍需借助文件和测试工具获取实际证据。写了“运行测试”并不等于测试已经运行。

Agent Skills 规范提供目录、元数据和正文等组织方式；Claude Code 又扩展了调用控制、动态上下文等宿主特性。可移植性应按字段和行为检查，不能看到都是 `SKILL.md` 就假设权限规则完全一致。[[40]](../references.md#source-skills-spec) [[41]](../references.md#source-cc-skills)

## 渐进加载的三个层次

发现层告诉宿主或模型哪些技能存在，通常包含名称和适用描述；选择后加载正文；只有正文引用的具体资源需要时，再读取脚本或参考文件。其意义是控制初始上下文，并让能力可发现，而不是让大正文永远零成本。

```text
索引：safe-config-review，适用于配置与环境覆盖检查
   ↓ 选择
正文：检查顺序、缺失信息处理、输出契约
   ↓ 需要某项操作时
参考：字段说明、测试命令、报告模板、受控辅助脚本
```

索引描述应有可区分的触发边界。两个 Skill 都写“帮助你完成所有编码任务”，会让选择退化；正文再完善也可能从未被加载。评价 Skill 时要分别测是否被选中、选中后是否执行正确、是否错误用于不相关任务。

## 一个最小 Skill 的内容

```markdown
---
name: safe-config-review
description: 检查配置字段及环境覆盖关系，输出带来源的审查结果。
---

先确认用户要求是读取还是修改。
读取配置与相关部署说明，区分显式值、默认值和运行时覆盖。
每项结论保留文件版本和范围；缺少环境信息时标记未验证。
需要修改时先给出候选差异，按宿主权限规则执行并验证。
输出：观察、风险、候选修改、验证证据、仍缺信息。
```

这份正文没有承诺越权能力，没有把脚本输出当成天然可信，也没有硬编码一个可能过期的模型名称。它说明行为和交付，具体凭据及环境权限留在宿主。

辅助脚本适合确定性格式转换、数据读取或测试，不必让模型每次重新生成。脚本本身是代码，加载、安装、执行必须经过与其他代码相同的信任和版本管理。不能因它位于 Skill 文件夹就绕过审核。

## Skill 索引与正文版本

模型根据旧描述选了技能，实际读取却是新正文，可能改变行为甚至执行范围。宿主可以选择不可变包版本，或者在 hash 变化时刷新索引并重新选择；不能默默忽略这种变化。

```python
# 教学代码：读取函数受宿主路径与权限约束。
import hashlib

def load_skill(index, read_text):
    body = read_text(index["path"])
    digest = hashlib.sha256(body.encode("utf-8")).hexdigest()
    if digest != index["body_sha256"]:
        return {"status": "catalog_changed", "content": None}
    return {
        "status": "loaded",
        "content": body,
        "provenance": {
            "skill": index["name"], "version": index["version"],
            "body_sha256": digest,
        },
    }
```

随后把加载结果的来源写入上下文 manifest。热更新可以让新请求采用新版，同时在途请求保留旧版；安全撤销仍需立即执行。这个问题与工具注册版本相似，但 Skill 内容主要改变模型输入，工具版本还改变实际执行代码，两者不能只用同一个“reload成功”状态概括。

## 宿主字段与权限

某些宿主支持限制用户调用、模型自动调用、选择执行上下文或允许工具等字段。字段含义必须按宿主文档核验：可能是提示范围、预授权策略、工具可见性或运行时限制中的某一种，不应自动推广成标准安全边界。

Claude Code 的 Skills 文档还描述动态内容注入：其中某些命令在模型接收正文前由宿主运行。于是 Skill 不再只是静态 Markdown，它可能接触当前目录、凭据和网络。使用这些能力时，应把展开阶段的命令也纳入授权、日志和 deadline，而不是只记录后续 Agent 工具调用。[[41]](../references.md#source-cc-skills)

这是一个容易被忽视的执行入口。扫描正文里有没有危险工具名，不足以评估安装包是否安全；还需要看被引用的脚本、依赖和自动执行的生命周期。

## Skill 与 Subagent 的组合

Skill 可以在主会话中提供方法，也可以交给独立子 Agent 使用。后一种组合改变的是上下文与执行者，而不是 Skill 本身变成了 Agent。子任务应明确输入证据、允许工具、输出契约和返回方式，不能假设子 Agent 自动继承主会话全部历史。

对只读审查，独立上下文有助于减少主会话干扰；对于紧密耦合编辑，拆成子 Agent 可能造成信息缺失和重复读取。应按任务比较，不以“Skill使用独立Agent”为固定最佳实践。委派机制见 [Subagent](../control/subagents-multi-agent.md)。

## 扩展生态中的分发与可移植性

Pi 将扩展、Skills、提示模板等作为可组合资源，使用户可在不修改循环内部的情况下改变工作流。这提供了一个实用的边界：知识内容与代码扩展可以一起分发，但应分别标识信任和能力。它不是对第三方包安全性的保证。[[42]](../references.md#source-pi-ext-doc)

包应锁定版本、列出依赖、记录校验值，并说明需要哪些宿主特性。升级时检查正文、脚本和 tool schema 的兼容关系。不要只验证能安装、能在列表看到；还要验证自动触发、手动调用、禁用和卸载后的行为。

## Skill 的评测与调优

用任务集同时测正确选择、误触发、步骤遗漏、产物格式、证据引用和累计成本。样例应包含“应当不用这个 Skill”的任务，否则只看正样例会低估误用风险。

正文过长可分层，但不能把关键限制藏在模型不一定读取的附件里。常驻描述要准确，加载后的正文给明确入口，辅助参考按需展开。修改后比较是否减少重复搜索和错误步骤，而不是仅比较 token 数。

还应测试脚本失败、依赖缺失、无网络、只读工作区和用户撤销权限。失败后的行为应明确：返回具体缺失能力、退回人工说明或只提供计划，不应该伪造执行成功。Skill 只是操作方法，最终结果仍由独立验收判断。

## 维护要点

将 Skill 当成可版本化的操作知识，而不是魔法提示。把内容变更与行为测试一起评审，保留已验证模型/宿主组合；对未经测试的兼容宿主只声明格式可读，不声明功能等价。这样既能复用方法，也不会把模型不确定性和插件运行权限混成一层。

## Skill 选择的正负样例

“配置审查”Skill的正样例包括检查覆盖关系、列出未知值和生成可验证修改建议。负样例包括翻译一段普通文本、总结无配置内容的会议记录、用户只询问某个术语。如果负样例频繁触发，先改描述的适用边界，而不是继续扩充正文。

还要测用户明确调用但条件不满足的情况：没有工作区、没有所需工具、资料版本未知。正确行为可能是说明缺少什么，而不是假装有环境继续生成报告。

## 包内脚本的版本和输出

例如Skill引用`inspect_config.py`。脚本版本改变输出字段后，正文仍要求读取旧字段，会引发模型误解或工具报错。把正文、脚本和输出schema作为一个发布单位，测试它们的组合；必要时在正文中写清返回状态含义。

脚本应尽可能输出结构化事实及来源，而不混入大量日志。日志到stderr或独立产物，标准结果用于后续模型。执行脚本前仍需要环境权限，不能让Skill内部的“已允许”文字成为批准凭据。

## 分层加载与长期缓存

静态正文可以按内容hash缓存，但是否允许当前任务使用，还需当前策略。用户撤销某个Skill、插件卸载或项目失去信任后，缓存命中不应继续加载它。正文载入后的模型历史可能还保留旧规则，此时新的任务输入与执行Gate要反映撤销。

“卸载”需要说明清理了什么：发现目录、加载缓存、注册工具、后台进程还是历史消息。历史通常不应被任意篡改，但后续输入投影和权限必须采用新状态。生命周期问题最终归宿主，见扩展专题。
