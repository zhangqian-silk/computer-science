# Agent Skills

一个通用 Agent 面对具体工作时，缺的往往不是能力而是**规程**：这个团队的迁移要拆成哪三步、这类文档的字段单位怎么核对、提交之前必须跑哪个检查。这些知识既不在模型参数里，也不属于任何一次对话——它是「这类任务在这里应该怎么做」。

把它塞进系统提示是最直接的做法，也是行不通的做法。系统提示占的是**每一次调用的固定预算**：十条规程还能忍，一百条就会把窗口吃掉一大半，而其中九十九条与当下这个任务无关。Skill 的全部设计张力都来自这里——**既要让模型知道有哪些规程可用，又不能让所有规程同时在场**。

本文按这条线索推进。先建立**渐进披露**的分级模型，再看**元信息的预算约束**——即「装得多」的真实代价落在哪里；然后是**发现路径与优先级链**，说明同名冲突为什么不能凭直觉迁移。

接着展开骨干问题：**Skill 与 tool、MCP server、slash command、subagent、系统提示、检索各自的分工判据**。之后依次是**打包与分发**、**激活方式**、**上下文生命周期**与**执行与信任边界**，最后落到**正文写法**与**度量方法**。

阅读本文只需要三点背景。

- **上下文是一次生成中模型实际可用的信息**——磁盘上的文件、已安装的技能、外部知识库都只是来源，只有真正进入本次请求的部分才构成本次上下文。
- **模型每次调用都是无状态的**，任何「记住了」都是模型外面那套机制的性质：有人把内容写到了某处，又在恰当时机取回。
- **工具调用是模型提议、程序授权并执行**——模型生成的是调用请求，是否执行由程序决定。

这三点在下文用到时会就地说明，不要求预先了解。

## 一、渐进披露：三级加载与各级的乘数

Skill 的规范形态很朴素：一个目录，里面至少有一个 `SKILL.md`，可选地带上脚本、参考文档与静态资源。[[1]](#ref-1) `SKILL.md` 由 YAML 前置元数据加 Markdown 正文组成，必需字段只有两个——`name` 与 `description`。

真正的机制在于这几部分**不在同一时刻进入上下文**，而各级的乘数完全不同。[[1]](#ref-1)[[2]](#ref-2)

| 层级 | 何时载入 | 乘以什么 | 单项量级 | 内容 |
| --- | --- | --- | --- | --- |
| 元信息 | 启动时 | 已安装技能数 | 每个约 100 token | 前置元数据里的 `name` 与 `description` |
| 正文指令 | 被激活时 | 本次命中数 | 建议低于 5000 token、500 行 | `SKILL.md` 的 Markdown 正文 |
| 附属资源 | 被引用时 | 实际读取的文件数 | 未读取则为零 | 参考文档、模板、schema |
| 包内脚本 | 被执行时 | 执行次数 | 只有输出占用 | 代码本身不进上下文 |

<SkillDisclosureLadder />

元信息是唯一常驻的一层，单项成本比正文小两个量级，却只有它随安装规模增长。于是得到两条方向相反的结论：**多装技能的边际成本很低，写长正文的边际成本很高。**

这也解释了一个常被误读为营销说法的判断——技能可打包的资料量在实践中没有上限。[[3]](#ref-3) 它成立的前提很具体：Agent 拥有文件系统与代码执行能力，因此「一份文件存在」与「一份文件进入上下文」是两件可以分开的事。没有这个前提，三级模型退化成一级，Skill 与「一段长提示词」就没有区别了。

表格最后一行是唯一**跳出了 token 计费**的那一行。脚本被执行而不被阅读，于是它同时解决确定性与成本两个问题：代码的行为不随采样波动，而排序一个列表靠生成 token 远比跑一遍排序算法贵。[[3]](#ref-3) 第九节讨论自由度时会回到这一点。

有一处常见误读需要澄清：渐进披露不等于「已经选中的必要指令只读一半」。正文是整体加载的，规范明确说明模型决定激活之后会载入整个文件。[[1]](#ref-1) 需要拆分的是**可独立使用且很长**的材料，而不是把一段完整的判据切成两半。

一句可以带走的话：**渐进披露省的不是总量，而是把总量从「乘以安装数」改成了「乘以命中数」。**

## 二、元信息的预算约束

上一节说元信息便宜，但便宜不等于免费。它是常驻的，于是必然有一条预算线。

多个公开实现都对这份清单设了上限，并且都不是硬截断而是**分级降级**：先缩短描述，再整条丢弃。

- 一种按模型窗口的 1% 折算清单的字符预算，溢出时从**最少被调用**的技能开始砍描述。[[4]](#ref-4)
- 另一种把上限定为窗口的约 2%，窗口未知时退化为 8000 字符；溢出时同样先缩短描述，技能集特别大时会有条目被整条省略并给出警告。[[5]](#ref-5)

这条降级链带来一类相当隐蔽的故障：**技能确实装着，模型却从不用它。** 因为描述被从尾部截短之后，用于匹配的关键词可能正好落在被砍掉的那一段里——而整个过程没有任何报错，现象与「模型判断力不行」完全一致。

<SkillDescriptionBudget />

这里得到的是一条具体的写法约束，而不是泛泛的「描述要写好」：**关键触发词必须前置**，因为截断是从尾部开始的；官方指引也正是这么表述的——把关键用例与触发词放在前面，这样即使描述被缩短仍然可以匹配上。[[5]](#ref-5)

描述的另一半职责是划边界。规范建议描述同时说明「做什么」与「何时用」，[[1]](#ref-1) 而反面样本恰恰是那些只说了前半句的。

> **反面**：帮助处理 PDF
> **可用**：提取 PDF 的文本与表格、填写表单、合并文档；在处理 PDF 文件或用户提到 PDF、表单、文档提取时使用

前者在预算充足时也没有选择价值，因为它不能把「该用」和「不该用」分开；后者既给出正例，也给出了词面上的触发条件。

还有一条容易被忽略的技术要求：描述应当用**第三人称陈述式**书写。理由是它会被注入系统提示，视角混乱会干扰发现；「我可以帮你处理 Excel」与「处理 Excel 文件并生成报表」在匹配上不是等价的写法。[[6]](#ref-6)

**描述不是介绍，而是路由表的键。** 它唯一的读者是那个要在上百个候选里做选择的模型。

## 三、发现路径与优先级链

技能从哪些位置被发现，以及同名时谁生效——这两个问题的答案在不同宿主之间**并不一致**，而不一致的方向恰好相反。

<SkillDiscoveryChain />

三种公开实现的取法并列如下。

| | 作用域分层 | 同名消解 |
| --- | --- | --- |
| A[[4]](#ref-4) | 企业、个人、项目、内置 | 企业覆盖个人、个人覆盖项目；插件技能走 `插件名:技能名` 命名空间，与任何层级都不冲突 |
| B[[5]](#ref-5) | 从工作目录 `.agents/skills` 逐级上扫到仓库根，再叠加用户目录、`/etc/codex/skills` 与内置 | **不做合并**，两者都出现在选择器里 |
| C[[7]](#ref-7) | 内置、扩展、用户、工作区 | 取优先级更高者；同层级内 `.agents/skills/` 别名目录优先于产品专属目录 |

B 的取法与「后者覆盖前者」是完全不同的语义：它要求使用者自己分辨，而覆盖式由宿主替你决定。

差异之外有两处共识值得记住。

**作用域是一条有序链，不是一组平级目录。** 越靠近具体工作范围的层级，越应当只放该范围专属的内容；把通用技能放进某个模块目录，等于让它在别处失效。

**同名冲突的消解规则必须逐宿主核对。** 「个人覆盖项目」和「项目最具体所以最优先」都是真实存在的设计，凭直觉迁移会得到相反的结论。

## 四、Skill 与相邻机制的分工

这是全文最容易出错、也最值得花篇幅的一节。实践中把 Skill、tool、MCP server、slash command、subagent、系统提示、检索混为一谈的成本不是效率损失，而是**各自的失败形态会安静地出现**。

<SkillBoundaryMatrix />

矩阵里的八个维度可以收敛成三条判据。

**第一条：这是连通性缺口，还是判断力缺口？** 模型此刻根本触达不到那个系统（数据库、工单、第三方接口、浏览器状态），那是连通性问题，要用 tool 或 MCP server 解决——写多少条指令都补不上一个不存在的通道。反过来，模型已经能做这件事、只是做得不合本地标准，那是判断力问题，归 Skill。有一句相当精确的公开表述：MCP 把模型连到数据，Skill 教模型拿这些数据做什么。[[8]](#ref-8)

**第二条：命中率有多高？** 几乎每次都相关的硬约束（安全边界、输出语言、提交前必跑的检查）应当常驻；只在特定话题下相关的长材料应当按需加载。把硬约束交给任何带匹配环节的机制都是**一个安静的错误**：平时都对，只在漏召的那一次出错，而那一次的输出看起来完全合理，只是不符合约定。

**第三条：时机该由谁决定？** 有副作用的动作——部署、发布、对外发消息——时机应当由人决定。有的实现为此提供了两个方向的开关：一个让技能只能由人触发、对模型隐藏（连描述都不进上下文），另一个让技能只能由模型触发、不作为人可用的命令出现。[[4]](#ref-4) 后者的适用场景是纯背景知识：一份解释遗留系统如何运作的技能，模型该在相关时知道它，但「/遗留系统说明」对使用者不是一个有意义的动作。

subagent 与 Skill 的边界另需一句。两者都常被用来「让某类任务做得更好」，但 subagent 提供的是**隔离的执行边界**（独立窗口、更严的工具白名单、可并行），Skill 提供的是**可被任何执行者加载的做法**。

判据很直接：如果多个执行者需要同一套做法，那应当写成 Skill，而不是塞进某一个执行者的系统提示。[[8]](#ref-8) 两者也可以叠加——有实现允许技能声明自己在一个派生的独立上下文里运行，正文成为该上下文的任务描述。[[4]](#ref-4)

至于什么时候**不该**写成 Skill：

- **一次性的临时指示**——「这次简短点」写成技能只会让它一直生效。
- **外部系统访问权**——技能不授予任何执行能力，所需工具必须由环境另行提供。
- **严格确定的执行**——确定性只能由代码提供，该写成脚本或一个真正的工具。
- **对所有人都一样且有权威外部来源的事实**——那是知识库的职责，抽成技能会导致文档更新时技能不跟着更新。

### 一条可执行的归属判断

把三条判据串成顺序，可以得到一个逐问收敛的过程：

```
CLASSIFY-CAPABILITY(need)
	// 第一问：模型此刻能不能触达所需的系统
	if not REACHABLE(need.target) then
		return "tool 或 MCP server"        // 连通性缺口，写指令补不上
	end if

	// 第二问：时机是否必须由人决定
	if HAS-SIDE-EFFECT(need) and TIMING-IS-HUMAN(need) then
		return "命令 + 审批"               // 不希望模型自行决定何时执行
	end if

	// 第三问：命中率
	if HIT-RATE(need) ≈ 1 then
		return "常驻：系统提示或每轮重读的指令文件"
	end if

	// 第四问：内容是否因人 / 因项目而异
	if not VARIES-BY-SUBJECT(need) and HAS-AUTHORITATIVE-SOURCE(need) then
		return "knowledge 检索"            // 对所有人一样的客观事实
	end if

	// 第五问：需要的是隔离的执行还是可复用的做法
	if NEEDS-ISOLATED-EXECUTION(need) then
		return "subagent"
	else
		return "Skill"                     // 一类任务的做法，按需加载
	end if
```

这个顺序不能随意调换。把命中率那一问提前，会把「模型根本访问不到数据库」误判成「该写一份数据库规程」；把隔离那一问提前，会把一套本应可被任何执行者复用的做法绑死在某个 subagent 的系统提示里。**判据的次序反映的是排除的强度：不可达是硬约束，命中率是概率约束，隔离是组织选择。**

一个具体的组合例子：团队要让 Agent 按规范查询数据仓库。数据仓库的连接归 MCP，「查询前必须按日期范围过滤」这条规程归 Skill，「表结构」这类对所有人一样的事实可以放在技能的分域参考文件里按需读取，「不许对生产库跑写操作」这条硬约束归常驻层。四件事落在四个位置，任何一处顶替另一处都会各自失败一次。

## 五、打包与分发：创作原语与分发原语

技能目录本身足够承载单机与单仓库的用法，但一旦要跨仓库复用、要版本化、要连同外部集成一起交付，就需要另一层。有一个把这件事说得很清楚的口径：**技能是可复用工作流的创作格式，插件是可安装的分发单元**；先用技能设计工作流本身，想让别人安装时再打包成插件。[[5]](#ref-5)

两种实现的插件形态对照如下。

| 维度 | 实现 A[[9]](#ref-9) | 实现 B[[10]](#ref-10) |
| --- | --- | --- |
| 清单位置 | `.claude-plugin/plugin.json` | `.codex-plugin/plugin.json` |
| 可打包组件 | 技能、命令、subagent、hooks、MCP 与 LSP 服务器、输出风格、后台监视器、加入 `PATH` 的可执行文件 | 技能、应用集成、MCP 服务器、生命周期 hooks |
| 目录约束 | 只有清单放在清单目录内，其余组件目录必须位于插件根 | 同上 |
| 自带 hooks | 随插件加载 | 属非受管 hooks，审阅并信任前会被跳过 |

两处细节容易踩空。

**组件路径字段的语义并不统一。** `skills` 声明的自定义目录是在默认 `skills/` 之外**追加**，而 `commands`、`agents`、`outputStyles` 等是**替换**默认目录。同一份清单里两种语义并存，凭字段名猜会猜错。[[9]](#ref-9)

**路径必须走变量，不能硬编码。** 三个变量各有分工：`${CLAUDE_PLUGIN_ROOT}` 指向插件安装目录，`${CLAUDE_PLUGIN_DATA}` 指向能跨插件更新存活的可写目录（依赖、生成物与缓存），`${CLAUDE_PROJECT_DIR}` 指向项目根。[[9]](#ref-9) 安装位置本身不确定，写死绝对路径的插件在别人机器上必然失效。

实现 B 还有一个值得记下的兼容动作：它为插件 hooks **同时设置两套环境变量名**，既有自己的 `PLUGIN_ROOT` / `PLUGIN_DATA`，也设置了实现 A 的同义变量。[[10]](#ref-10)

技能声明外部依赖也有对应形态。一份可选的 `agents/openai.yaml` 可以配置展示元信息、调用策略与工具依赖，依赖项可直接声明一个 MCP 服务器（类型、地址、传输方式）。[[5]](#ref-5) 其中 `policy.allow_implicit_invocation` 置为 `false` 时，模型不再隐式选用该技能，显式点名仍然有效——这与上一节的「只允许人触发」是同一类控制，落在了不同的配置位置。

**创作与分发是两个阶段，混在一起会同时失去两者的好处**：不打包则无法版本化与跨仓复用，过早打包则每次改动都要走一遍分发流程。

## 六、激活方式

技能被激活有两条路径，它们的可靠性来源完全不同。

**显式点名**由使用者发起——不同实现的形态是 `$技能名`、`/技能名` 或 `/skill:技能名`。[[5]](#ref-5)[[4]](#ref-4)[[11]](#ref-11) 它的价值是时机完全确定：不依赖描述匹配，也不依赖模型此刻是否想起来。

**隐式匹配**由模型按 `description` 判断。它的可靠性受两层因素影响：描述本身写得准不准（第二节），以及模型是否真的会去读那个文件。第二层不是理论担忧——有实现在文档里明确写了「模型并不总是这么做，可以用提示或显式命令强制它读」。[[11]](#ref-11)

这条差异有一个直接的工程推论：**对正确性关键的规程不要只依赖隐式匹配。** 三种加固手段分别落在不同层次——把约束提到常驻层（系统提示或每轮重读的指令文件）、把触发改成显式命令、或者用 hooks 之类的确定性机制强制行为。有实现对「技能似乎第一次回应之后就不再影响行为」这个现象给了同样方向的建议：内容通常还在上下文里，模型只是选择了别的路径；对策是加强描述与指令，或者用 hooks 确定性地强制。[[4]](#ref-4)

激活过程还可以带上一道人工确认。一种实现在模型调用激活工具后会弹出确认，展示技能名称、用途与它将获得读取权限的目录路径；确认之后正文与目录结构进入历史，**同时该目录被加入可读路径白名单**。[[7]](#ref-7) 这个设计把「加载知识」与「授予读取范围」两件事显式绑在了同一次确认上，比隐含地扩大可读范围要诚实。

**显式点名换取的是时机的确定性，隐式匹配换取的是使用上的省心。** 关键规程要前者，日常规程要后者，两者不是同一个可靠性等级。

## 七、上下文生命周期

技能正文进入上下文之后并不是就此结束，它还要经历若干次轮转，而这几处行为差异会直接影响写法。

**正文一旦读入即留在历史里。** 有实现明确说明，渲染后的 `SKILL.md` 内容作为一条消息进入对话并在后续轮次中保留，而宿主**不会**在后续轮次重读该文件。[[4]](#ref-4) 推论是写法上的：应当长期生效的内容要写成**常设指令**，而不是「一次性步骤」——因为它此后不会被再读一遍，措辞上的时态差别会被模型当真。

**重复调用不必然重复注入。** 同一实现的做法是：若渲染后的内容与已在上下文中的副本完全相同，只追加一条「该技能已加载」的短提示；若内容不同（参数变了，或某个动态注入的命令产生了新输出），则再次追加完整内容。[[4]](#ref-4) 这条规则解释了一个容易被误判为 bug 的现象：带参数调用同一个技能，上下文会实打实地涨两份。

**压缩会重新注入，但受上限约束。** 同一实现给出的口径相当具体：自动压缩把已调用的技能带过摘要，做法是在摘要之后重新附上每个技能**最近一次**调用的内容，每项保留前 5000 token，重新附上的技能共享 25000 token 的合计预算，且从最近调用的技能开始填——因此一次会话里调用过很多技能时，较早的那些在压缩后可能被整条丢弃。[[4]](#ref-4)

这三个细节合起来给出一条排版纪律：**截断保留开头**，意味着最重要的约束应当写在正文前部，而不是压在文末的「注意事项」里；正文越长，压缩后越可能只剩一个残缺的开头。这为「正文控制在 5000 token 内」提供了第二个理由——前一个是省预算，这一个是**保真**。

**权限不随内容一起存续。** 同一实现指出，预授权工具的授予会在使用者发下一条消息时清除，而指令内容仍在。[[4]](#ref-4) 于是会出现一个反直觉但合理的状态：技能还在指导行为，它当初带来的免审批额度已经没了。

**内容会留下，权限不会；开头会保住，结尾会被截。** 这两句决定了正文的排版顺序。

## 八、执行与信任边界

技能是**可读的文本加可执行的代码**，这两件事都在扩大攻击面，而它没有任何天然的可信性。

风险的形态在官方文档里说得很直接：恶意技能可以指示模型以不符合其声明用途的方式调用工具或执行代码，可能导致数据外泄与越权访问。从外部 URL 取内容的技能尤为突出，因为取回的内容可能带有指令；即使原本可信的技能，也可能因外部依赖随时间变化而被污染。[[2]](#ref-2)[[3]](#ref-3)

对应的建议同样明确：只用可信来源的技能。不得不用来源不明的技能时，先逐个读完包内的文件——`SKILL.md`、脚本、图片与其他资源，重点看依赖与那些与声明用途不符的操作。[[2]](#ref-2)

有三条判断值得从中提炼出来。

**其一，「文档说要验证」不等于验证已经发生。** 包内脚本被运行时，它就是一次真实的工具执行，需要参数校验、权限判断与结果检查；脚本报告成功也仍要核对它对应的是本次输入与本次产物。把技能正文里的一句「运行验证脚本」当成验证已完成，是一类典型的记账错误。

**其二，包内引用不构成越界读取的理由。** 技能可以引用文件，但引用本身不扩大它的授权范围。前面提到的那种「激活时展示将获得读取权限的目录并要求确认」的设计[[7]](#ref-7)，正是在把这条边界做成显式的一步。

**其三，指令性文字的来源决定它的身份。** 工具返回内容、外部网页、被读取的参考文件里出现的「忽略之前的指令」保持数据身份，不获得指令优先级——这条规则对技能内容同样适用，尤其是那些从网络取回的部分。

运行环境的约束也影响可行性判断，而它随宿主而异：有的宿主里技能运行在沙箱容器中，**无网络访问、不能在运行时安装依赖**，只能用预装包；有的宿主里技能与用户机器上的其他程序享有同等网络访问，但被建议只在本地安装依赖以免影响用户环境。[[2]](#ref-2) 一个在前者能跑的技能，写法上必须先声明它需要哪些包并确认这些包已预装。

同一份技能在不同宿主之间也不自动同步。有实现明确说明自定义技能**不跨界面同步**：上传到网页端的不会出现在接口侧，接口侧上传的不会出现在网页端，命令行侧是基于文件系统的、与两者都分离；共享范围也不同——网页端是每个用户各自上传，接口侧是工作区共享。[[2]](#ref-2) 「装过一次就到处都有」是个需要逐宿主核对的假设。

**技能是知识包，不是许可证。** 它给出方法，能力与授权始终来自执行环境。

## 九、正文的组织与写法

一份可用的 `SKILL.md` 覆盖这些内容：**适用与不适用的任务范围**（对应描述里的边界，正文里再展开）、**输入与前置条件**、**核心步骤**、**结果要求**、**检查项**、以及**对附属资料的索引**。规范的建议是把详细的参考材料移到单独文件，正文只留导航；文件引用保持在一层深度，避免深层嵌套的引用链。[[1]](#ref-1)

以一个「配置说明审阅」的技能为例，各段落承担的职责可以对照如下：

| 段落 | 承担什么 | 写不好的表现 |
| --- | --- | --- |
| 适用范围 | 与描述里的边界对应，正文展开正例与反例 | 写成「适用于所有文档工作」，选择时不起作用 |
| 输入与前置 | 需要哪些材料、哪些工具必须可用 | 假设某个包已装、某个工具已授权 |
| 核心步骤 | 按顺序的必要动作，自由度与脆弱性匹配 | 把必要动作与可选扩展混在一起 |
| 结果要求 | 交付物形态、必须给出的结论与未知项 | 只写过程，不写「做完是什么样」 |
| 检查项 | 完成前须自证的条目 | 写成「注意质量」这类不可验证的话 |
| 资料索引 | 每个附属文件里有什么、何时该读 | 只列文件名，模型无从判断该不该读 |

拆分的判据不是长度而是**互斥性**。官方指引给出的说法是：当某些上下文互斥或很少同时用到时，把路径分开可以减少 token 消耗。[[6]](#ref-6) 一个技能同时服务财务、销售、产品三类查询时，正确的组织是三份分域参考文件加一份索引，而不是一份把三类 schema 都写进去的长正文——因为问财务指标的那次任务读到销售 schema 是纯浪费。

还有一条维度值得单独展开：**自由度应当匹配任务的脆弱性**。[[6]](#ref-6) 官方指引配了个好记的类比——悬崖之间的窄桥只有一条安全路径，要给精确的护栏；空旷的原野有很多条路，给个大方向就好。

| 自由度 | 适用条件 | 写法 | 确定性来自 |
| --- | --- | --- | --- |
| 高 | 多条路径成立，决策依赖上下文 | 文字步骤与启发式 | 模型判断 |
| 中 | 存在偏好模式，允许一定变化 | 伪代码或带参数的脚本 | 模式约束 |
| 低 | 操作脆弱易错，顺序不可变 | 写死的脚本，禁止改参数 | 代码 |

这张表与第一节「脚本被执行而不被阅读」是同一件事的两面：**需要确定性时不要试图把指令写得更严，而应当把这一步交给代码。** 一次数据库迁移的三个步骤，写成三条祈使句和写成一个不接受额外参数的脚本，可靠性不在同一个量级。

还有两条容易被写反的地方。

**执行意图必须写清楚。** 「运行 `analyze_form.py` 提取字段」与「`analyze_form.py` 里是提取算法，可作参考阅读」是两种完全不同的指示，而对同一个文件都成立。[[6]](#ref-6) 不写清楚，模型可能把一个本该执行的脚本整篇读进上下文——既花了 token 又没得到确定性。

**不要假设依赖已安装。** 需要哪个包就明确写出安装命令与用法，而不是「用那个 PDF 库处理一下」。[[6]](#ref-6) 这条在无网络的沙箱环境里会直接决定技能能不能跑。

多个技能同时适用时还有一层协调问题：步骤是否重复、输出要求是否冲突、工具使用范围是否一致。这些冲突不能靠「最后加载的文件自动覆盖」来消解——加载顺序不是一个可靠的语义。

**正文的读者是一个已经很聪明、但不了解本地约定的执行者。** 只写它不知道的部分，别解释它已经会的东西。

## 十、几种实现的横向对照

分歧点标出了哪些参数是可调的，共识点标出了哪些结论是稳定的。

| 维度 | 常见做法 | 分歧所在 |
| --- | --- | --- |
| 必需字段 | `name` 与 `description` | 一致。可选字段各家有扩展 |
| 名称与目录名 | 规范要求 `name` 与父目录同名 | 有实现刻意放宽，理由是共享目录被多个宿主使用时该约束不合适 |
| 元信息预算 | 按窗口比例折算，溢出时先缩描述 | 比例取值与降级顺序不同 |
| 发现路径 | 项目 / 用户 / 机器 / 内置多级 | 目录名不同，且**消解方向相反**：有的组织优先，有的就近优先，有的不合并 |
| 调用方式 | 显式点名 + 隐式匹配 | 命令前缀不同（`$` / `/` / `/skill:`） |
| 调用控制 | 可禁用隐式匹配、可禁用人工触发 | 落在前置元数据、独立配置文件或宿主设置里 |
| 激活确认 | 部分实现要求人工确认并展示可读路径 | 是否需要确认、是否同时扩展读取权限 |
| 分发单元 | 插件：清单 + 组件目录 | 可打包的组件类型数量差异很大 |
| 压缩后行为 | 已调用技能重新注入 | 是否有上限、截断保留哪一端 |
| 校验严格度 | 违反命名规则时告警 | 是拒绝加载还是告警后仍加载 |

几个具体细节值得记住，因为它们各自代表一类思路。

**规范的严格程度可以被有意放宽。** 规范要求 `name` 与父目录名一致，而有实现明确不强制这一条，理由写得很清楚：这条规则对被多个 Agent 宿主共用的共享技能目录不合适。[[11]](#ref-11) 这不是实现偷懒，而是一个跨宿主共用场景暴露出的规范缺陷。

**命名冲突可以选择不解决。** 「同名不合并、两者都出现在选择器里」[[5]](#ref-5) 与「优先级高者胜出」[[4]](#ref-4)[[7]](#ref-7) 是两种取向：前者把判断权还给使用者，后者替使用者决定。也有实现取第三种——告警并保留最先发现的那一个。[[11]](#ref-11)

**跨宿主复用可以靠配置而不是复制。** 有实现允许在设置里直接把其他宿主的技能目录加进自己的搜索路径。[[11]](#ref-11) 这比复制文件更可维护，代价是要接受那些目录里可能存在自己不认识的前置字段——而它的处理是忽略未知字段。

**兼容性会体现在最不显眼的地方。** 一个实现为插件 hooks 同时设置了自己的和另一个实现的环境变量名。[[10]](#ref-10) 这类细节比任何声明都更能说明格式已经在事实上趋同。

**格式在收敛，宿主行为没有收敛。** 一份 `SKILL.md` 基本可以跨宿主使用，但它的发现顺序、冲突消解、压缩后行为与权限语义都得逐个核对。

## 十一、度量与故障定位

技能的效果必须被度量，而度量要**分开评价选择与执行**——这两者的故障形态完全不同。

**选择的度量**：正例任务是否被选中，邻近但不适用的任务是否被正确排除。第二项常被漏掉，而它才是描述边界写得准不准的检验。

**执行的度量**：选中之后是否完成了必要的读取与检查，输出是否满足任务标准——而不是机械复述了步骤。这里有一条容易被忽略的观察点：模型是否跟随了正文里的文件引用。引用没被跟随时，往往是链接写得不够显眼或不够明确，而不是模型不愿意读。[[6]](#ref-6)

**评测应当先于文档。** 官方指引的次序是：先在代表性任务上跑一遍，观察 Agent 在哪里卡住或需要额外交代，据此建立三个测试场景，再增量地写技能。[[6]](#ref-6) 反过来做——先写一份详尽的文档再找场景验证——很容易在解决想象出来的问题。

**跨模型测试是必要的。** 技能是对模型的补充，效果依赖底层模型：对推理更强的模型有效的简洁写法，可能对更小更快的模型信息量不足；反之，为小模型写得很详尽的技能，在强模型上属于过度解释。[[6]](#ref-6) 所以「计划用哪些模型，就在哪些模型上测」。

还有一组指标值得单列，因为它们指向不同的问题：**与不用技能的同一任务相比**，质量、输出长度与调用成本各自如何变化；命中之后是否发生了**不必要的整篇读取**（该执行的脚本被读成了参考）；以及压缩之后技能是否仍在起作用（第七节的上限约束会让较早调用的技能被丢弃）。

**版本更新要同时检查描述与正文。** 描述还在宣传旧能力、正文已经改成新流程，会造成一种特别难查的故障——**选择正确而执行错误**。它的现象是「技能确实被用了，但做出来的事不是我要的」，排查方向既不在匹配也不在模型，而在这两份内容的不一致上。

按现象定位故障，可以整理成一张对照：

| 现象 | 首查位置 | 不该先改什么 |
| --- | --- | --- |
| 装了却从不触发 | 描述是否完整进入清单（元信息预算） | 不要先重写正文——正文压根没被读到 |
| 邻近任务被误触发 | 描述有没有写出不适用的边界 | 不要先降低技能数量 |
| 命中了但没跟随文件引用 | 引用链接是否够醒目、是否说明了何时该读 | 不要先把附件内容并回正文 |
| 该执行的脚本被整篇读入 | 正文是否写清了执行意图 | 不要先缩短脚本 |
| 第一次之后似乎不再生效 | 内容通常仍在上下文，模型选了别的路径 | 不要先重复调用；先加强指令或改用确定性机制 |
| 压缩之后行为回退 | 重新注入是否受合计上限影响、正文是否只剩开头 | 不要先怀疑摘要质量 |
| 被用了但做的事不对 | 描述与正文是否已经不一致 | 不要先调匹配策略 |

这张表的共同结构值得注意：**七类现象里有四类的第一排查位置都不在模型判断力上，而在预算、引用与措辞这些工程细节上。** 先看这一层，再谈提示词。技能的故障形态是重复出现的，把每次修好的故障沉淀成测试场景，比逐个排查更划算。

## 十二、小结

关于 Skill，可以收敛成四句话。

**渐进披露改变的是乘数，不是总量。** 元信息乘已安装数、正文乘命中数、附件乘实际读取数。这既是「多装技能便宜、写长正文贵」的来源，也是「可打包内容没有实际上限」成立的条件——前提是有文件系统与代码执行。

**元信息虽便宜但有预算，且降级是静默的。** 清单溢出时先缩描述再丢条目，被缩掉的尾部可能正好带走匹配所需的关键词。于是「装了却从不触发」的第一排查方向不是模型判断力，而是描述有没有完整进入清单。

**分工判据只有三条：缺通道、缺判断，还是缺时机。** 缺通道归 tool 与 MCP，缺判断归 Skill，缺时机归命令与审批。把这三条弄反的代价不是效率，而是各自的失败形态会安静地出现——尤其是把硬约束交给带匹配环节的机制，它平时都对，只在漏召的那一次出错。

**技能是知识包，不是许可证。** 它给出方法，能力与授权始终来自执行环境；「文档说要验证」不等于验证已经发生，包内引用也不扩大授权范围。

最后一点不属于机制而属于判断：**格式已经在跨宿主收敛，宿主行为并没有。** 发现顺序、同名消解、压缩后的注入上限、激活是否需要确认、权限语义如何存续——这些都是逐产品的行为契约。把某一家的默认值当成通则，是这个主题上最常见的错误来源。
