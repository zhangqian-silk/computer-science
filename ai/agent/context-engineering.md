# Agent 上下文工程

上下文工程负责在每次模型调用前构造当轮输入，并在调用结束后决定哪些新信息进入下一轮。核心问题是：**窗口里有哪些内容、按什么关系排列、如何随任务进展更新，以及信息变多时怎样保持必要内容可见**。窗口容量只是硬上限；无关、过期或相互矛盾的内容即使尚未装满窗口，也会影响判断。

---

## 窗口内容

一次调用的 Context 是实际提供给模型的消息和其他模型可见输入。窗口按本轮任务装配：稳定指令、当前目标、任务状态、相关资料、会话历史和工具结果各占一部分，未被选中的材料不会因存放在会话或资料库里而自动可见。

按内容的变化方式，窗口可分为三组。下表列出的是候选模块，不要求每轮全部常驻。

| 变化方式 | 典型模块 | 装配重点 |
| --- | --- | --- |
| 相对稳定 | 高优先级指令、工具名称与描述、必要的 Skill 发现信息、少量示例 | 维持明确边界，避免冗余和相似能力互相干扰 |
| 按轮选择 | 当前用户目标、任务状态、相关 Knowledge、召回的 Memory、阶段性说明 | 核对权限、来源、时间与当前决策的相关性 |
| 随行动累积 | 用户与助手消息、工具调用及结果、错误、验证记录 | 保留因果关系，清理过长或已失效的旧内容 |

工具定义可能通过 API 的独立字段提供；采用按需加载 Skill 的系统，也可能在不同轮次提供描述或完整正文。因此要记录每轮模型实际可见的内容，而不能只查看消息正文。

---

## 装配约束

每个候选内容单元在进入窗口前，需要能够回答“它是什么、谁可以看、现在还有效吗、移走后能找回吗”。这比将所有资料直接拼成字符串更易于过滤和更新。

| 信息 | 判定用途 |
| --- | --- |
| 来源与定位 | 区分用户陈述、工具观察、模型推断和文档片段；必要时回到原文 |
| 权限与主体 | 确定当前任务是否有权读取，阻止跨用户或跨租户混入 |
| 时间与版本 | 判断旧观察是否被新状态覆盖，引用是否仍对应当前资料 |
| 类型与信任 | 标明指令、待处理数据、未核实推断或已验证事实 |
| 生命周期与恢复入口 | 决定常驻、阶段性保留、仅本轮使用或退出后按句柄重取 |
| 大小与依赖 | 估算 token 成本，并识别不能拆散的调用—结果—结论链 |

权限、主体和有效期是**先于相关性排序的硬过滤**：语义上很相似的越权文档不应进入候选集。过滤后的内容再按当前目标、任务阶段、时效和信息增益选择。未核实的推断与有来源支持的事实分别标记，以免下一轮把猜测当作新证据。

来自网页、代码注释和工具结果的命令式文字按资料内容标记，并保留来源区，以免与当前任务要求混在一起。

---

## 内容排列与预算

排列要同时保持规则可辨认、动态信息靠近其用途，并尽量减少每轮不必要的重排。一种可维护的**逻辑视图**如下：

```text
相对稳定：系统／应用指令、工具契约、必要示例与能力发现信息
本轮任务：用户目标、验收条件、当前阶段与剩余工作
本轮依据：带来源、版本与时间的相关知识、记忆和工具观察
近期轨迹：必要的用户消息、工具调用—结果及验证记录
当前事件：最新用户修正、刚返回的工具结果或待处理问题
```

这是逻辑视图，不是所有 API 的固定物理顺序。稳定前缀有利于某些提供方的缓存；近期目标与观察放在易辨认的位置，有助于减少旧状态干扰。两者的排列效果应在目标模型与任务数据上比较，而不是断言首尾位置必然最优。

有三组关系不能随意打散：当前指令与其适用范围，证据与来源标签，工具调用与对应结果。对不同版本的事实要显式标注替代关系；不应把旧结论、新观察并列后让模型猜测哪个仍有效。

预算不仅是“当前请求能否装下”。需要同时为模型输出、可能的工具调用与回填、失败恢复和下一轮输入留空间。超过硬上限会使调用无法继续；未达上限时，重复示例、无关历史与大段工具输出仍可能挤掉关键证据。先减少无关内容，再决定是否摘要；前缀缓存可能降低重复输入的成本，但不会扩大窗口，也不能弥补遗漏。

## 逐轮更新

每轮更新可写成一条固定的装配链：

```text
任务与事件记录
  → 获取候选（稳定指令、状态、相关资料、最近观察）
  → 权限／主体／版本过滤
  → 按当前决策选择并确定表示
  → 排列与预算装配
  → 模型调用与工具观察
  → 校验事实、更新任务状态和事件记录
  → 下一轮重新装配
```

新消息通常追加到事件记录，但**下一轮窗口不等于上一轮窗口加上新消息**。稳定规则可以保持；用户修正会更新当前目标；新的工具结果可替换旧观察；阶段结束后，细节可退出活动窗口而保留恢复入口。调用结果应先经过应用侧核对，再更新“已完成”“已验证”等状态。

下面以修复接口测试为例。用户目标是“使订单接口测试通过，并说明改动依据”；日志及代码文件保存在窗口外，窗口只放当前步骤必需的片段。

| 时刻 | 窗口保留或加入 | 更新与退出 |
| --- | --- | --- |
| 初始调用 | 稳定规则、用户目标、测试失败摘要、相关代码片段、当前状态“待定位” | 不注入整仓代码与无关旧测试日志 |
| 定位后下一轮 | 新的堆栈片段、对应源码位置、工具调用与结果、状态“超时分支待修改” | 旧测试输出保留文件句柄；模型的原因猜测标为待验证 |
| 修改并复测后 | 改动摘要、复测命令及真实结果、仍失败的用例或验收结果 | 若测试通过，将已验证结果更新到状态；旧猜测若被证伪，显式作废 |

任务状态应从事件和校验结果计算，不由模型在长对话里自行计数。发生用户修正时保留新目标及其生效范围，避免旧任务表述与新任务表述并列竞争。真实失败记录可以从活动窗口退出，但不能把“确实执行失败”与“关于失败原因的错误猜测”一同当成噪声抹掉。

## 工作集增长治理

信息总量可以大于窗口，窗口只维持当前决策所需的工作集。先处理候选质量，再处理大小：

| 操作 | 作用于窗口的变化 | 主要代价与检查 |
| --- | --- | --- |
| 选择 | 不相关知识、记忆或工具定义不进入本轮 | 漏选会使模型缺少依据 |
| 结构化 | 将目标、状态、来源和替代关系标清 | 元数据会占用少量空间 |
| 外置 | 长日志、文档或中间产物留在外部，窗口内保留可读句柄 | 重新读取有延迟，句柄必须可恢复且有权限 |
| 压缩 | 将已稳定阶段的旧轨迹变为较短摘要 | 可能丢失后续才需要的细节 |
| 隔离 | 不同分支使用各自的工作集，只回传必要结果 | 交接成本与重复输入增加 |

外部资料只在当前决策需要时选入：需要文档依据时取相关片段，需要主体偏好时取有效条目。会话内笔记或摘要则按当前目标保留关键进度，不必每轮重放完整历史。

压缩优先从源头字段裁剪、清理可恢复的大结果与旧工具输出开始；只有仍不足时才摘要已结束阶段。摘要至少保留当前目标、已验证事实、未解决问题、关键决策、失败证据和恢复入口。若之后要逐字引用原资料，应能够凭来源或句柄重新读取。隔离适用于多个分支确实不共享工作细节的场景，不因为“可以用多个 Agent”就默认拆分。

---

## 失效与验证

窗口质量可以沿“遗漏、污染、干扰、冲突”诊断，而不是等到 token 达上限才处理。

| 症状 | 可能机制 | 首要检查 |
| --- | --- | --- |
| 反复询问已提供的信息 | 关键约束或证据未入选，或压缩时丢失 | 实际请求载荷、筛选与摘要记录 |
| 错误结论被持续引用 | 未验证推断写成了当前状态 | 来源标注、验证状态与撤销记录 |
| 错选工具、复述无关历史 | 相似定义或旧轨迹占据工作集 | 工具候选、各模块占比与相关性 |
| 使用过期事实 | 新旧版本同时可见且缺少替代关系 | 版本、时间与权威来源 |
| 资料中的命令改变了当前任务 | 数据与本轮要求混在一起 | 数据分区、来源标记与窗口实际内容 |

有效评测以**每轮真实输入**为最小观测对象：记录候选与入选内容、过滤原因、来源版本、排列、各模块 token 占比、压缩前后恢复入口，以及后续决策和任务验收。对同一批任务分别做删除某来源、加入旧版本、调整证据位置、放入相似工具和压缩后恢复等扰动，观察完成率、错误率、成本与延迟。只减少 token、却使关键事实更容易遗漏，不算改进。
