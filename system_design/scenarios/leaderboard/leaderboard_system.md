# 排行榜系统

> **摘要**：排行榜要在**高频分数更新**下支持**实时 TopN**、**查我的名次/邻居**，还要防刷分、支持多维度与赛季。核心数据结构是有序集合（ZSet），核心难点是海量榜单的分片、热点写入与实时/结算口径分离。本文按「需求 → ZSet 模型 → 写热点治理 → 海量榜单分片 → 实时榜 vs 结算榜 → 防刷 → 关键设计要点」推进。

> **关联**：读放大靠[缓存](../../components/cache_component/cache_component.md)；写幂等靠[幂等](../../base/idempotence.md)；分片思想见[一致性哈希](../../components/consistent_hash/consistent_hash.md)。

---

## 一、需求与核心操作

- **更新分数**：某用户加分/设分（高频写）。
- **TopN**：取前 N 名（高频读）。
- **查名次**：某用户当前排名（高频读）。
- **查邻居**：我前后各几名（社交激励）。

## 二、ZSet 数据模型

Redis ZSet（跳表 + 哈希）是天然的排行榜结构：

| 操作 | 命令 | 复杂度 |
| :--- | :--- | :--- |
| 更新分数 | `ZADD` / `ZINCRBY` | $O(\log N)$ |
| TopN | `ZREVRANGE 0 N-1` | $O(\log N + M)$ |
| 查名次 | `ZREVRANK` | $O(\log N)$ |
| 查邻居 | `ZREVRANK` + `ZREVRANGE` | $O(\log N + M)$ |

分数相同要稳定排序时，可把「分数 + 时间戳」编码进一个 score（高位分数、低位反向时间），保证「同分先到者靠前」。

---

## 三、写热点治理

超热门榜单（如全站总榜）单 key 写入会成为热点：

- **写合并/批量**：高频加分先在本地/Redis 累积，定时批量刷入榜单，降低写频。
- **分片聚合**：把总榜拆成多个分片 ZSet 分散写入，查询时合并 TopN（各分片取 TopN 再归并）。
- **冷热分层**：只有 TopK 是热点，长尾名次可降级到离线计算。

---

## 四、海量榜单分片

当用户量极大（亿级），单个 ZSet 装不下或太慢：

- **按维度分榜**：地区榜、好友榜、赛季榜各自独立，缩小单榜规模。
- **分段/分桶**：按分数区间分段，跨段查询归并。
- **精确 TopN + 近似名次**：TopN 要精确，但「你超过了 87% 的人」这类可用近似（分数直方图/概率结构）降成本。

---

## 五、实时榜 vs 结算榜

**口径分离**是排行榜的关键设计：

- **实时榜**：低延迟、允许短暂不精确，用 ZSet 直接更新。
- **结算榜（赛季/发奖）**：以离线批计算为准，要求准确、可审计、可复算，作为发奖依据。
- 两者分开，避免「实时榜的近似/抖动」影响真金白银的发奖。

---

## 六、防刷与安全

- **写入幂等去重**：同一分数事件（`事件ID`）只计一次，防重复上报刷分（见[幂等](../../base/idempotence.md)）。
- **异常检测**：分数增速异常、行为特征识别刷分，异常分数可回滚。
- **封榜与审计**：赛季结束封榜，结算前审计，保留分数变更流水可追溯。

---

## 七、指标体系

- 更新延迟、TopN/名次查询 P99；
- 榜单准确率（实时榜与结算榜偏差）；
- 热点 key QPS、刷分拦截率。

---

## 八、关键设计要点

- **数据结构**：Redis ZSet，更新/TopN/名次/邻居都是 $O(\log N)$。
- **同分排序**：分数 + 反向时间戳编码进 score，先到者靠前。
- **热点榜写入**：写合并批量 + 分片聚合 + 冷热分层。
- **亿级用户**：按维度分榜 + 分段，精确 TopN + 近似名次。
- **发奖口径**：实时榜允许近似/抖动，发奖用可复算的离线结算榜。
- **防刷分**：写入幂等去重 + 异常检测 + 可回滚 + 审计。
