# 分布式锁（Distributed Lock）

> **摘要**：单机用互斥量/`synchronized` 就能保证临界区互斥，但多实例部署后进程内锁失效——需要一把所有实例都认的「分布式锁」。它看似简单（`SET key val NX EX`），坑却很深：**锁提前过期、误删他人锁、主从切换丢锁**。本文按「为什么需要 → 三种实现 → Redis 锁的三个必答坑 → 看门狗 → Redlock 争议 → 选型 → 面试问答」推进。

> **关联**：解锁的原子性与唯一性呼应[幂等机制](../../base/idempotence.md)；锁只是互斥手段，不能替代[分布式事务](../../base/distributed_transaction.md)的补偿。

---

## 一、为什么需要分布式锁

多个实例可能同时操作同一共享资源（扣库存、生成唯一编号、防重复下单、定时任务防并发触发）。进程内锁只在单进程有效，跨实例必须借助一个**外部共享存储**来仲裁「同一时刻只有一个持有者」。

锁的基本语义要求：

- **互斥**：任意时刻至多一个客户端持有。
- **不死锁**：持有者宕机后锁能自动释放（靠 TTL）。
- **只能自己解自己的锁**：避免误删他人锁。
- （可选）**可重入、阻塞/非阻塞、公平性**。

## 二、三种实现对比

| 实现 | 原理 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 数据库 | 唯一键插入 / `SELECT ... FOR UPDATE` | 简单、强一致 | 性能低、连接压力大、需处理死锁 |
| Redis | `SET key token NX EX ttl` | 高性能、常用 | 需处理过期/误删/主从丢锁 |
| ZooKeeper / etcd | 临时顺序节点 + watch | 天然容错、公平、会话失联自动释放 | 运维复杂、吞吐低于 Redis |

主流是 **Redis**（性能优先）与 **ZooKeeper/etcd**（一致性/可靠性优先）。

## 三、Redis 锁的三个必答坑

### 3.1 加锁必须原子

必须用单条命令 `SET key <token> NX EX <ttl>` 同时完成「不存在才设置」+「设置过期时间」。分成 `SETNX` + `EXPIRE` 两步，会在两步之间宕机导致锁永不过期（死锁）。

### 3.2 解锁必须校验 token 且原子

锁的 value 要写入**客户端唯一 token**（如 UUID）。解锁时先比对 token 再删除，且这两步必须原子（用 Lua 脚本），否则会误删他人的锁：

> 典型误删：A 的锁已过期被 B 获取，A 业务结束直接 `DEL`，删掉的其实是 B 的锁。

```lua
-- 解锁：仅当 value 等于自己的 token 才删除
if redis.call("GET", KEYS[1]) == ARGV[1] then
	return redis.call("DEL", KEYS[1])
else
	return 0
end
```

### 3.3 锁过期早于业务完成

TTL 设短了，业务还没跑完锁就过期，别的客户端拿到锁 → **并发进入临界区，互斥被破坏**。TTL 设长了，持有者宕机后锁又长期不释放。这个两难由**看门狗**解决。

## 四、看门狗（自动续约）

思路：加锁时给一个较短 TTL，同时启动后台线程每隔 `TTL/3` 检查业务是否还在执行，是则续期（重置 TTL）。业务结束或进程崩溃则停止续约，锁自然过期。这样**锁始终覆盖业务全程，又不会在宕机后长期滞留**。Redisson 的 watchdog 就是这一机制。

```mermaid
flowchart LR
	L[加锁 TTL=10s] --> W{业务进行中?}
	W -->|是, 每 TTL/3| R[续约重置 10s] --> W
	W -->|完成/崩溃| E[停止续约 → 锁到期释放]
```

## 五、Redlock 与主从丢锁争议

单 Redis 主节点存在一个可靠性缺口：主节点写入锁后**尚未同步到从节点就宕机**，从节点被提升为主，新主上没有这把锁，导致两个客户端同时持锁。

- **Redlock**：向 $N$ 个独立 Redis 节点依次加锁，多数（$N/2+1$）成功且在有效期内才算持锁。提升了容错，但 Martin Kleppmann 与 antirez 有著名争论——Redlock 对时钟假设敏感，不能提供严格正确性。
- **结论**：需要**严格互斥正确性**（如涉及资金、绝不允许双写）时，用 ZooKeeper/etcd 这类基于共识的方案，或在业务层叠加**唯一约束/fencing token**（带单调递增版本号，下游拒绝旧版本）兜底；Redis 锁适合「绝大多数场景够用、偶发并发可由业务幂等兜底」。

## 六、选型

| 诉求 | 选择 |
| :--- | :--- |
| 高性能、可容忍极小概率并发（业务有幂等兜底） | Redis + 看门狗 + token |
| 严格互斥、公平、可靠 | ZooKeeper/etcd 临时顺序节点 |
| 简单低频、已有 DB | 数据库唯一键 |
| 绝对正确性 | 共识存储 + fencing token |

## 七、面试高频问答

- **加锁为什么要一条命令？** `SETNX`+`EXPIRE` 分两步会在中间宕机造成死锁；用 `SET NX EX` 原子完成。
- **为什么解锁要 Lua + token？** 防止误删他人锁，且判断与删除必须原子。
- **锁过期但业务没完成怎么办？** 看门狗自动续约，业务结束或崩溃才停止。
- **Redis 主从切换会丢锁吗？** 会，未同步即主挂会双持；用 Redlock 缓解，严格场景改用 ZK/etcd 或 fencing token。
- **Redlock 一定安全吗？** 有争议，对时钟敏感，不保证严格正确性。
- **锁能替代分布式事务吗？** 不能，锁只保互斥，跨资源一致性仍需事务/补偿。
