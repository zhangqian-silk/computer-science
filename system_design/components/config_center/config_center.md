# 配置中心（Config Center）

> **摘要**：把配置从代码/本地文件中抽出来集中管理，实现**改配置不重启、动态推送、灰度发布、秒级回滚、多环境隔离**。本文按「为什么需要 → 核心能力 → 推送机制（长轮询 vs Watch）→ 灰度与回滚 → 高可用与本地兜底 → 选型 → 面试问答」推进。

> **关联**：配置中心常与[服务注册](../service_registry/service_registry.md)由同一组件承担（Nacos/Consul）；动态阈值热更新是[限流](../../base/high_availability/rate_limiting.md)、[降级](../../base/high_availability/degradation.md)的开关面。

---

## 一、为什么需要配置中心

配置写在代码或本地文件里的痛点：改一个开关要重新打包发布、重启；多实例配置不一致；多环境（dev/test/prod）配置散乱；无法灰度、无法审计。配置中心把配置变成**可动态下发、可版本管理、可灰度、可审计**的中心化资源。

典型用途：功能开关（feature flag）、限流/降级阈值、数据源与路由、业务参数（活动规则）。

---

## 二、核心能力

- **动态生效**：客户端监听变更，更新内存中的配置值，无需重启。
- **多环境/多租户隔离**：namespace + group + dataId 三级隔离。
- **版本管理与回滚**：每次发布产生版本，可一键回滚到历史版本。
- **灰度发布**：先推送给部分实例/机器验证，再全量。
- **权限与审计**：谁在什么时候改了什么，可追溯。

---

## 三、推送机制：长轮询 vs Watch

客户端如何第一时间感知变更？

- **长轮询（Long Polling，Nacos/Apollo）**：客户端发请求，服务端 hold 住不立即返回，配置变更或超时才返回。兼具「准实时」与「HTTP 友好」，是主流。
- **Watch 长连接（etcd/ZooKeeper）**：客户端与服务端保持长连接，变更通过事件即时推送，毫秒级，但连接管理更重。
- **纯轮询**：定时拉取，实现最简单但有延迟、浪费请求，基本被长轮询取代。

## 四、灰度与回滚

- **灰度（金丝雀）**：按 IP/机器/比例把新配置先推给一小部分实例，观察监控指标正常后逐步扩大到全量。避免一次全量的错误配置引发全站故障。
- **回滚**：配置错误是线上事故的高频来源。版本化 + 一键回滚让「改错→秒级恢复」成为可能，比回滚代码快得多。

这与[灰度发布与回滚](../../governance/release_and_rollback.md)治理实践一脉相承——配置变更也是变更，要走同样的准入与灰度纪律。

---

## 五、高可用与本地兜底

配置中心是**强依赖**：拉不到配置可能导致服务无法启动。关键设计：

- **客户端本地快照**：把最近一次配置落盘，配置中心不可用时用本地快照兜底启动与运行。
- **服务端集群 + 持久化**：多副本 + DB 存储，避免单点。
- **推送失败降级为拉取**：推送链路异常时回退到定期拉取，保证最终一致。

## 六、选型

| 组件 | 推送 | 特点 |
| :--- | :--- | :--- |
| Nacos | 长轮询 | 配置 + 注册一体，国内常用 |
| Apollo | 长轮询 | 灰度/权限/审计完善，携程开源 |
| etcd | Watch | K8s 生态，强一致 |
| Consul | Watch/轮询 | 配置 + 服务发现 + 健康检查 |

---

## 七、面试高频问答

- **配置中心怎么做到不重启生效？** 客户端监听变更并更新内存值。
- **变更如何实时下发？** 长轮询（主流）或 Watch 长连接；纯轮询有延迟。
- **配置中心挂了服务还能起吗？** 能，客户端用本地快照兜底。
- **配置改错了怎么快速恢复？** 版本化 + 一键回滚，比回滚代码快。
- **怎么安全地上新配置？** 灰度发布 + 指标观察 + 可回滚。
- **多环境怎么隔离？** namespace/group/dataId 三级隔离 + 权限控制。
