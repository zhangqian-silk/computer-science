# 服务注册与发现（Service Registry & Discovery）

> **摘要**：微服务实例随发布、扩缩容、故障不断变化，调用方不能写死 IP。注册中心提供**动态实例目录**：实例注册/注销、心跳保活、消费者发现、故障剔除。本文建立评价维度，深入健康检查模型（心跳 TTL / 会话临时节点 / 主动探测）与 Eureka 自我保护、AP vs CP 的取舍、数据模型与增量推送、**无损上下线**、同机房就近路由、推送风暴与故障兜底。

> **前置阅读**：注册中心是[微服务](../../base/microservices.md)治理地基，常与[配置中心](../config_center/config_center.md)一体（Nacos/Consul）；发现到的实例列表上做[负载均衡](../../base/high_availability/load_balancing.md)、配合[熔断](../../base/high_availability/circuit_breaker.md)。

---

## 1. 问题定义与目标

没有注册中心时，调用方靠硬编码 IP/静态配置，实例一变就得改配置重启，无法弹性扩缩容与故障转移。注册中心解耦「调用方」与「实例地址」，目标：

- **动态目录**：实例增减实时可见。
- **故障剔除**：宕机实例及时从可用列表移除。
- **高可用**：注册中心本身不能成为全局单点，挂了也不能阻断已有调用。
- **无损上下线**：发布/缩容时不丢请求。

---

## 2. 评价维度

| 维度 | 含义 |
| :--- | :--- |
| CAP 取向 | 分区时优先可用（AP）还是一致（CP） |
| 摘除时延 | 实例宕机到被移除的时间 |
| 发现实时性 | 实例变更到消费者感知的延迟 |
| 可用性兜底 | 注册中心不可用时消费者能否继续调用 |
| 容量 | 支撑的服务数/实例数/订阅数 |
| 多机房 | 是否支持就近路由与跨机房容灾 |

---

## 3. 核心流程

```mermaid
flowchart LR
	P[服务提供者] -->|1 注册 服务名+IP+端口| R[(注册中心)]
	P -->|2 定期心跳| R
	C[服务消费者] -->|3 订阅/拉取实例列表| R
	R -->|4 变更推送/下线通知| C
	C -->|5 负载均衡选一个实例调用| P
```

- **注册**：实例启动时上报服务名、地址、元数据（版本、权重、区域）。
- **心跳/续约**：周期上报存活。
- **发现**：消费者拉取（或订阅）某服务的健康实例列表。
- **注销**：优雅下线时主动注销；异常宕机由健康检查兜底剔除。

---

## 4. 健康检查与实例摘除

两种主流模型，直接决定「故障实例多快被摘除」：

- **心跳 + TTL（Eureka/Nacos 临时实例）**：实例定期发心跳，注册中心在 TTL 内没收到就判定下线。TTL 要覆盖多个心跳周期以容忍网络抖动——太短会误摘健康实例，太长则宕机实例长期滞留。
- **会话/临时节点（ZooKeeper/etcd）**：客户端与注册中心维持长连接/租约，连接断开则临时节点消失，即时感知下线，更快但依赖连接稳定。
- **主动探测（Consul）**：注册中心/agent 主动对实例做 HTTP/TCP/脚本探测，能感知「进程活着但服务不健康」（如依赖挂了），比被动心跳更准，代价是探测开销。

**自我保护（Eureka self-preservation）**：网络分区时，注册中心可能在短时间内收不到大量实例的心跳。若无脑全摘，会把大批其实健康、只是网络抖动的实例踢掉，引发「误摘雪崩」。自我保护机制在「短期内丢失心跳的实例比例超过阈值」时**停止摘除**、宁可保留可能过期的实例，等网络恢复。这是 AP 取向的具体体现：宁可留脏也不误杀。

---

## 5. AP 还是 CP

注册中心本身是分布式集群，面临 CAP 取舍：

- **AP（Eureka、Nacos 默认）**：优先可用性。网络分区时宁可返回**可能过时**的实例列表，也要保证服务发现可用。少量脏数据由调用方重试/熔断兜底。**多数微服务场景应选 AP**——发现功能挂掉比列表短暂不准更致命。
- **CP（ZooKeeper、etcd、Consul）**：优先一致性。分区时少数派不可写，保证列表强一致，代价是可用性下降。适合对一致性敏感的元数据（如 leader 选举）。

经典结论：**服务发现要 AP**。ZooKeeper 作 CP 系统用于服务发现，在分区时少数派可能拒绝读写，反而降低整体可用性。Nacos 支持 AP（临时实例，心跳）与 CP（持久实例，Raft）两种模式按需选择。

## 6. 数据模型、推拉与本地缓存

- **数据模型**：`命名空间(namespace) → 服务(service) → 集群/分组 → 实例(ip:port + 元数据)`。命名空间/分组用于多环境隔离与灰度分组，元数据含版本、权重、区域。
- **拉（Pull）**：消费者定期全量拉取，简单但有延迟。
- **推（Push）**：变更时主动推送，实时性好；大规模下用**增量推送**（只推变化的实例）而非全量，并用版本号/MD5 比对避免无谓刷新。
- **本地缓存快照**：消费者把实例列表落本地，注册中心短暂不可用时用旧快照继续调用——这是**可用性的关键兜底**，也是「注册中心挂了服务仍能互调」的原因。多数框架是「推拉结合 + 本地缓存」。

---

## 7. 无损上下线

发布/扩缩容时不能丢请求：

- **上线预热**：实例注册后不应立刻承接满负载——冷实例的缓存/JIT 未热，突发流量会超时。做法：注册后按权重**慢启动**（逐步放量）或先探测就绪再注册。
- **无损下线**：直接 kill 会让「消费者本地缓存里还有该实例」的请求打到已死实例。正确顺序：**先注销（或标记下线）→ 等消费者感知（推送/拉取刷新）+ 停止接收新请求 → 等存量请求处理完（drain）→ 再退出**。K8s 里配合 `preStop` 钩子 + 就绪探针摘除。

---

## 8. 多机房与就近路由

- **同机房优先**：消费者优先调用同机房实例，降低跨机房延迟与带宽；同机房全挂再跨机房兜底。实例元数据带 region/zone，负载均衡按此过滤。
- **跨机房容灾**：注册中心多机房部署，单机房故障不影响其他机房的发现。

---

## 9. 性能与扩展

- **推送风暴**：一个大服务（上千实例）频繁变更会向所有订阅者推送，形成风暴。对策：增量推送、变更合并（防抖）、推送限速。
- **规模**：海量实例/订阅需分组、分片管理注册中心数据；心跳频率与实例数共同决定注册中心负载。

---

## 10. 故障模式与处理

| 故障 | 成因 | 对策 |
| :--- | :--- | :--- |
| 注册中心宕机 | 单点/集群故障 | 消费者本地缓存快照兜底，读旧列表继续调用 |
| 网络分区误摘 | 大批心跳短期丢失 | 自我保护：超阈值停止摘除 |
| 推送风暴 | 大服务频繁变更 | 增量推送 + 变更合并 + 限速 |
| 下线丢请求 | 直接 kill、消费者未刷新 | 无损下线：先注销 drain 再退出 |
| 冷实例超时 | 新实例立刻满载 | 上线预热/慢启动 |
| 假健康 | 进程活但服务不可用 | 主动探测 + 客户端熔断 |

## 12. 测试与验证

- **摘除时延**：停止某实例心跳，测量它从可用列表消失的时间是否符合 TTL 设定。
- **可用性兜底**：模拟注册中心不可用，验证消费者用本地快照仍能发现并调用。
- **无损下线**：注销后立即停止心跳，验证在途请求不打到已注销实例。
- **误摘保护**：模拟大批心跳丢失，验证自我保护不误摘。

## 13. 选型与工业实践

| 组件 | 模型 | CAP | 特点 |
| :--- | :--- | :--- | :--- |
| Eureka | 心跳 | AP | Netflix 系，自我保护机制 |
| Nacos | 心跳/长连接 | AP/CP 可选 | 注册 + 配置一体 |
| Consul | 健康检查 | CP | 多数据中心、健康检查丰富 |
| ZooKeeper | 临时节点 | CP | 强一致，早期 Dubbo 常用 |
| etcd | 租约 | CP | K8s 服务发现底座 |

## 14. 常见误区与澄清

- **误区：服务发现要强一致（CP）。** 发现不可用比列表短暂不准更致命，绝大多数场景应选 AP，脏数据由重试/熔断兜底。
- **误区：注册中心挂了服务就不能互调。** 消费者本地缓存快照可兜底，因此挂一段时间不致命。
- **误区：下线直接 kill 即可。** 消费者本地缓存里还有该实例会打到死实例，必须无损下线（先注销 drain 再退出）。
- **误区：新实例注册即满载。** 冷实例需预热/慢启动，否则突发流量超时。
- **误区：网络抖动就摘实例。** 大批误摘会雪崩，需自我保护 + TTL 覆盖多个心跳周期。
