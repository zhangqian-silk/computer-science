# 通知/消息推送（Notification）

> **摘要**：通知组件统一承接「把一条消息通过某个渠道可靠送达用户」：站内信、Push、短信、邮件。它要解决**多渠道抽象与路由降级、模板管理、去重与多维频控、可靠送达与回执、优先级隔离、合规退订**。本文建立评价维度，深入渠道特性、频控算法、回执状态机、渠道路由策略、Push 通道（APNs/FCM/厂商）、限速与削峰、合规与故障模式。

> **前置阅读**：异步发送依赖[消息可靠性](../../base/message_reliability.md)与[任务调度](../task_scheduler/task_scheduler.md)（定时/延迟通知）；去重依赖[幂等机制](../../base/idempotence.md)；营销触达见[营销系统](../../scenarios/marketing/marketing_system.md)。

---

## 1. 问题定义与职责边界

通知组件是**执行层**：接收「发送指令」并可靠、合规、不打扰地送达。目标：高送达率、时效达标、不重不扰、成本可控、合规可审计。

- **负责**：渠道接入与抽象、模板渲染、去重、频控、发送重试、送达回执、优先级、退订。
- **不负责**：「什么时候发、发给谁」的业务决策（营销/业务系统的事）。清晰边界让它可被多业务复用而不耦合业务规则。

## 2. 评价维度

| 维度 | 含义 |
| :--- | :--- |
| 送达率 | 成功触达用户的比例 |
| 时效 | 从请求到送达的延迟（验证码要秒级） |
| 不重不扰 | 去重 + 频控，避免重复与轰炸 |
| 成本 | 短信按条计费，成本敏感 |
| 可靠性 | 渠道故障时的降级与重试 |
| 合规 | 退订、静默、审计 |

## 3. 多渠道抽象与渠道特性

对上游暴露统一发送接口，屏蔽各渠道差异：

| 渠道 | 时效 | 成本 | 到达率 | 富媒体 | 典型用途 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 站内信 | 用户打开才见 | 低 | 高(存库) | 富 | 通知中心、历史留存 |
| Push | 秒级(在线) | 低 | 中(依赖厂商/在线) | 中 | 活跃用户触达 |
| 短信 | 秒级 | **高** | **高** | 无(纯文本) | 验证码、重要通知 |
| 邮件 | 分钟级 | 低 | 中(易进垃圾箱) | 富 | 账单、正式通知 |

## 5. 去重与频控（通知特有难点）

- **去重**：同一业务事件可能重复触发发送（上游重试、消息重投）。用「业务幂等键（如 `事件ID+用户+渠道`）+ 去重表/缓存」保证同一通知只发一次，避免重复打扰与短信资损（见[幂等机制](../../base/idempotence.md)）。
- **多维频控（疲劳度控制）**：限制单用户在单位时间收到的通知条数，且要**多维叠加**：单渠道频次（每天最多 3 条营销短信）、跨渠道总频次、单活动频次、跨活动统一频次。用滑动窗口计数（Redis ZSet/计数）实现。频控是防止「营销轰炸 → 投诉/退订」的关键，也直接省成本。
- **静默时段（quiet hours）**：夜间不发打扰类通知，延到次日；验证码等强时效通知不受限。
- **合并/聚合**：短时间多条同类通知合并成一条（「你有 3 条新评论」），减少打扰。

---

## 6. 可靠送达与渠道路由

- **至少一次 + 幂等**：发送失败重试（退避），配合去重保证不重发。
- **死信与告警**：多次重试失败进死信，人工/异步处理。
- **回执状态机**：`待发送 → 已提交渠道 → 已送达 → 已读`（或 `失败`）。渠道回调异步更新状态，用于统计、重试决策与「未读转其他渠道」。回调可能重复/乱序，状态机需幂等且只能正向推进。
- **优先级隔离**：验证码/告警等高优先级通知与营销通知**分队列**，避免营销积压拖慢关键通知（验证码晚到即失效）。
- **渠道路由与降级**：首选 Push，未安装 App/离线则降级短信；短信接多供应商，按**实时成功率/成本/限额**动态选路与故障切换，单供应商故障不影响整体。

## 7. Push 推送通道

Push 比其他渠道复杂，涉及设备与厂商通道：

- **设备 token 管理**：客户端注册后上报 device token，服务端维护 `用户 → 设备 token`（一人多端）；token 会失效，需按厂商回执清理无效 token。
- **厂商通道**：iOS 走 **APNs**，Android 国内走**厂商推送**（小米/华为/OPPO/vivo，因国内无 GCM/FCM 常驻）、海外走 **FCM**。需按设备类型路由到对应通道。
- **在线长连接 vs 厂商离线推送**：App 在线时可用自建长连接直推（快、省厂商额度）；离线时走厂商通道（能唤醒但受厂商限额与折叠策略约束）。

---

## 8. 模板、限速与削峰

- **模板管理**：内容与代码解耦，支持变量占位、多语言、审核；**防注入/防越权**——变量要转义，避免把用户输入直接拼进短信导致钓鱼或敏感信息串号。
- **渠道限速**：每个渠道/供应商有 QPS 与日额度上限，发送端要**按渠道限速**（见[限流](../../base/high_availability/rate_limiting.md)），超限排队而非被供应商拒。
- **削峰**：大批量营销触达先进[消息队列](../../base/message_reliability.md)，按渠道额度匀速发送，避免瞬时打爆供应商与自身。

---

## 9. 合规

- **退订（opt-out）**：营销类必须支持退订，且退订后不再发送，否则违规。
- **用户偏好**：尊重用户的渠道与频次偏好。
- **审计与脱敏**：发送记录可追溯（谁在何时发了什么）；日志中手机号等敏感信息脱敏。

---

## 10. 故障模式与处理

| 故障 | 成因 | 对策 |
| :--- | :--- | :--- |
| 重复发送 | 上游重试/消息重投 | 业务幂等键 + 去重表 |
| 营销轰炸投诉 | 频控缺失 | 多维滑动窗口频控 + 静默时段 |
| 验证码延迟 | 与营销共队列积压 | 优先级队列隔离 |
| 渠道供应商故障 | 单点依赖 | 多供应商 + 按成功率/成本路由切换 |
| 被供应商限流 | 超 QPS/额度 | 按渠道限速 + 排队削峰 |
| 无效 token 堆积 | 卸载/换机 | 按回执清理无效 token |

## 12. 测试与验证

- **去重**：重复事件断言只发一次。
- **频控**：多维超限断言被拦截、不同维度独立计数。
- **优先级**：营销积压时验证码仍及时发出。
- **降级**：主渠道/供应商故障时验证切换。
- **回执状态机**：重复/乱序回调不导致状态倒退。

## 13. 选型

- 自研通知中心 + 短信/Push 供应商聚合（多供应商容灾）是主流；小规模可直接对接单一云厂商的消息推送服务。

## 14. 常见误区与澄清

- **误区：通知同步发送。** 慢渠道会阻塞上游，且无法削峰/限速，必须异步进 MQ。
- **误区：验证码和营销同队列。** 营销积压会拖垮验证码时效，必须优先级隔离。
- **误区：频控只按单渠道。** 需多维叠加（跨渠道、跨活动统一），否则用户仍被轰炸。
- **误区：单短信供应商。** 单点故障即全站发不出，需多供应商 + 成功率路由。
- **误区：模板直接拼用户输入。** 需转义防注入，避免钓鱼/敏感信息串号。
- **误区：不清理无效 token。** 无效 token 堆积浪费额度、拉低送达率统计。
