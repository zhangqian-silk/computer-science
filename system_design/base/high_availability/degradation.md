# 降级（Degradation）

> **摘要**：降级是在高并发、资源不足或依赖故障时，主动**牺牲非核心功能保住核心链路**的策略性妥协。核心是「核心/非核心分级 + 兜底数据 + 可动态开关 + 可观测可恢复」，并与限流、熔断组成立体防护。本文覆盖目标与原则、降级分级、降级方案、开关体系、与限流熔断的协同、预案与演练、故障模式与常见误区。

> **前置阅读**：降级常由[熔断](./circuit_breaker.md)/[限流](./rate_limiting.md)触发，开关经[配置中心](./../../components/config_center/config_center.md)动态下发，演练见[混沌工程](../../governance/chaos_engineering.md)。

服务降级是分布式系统在高并发、资源不足或依赖服务故障时，为保证核心功能可用性而采取的**策略性妥协**，侧重于从全局视角考虑，其目标如下：

- **核心保障**：优先保障核心业务链路
- **及时恢复**：降级后能及时感知可恢复时机，并自动 / 手动恢复

---

## 降级分级

降级不是一刀切，而是按业务重要性**分级**，过载时从低到高逐级牺牲：

- **L1 可有可无**：个性化推荐、猜你喜欢、广告位——最先降级，返回通用/空内容。
- **L2 体验相关**：商品评价、详情富媒体、非关键字段——次之，返回精简/缓存。
- **L3 核心相关但可延迟**：积分、通知、统计——异步化或跳过。
- **L4 核心不可降**：下单、支付、库存扣减——绝不降级，宁可限流排队也要保住。

明确分级是降级预案的前提，需在设计期就标注每个功能的等级。

## 设计原则

- **核心与非核心分离**：通过微服务拆分明确核心服务边界（如订单服务 vs 积分服务）
- **降级兜底数据**：提前准备静态数据、默认值或缓存热数据
- **用户体验平滑**：降级时提示“部分功能暂不可用”，而非直接报错
- **可监控可恢复**：实时监控降级状态，故障恢复后自动检测并回滚

## 降级方案

### 触发方式分类

**手动降级**  

- **场景**：预知的高流量（如大促、春节）、人工介入紧急情况
- **实现**：通过配置中心动态关闭非核心功能，或调整限流大小
- **示例**：关闭商品评价、推荐列表，保留购物车和支付

**自动降级**

- **场景**：系统自动检测到异常（如超时、错误率飙升）
- **实现**：结合熔断器设置阈值规则
- **示例**：依赖的积分服务故障时，自动跳过积分抵扣逻辑

### 功能层面分类

**读服务降级**

- 返回缓存数据：如商品详情页降级到本地缓存或静态数据
- 精简数据字段：仅返回核心字段（如价格、库存），隐藏详情描述

**写服务降级**

- 异步化处理：将非实时操作异步化（如订单成功后异步发送通知）
- 简化流程：跳过次要校验（如风控校验降级为简单规则）

**依赖服务降级**

- 熔断依赖：通过熔断器快速失败，避免线程池耗尽
- 静态兜底：返回预设默认值

### 降级策略分类

**限流降级**

- 触发限流时，拒绝部分请求并返回友好提示（“系统繁忙，请重试”）

**功能开关**

- 代码中预埋开关，动态关闭非关键功能模块，如关闭个性化推荐，改为返回通用列表

**弹性超时**  

- 动态调整超时时间，避免线程长时间阻塞。例如，正常超时 2s，降级时缩短为 500ms

**服务权重调整**  

- 在负载均衡层降低某节点的流量权重，或将请求导向备份服务

## 降级开关体系

降级要能「随时开、随时关、可灰度」，靠**开关体系**支撑：

- **配置化开关**：每个可降级点预埋开关，值放[配置中心](../../components/config_center/config_center.md)，秒级动态生效、可灰度、可回滚——不需要发版。
- **多级开关**：全局总开关 + 单功能开关，大促时可一键降到「最小可用集」。
- **默认安全**：开关缺失/配置中心不可用时用本地默认值，避免因拿不到开关而误降或不能降。

---

## 与限流、熔断的协同

三者层次不同，组合成立体防护：

- **[限流](./rate_limiting.md)**：控入口总量，过载时拒绝部分请求（限流降级）。
- **[熔断](./circuit_breaker.md)**：依赖故障时快速失败，触发降级返回兜底。
- **降级**：是限流/熔断触发后的「兜底动作」——返回默认值、缓存、友好提示，保住主链路。

即：限流/熔断决定「何时降」，降级决定「降成什么样」。

## 预案与演练

- **预案**：大促前把降级点、分级、开关、兜底数据整理成预案，明确「什么信号触发降哪些」。
- **演练**：通过[混沌工程](../../governance/chaos_engineering.md)注入依赖故障，验证降级开关真的生效、兜底数据正确、恢复顺畅——**没演练过的降级开关约等于没有**。
- **可恢复**：降级状态要可观测，故障恢复后自动/手动回滚，避免「降了忘了恢复」。

## 故障模式与常见误区

| 问题 | 说明 | 对策 |
| :--- | :--- | :--- |
| 核心链路被误降 | 分级不清 | 明确 L4 不可降，开关不覆盖核心 |
| 兜底数据错误 | 兜底未维护/演练 | 定期演练校验兜底数据 |
| 降了忘恢复 | 无状态跟踪 | 降级状态可观测 + 恢复检查 |
| 拿不到开关误降 | 配置中心不可用 | 本地默认值兜底 |

- **误区：降级就是关功能。** 降级是分级牺牲 + 兜底，核心链路绝不降。
- **误区：降级开关写死在代码。** 应配置化、可灰度、可秒级回滚。
- **误区：预案写完就行。** 未经演练的降级不可信，必须定期演练。
