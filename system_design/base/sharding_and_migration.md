# 分片与扩容迁移（Sharding & Migration）

> **摘要**：单库单表撑不住数据量与写入量时，就要分库分表（sharding）。难点有二：**分片键怎么选**（决定是否均匀、能否避免跨片查询）与**如何在线扩容迁移不停服**。本文按「为什么分片 → 拆分方式 → 分片键与路由 → 扩容迁移方案 → 在线迁移四步法 → 跨片难题 → 面试问答」推进。

> **关联**：路由思想与[一致性哈希](../components/consistent_hash/consistent_hash.md)一脉相承；迁移期的一致性靠[分布式事务](./distributed_transaction.md)/对账与[消息可靠性](./message_reliability.md)兜底；ID 需全局唯一见[分布式 ID](../components/id_generator/id_generator.md)。

---

## 一、为什么分片

单库瓶颈来自：单表数据量过大（索引变深、查询变慢）、单机写入/连接上限、单点容量与可用性。分片把数据水平切分到多个库/表/实例，突破单机上限。代价是引入分布式复杂度（跨片查询、分布式事务、扩容迁移），因此**能不分就不分**——先用读写分离、归档冷数据、加缓存，撑不住再分片。

---

## 二、拆分方式

- **垂直拆分**：按业务/字段拆。垂直分库把不同业务表拆到不同库；垂直分表把大字段/冷字段拆出。解决「表宽、业务耦合」。
- **水平拆分**：同一张表按行拆到多个分片（分库分表）。解决「单表行数过大」。是通常说的 sharding 重点。

---

## 三、分片键与路由

**分片键（shard key）是最关键的决策**，一旦选定极难更改：

| 路由策略 | 做法 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 范围分片（Range） | 按区间（时间/ID 段）分片 | 范围查询友好、扩容简单（加段） | 易热点（新数据都写最新片） |
| 哈希分片（Hash mod） | `hash(key) % N` | 分布均匀 | 扩容迁移量大、范围查询要广播 |
| 一致性哈希 | 哈希环 | 扩容迁移少 | 实现复杂、范围查询差 |
| 查表/目录路由 | 维护 key→shard 映射表 | 灵活可精细控制 | 映射表需高可用 |

选分片键的三条准则：**分布均匀**（避免数据/访问倾斜）、**高频查询能带上分片键**（避免跨片扫描）、**避免热点**（如用「用户ID」而非「时间」做电商订单分片键，让读写分散）。常见做法是订单表用 `user_id` 分片，让「查我的订单」命中单片。

## 四、扩容迁移：为什么不能随手加一台

哈希取模分片扩容时，$N$ 变化会导致大量 key 重新路由。下面的组件对比三种策略的迁移比例：

<ShardingMigrationExplorer />

关键结论：

- **取模 +1**：几乎迁移全部数据，不可接受。
- **取模倍增（N→2N）**：利用取模性质只迁移约一半，是分库分表「按 2 的幂扩容」的原因。
- **一致性哈希**：只迁移约 $1/N$，缓存分片常用。
- **预分片（presharding）**：一开始就分成很多逻辑分片（如 1024 个 slot），物理节点少时多个 slot 落一台，扩容时迁移的是 slot 而非重算，运维最平滑（Redis Cluster 思路）。

## 五、在线迁移四步法（双写迁移）

要不停服地把数据从旧分片方案迁到新方案，标准做法是「双写 + 校验 + 切读 + 收尾」：

```mermaid
flowchart LR
	A[1 双写: 新旧库同时写] --> B[2 存量迁移: 历史数据搬到新库]
	B --> C[3 校验: 对账比对新旧差异并修复]
	C --> D[4 切读: 灰度把读切到新库]
	D --> E[5 收尾: 停旧写, 下线旧库]
```

1. **双写**：应用同时写新旧两套存储（旧为主、新为影子），保证迁移期间增量不丢。
2. **存量迁移**：后台把历史数据批量搬到新库。
3. **校验**：对账比对新旧数据，修复差异（差异多来自双写时序，需幂等修复）。
4. **灰度切读**：按比例把读流量切到新库，观察指标，可随时回切（读旧库兜底）。
5. **收尾**：确认稳定后停旧写、下线旧库。

每一步都可回滚，是「大迁移零事故」的关键。影子读（新库读结果与旧库比对但不返回给用户）可在切读前提前验证新库正确性。

## 六、跨片难题

- **跨片查询**：无分片键的查询要广播到所有分片再聚合（scatter-gather），代价高。对策：为高频查询维护「异构索引」（如按另一维度再存一份，或用[搜索](../components/search_component/search_component.md)/ES）。
- **跨片事务**：跨分片的写要用[分布式事务](./distributed_transaction.md)（Saga/TCC）或最终一致 + 对账。
- **分页与排序**：跨片全局排序分页需各片取 TopN 再归并。
- **全局唯一 ID**：不能再用单库自增，用[分布式 ID](../components/id_generator/id_generator.md)。

## 七、面试高频问答

- **分片键怎么选？** 分布均匀、高频查询能带上、避免热点；电商订单常用 user_id。
- **为什么按 2 倍扩容？** 取模倍增只迁移约一半数据；随手 +1 几乎全量迁移。
- **如何不停服迁移？** 双写 → 存量迁移 → 对账校验 → 灰度切读 → 收尾，每步可回滚。
- **迁移期数据不一致怎么办？** 对账比对 + 幂等修复，影子读提前验证。
- **跨片查询怎么办？** 尽量带分片键；否则异构索引或搜索引擎，避免广播。
- **范围分片和哈希分片怎么选？** 范围查询多用范围分片（防热点需设计），均匀分散用哈希/预分片。
